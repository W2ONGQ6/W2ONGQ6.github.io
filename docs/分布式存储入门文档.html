分布式存储：从一块磁盘到会故障的集群

面向会用数据库、写过文件读写，但没有系统学习过分布式存储原理的读者。

READING NOTE·55 sections

一、阅读目标

阅读本文后，希望能够回答四个问题：

  1. 把数据放到多台机器上，到底难在哪里？
  2. CAP、一致性、共识、Quorum 这些词分别在解决什么问题？
  3. 数据库、文件系统、对象存储看起来千差万别，为什么骨子里是同一件事？
  4. Kafka、Redis、Ceph、JuiceFS、3FS 这些系统各自走了哪条路线？

本文不追求记住所有系统名字，而是希望建立一条主线：

先看一块磁盘怎么存数据
    ↓
搬到会故障的多台机器上，遇到三条铁律
    ↓
用一致性、时间、复制、共识、分区、事务六件武器应对
    ↓
按对外承诺的语义分叉：ACID / POSIX / Key-Value
    ↓
在云、NVMe、RDMA、AI 的新条件下重新组合
    ↓
形成 Kafka、Ceph、JuiceFS、3FS 等真实系统

一句话先放在最前面，后面所有内容都是在拆解它：

所有分布式存储系统，都是在「网络不可靠、节点会挂、没有全局时钟」这三条铁律下，用复制、共识、分区、事务这几件武器，去尽力兑现某一套对外语义承诺（ACID 或 POSIX 或简单的 Key-Value）。

二、为什么分布式存储这么难

2.1 单机世界的美好直觉

在一台机器上写文件、读数据库，我们默认了很多「理所当然」：

write() 返回成功 → 数据一定写进去了
read() 读到旧值   → 那一定是因为我还没写
两个操作          → 总能问出「谁先谁后」
程序跑一半崩溃    → 重启后数据要么全在要么全不在

这些直觉之所以成立，是因为单机有一个统一的内存、统一的磁盘、统一的时钟，操作系统用锁、页缓存、原子指令替我们把一切都协调好了。

2.2 三条无法回避的物理铁律

一旦数据要跨越多台机器，上面每一条直觉都会崩塌。原因是分布式系统有三条物理事实，它们不是工程没做好，而是物理规律决定的：

铁律 含义 打破了哪个直觉
网络不可靠 消息会丢失、重复、乱序、延迟无上界 「发出请求就一定有回应」
节点会故障 机器会宕机、磁盘会坏、进程会崩溃 「数据放进去就一直在」
没有全局时钟 每台机器各有时钟，会漂移、会回退 「任何两个操作都能比出先后」

最致命的是第三条的推论——在异步网络里，你无法区分一个节点是「死了」还是「只是慢」。

节点 A 向节点 B 发请求，超时没收到回应。
B 到底是：① 宕机了？② 网络把回包丢了？③ B 还在慢慢处理？
A 无从判断——这三种情况在 A 看来完全一样。

2.3 FLP：一个令人沮丧的结论

正因为「无法区分慢和死」，分布式理论有一个著名的不可能性结果 FLP 定理：

在完全异步、且至少有一个节点可能崩溃的系统中，不存在一个确定性算法能保证在有限时间内达成共识。

直觉上，这是因为任何「等待」都可能是在等一个已经死掉的节点，而你又不敢永远等下去。

这听起来很绝望，但现实系统给出了三条出路：

  • 放弃完全异步假设：现实中网络大多数时候是好的（部分同步 partial synchrony），Raft/Paxos 正是建立在这个折中上；
  • 引入随机化或超时：用超时和随机退避绕过确定性限制；
  • 缩小目标：不追求「永远正确且永远可用」，而是在二者间做明确的取舍。

过渡：

既然不能既要绝对正确、又要绝对可用，那当故障来临时，系统到底该保哪一个？这就引出了 CAP。

三、取舍的艺术：CAP 与一致性谱系

3.1 CAP 不是「三选二」的随意选择

CAP 定理说的是：一致性（Consistency）、可用性（Availability）、分区容忍（Partition tolerance）三者最多同时满足两个。

但这里有个常见误解需要澄清：

网络分区（P）在分布式系统中是必然会发生的，你不能放弃它。所以真正的选择只发生在「分区已经出现」的那一刻——在 C 和 A 之间二选一。

网络把集群切成两半（分区发生）：
  选 C：为了不出错，少数派一侧拒绝服务（牺牲可用性）
  选 A：为了不停服，两侧都继续写（牺牲一致性，事后处理冲突）
取舍 分区时的行为 代表系统
CP 拒绝服务以保证一致 ZooKeeper、etcd、HBase、Spanner
AP 继续服务但可能读到旧数据 Dynamo、Cassandra、Riak

3.2 PACELC：把「没分区的时候」也补上

CAP 只讨论了分区发生时，却忽略了绝大多数时候网络是正常的。PACELC 补上了这一半：

即：分区时在可用性与一致性间取舍；正常时在延迟与一致性间取舍。这更贴近工程现实——哪怕没有任何故障，强一致也要付出跨节点同步的延迟代价。

系统 分类 含义
Dynamo / Cassandra PA / EL 分区选可用，正常选低延迟
Spanner PC / EC 始终优先一致性
MongoDB（默认） PA / EC 分区选可用，正常选一致

3.3 一致性是一条从强到弱的谱系

「一致性」是被滥用最严重的词。它不是非黑即白，而是一条连续谱系——越强越好编程，但越慢；越弱越快、可用性越高，但越难写对：

模型 保证 代价
线性一致性 每个操作看起来在某一瞬间原子生效，且遵守全局实时顺序 最强，需共识/同步，延迟高
顺序一致性 所有节点看到相同的操作顺序，但不必与实时吻合 略弱于线性
因果一致性 有因果关系的操作顺序一致，并发操作可乱序 无需全局同步，可用性好
最终一致性 停止写入后，副本最终收敛到相同值 最弱，最高可用/最低延迟

线性一致性为什么贵？因为它要求「一旦写入完成，之后任何读、在任何节点上都能看到它」。多副本下这意味着写要同步到多数派、读要确认自己没读到过时副本，两者都必须跨节点通信，无法用纯本地操作完成。

3.4 客户端为中心的一致性：够用的补丁

除了上面「以数据为中心」的模型，还有一组面向单个客户端会话的保证，工程上极其实用：

  • 读己之写：用户能读到自己刚写的内容；
  • 单调读：不会读到比之前更旧的值（时间不倒流）；
  • 单调写：同一客户端的写按序生效；
  • 前缀读：不会看到「果」却缺了「因」。

这些保证常用「读写都走同一副本 / 粘性会话 / 版本向量」实现，是最终一致系统「够用」的关键补丁。

过渡：

一致性谱系里反复出现「谁先谁后」「实时顺序」。可分布式系统明明没有全局时钟——那「顺序」到底是怎么被定义出来的？

四、没有全局时钟，怎么排顺序

4.1 物理时钟靠不住

机器的墙上时钟（wall clock）会漂移，NTP 同步也有毫秒到几十毫秒的误差。直接用物理时间戳比较跨节点事件，可能出现「后发生的事件时间戳反而更小」的时钟回退。所以分布式系统必须自己造一套定义顺序的机制。

4.2 Lamport 逻辑时钟：捕捉因果先后

Lamport 的逻辑时钟用一个整数计数器，刻画「因果先后（happens-before，记作 ）」：

本地事件：       C ← C + 1
发消息：         附带自己的 C
收消息：         C ← max(C, C_msg) + 1

它保证：若 ，则 。

但反过来不成立——时间戳小，不代表真有因果关系。逻辑时钟只能给出一个全序（用来打破平局），无法判断两个事件是否其实是「并发」的。

4.3 向量时钟：能检测出「并发」

向量时钟解决了「能否识别并发」的问题。每个节点维护一个向量 ，记录它所知道的每个节点的进度：

代价是每条消息要携带 的向量。Dynamo 正是用向量时钟检测并发写冲突，再交给应用或「最后写入者胜（LWW）」来裁决。

4.4 TrueTime：用不确定性区间反将一军

Google Spanner 的 TrueTime 是一个精彩的反直觉设计：它不假装时钟精确，而是显式返回一个时间区间 ，并保证真实时间一定落在区间内（靠 GPS + 原子钟把误差 压到几毫秒）。

过渡：

顺序问题解决了。接下来是最朴素的需求——把同一份数据放多份，免得一台机器坏了数据就没了。但「放多份」恰恰是一致性问题的源头。

五、数据冗余：复制与 Quorum

复制（replication）是分布式容错的核心手段：同一份数据放多个节点，任一节点故障时其他节点仍能服务。难点全在「如何让多份副本保持一致」。

5.1 三种复制拓扑

模式 机制 优点 缺点
单主（Leader-based） 所有写走主，主再复制给从 简单、无写冲突 主是瓶颈与单点，故障要选主
多主（Multi-leader） 多个主都能写，互相复制 跨数据中心低延迟写 写冲突需要解决
无主（Leaderless / Dynamo） 客户端直接写多个副本，靠 quorum 高可用、无需选主 需要读修复与冲突处理

5.2 同步还是异步

  • 同步复制：主等所有（或多数）从确认后才返回。不丢数据，但延迟受最慢的从拖累，从故障会阻塞写；
  • 异步复制：主写完本地即返回，后台慢慢复制。低延迟，但主故障时未复制出去的写会丢失；
  • 半同步：至少一个从确认即可，兼顾两者。

这本身就是一次「延迟 vs 持久性」的取舍。

5.3 Quorum：用集合相交保证读到最新

无主复制的一致性靠 quorum 的数学保证。设副本数 ，写需要 个确认，读需要 个响应：

例如 ：任意一次读涉及的 2 个副本，与任意一次写涉及的 2 个副本，至少共享 1 个，于是最新值一定被读到。

调参就是在读写快慢间取舍：

W=N, R=1   →  读快写慢，适合读多写少
W=1, R=N   →  写快读慢
W+R ≤ N    →  牺牲一致性，换更高可用/更低延迟

配套技术：读修复（读时顺手更新发现的旧副本）、反熵（后台用 Merkle 树对比副本差异并同步）。

过渡：

Quorum 解决的是「无主」下如何读到最新值。但很多系统需要一个「主」来串行化所有写、避免冲突——那当主挂了，谁来当新主？这就需要在会故障的节点之间达成共识。

六、共识：让会故障的节点达成一致

共识（consensus）是分布式系统皇冠上的明珠：让一组节点对某个值达成一致，即使部分节点故障。选主、原子提交、复制状态机，底层都是它。

6.1 复制状态机：把问题归约到「日志顺序」

核心思想极其优雅：

如果所有副本从相同初始状态出发，按相同顺序执行相同的确定性操作，就会到达相同的最终状态。

于是「让副本一致」就被归约成一个更清晰的问题：让所有副本对「操作日志的顺序」达成一致。这正是共识要解决的。

6.2 多数派：所有正确性的数学基石

为什么是「多数派」？因为：

「任意两个多数派必然相交」意味着：新的决议无法绕开旧的决议——它们至少有一个共同节点记得历史。这一个性质，撑起了 Paxos、Raft、Quorum 读写的全部正确性。

也由此得到容错的数量关系：

崩溃容错：容忍 f 个故障，需要 2f+1 个节点（如 3 节点容 1 个，5 节点容 2 个）
拜占庭容错：容忍 f 个恶意节点，需要 3f+1 个节点

6.3 从 Paxos 到 Raft

Paxos 是第一个被证明正确的共识算法，分 Prepare 和 Accept 两阶段。它正确，但难懂、难实现，且基础版只能对单个值达成一致，要靠 Multi-Paxos 选一个稳定 Leader 来连续定一串日志才实用。

Raft 以「可理解性」为设计目标，把共识拆成三个能独立理解的子问题：

① Leader 选举

  • 节点有三种角色：Follower、Candidate、Leader；
  • 时间划分为一个个 term（任期），每个 term 最多一个 Leader；
  • Follower 超时没收到心跳 → 变 Candidate、term+1、发起投票，得多数票即当选；
  • 随机化选举超时，避免大家同时发起导致选票被瓜分。

② 日志复制

  • 所有写经 Leader，Leader 追加到本地日志后并行复制给 Followers；
  • 多数派确认后，该条目即 committed，Leader 应用到状态机并回复客户端。

③ 安全性

  • 选举限制：只有日志「至少和多数派一样新」的候选人才能当选，保证已提交的条目不会丢；
  • 日志匹配性质：若两份日志在某条目的 term、index 相同，则它之前的所有条目也都相同。

Raft 已经成为工程首选——etcd、TiKV、CockroachDB、Consul 都用它。本系列的 Raft 实现细节：braft 源码解析 进一步把这些理论落到工业级 C++ 代码：PreVote 如何避免任期膨胀、流水线复制、BallotBox 如何推进提交、ReadIndex/Lease 如何实现线性一致读。

过渡：

共识让一组节点像一台可靠的机器。但当数据量大到一组节点装不下时，就要把数据切成很多份、分给很多组——这就是分区。

七、一台机器装不下：分区与路由

分区（partitioning / sharding）把数据集切成多份，分散到不同节点，以突破单机容量与吞吐的上限。

7.1 三种分区策略

策略 机制 优点 缺点
范围分区（Range） 按 key 区间切分 支持高效范围扫描 易热点（如按时间递增写）
哈希分区（Hash） 对 key 哈希后取段 负载均匀 破坏范围查询
一致性哈希 key 和节点都映射到哈希环 加减节点只影响相邻数据 需虚拟节点解决倾斜

7.2 一致性哈希：让扩缩容只动一点点

朴素哈希取模 hash(key) % N 有个致命问题： 一变（增删节点），几乎所有 key 都要重新映射，等于全量数据搬迁。

一致性哈希把节点和 key 都映射到一个环 上，每个 key 归属顺时针方向最近的节点。增删节点时，只有相邻区间的数据需要迁移，其余原地不动。

虚拟节点（vnode） 进一步解决两个问题：每个物理节点在环上放多个虚拟点，(1) 让数据分布更均匀；(2) 让异构机器可以按能力分配不同数量的虚拟点。Cassandra、Dynamo 都用此技术。

Ceph 走了一条更激进的路：CRUSH 算法。它不靠查表、也不靠哈希环，而是用一套可配置的规则（CRUSH Map + 故障域）直接算出数据该放在哪几台机器上，做到「无中心查表、算法定位、自治恢复」。详见 Ceph 架构与实现深度解析。

7.3 再平衡与路由

再平衡（rebalancing） 是节点增删后迁移数据以恢复均衡，原则是：

  • 不要用 hash mod N（会全量重映射）；
  • 固定分区数：预分配远多于节点的分区（如上千个），迁移时整块搬（Riak、ES）；
  • 动态分区：分区随数据量增长而分裂/合并（HBase、TiKV region）；
  • 再平衡要限速，避免抢占正常请求的网络与 IO。

路由 解决「客户端怎么知道某 key 在哪台机器」，三种方案：问任意节点由其转发、独立路由层（Vitess、mongos）、客户端内置路由表直连（Cassandra driver）。通常用 ZooKeeper/etcd 等协调服务维护权威的「分区 → 节点」映射。

过渡：

到这里，六件武器已经齐了。最后也是最硬的一块骨头：当一个操作要同时改动分布在多个节点上的数据，如何保证它们「要么全成功，要么全失败」？

八、最硬的骨头：分布式事务

事务要在多个节点上保持 ACID，是分布式系统最难的部分。

8.1 2PC：两阶段提交

经典的原子提交协议，有一个协调者（coordinator）和多个参与者（participant）：

阶段一 Prepare（投票）：
  协调者问所有参与者「能提交吗？」
  参与者写好 undo/redo 日志，回复 Yes/No，进入「不确定态」（已承诺但未提交）

阶段二 Commit/Abort（执行）：
  全 Yes → 协调者发 commit；有一个 No → 发 abort
  参与者执行并回 ACK

2PC 的致命弱点是协调者单点：如果参与者在投了 Yes 之后、收到决议之前，协调者崩溃，参与者就会卡在「不确定态」——既不敢提交也不敢回滚。3PC 试图通过增加一个阶段和超时来缓解，但代价更高、仍不完美。真正的工程解法是：把协调者本身也做成一个共识组（Raft/Paxos），让协调状态本身高可用。

8.2 Saga：用补偿代替回滚

对长事务、跨服务的事务，2PC 持锁太久不现实。Saga 把一个大事务拆成一串本地事务，每个都配一个补偿操作；中途失败时，逆序执行已完成步骤的补偿，达到「最终回滚」的效果。它牺牲了隔离性，换取了可用性，常见于微服务编排。

8.3 NewSQL 的配方：把六件武器组装起来

现代分布式数据库（Spanner、CockroachDB、TiDB）之所以能既扩展又保持事务，正是把前面所有武器组合到了一起：

  • 分片让数据水平扩展，每个分片是一个 Raft 组保证自身高可用；
  • 跨分片事务用 2PC，而协调者本身也用 Raft 做高可用；
  • MVCC 提供快照隔离，让读写不互相阻塞；
  • 全局时钟（TrueTime / HLC / TSO）给所有事务一个一致的时间戳顺序。

过渡：

至此，地基全部打完：一致性、时间、复制、共识、分区、事务。接下来你会看到，正是「对外承诺什么语义」这一个选择，让同样的地基长出了三种截然不同的系统。

九、一个分叉点：三种语义承诺

分布式数据库、分布式文件系统、对象存储，表面是不同产品，骨子里都是分布式系统这一母题的具体形态。它们面对的是同一批敌人（三条铁律），用的是同一批武器（六件核心机制）。区别只在于对外承诺的语义不同。

                    同样的地基与武器
                          │
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
   数据库              文件系统            对象存储
  承诺 ACID + SQL      承诺 POSIX 语义     承诺简单 Key-Value
  语义最丰富           语义最微妙          语义最简单、最易扩展

9.1 数据库：承诺 ACID 与事务

数据库是语义最丰富的一类。它的核心矛盾是内存快但易失、磁盘持久但慢，几乎所有精巧设计都在调和这对矛盾：

  • 存储引擎：B-Tree（原地更新）vs LSM-Tree（追加写），背后是 RUM 三角的取舍；
  • 事务与隔离级别：脏读、不可重复读、幻读、写偏斜，对应从读已提交到可串行化的隔离级别谱系；
  • 并发控制：2PL（悲观锁）、MVCC（多版本）、OCC（乐观）、SSI（可串行化快照隔离）；
  • 崩溃恢复：WAL（预写日志）+ redo/undo + ARIES 算法，保证「写成功就一定不丢」；
  • 查询优化：基于规则改写 + 基于代价选计划（CBO）+ 连接算法与执行模型。

这条线在本系列对应 数据库原理：存储引擎、事务与查询。

9.2 文件系统：承诺 POSIX 语义

文件系统承诺的是 POSIX——open/read/write/rename/fsync 等系统调用的一致性与原子性保证。单机里这些靠内核锁和页缓存轻松实现，分布式下却每一条都要专门重建：

POSIX 语义 单机保证 分布式难点
原子写 / read-after-write 一次 write 原子可见 数据分散多节点，可见性需协调
rename 原子性 单次 inode 操作 跨目录/跨节点的原子改名
open-unlink inode 引用计数 跨节点引用计数与延迟删除
O_APPEND 原子追加 内核串行化 并发追加需全局串行点
fsync 持久性 刷盘即可 多副本下「持久」的定义变复杂

一个关键洞察：文件名和文件本体（inode）是分离的——这解释了硬链接、rename 原子性、删除仍打开的文件等「奇怪」行为。而分布式文件系统的第一个根本决策，就是把元数据与数据分开（GFS/HDFS 的 Master+ChunkServer、Ceph 的 MDS+OSD），其中元数据服务是最难扩展的部分。

这条线对应 分布式文件存储与 POSIX 语义。

9.3 对象存储：承诺最简单的 Key-Value

对象存储（S3、OSS、MinIO、Ceph RGW）刻意选择最弱的语义来换最好的扩展性：

  • 扁平命名空间：没有真正的目录，a/b/c.jpg 只是一个带斜杠的 key，「目录」是前缀列举制造出的幻觉；
  • 简单 API：PUT 整个对象、GET 整个对象、对象不可原地修改（要改就整体覆盖）；
  • 冗余靠纠删码（EC）：相比三副本，EC 用更低的存储开销（如 1.5x vs 3x）达到同等甚至更高的持久性，代价是重建时要读多个分片、计算开销大；
  • 一致性演进：S3 早期是最终一致，2020 后升级为强一致（read-after-write），但列举等部分操作仍有边界。

正是「语义足够简单」，让对象存储成为云时代海量数据的事实底座，也成为 JuiceFS、数据湖、备份归档的地基。这条线对应 对象存储原理与实现。

过渡：

三种语义里，数据库和文件系统的底层都反复出现同一个「本地存储引擎」——LSM-Tree。它是几乎所有现代分布式系统的「标准件」，值得单独认识。

十、本地引擎标准件：LSM 与 RocksDB

无论上层是数据库、文件系统还是对象存储的元数据，落到单台机器的一块磁盘上时，都要回答同一个问题：数据在本地怎么组织？两大流派主宰了现代存储：

10.1 B-Tree vs LSM-Tree

  • B-Tree（原地更新派）：数据按 key 有序存放在固定大小的页里，就地修改。读快（一次到叶），但随机写多、有写放大。代表：MySQL InnoDB、PostgreSQL；
  • LSM-Tree（追加写派）：写先进内存 MemTable + 追加 WAL，MemTable 满了顺序刷成不可变的 SSTable，后台 Compaction 归并。把随机写转成顺序写（对磁盘/SSD 友好），代价是读要查多层。代表：RocksDB、Cassandra、HBase、TiKV。

10.2 RUM 三角：没有免费午餐

理解存储引擎的核心是 RUM 猜想——读放大（Read）、写放大（Write）、空间放大（Memory）三者不可兼得：

引擎 写放大 读放大 空间放大 擅长
B-Tree 高 低 中 读多写少、点查
LSM-Tree 低 高 可高可低（看策略） 写多、顺序写

10.3 RocksDB：把 LSM 的权衡工程化

RocksDB 是这套理论的工业级落地，也是分布式存储的「本地引擎标准件」——3FS、Ceph BlueStore、TiKV、MyRocks 都以它为底座。它把 RUM 三角的三个顶点做成了可调旋钮：三种 Compaction（Leveled / Universal / FIFO）对应不同的读写空间权衡，Bloom Filter 跳过不含目标 key 的 SSTable，序列号实现快照 MVCC，列族隔离不同数据，Merge Operator 与 BlobDB 支持键值分离。

理解 RocksDB，就理解了「上层分布式系统脚下踩的那块本地存储」长什么样。这条线对应 RocksDB 架构与实现深度解析。

过渡：

原理与标准件都齐了。最后，让我们把本系列剖析的十几个真实系统，按它们「走了哪条路线」归到一张地图上。

十一、系统地图：十几条路线，同源而异形

下面把本专题的深度解析文章按设计路线归类。它们用的都是前面那六件武器，只是在「兑现什么语义、面向什么负载、押注什么硬件」上做了不同选择。

11.1 日志与流：一切皆追加

  • Kafka：把存储抽象成一个分布式提交日志——Topic/Partition/Offset，只能追加、可回放。副本靠 ISR（同步副本集）+ 高水位（High Watermark）保证已提交数据不丢，控制器从依赖 ZooKeeper 演进到自管理的 KRaft。它是「日志即数据库」思想的极致。→ Kafka 架构与实现深度解析

11.2 内存与缓存：用 RAM 换延迟

  • Redis：内存数据结构服务器，单线程事件循环（避免锁竞争、靠内存和 IO 多路复用取胜），RDB/AOF 持久化，主从复制 + 哨兵故障转移 + Cluster 16384 槽分片。它示范了「把热数据放内存」这条延迟路线。→ Redis 架构与实现深度解析

11.3 统一存储与算法定位：不靠中心查表

  • Ceph：RADOS 底座 + CRUSH 算法定位 + PG 中间层 + OSD/MON，对外同时提供块（RBD）、对象（RGW）、文件（CephFS）三种接口。核心是「无中心查表、算法定位、自治恢复」。→ Ceph 架构与实现深度解析

11.4 云原生文件：元数据外包 + 对象存储 + 富客户端

  • JuiceFS：把数据切成 Chunk/Slice/Block 三级存进对象存储，元数据交给独立的数据库引擎（Redis/TiKV/MySQL…），客户端做缓存与拼装。在不可变的对象存储之上落地完整 POSIX 语义，是「组合式云原生」的代表。→ JuiceFS 架构与实现深度解析
  • RapidFS：百度智能云的对象存储加速层，架在 BOS 之上做近计算缓存。与 JuiceFS 目标相似但路线相反——保留 BOS 原始数据布局、只做缓存加速，把扁平 key 重建成层级目录树。→ 百度 RapidFS 架构与实现深度解析

11.5 AI 时代的垂直自研：榨取新硬件

  • 3FS：DeepSeek 出品、为 AI 训练而生。与 JuiceFS 的「组合式」相反，走垂直自研 + 硬件榨取路线：无状态元数据（FoundationDB 事务）、CRAQ 链式复制（读分摊到全链的强一致）、自管 NVMe 裸盘的 Chunk Engine、全链路 RDMA、绕开 FUSE 的用户态零拷贝 IO（USRBIO）。聚合读带宽做到 6.6 TiB/s 量级，也是 KV Cache 卸载的存储后端。→ 3FS 架构与实现深度解析

11.6 数仓与湖仓：为分析而生

  • ByteHouse：云原生数据仓库，shared-nothing 计算层 + shared-everything 存储层，用 shard/replica、列式存储、向量化执行、分布式缓存支撑大规模 OLAP。→ ByteHouse 架构与实现深度解析
  • Apache Iceberg：开放表格式，用 metadata / snapshot / manifest list / manifest file 的多层元数据树，实现快照、时间旅行、隐藏分区、分区演进、schema 演进、乐观并发控制。它是湖仓一体的共同表层。→ Apache Iceberg 架构与实现深度解析

11.7 把它们连成一条因果链

如果想知道这些系统「在历史中处于什么位置、为什么这样设计」，分布式存储经典工作全景 是全局坐标系：它把 NFS/AFS、LFS/LSM、GFS/BigTable、CRUSH/Ceph、Dynamo、Spanner、Raft、RocksDB、FoundationDB、TiKV、JuiceFS 与 3FS 串成同一条因果链——先看系统对外承诺什么语义，再看它用复制、共识、分片、事务与本地引擎如何兑现。

十二、总结：用一张图记住分布式存储

12.1 从问题到武器

核心问题 武器 / 机制 代表
慢和死无法区分 部分同步假设、超时、随机化 FLP 的三条出路
故障时保 C 还是保 A CAP / PACELC 取舍 CP（Spanner）/ AP（Dynamo）
一致性要多强 线性→因果→最终谱系 会话一致性补丁
没有全局时钟 Lamport / 向量时钟 / TrueTime Spanner commit-wait
一台机器会丢数据 复制 + Quorum（NWR） 单主 / 无主
节点故障下达成一致 共识（多数派 + 复制状态机） Paxos / Raft / braft
一台机器装不下 分区 + 一致性哈希 / CRUSH Cassandra / Ceph
跨节点要么全成要么全败 2PC / Saga + 共识协调者 NewSQL 配方
数据在本地怎么存 B-Tree / LSM（RUM 三角） RocksDB
对外承诺什么语义 ACID / POSIX / Key-Value 数据库 / 文件系统 / 对象存储

12.2 最后用五句话带走

  1. 分布式存储的难，源自三条物理铁律：网络不可靠、节点会故障、没有全局时钟。
  2. 「无法区分慢和死」是一切困难的根源，也是 FLP 不可能性的直觉所在。
  3. 系统的差异，本质是取舍的差异：CAP/PACELC 决定保 C 还是保 A，RUM 决定读写空间怎么分配。
  4. 六件武器——复制、共识、分区、事务、时间、本地引擎——组合出了所有分布式存储系统。
  5. 数据库、文件系统、对象存储同源而异形，区别只在对外承诺的语义（ACID / POSIX / Key-Value）；理解这一点，再看 Kafka、Ceph、JuiceFS、3FS，就都是在回答「用什么取舍兑现什么承诺」。
