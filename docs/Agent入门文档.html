Agent：从会回答到会完成任务

面向了解大语言模型基本概念、但没有系统学习过 AI Agent 的读者。

一、阅读目标

本文希望回答：

  1. Agent 和普通 LLM 应用有什么区别？
  2. 一个 Agent 如何规划、调用工具、记忆和纠错？
  3. 为什么“模型能力强”仍然不等于“Agent 可靠”？
  4. Harness、编排框架和评测如何决定 Agent 的实际效果？

核心循环是：

感知任务 → 推理规划 → 调用工具 → 获得观察
    ↑                              ↓
    └────────── 反思与纠错 ←────────┘

二、什么是 Agent

2.1 LLM、工作流和 Agent

普通 LLM 应用：

用户问题 → 模型 → 文本答案

固定工作流：

步骤 A → 步骤 B → 步骤 C

Agent：

任务目标 → 模型决定下一步 → 工具执行
        → 读取结果 → 再决定下一步

Agent 的关键不是使用了某个模型，而是拥有：

  • 持续循环；
  • 外部行动；
  • 根据结果动态改变计划；
  • 在任务完成或失败时停止。

例如，“修复本地项目测试失败”不是一次问答，而是一条闭环任务：

读取项目结构 → 运行测试 → 阅读报错
→ 修改代码 → 再次运行测试 → 检查改动并汇报结果

如果第一次修改没有解决问题，Agent 应该根据新的测试输出调整计划，而 不是重复执行原来的动作。

三、Agent 的四项能力

3.1 规划

复杂目标通常需要拆成子任务：

例如“完成一个研究报告”可能拆成：

定义问题 → 搜集资料 → 验证来源 → 组织结构 → 写作 → 检查

规划可以是：

  • 一次性生成完整计划；
  • 每完成一步再规划下一步；
  • 根据工具反馈动态修改。

长计划的问题是早期错误会影响后续步骤，因此实际 Agent 常采用“短计划 + 频繁重规划”。

例如计划原本是“搜索资料 → 打开页面 → 摘要”。如果搜索结果中没有可靠 来源，下一步就不应机械地打开第一个结果，而应扩大查询、换用官方来源， 或报告无法验证。

3.2 工具使用

LLM 的知识主要来自参数和上下文，工具让它访问外部世界：

  • 搜索引擎；
  • 数据库；
  • 计算器；
  • 代码解释器；
  • 浏览器；
  • 文件系统；
  • 企业 API。

工具调用可以抽象为：

工具描述本身也是上下文的一部分。工具越多，模型越需要准确理解参数、权限和失败返回。

一个天气工具可能要求：

{"city": "上海", "unit": "celsius"}

如果 Agent 错把参数写成 {"location": "上海"}，工具会返回参数错误。 可靠的 Agent 会读取错误信息，修正参数后重试，并设置最大重试次数。

3.3 记忆

上下文窗口只保存当前会话可见的信息。Agent 还需要长期记忆：

  • 用户偏好；
  • 项目背景；
  • 历史任务；
  • 已验证事实；
  • 过去失败原因。

记忆系统通常包含：

写入 → 索引 → 检索 → 注入上下文 → 更新

检索记忆可以表示为：

但记忆不是越多越好。错误、过期或无关记忆会污染上下文，因此需要来源、时间和置信度。

例如用户先说“我不吃花生”，后来又说“这次聚餐可以推荐含花生的菜”。 系统需要记录时间和适用范围，判断这是一次临时例外，还是用户偏好的永久 更新，而不是把两句话无条件拼进提示词。

3.4 反思

反思让 Agent 检查：

  • 目标是否完成；
  • 工具结果是否可信；
  • 是否违反约束；
  • 下一步是否需要回退。

可以把它看成一个验证器：

如果 判断当前路径不可靠，就触发重规划或回滚。

四、ReAct：推理与行动交替

ReAct 的核心循环：

Thought → Action → Observation → Thought → ...

形式化表示：

它比“先想完整计划再执行”更适合开放环境，因为工具返回的新信息可以改变后续决策。

例如查询一个事实：

思考：我需要确认最新来源
行动：搜索
观察：得到多个候选结果
思考：比较来源可信度
行动：打开官方页面
观察：获得原文
思考：整理答案并引用

ReAct 的代价是循环次数增加、错误可能持续传播，因此需要工具校验、最大步数和终止条件。

例如在修复代码任务中，测试第一次失败可能是导入错误，修复后第二次失败 可能变成类型错误。每次观察都会改变当前状态，Agent 需要动态重规划：

测试失败：模块找不到 → 修复导入路径
→ 测试失败：类型不匹配 → 修改接口调用
→ 测试通过

5.3 检查点和恢复

长任务必须保存中间状态：

任务开始 → 检查点 1 → 工具调用 → 检查点 2
         → 失败 → 从检查点 2 恢复

这比让模型从头重新解释整个任务更可靠，也降低了失败成本。

例如报告生成任务已经完成资料检索和数据清洗，随后排版步骤失败。保存 检查点后，可以从清洗结果继续，而不必重新调用所有外部工具。

六、为什么 Agent 会失败

6.1 规划错误

计划可能遗漏前置条件、顺序不合理或目标理解错误。

6.2 工具调用错误

  • 参数格式错误；
  • 调用了错误工具；
  • 没有处理异常；
  • 把工具返回当成事实而不验证。

6.3 上下文退化

长任务中，重要信息可能被大量中间内容淹没：

解决办法包括摘要、分层记忆、上下文压缩和按需检索。

6.4 权限和副作用

读文件和删文件、查询数据和修改生产数据，风险完全不同。Agent 必须知道：

  • 哪些工具可以自动执行；
  • 哪些动作需要确认；
  • 失败时是否可以回滚；
  • 是否存在资源上限。

例如“读取配置文件”通常可以自动执行，“删除目录”则应要求明确确认； “查询生产数据库”和“修改生产数据”也应使用不同权限。权限最好在工具 层强制执行，而不是只依赖提示词提醒模型。

七、Harness：包裹模型的工程外壳

Harness 可以理解为 Agent 的运行时系统，负责：

  • 上下文组织；
  • 工具注册与执行；
  • 权限控制；
  • 记忆管理；
  • 检查点；
  • 重试和恢复；
  • 日志与评测；
  • 子代理调度。

一个可靠的 Agent 架构通常是：

模型
  ↓
策略循环 / 状态机
  ↓
上下文与记忆
  ↓
工具与权限
  ↓
执行环境

同一个模型换一个 Harness，任务成功率可能显著变化，因为模型本身只是决策组件，可靠性还取决于周围的控制系统。

八、多智能体与子代理

当任务可以并行拆解时，可以启动多个子代理：

主代理
├── 资料检索代理
├── 代码分析代理
├── 测试代理
└── 汇总代理

但多代理不是越多越好。需要考虑：

  • 子任务是否真正独立；
  • 通信成本；
  • 结果冲突；
  • 权限隔离；
  • 最终汇总是否可靠。

可以把总成本粗略写成：

如果协调成本超过并行收益，多代理反而会降低效率。

例如三个代理分别搜索同一个问题，最后还需要主代理消除重复和矛盾。若 任务本身只需要一次官方文档查询，直接由一个代理完成通常更合适。

十、Agent 评测

Agent 不能只评估单轮答案，还要评估闭环任务：

  • 是否完成目标；
  • 工具调用是否正确；
  • 是否遵守权限；
  • 成本和耗时；
  • 是否能从失败恢复；
  • 输出是否可验证。

代表性任务包括：

  • 软件工程；
  • 深度研究；
  • 浏览器和计算机操作；
  • 终端任务；
  • 企业流程自动化。

十一、技术演进

静态 LLM：只生成文本
    ↓
ReAct：增加推理—行动循环
    ↓
工具 Agent：可以访问外部系统
    ↓
Memory/RAG：获得长期知识和私有数据
    ↓
Harness：上下文、权限、恢复和评测工程化
    ↓
多代理：拆解并行复杂任务
    ↓
闭环 Agent：在真实环境中持续执行和纠错

十二、总结

  1. Agent 的核心不是模型名字，而是“模型 + 环境 + 工具 + 循环”。
  2. 规划决定走哪条路，工具让模型能够行动，记忆让任务能够延续，反思让系统能够纠错。
  3. ReAct 把推理和行动交替起来，适合信息不断变化的环境。
  4. 长任务需要状态管理、检查点、权限和恢复机制。
  5. Harness 决定模型能力能否变成稳定的生产行为。
  6. Agent 的评测必须从单轮答案走向闭环任务完成。
