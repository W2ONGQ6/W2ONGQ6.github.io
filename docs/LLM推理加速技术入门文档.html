二、为什么大模型推理慢

2.1 推理的两个阶段

LLM 推理分为两个截然不同的阶段：

Prefill 阶段（处理输入 prompt）：

  • 一次性计算所有输入 token 的表示
  • 计算密集型（大量矩阵乘法）
  • GPU 利用率高
  • 延迟与 prompt 长度成正比

Decode 阶段（逐 token 生成）：

  • 每次只生成一个 token
  • 内存带宽受限（需要读取整个模型权重）
  • GPU 利用率低（算力浪费）
  • 延迟与生成长度成正比

例如，生成一个 100 token 的回答：

Prefill:  处理 1000 token prompt → 耗时 0.5 秒
Decode:   生成 100 token × 每个 0.05 秒 → 耗时 5 秒
总耗时:   5.5 秒（decode 占 91%）

瓶颈 3: 内存带宽墙

Decode 阶段的瓶颈是内存带宽，而非算力：

每生成一个 token:
  ├─ 需要读取: 整个模型权重（7B × 2 bytes = 14 GB）
  ├─ 计算量: 极小（一个 token 的前向传播）
  └─ GPU 利用率: <5%（大部分时间在等数据）

这就是为什么 A100（312 TFLOPS）生成速度只比 RTX 3090（142 TFLOPS）快一点——瓶颈不在算力。

三、FlashAttention：让注意力计算飞起来

3.1 核心思想

标准注意力的问题：

# 伪代码
S = Q @ K.T  # 显存: O(n²) - 存储完整注意力矩阵
P = softmax(S)
O = P @ V

注意力矩阵 需要完整物化到显存（HBM），导致：

  • 显存占用爆炸
  • 大量 HBM 访问（慢）

FlashAttention 的解决方案：

不存储完整注意力矩阵，用分块计算+在线 softmax+重计算来换取线性显存。

3.2 技术原理

分块计算（Tiling）：

将 分成小块，逐块计算注意力：

SRAM (快但小)
  ↓
分块加载 Q[i], K[j], V[j]
  ↓
计算局部注意力
  ↓
在线更新 softmax 统计量
  ↓
HBM (慢但大)

在线 Softmax：

不需要完整的 就能计算 softmax：

通过维护 和 统计量，逐块更新结果。

3.3 实际效果

版本 速度提升 显存占用 代表硬件
FlashAttention v1 2-4x A100
FlashAttention v2 5-8x A100
FlashAttention v3 10-15x H100 + FP8

关键洞察：

GPU 性能瓶颈已从算力转向内存带宽。减少 HBM 访问比增加 FLOPS 更重要。

四、KV Cache 管理：节省显存的艺术

4.1 问题：KV Cache 太大了

在服务场景下，KV Cache 是主要显存开销：

A100 80GB GPU 能服务多少请求？

模型权重: LLaMA-7B FP16 = 14 GB
每个请求: 2K context × 1 GB = 1 GB
理论上限: (80-14) / 1 = 66 个请求

实际情况: 由于碎片，只能服务 20-30 个请求

4.2 解决方案 1: PagedAttention

核心思想：像操作系统管理虚拟内存一样管理 KV Cache。

传统方法：

请求 A: [████████████_________] 12/20 tokens（浪费 40%）
请求 B: [████████████_________] 15/20 tokens（浪费 25%）

预分配固定大小，导致大量碎片。

PagedAttention：

KV Cache 分成固定大小的块（如 16 tokens）
  ├─ 块可以存储在非连续内存
  ├─ 用块表映射逻辑位置→物理位置
  └─ 动态分配，几乎零碎片

效果：

  • 显存利用率从 30% 提升到 95%
  • 吞吐量提升 2-4 倍
  • 支持高效 beam search（共享 KV Cache 块）

4.3 解决方案 2: KV Cache 压缩

观察 1：注意力汇（Attention Sink）

StreamingLLM 发现：

前 4 个 token 总是获得异常高的注意力，无论语义内容如何。

策略：保留 4 个初始 token + 滑动窗口，即可稳定处理无限长序列。

观察 2：重击者（Heavy Hitter）

H2O 发现：

95% 的累计注意力集中在少数"重击者" token 上，符合幂律分布。

策略：驱逐注意力分数低的 token，保留重击者 + 最近 token。

观察 3：逐层相似性

MiniCache 发现：

相邻层的 KV Cache 高度相似（余弦相似度 > 0.9）。

策略：在深度维度合并相邻层，实现 5 倍压缩。

4.4 解决方案 3: KV Cache 量化

KIVI 和 KVQuant 将 KV Cache 量化到 2-4 bit：

非对称量化：

  • Key：逐通道量化（因为异常值固定在某些通道）
  • Value：逐 token 量化（没有固定的通道模式）

Pre-RoPE 量化：

在应用旋转位置编码（RoPE）之前量化 Key，因为 RoPE 会混合通道对。

效果：

  • 2-bit KV Cache，峰值显存减少 2.6 倍
  • 困惑度退化 < 0.1
  • 吞吐量提升 2.3-3.5 倍

五、投机解码：让大模型学会"猜答案"

5.1 核心思想

问题：自回归解码必须逐个生成 token，无法并行。

洞察：

语言生成任务中，很多 token 是"简单的"（如常见词、语法词），小模型也能预测准确。

方法：

1. 小模型快速生成 K 个候选 token
2. 大模型一次并行验证所有候选
3. 接受正确的前缀，拒绝后续 token
4. 重复

关键保证：输出分布与大模型逐 token 生成完全相同（无损）。

5.2 经典方法：Speculative Decoding

Google 提出的奠基性方法：

算法流程：

# 伪代码
draft_tokens = small_model.generate(k=5)  # 快速生成 5 个候选
logits = large_model(draft_tokens)        # 一次前向传播验证所有

accepted = []
for i, token in enumerate(draft_tokens):
    if reject_sample(token, logits[i]):   # 拒绝采样
        break
    accepted.append(token)

return accepted + large_model.sample(logits[len(accepted)])

拒绝采样确保输出分布一致性：

效果：2-3 倍加速，完全无损。

5.3 进阶方法：Medusa

问题：需要单独加载小模型（显存和维护成本）。

Medusa 的方案：

在大模型最后一层添加多个轻量解码头：

LLaMA-7B Backbone (冻结)
    ↓
[Head 1] → 预测下 1 个 token
[Head 2] → 预测下 2 个 token
[Head 3] → 预测下 3 个 token
[Head 4] → 预测下 4 个 token

树状验证：

从多个头的预测构建候选树，一次前向传播验证所有路径：

Current token: "The"
    ├─ cat (Head 1)
    │   ├─ is (Head 2)
    │   └─ was (Head 2)
    └─ dog (Head 1)
        └─ runs (Head 2)

效果：

  • 无需草稿模型
  • 2.2-3.6 倍加速
  • 解码头训练成本低（~1 GPU 天）

5.4 前沿方法：EAGLE-2

核心创新：在特征层面预测，而非 token 层面。

为什么特征预测更好：

Token 预测: P(token[t+1] | tokens[1:t])
  └─ 高度不确定（词汇表有 50K+ 选择）

特征预测: P(feature[t+1] | tokens[1:t])
  └─ 连续空间，不确定性更低
  └─ 解码: feature[t+1] → token[t+1]

动态草稿树：

根据草稿模型的置信度动态调整树结构：

高置信度 → 扩展更多分支
低置信度 → 保守预测

效果：

  • 3.05-4.26 倍加速
  • 平均每次接受 4-5.5 个 token
  • RTX 3060 可达到 A100 级别的生成速度

七、推理服务系统：工程化落地

7.1 连续批处理（Continuous Batching）

传统批处理：

Batch 1: [Req A, Req B, Req C] 全部完成后才处理下一批
  └─ 问题: 长请求拖累短请求，GPU 空闲

连续批处理：

每个 iteration:
  ├─ 移除已完成的请求
  ├─ 添加新到达的请求
  └─ 动态调整 batch

效果：吞吐量提升 2-10 倍。

7.2 分块 Prefill

问题：长 prompt 的 prefill 阶段会阻塞所有 decode 请求。

传统方式:
  Prefill (10K tokens) → 耗时 2 秒 → 所有 decode 停顿 2 秒

Sarathi-Serve 的方案：

将 prefill 拆分成小块，与 decode 交替执行：

Iteration 1: Prefill[0:512]    + Decode (all requests)
Iteration 2: Prefill[512:1024] + Decode (all requests)
Iteration 3: Prefill[1024:1536] + Decode (all requests)
...

效果：

  • 消除"生成停顿"
  • 服务容量提升 5.6 倍
  • P99 延迟降低 10 倍

7.3 Prefill-Decode 分离

观察：

Prefill:  计算密集，需要算力
Decode:   内存密集，需要带宽

两者硬件需求不同，应该分离部署。

Mooncake 架构：

Prefill 集群 (高算力 GPU)
    ↓ 生成 KV Cache
分布式 KV Cache 存储 (CPU/DRAM/SSD)
    ↓ 提供 KV Cache
Decode 集群 (高带宽 GPU)

效果：

  • 吞吐量提升 525%
  • 充分利用异构硬件
  • 成本效率大幅提升

7.4 RadixAttention：自动 KV Cache 复用

问题：多轮对话、few-shot、RAG 场景有大量公共前缀。

请求 A: "你好，请帮我" + task1
请求 B: "你好，请帮我" + task2
请求 C: "你好，请帮我" + task3

传统方法会为每个请求分别计算 "你好，请帮我" 的 KV Cache。

SGLang 的 RadixAttention：

用基数树（Radix Tree）自动识别和复用公共前缀：

Root
 └─ "你好，请帮我" (共享 KV Cache)
     ├─ task1
     ├─ task2
     └─ task3

效果：

  • 多轮对话吞吐量提升 6.4 倍
  • Few-shot 学习提升 3.2 倍
  • 自动识别，无需手动管理

8.3 替代架构：从 Transformer 到 SSM

Mamba/Mamba-2：

状态空间模型（SSM），线性复杂度：

  • 训练： 时间和显存
  • 推理： KV Cache（只需存储状态）
  • 长上下文性能优于 Transformer

RWKV：

结合 RNN 和 Transformer 优点：

  • 推理复杂度 （与序列长度无关）
  • 并行训练，高效推理
  • 适合流式场景

当前状态：

  • SSM 在某些任务上已接近 Transformer
  • 超长上下文（1M+ tokens）场景优势明显
  • 尚未在所有任务上全面超越

九、实践指南：如何选择加速方案

  1. 极致量化 (INT4/INT2)
  2. 模型剪枝
  3. llama.cpp + GGUF

超长上下文处理：

优先级:
  1. KV Cache 压缩 (H2O/SnapKV)
  2. 分布式 KV Cache (Mooncake)
  3. 位置编码外推
  4. 考虑 SSM 架构

9.3 性能优化清单

Level 1：零成本优化（必做）

  • 使用 FlashAttention（torch.nn.functional.scaled_dot_product_attention）
  • 启用连续批处理
  • 编译模型（torch.compile）
  • 使用 FP16/BF16

Level 2：低成本优化（推荐）

  • PagedAttention（vLLM）
  • W4A16 量化（GPTQ/AWQ）
  • KV Cache 量化（2-4 bit）
  • 分块 Prefill

Level 3：高级优化（视场景而定）

  • 投机解码（训练 Medusa 头或 EAGLE 草稿模型）
  • Prefill-Decode 分离
  • 多机分布式推理
  • 自定义 CUDA kernel

十、总结

LLM 推理加速的技术演进可以浓缩为：

识别瓶颈: 内存带宽墙 + KV Cache + 序列依赖
    ↓
FlashAttention: IO 感知注意力，线性显存
    ↓
PagedAttention: 类虚拟内存管理，零碎片
    ↓
KV Cache 优化: 压缩/量化/驱逐/分离
    ↓
投机解码: 打破序列依赖，并行生成
    ↓
模型量化: FP16 → INT8 → INT4 → INT2
    ↓
系统工程: 连续批处理 + 分块 Prefill + 分离架构
    ↓
新架构探索: MoE + SSM + 超长上下文

记住七个关键点：

  1. 推理≠训练 —— 瓶颈从算力转向内存带宽，优化思路完全不同
  2. FlashAttention 是基础 —— 几乎所有现代推理框架的必备组件
  3. KV Cache 是核心 —— 管理好它就掌握了推理优化的关键
  4. 投机解码是质变 —— 突破自回归限制，实现 3-5 倍加速
  5. 量化是必然 —— FP16 已不够，W4A16 成为新标准，FP8 是未来
  6. 系统工程是放大器 —— 单项技术叠加，实现 10-100 倍整体提升
  7. 场景决定方案 —— 没有银弹，根据吞吐/延迟/成本权衡选择
