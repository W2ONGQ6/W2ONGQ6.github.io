SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering

SWE-agent: 智能体-计算机接口实现自动化软件工程

原文摘要翻译

大语言模型越来越多地被用于执行编码任务。然而，当面对需要在大型代码仓库中进行多文件编辑的现实世界软件工程任务时，现有方法仍然不足。本文提出了 SWE-agent，其核心洞察是将 LLM 视为一种新型用户类别，专门为其设计了”智能体-计算机接口”（Agent-Computer Interface, ACI）——一个为 LLM Agent 量身定制的代码浏览和编辑环境。ACI 包含精心设计的 LM 友好型命令（如查看、搜索、编辑文件）和结构化的反馈格式，显著降低了 LLM 与代码库交互的认知负担。在 SWE-bench（真实 GitHub issue 自动修复）评测中，SWE-agent 取得了发表时的最佳成绩：12.5% 的完整测试集 Pass@1 解决率，远超此前任何非交互式方法（此前 SoTA 仅为 1.96%）。在 HumanEvalFix 上达到 87.7%。我们系统地分析了接口设计对 Agent 行为的影响，发现命令的粒度、反馈的格式和信息的丰富程度直接决定了 Agent 的任务成功率。

研究问题

核心问题：当 LLM 需要在一个陌生的、大型的代码仓库中定位并修复一个真实 Bug 时，什么样的交互界面能最大限度地帮助 LLM 完成这个任务？

与简单的代码补全不同，SWE-bench 中的任务是真实的 GitHub Issue——需要理解 bug 描述、在可能数百个文件中定位相关代码、跨多个文件编辑、并确保修复通过所有测试。这个问题上，裸 LLM 的解决率极低（~2%）。SWE-agent 的核心假设是：这不是 LLM 能力不足的问题，而是人与 LLM 之间的接口不够高效的问题。

创新点

  1. Agent-Computer Interface (ACI) 概念：首次明确提出”当 LLM 成为计算机使用者时，需要重新设计计算机接口”——为 LLM 量身设计的命令行界面，显著降低 Agent 与代码库交互的认知负担。

  2. LM 友好型交互原语设计：文件查看（支持行号标记）、代码搜索、文件编辑（搜索替换或行范围指定）、测试执行和 lint 检查——这些命令的粒度和格式针对 LLM 的特性进行了精心调优。

  3. SWE-bench 的突破性成绩：12.5% 的解决率（此前 SoTA 仅 1.96%）——6.4 倍的绝对提升，证明了”好的接口设计”与”强的 LLM 能力”同样重要。

一句话总结

SWE-agent 提出”Agent-Computer Interface”概念，为 LLM 量身设计代码浏览和编辑界面，在 SWE-bench 上以 6.4 倍优势碾压此前方法，证明了构建好的代码 Agent 不仅是提升 LLM 能力的问题，更是人机交互设计的问题。

核心架构：Agent-Computer Interface (ACI)

ACI 设计哲学

左侧：传统的人类 CLI——命令紧凑快捷（grep -rn "buggy_function"），适合熟悉终端的开发者。右侧：SWE-agent 的 ACI——命令冗长但自解释（search "buggy_function" across all .py files），适合需要”阅读输出并理解上下文”的 LLM。ACI 不是简化 CLI，而是为 LLM 重新设计 CLI。

人用 CLI vs LLM 用 ACI：根本差异

维度 人类 CLI SWE-agent ACI
输出解析 人类可以解析密集输出 LLM 需要结构化但自然语言风格的输出
交互模式 快速反复尝试 每次交互消耗大量 token，需审慎
错误处理 人类直觉 + 经验 需要明确的错误消息和修复建议
学习成本 人类可以记忆 LLM 每次从头理解
符号 vs 语言 人类偏好简洁符号 LLM 偏好描述性自然语言
信息密度 高密度（一行可显示数百个结果） 低密度（需要解释和上下文）

ACI 的四大设计原则

原则 1：结构化但自然语言风格的输出

为什么：LLM 是在自然语言上训练的——它”理解”自然语言，但对 -rw-r--r-- 这类符号的理解远不如对人类可读文本的理解。这不是 LLM 不能处理符号，而是自然语言的表达更”LLM 原生”。

原则 2：行号作为通用锚点

所有文件查看命令必须返回行号，所有编辑命令通过行号指定范围。行号成为 LLM 与代码之间的”坐标系统”——精确、无歧义。

原则 3：每次交互最小化信息量

不返回整个文件——只返回相关区域的 N 行（上下文窗口 + N 行前后）。为什么：LLM 的上下文窗口是宝贵的（也是昂贵的），将不相关的代码放入上下文实际上会稀释 LLM 对关键代码的注意力。

原则 4：错误消息对人类和 LLM 同样可读

当代码执行失败时，ACI 返回的错误信息应包含：

  • 错误类型（语法、运行时、测试失败）
  • 错误位置（文件名 + 行号，如果可确定）
  • 错误上下文（相关代码片段）
  • 提示性建议（如果可推断原因）

ACI 命令集：完整解析

命令分类

类别 命令 功能 设计考量
导航 open <file> 浏览文件内容（带行号） 限制显示行数，默认 50 行
导航 scroll_up / scroll_down 翻页浏览文件 保持行号连续性
导航 search_dir <term> 在文件名中搜索 返回匹配文件列表而非内容
搜索 search <pattern> 代码搜索 返回精简上下文 + 行号
搜索 find_file <name> 按文件名查找 支持通配符
编辑 edit <start> <end> 精确替换指定行范围 最安全的编辑方式
编辑 search_replace <old> <new> 全局搜索替换 适用于重命名等批量操作
验证 execute <command> 执行 bash 命令 如 pytest、linter
提交 submit 提交最终修复 不可逆——触发最终测试

关键命令详解

open 命令

为什么限制行数：如果 LLM 打开了一个 2000 行的文件，将全部内容投入上下文，不仅浪费 token，还会”淹没”真正需要关注的小范围代码。好的接口应该让 LLM 像人类开发者一样——先看概览，再聚焦细节。

edit 命令

为什么使用 <<<<====>>>> 标记：这是一种”diff 风格”的编辑语法，既对 LLM 自然（LLM 在预训练中见过大量 diff 格式），又对解析精确。相比 “edit line 45 to add try-except…”，这种格式消除了歧义。

search 命令的响应格式

关键设计：搜索结果不显示完整实现——只显示匹配行和周围 1 行上下文。这避免了在 LLM 还不知道哪些结果相关时就把大量代码塞入上下文 — LLM 应该先看到”搜索结果概览”，再决定打开哪些文件查看详情。

SWE-bench：评估基准详解

SWE-bench 是什么

SWE-bench 是一个从 12 个真实 Python 开源项目（如 Django、Flask、requests、scikit-learn）中提取的真实 GitHub Issue 集合。每个 Issue 都已被人类贡献者解决，具有：

  • 经过验证的、造成 Bug 的精确 commit（用于设置环境）
  • 问题描述（Issue 文本）
  • 人类编写的正确修复（用于对比和评估）
  • 完整的测试套件（用于验证修复是否正确）

SWE-bench 将这些问题转化为 AI 评估任务：给定 Issue 描述和一个处在”问题恰好出现前”状态的代码库，AI agent 需要定位并修复问题。

SWE-bench 数据集特征

特征 数据
总任务数 2,294（测试集）
涉及的项目 12 个（Python）
平均文件数 每个仓库数百到数千个
平均 Issue 描述长度 ~200 词
平均修复涉及文件数 1.7 个
平均修复行数 ~4 行
评估指标 Pass@1（一次尝试通过所有测试的解决率）

为什么 SWE-bench 如此难

挑战 具体说明
仓库规模 数千个文件——无法将所有代码放入上下文
隐式知识 Issue 描述假设读者了解项目架构——LLM 需要自行探索
多文件依赖 修复往往涉及多个文件——修改一处可能需要在别处做配套修改

测试覆盖 修复必须通过为这个问题创建的新测试，同时不破坏旧测试
环境复杂性 需要正确设置依赖、版本、配置才能运行测试

接口消融实验

为了证明 ACI 设计的每个元素都有贡献，研究者进行了系统的消融实验：

ACI 变体 SWE-bench Lite 解决率 相对完整 ACI 的损失

关键发现：

  • 行号 和 代码搜索 是最关键的两个设计——移除任何一个都导致解决率腰斩
  • 搜索命令的必要性证明了”在陌生代码库中定位代码”是核心瓶颈
  • 行号提供了精确性——没有行号时 LLM 试图通过字符串匹配定位编辑，错误率极高

详细机制流程（Numbered）

流程 A：SWE-agent 的完整任务执行流程

Step 1：环境初始化

  • 输入：GitHub Issue URL（指定仓库、问题号）
  • 操作：拉取仓库在问题出现前的精确 commit，构建 Docker 容器，安装依赖
  • 输出：一个包含 Bug 代码 + 完整测试环境 + 问题描述的沙盒

Step 2：初始上下文注入

  • 输入：GitHub Issue 描述文本 + 仓库的基本结构（顶层目录、主要模块）
  • 操作：构造初始 System Prompt + 问题描述 + 环境信息
  • 输出：LLM 的第一个”认知”（”这个 Bug 可能是关于 X 的问题，需要查看 Y 和 Z”）

Step 3：代码探索循环

  • 输入：LLM 的上一个推理 + 上一个 ACI 命令的返回结果
  • 操作：
    a. LLM 推理”我需要查看什么？”
    b. LLM 发出 ACI 命令（search / open / scroll）
    c. ACI 返回命令结果
    d. LLM 分析结果，更新对 Bug 的理解
    e. 如果还需要更多信息，回到 a；否则进入修复
  • 输出：对 Bug 根因的准确定位 + 修复所需修改的文件/行号

Step 4：代码编辑循环

  • 输入：Bug 根因理解 + 修复方案
  • 操作：
    a. LLM 生成 edit 命令（指定文件 + 行范围 + 新旧代码）
    b. 对每个涉及的文件执行编辑
    c. 如果涉及多个文件，按依赖顺序编辑（先改定义，后改调用）
  • 输出：修改后的代码库状态

Step 5：验证循环

  • 输入：修改后的代码库
  • 操作：
    a. 执行测试套件（pytest / unittest）
    b. 执行 linter / type checker
    c. 如果测试失败：查看失败信息 → 回到 Step 3 或 Step 4
    d. 如果测试通过且无 linter 错误 → 进入提交
  • 输出：通过所有验证的修复

Step 6：提交修复

  • 输入：通过验证的代码修改
  • 操作：执行 submit 命令
  • 输出：最终的 git diff（用于与人类提交的修复进行精确对比评估）

流程 B：LLM 推理-行动循环（ReAct 风格）

Step 1：Observation

  • 输入：上一个 ACI 命令的返回结果
  • 操作：LLM 解析结构化输出，提取关键信息
  • 输出：对当前代码库状态的理解

Step 2：Thought（推理）

  • 输入：Observation + 问题描述 + 历史推理链
  • 操作：LLM 生成推理文本——“这个函数看起来没问题，但它的调用者可能传入了错误参数……”
  • 输出：自然语言推理 + 下一步行动计划

Step 3：Action（行动）

  • 输入：推理决定的下一个行动
  • 操作：LLM 发出一个 ACI 命令
  • 输出：ACI 命令执行结果 → 回到 Step 1

Step 4：完成判断

  • 输入：推理链
  • 操作：如果 LLM 认为已经完成修复并通过验证，发出 submit
  • 输出：最终 git diff

ACI 设计的 HCI 理论基础

SWE-agent 的核心贡献不是算法创新——而是将人机交互（HCI）理论应用于 LLM Agent 场景。传统 CLI 是为人类设计的——人类可以通过经验学习复杂的命令行约定，可以通过视觉在密集的输出中快速扫描，可以用直觉判断”这个输出看起来有问题”。LLM 没有这些能力——但它有另一个优势：可以处理大量的自然语言描述。

ACI 的设计本质上是回答一个问题：如果你的用户是一个语言模型，它的”需求特征”是什么？

LLM 的用户特征：

  • 擅长处理自然语言格式的输出
  • 需要显式标签来指导注意力（行号、分隔符、标题）
  • 倾向于在”探索”和”利用”之间高效切换
  • 对过于冗余或过于简洁的信息都很敏感
  • 使用 token 预算作为隐性约束

为什么 SWE-bench 12.5% 已经是突破

第一次看到 12.5% 的解决率可能觉得”不高”。但要理解这个数字的背景：

  • 人类开发者面对这些 Issue 的解决率不是 100%（需要理解项目架构的隐式知识）
  • 此前任何非交互式方法的解决率不超过 2%——SWE-agent 是 6 倍提升
  • 12.5% 意味着 AI 可以独立解决大约每 8 个真实 GitHub Bug 中的 1 个——这在之前是不可想象的
  • 如果按 Bug 类型筛选，简单逻辑错误的解决率高达 35%

这是从”AI 不能解决真实世界 Bug”到”AI 可以辅助解决真实世界 Bug”的范式跃迁。

ACI vs IDE：LLM 需要不同的工具

一个自然的想法是：为什么不直接让 LLM 使用 VS Code？这个问题揭示了 ACI 的核心洞察。VS Code 的 UI 是为人类设计的——鼠标操作、可视化滚动、侧边栏面板。LLM 无法使用鼠标，也不需要可视化渲染。

ACI 可以被看作是”LLM 的 IDE”——它的设计约束与人类 IDE 完全不同：

  • 输入方式：自然语言命令 > 键盘快捷键
  • 输出方式：结构化的自然语言 > 视觉渲染
  • 导航方式：语义搜索 > 目录树点击
  • 编辑方式：行号锚点 > 光标操作

局限

  1. 解决率天花板：即使在优化了 20 年接口设计后，顶尖模型的解决率也仅约 20-25%。这意味着 75%+ 的真实 Bug 仍然超出 AI Agent 的能力——其中许多涉及需要理解人类意图、领域知识和隐式约定的复杂推理。

  2. 环境敏感性和复现难度：SWE-bench 的成功高度依赖于精确定位到”Bug 出现前的 commit”和配置正确的测试环境。略微的依赖版本差异、操作系统差异或配置差异都可能导致完全不同的结果——这使得 SWE-bench 的结果在实践中的”可复现性”成为一个已知问题。

  3. LLM 对大型代码库的过度依赖搜索：LLM 倾向于使用 search 命令寻找”看起来相关”的函数名——但 Bug 可能由两个看似不相关的模块间的微妙交互引起。这种”关键词偏差”使 AI Agent 容易错过需要跨语义边界推理的 Bug。

  4. Token 成本与上下文窗口竞争：每个 task 涉及数十到数百轮 ACI 交互——每轮都需要将历史上下文重新发送给 LLM。在处理大型文件的长时间探索中，token 消耗呈指数增长，接近上下文窗口限制。

  5. 缺乏持久的项目知识：SWE-agent 每次处理新 Issue 时都从零开始探索代码库——不维护”对项目的理解”。人类开发者在修复多个 Bug 后会对项目结构形成心智模型。AI Agent 缺乏这种累积理解。

  6. 编辑安全性的缺失：ACI 的 edit 命令允许 LLM 在没有人类审查的情况下直接修改代码。在生产环境中，这带来了恶意修复（introduce vulnerability）或错误修复（看似正确但引入新 Bug）的风险。submit 前没有人类 Gate。

  7. 多模态代码理解的欠缺：现实世界的 Bug 修复常常涉及阅读文档（非代码）、分析截图（UI Bug）、查看设计图——这些信息不在 SWE-bench 中，也不在 ACI 的设计范围内。扩展到这些场景需要更丰富的 Agent-Computer 交互能力。

可复用洞见

洞见 1：接口设计是 AI Agent 的第一性原理

核心思想：LLM 的能力很强，但能否将这种能力转化为任务成功率，很大程度上取决于它为 LLM 提供的交互接口。好的接口设计带来的提升（6.4x）甚至可以超过模型代际升级带来的提升。

如何在你的工作中应用：

  • 在构建任何 LLM Agent 系统时，先投入时间设计 Agent 与目标环境的交互接口
  • 不要假设”给 LLM 一个 bash shell 就够了”——为 LLM 定制每个交互原语
  • 测试接口的每个元素：输出格式、错误消息风格、信息密度都对 LLM 性能有可量化影响
  • 为 LLM Agent 设计”API”时，遵循”自然语言优先，结构化第二，简洁第三”的原则

洞见 2：行号是代码编辑的通用锚点

核心思想：在代码编辑的场景中，行号提供了 LLM 与代码之间最精确、最无歧义的”坐标系统”。相比内容搜索替换，行号避免了字符串匹配的歧义和效率问题。

如何在你的工作中应用：

  • 在任何让 LLM 编辑代码的场景中，始终显示行号
  • 编辑命令以行号范围指定（edit 45:52 而非 replace "old code" with "new code"）
  • 对于多文件项目，采用 文件路径:行号 的命名约定
  • 如果代码可能变长（插入新行），需要处理行号的动态偏移

洞见 3：信息量控制 = 注意力管理

核心思想：将 2000 行代码全部放入 LLM 的上下文是一种”信息过载”——LLM 的注意力会被稀释。好的接口应该像一位好的导师——“先看这里，这里有问题，其他地方暂时不用管”。

如何在你的工作中应用：

  • 默认返回”精简但有上下文”的内容（如搜索结果返回匹配行 + 前后各 1 行）
  • 提供 scroll 命令供 LLM 主动扩展视野——由 LLM 自己决定何时需要更多信息
  • 避免在一次交互中返回 LLM 没有请求的信息
  • 使用分层信息架构：概要 → 详情，由 LLM 主动”展开”

洞见 4：好的错误消息是 Agent 的”自我修复引擎”

核心思想：当 Agent 犯错误时，错误消息不仅是”提示失败”——它是引导 LLM 自行修复的最重要信息。SWE-agent 的成功率很大程度依赖于迭代反馈循环中错误消息的质量。

如何在你的工作中应用：

  • 对 Agent 系统的错误消息做投入——不仅说”出错”，还要说”哪错了、可能原因是什么”
  • 将错误消息构造为 Prompt 的一部分：
  • 设置最大重试次数（如 5 次），防止 LLM 陷入”修复-再失败”的无限循环

洞见 5：搜索优于浏览——LLM 需要”找到”而非”看到”

核心思想：在大型代码库中，LLM 依赖 grep/语义搜索来定位代码——而非逐文件浏览。搜索的覆盖率和精确度直接决定了 Agent 能否”找到 Bug 在哪里”。

如何在你的工作中应用：

  • 为 LLM 提供强大的代码搜索能力（grep、regex、或语义搜索）
  • 搜索结果应展示”匹配行 + 少量上下文”，而非完整的函数实现
  • 允许 LLM 在搜索结果和文件浏览之间迭代——搜索 → 浏览 → 搜索 → …
  • 如果你的代码库很大，考虑预构建语义搜索索引供 Agent 使用

我的笔记

读后反思

这篇论文最有价值的洞察不在于系统本身——而在于它提出的范式转变：当 AI 成为计算机的用户，我们需要为这个新用户重新设计计算机。 这让我想到”无障碍设计”（accessibility）——我们为视障用户设计屏幕阅读器，为行动不便的用户设计语音控制，而 SWE-agent 本质上是为”语言模型用户”设计的无障碍界面。

不同的是，LLM 的”无障碍需求”与人类的完全不同。人类需要视觉化 + 快捷操作 + 图标隐喻。LLM 需要自然语言 + 行号锚点 + 结构化但自然的输出。这两种需求几乎是对立的——为其中一个优化会损害另一个。

关键认识

不是 AI 不够聪明，而是 AI 的手不够灵巧。 SWE-bench 的基线（2%）显示 LLM 在裸壳中挣扎——不是因为它不知道如何修 Bug，而是因为它无法高效地”看”代码和”改”代码。ACI 给了 LLM 一双灵巧的手——结果从 2% 跃升到 12.5%。

这让我重新审视正在构建的 Agent 系统：花了多少时间优化 LLM 的能力（选更强的模型、写更好的 prompt），又花了多少时间优化 LLM 与环境的交互界面？SWE-agent 的实验证明后者能带来 6 倍的提升——比换一代模型还显著。

未探索的方向

  1. 自适应的 ACI：能否让 LLM 在任务过程中自己调整 ACI 的参数（如返回行数、搜索广度）？
  2. 多 Agent 代码审查：一个 Agent 修复，另一个 Agent 审查修复——能否模拟人类 PR review 流程？
  3. 项目长期记忆：Agent 在修复多个 Bug 后，能否建立”项目理解”并在后续 Bug 中受益？
  4. 跨语言泛化：ACI 设计是否能从 Python 扩展到 C++、Rust、TypeScript？
  5. 安全护栏：如何让 Agent 在编辑关键安全代码（如认证、加密）时要求人类审查？
