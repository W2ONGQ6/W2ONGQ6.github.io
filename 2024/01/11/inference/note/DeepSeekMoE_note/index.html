DeepSeekMoE: Towards Ultimate Expert Specialization in Mixture-of-Experts Language Models

date: 2024-01-11

DeepSeekMoE: Towards Ultimate Expert Specialization in Mixture-of-Experts Language Models

核心信息

  • 标题: DeepSeekMoE: Towards Ultimate Expert Specialization in Mixture-of-Experts Language Models
  • 作者: Damai Dai, Chengqi Deng, Chenggang Zhao, R.X. Xu, Huazuo Gao, Deli Chen, Jiashi Li, Wangding Zeng, Xingkai Yu, Y. Wu, Zhenda Xie, Y.K. Li, Panpan Huang, Fuli Luo, Chong Ruan, Zhifang Sui, Wenfeng Liang (DeepSeek-AI)
  • 发表: arXiv 2024年1月, 预印本 2401.06066
  • 核心贡献: 提出 DeepSeekMoE 架构，通过细粒度专家分割（Fine-Grained Expert Segmentation）和共享专家隔离（Shared Expert Isolation）两大策略，实现专家专业化水平的显著提升。
  • 规模: 总参数 145B，激活参数 22.2B（仅约15%的参数在每次前向传播中被激活）
  • 性能: 在相同总参数规模下，以 75% 更少的计算量（FLOPs）超越 GShard；在 2T tokens 上预训练后，性能与 DeepSeek 67B Dense 模型相当
  • 后续影响: 该架构成为 DeepSeek-V2 和 DeepSeek-V3 的核心基础组件，直接推动了 DeepSeek 系列模型的成功

原文摘要翻译

Mixture-of-Experts (MoE) 架构在各种大规模语言模型的成功中发挥了关键作用。然而，现有 MoE 架构的训练面临专家专业化不足的问题，导致次优性能。本文中，我们提出 DeepSeekMoE 架构，旨在实现终极专家专业化（ultimate expert specialization）。具体而言，我们引入两大核心策略：（1）细粒度专家分割（Fine-Grained Expert Segmentation）：在保持总参数量不变的前提下，将标准 FFN 专家进一步切分为更细粒度的子专家，通过激活更多且更多样化的专家组合来提升知识获取的精确性；（2）共享专家隔离（Shared Expert Isolation）：将部分专家指定为共享专家（Shared Expert），这些专家始终被激活，用于捕获和巩固跨上下文的通用知识，从而减轻其他路由专家之间的冗余。我们还在工程层面设计了负载均衡损失和设备级路由机制。实验结果表明，DeepSeekMoE 2B 在相同总参数量的前提下，仅用约 40% 的计算量即达到与 GShard 2.9B（1.5x 专家数量）相当的性能。当我们将 DeepSeekMoE 扩展到 16B 总参数（激活参数约 2.8B）时，其性能与 DeepSeek 7B Dense 和 LLaMA2 7B 相当，但仅需后者约 40% 的计算量。进一步扩展到 145B 总参数时，DeepSeekMoE 16B MoE 的性能与 GShard 架构 137B（激活参数 30.1B）相当，计算量仅为后者的 25.4%（约 1/4）。

创新点 + Why Important

创新点 1: 细粒度专家分割（Fine-Grained Expert Segmentation）

传统 MoE 架构（如 GShard、Switch Transformer）中，每个专家通常是一个完整的 FFN 层。DeepSeekMoE 提出将标准的 N 个 FFN 专家切分为 mN 个更小的子专家（每个子专家的隐藏维度减少为原来的 1/m），在激活参数总量不变的情况下（top-K 路由改为 top-mK），激活更多且更多样化的专家组合。

Why important: 这个设计的洞察在于——知识本质上是细粒度的。一个”数学专家”内部可能同时封装了代数、几何、微积分等不同子领域的知识，当路由到一个专家时，这些知识被捆绑激活，造成了不必要的计算冗余和知识干扰。将专家切分后，每个子专家可以聚焦于更细粒度的知识单元，路由系统可以更精确地组合所需的知识片段。这在不增加总计算量的前提下，显著提升了模型的表达能力。

创新点 2: 共享专家隔离（Shared Expert Isolation）

在传统 MoE 中，所有专家都是路由专家，某些通用知识（如语法规则、基础词汇语义）会在多个专家中冗余出现。DeepSeekMoE 将 K_s 个专家指定为”共享专家”（Shared Expert），这些专家始终对所有 token 激活，而其余 mN - K_s 个专家作为”路由专家”（Routed Expert）通过 top-K_r 路由选择性激活。

Why important: 这是一个优雅的归纳偏置（inductive bias）设计。通过预先分离通用知识和专业知识，路由专家可以更专注于学习特定的、非冗余的知识模式，从而减少专家之间的参数冗余，提升每个路由参数的信息密度。这与人类认知中的”晶体智力”（通用知识）和”流体智力”（特定领域推理）的分工有异曲同工之妙。

创新点 3: 设备级负载均衡（Auxiliary-Loss-Free Device-Level Balance）

传统负载均衡通常依赖辅助损失（auxiliary loss）来鼓励均匀的专家利用率，但这会引入一个与语言建模目标相冲突的梯度信号。DeepSeekMoE 在训练中不使用传统的专家级负载均衡辅助损失，而是通过设备级路由机制确保跨设备的计算负载均衡，通过限制每个设备上处理的 token 数量上限来自然避免负载倾斜。

一句话总结

DeepSeekMoE 通过”把专家切细”（细粒度分割）和”把通用知识抽出来”（共享专家隔离）两个简单而深刻的设计，让每个专家专注于更纯粹的知识片段，在仅激活 15% 参数的情况下以 1/4 的计算量匹配 GShard 性能，为后续 DeepSeek-V2/V3 的成功奠定了架构基础。

研究问题

论文试图解决 MoE 架构中的三个核心挑战：

  1. 专家专业化不足（Insufficient Expert Specialization）: 现有 MoE 模型（GShard、Switch Transformer）中的专家倾向于学习到冗余的知识表示，不同专家之间的知识重叠度高，意味着参数利用效率低下。

  2. 知识混合与冗余（Knowledge Hybridity and Redundancy）: 标准 MoE 中，每个路由专家被迫同时学习通用知识（对所有 token 有用）和专业知识（仅对特定 token 有用），导致每个专家内部的知识表示混合且不够纯粹。

  3. 负载均衡与模型质量的权衡（Load Balance vs. Model Quality Trade-off）: 传统的辅助损失（auxiliary loss）机制虽然可以实现负载均衡，但会引入额外的训练信号干扰，在极端情况下可能损害模型质量。

机制三：负载均衡策略

专家级负载均衡（Auxiliary-Loss-Free）:

DeepSeekMoE 在训练中不使用传统的专家级辅助损失。论文认为辅助损失会引入与语言建模目标冲突的梯度，影响模型质量。替代方案是在损失函数中完全不加入负载均衡项，仅依靠自然的训练动态。

设备级负载均衡（Device-Level Balance）:

在实际部署中，通过设备级约束确保计算均衡:

  1. 将不同专家分布到不同设备上
  2. 限制每个设备上可处理的最大 token 数量
  3. 如果某设备的 token 分配超过上限，将多余 token 路由到次优专家（secondary routing）

这种方法将负载约束从训练机制转移到推理调度，避免了训练目标的污染。

1. 为何细粒度分割有效：信息论视角

从信息瓶颈（Information Bottleneck）理论来看，每个专家的隐藏维度决定了该专家的信息容量上限。传统 MoE 中，一个专家必须在一个较大的隐藏空间中编码其所有相关知识的表示，但由于路由是 hard top-K 选择，一个 token 只能访问 K 个完整专家。如果某个专家内部混合了多种知识，路由无法仅激活其中”对当前 token 有用”的部分。

细粒度分割增加了路由的自由度：更多的专家意味着更多的组合可能性，路由系统可以更精细地”拼装”所需的知识组合。这类似于从”大块积木”升级为”小块积木”——虽然总体积木量相同，但小块积木可以搭出更精细的结构。

2. 共享专家的双重角色

共享专家不仅减少冗余，还在训练中扮演着一个微妙的”锚定”角色。由于共享专家始终被激活，它们为路由专家提供了一个稳定的”背景知识”基础。这使得路由专家在训练初期更容易找到有意义的专业化方向——路由专家不需要”重新发明轮子”来学习基础语法和语义，可以更早地聚焦于专业化知识的学习。

这个设计可以类比为：共享专家是”通识教育”，路由专家是”专业选修”——通识教育为所有人提供基础能力，专业选修则让每个人发展独特专长。

3. 负载均衡的无损策略

放弃辅助损失是一个大胆的选择。大多数 MoE 工作视负载均衡为”必要之恶”——虽然没有它训练会不稳定，但加入它会损害质量。DeepSeekMoE 的方案本质上是将负载均衡从训练时的软约束（loss-based）转化为推理/部署时的硬约束（capacity-based），从而在训练质量上获得”免费午餐”。

4. 参数量与计算量的解耦

DeepSeekMoE 最深刻的贡献或许是证明了：在 MoE 架构下，总参数量（知识容量）和每 token 计算量（推理成本）可以被有效解耦。145B 总参数 + 22.2B 激活参数的配置意味着：

  • 知识存储能力 = 145B 参数的量级
  • 推理计算成本 = 22.2B 参数的量级
  • 训练计算成本 = 约为同性能 Dense 模型的 40%

5. 与后续工作的联系

DeepSeekMoE 的架构设计直接影响了：

  • DeepSeek-V2: 在 DeepSeekMoE 基础上加入 Multi-head Latent Attention (MLA)，实现 KV Cache 压缩
  • DeepSeek-V3: 将专家规模扩展到 671B 总参数，引入多 token 预测和 FP8 训练

局限

  1. 设备级路由的工程复杂性: 设备级负载均衡虽然理论上无损，但在实际分布式训练中实现复杂，需要精心设计的 all-to-all 通信模式。特别是在专家数多、设备数有限的情况下，secondary routing 可能导致模型性能的微小波动。

  2. 切分因子 m 的调优: 论文对 m=2 的实验较为充分，但更大的 m（如 m=4,8）的效果和最优值尚不明确。理论上 m 过大会导致每个子专家信息容量不足，存在一个最优平衡点。

  3. 共享专家数量的敏感性: K_s 的选择缺乏理论指导，主要依赖经验调优。K_s 过小无法有效分离通用知识，过大则会挤占路由专家的参数量。

  4. 训练数据规模的验证不足: 论文的大规模实验（145B）仅在 2T tokens 上训练，对于现代标准（如 LLaMA 3 的 15T tokens）而言偏少。

  5. 推理时的专家部署: 细粒度专家虽然降低了计算量，但所有专家仍需加载到内存中（145B 参数）。对于资源受限的推理场景，内存占用仍然是一个挑战。

可复用洞见

  1. 专家分割是一种通用的参数效率提升策略: 任何 MoE 架构都可以通过将现有专家进一步细分来提升路由精度，无需改变训练流程或损失函数。

  2. 共享专家是低成本高收益的设计: 仅额外增加极少参数（通常 2 个共享专家），就可以显著减少路由专家之间的知识冗余。

  3. 负载均衡不必依赖辅助损失: 将负载均衡从训练目标转移到系统调度层面是一个通用的设计模式。对于任何面临”优化目标 vs 约束条件”张力的问题，考虑将约束从损失函数移到系统机制都是值得尝试的思路。

  4. 激活参数不等于总参数的价值: 在评估 MoE 模型时，应区分”知识容量”（总参数）和”推理成本”（激活参数）。

  5. 共享专家 + 路由专家的二分法可推广: 将能力分为”通用基础”和”专业化扩展”两个层次，是设计大规模 AI 系统的通用方法论。

我的笔记

DeepSeekMoE 是理解 DeepSeek 整个技术路线图的最佳起点。这篇论文的贡献不在于提出颠覆性的新算法，而在于对 MoE 架构进行了两项精准的”外科手术式”改进。以下是我认为最重要的几点思考：

  1. “细粒度分割”本质上是增加了路由的组合空间: 从 N 选 K 变为 mN 选 mK，组合数从 C(N,K) 增加到 C(mN,mK)，扩大了数个数量级。这种指数级的组合空间增长是性能提升的深层数学原因。

  2. 共享专家的设计灵感可能来自计算机体系结构: 共享专家类似于 CPU 中的 L1 Cache——小而快，始终可访问，存储最常用的操作；路由专家类似于 L2/L3 Cache 或主存——更大但访问成本更高。这种层次化设计在计算机系统中被反复验证有效。

  3. “Auxiliary-Loss-Free”是大胆的选择: 在 MoE 社区中，负载均衡辅助损失几乎被视为标配。DeepSeekMoE 的实验表明为训练质量放弃辅助损失是值得的，这挑战了社区的一个隐性假设。

  4. 这篇论文的价值在于架构思想而非工程技巧: 与许多注重训练技巧的论文不同，DeepSeekMoE 的核心贡献是架构设计，这意味着其思想可以跨模型规模、跨训练框架移植。

  5. 后续工作的自然延伸: DeepSeek-V2 在此基础上加了 MLA（解决 KV Cache 问题），DeepSeek-V3 进一步加了 FP8 训练和多 token 预测。三者形成了一个完整的”高效大模型”技术栈。

后续问题

  1. 细粒度分割的最优 m 值如何随模型规模变化？是否存在一个 Scaling Law 可以预测最优 m？
  2. 共享专家的数量 K_s 是否需要随总参数量扩展？扩展规律是什么？
  3. 细粒度分割是否可以与 Mixture-of-Depths 等方法结合，实现动态的计算分配？
  4. 在持续预训练（continual pretraining）场景中，细粒度专家的专业化模式如何演变？
  5. 共享专家的设计是否可以推广到 Attention 层？例如设一个始终激活的共享 KV head？
  6. 细粒度专家如何影响模型的可解释性？更细的专家是否意味着更容易理解每个专家学到的知识？
  7. 在 MoE 推理的专家卸载场景（expert offloading）中，细粒度分割是否有助于更精细的内存管理？
