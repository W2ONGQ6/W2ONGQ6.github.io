原文摘要翻译

代码智能的增长已成为大语言模型时代最引人注目的现象之一。本文提出DeepSeek-Coder，一个从零开始用2万亿token代码数据训练的开源代码模型系列。与基于通用LLM微调的代码模型不同，DeepSeek-Coder采用”代码优先”策略——在训练中分配87%的数据为代码，并在训练后期引入10%的自然语言数据以保持语言理解能力。模型支持仓库级代码理解，通过文件间关系建模实现了对整个项目的跨文件代码生成。我们在1.3B到33B参数范围内提供多个尺寸的模型。在HumanEval、MBPP、DS-1000等多个编程基准上，DeepSeek-Coder-33B达到了当时开源代码模型的SOTA水平。

创新点

  1. “代码优先”从零训练——与Code Llama等微调路线的根本分歧：DeepSeek-Coder从随机初始化权重开始，87%训练token为代码。这与Code Llama（基于LLaMA微调）和StarCoder（通用+代码混合预训练）是根本不同的策略——代码知识不是附加插件，而是模型知识结构的根基。

  2. 仓库级（Repository-level）代码理解：引入跨文件上下文建模——通过在训练中注入文件间的import/调用关系，模型学会理解仓库的拓扑结构。在CrossCodeEval上，跨文件上下文将性能从58.9%提升到76.4%（+17.5pp）。

  3. 16K上下文窗口的FIM训练：支持长达16K token的Fill-in-the-Middle训练，使模型能在长代码段中精确插入代码。16K窗口是StarCoder 8K的2倍。

  4. 广泛多语言和多基准评测的全面覆盖：在超过10个基准上进行全面评测，提供了当时最全面的开源代码模型性能画像。

一句话总结

DeepSeek-Coder以”代码优先”从零训练策略，在2万亿token代码数据上训练，通过仓库级理解和16K长上下文，在33B规模达到开源代码模型SOTA，代表了当时中国AI在代码生成领域的最高水平。

研究问题

核心问题分解

当模型从一开始就以代码为中心进行训练（而非先学会通用语言再学代码），它能获得怎样不同的代码理解模式？这种策略能否在更小的参数规模上达到与更大通用模型相当的性能？

子问题 1：”代码优先” vs “通用优先”的知识组织差异

Code Llama（基于LLaMA微调）的知识结构是”自然语言地基 + 代码上层建筑”。DeepSeek-Coder的知识结构是”代码地基 + 语言上层建筑”。

这两种策略在知识组织上可能有本质差异：（a）代码优先模型可能形成更高效的编程知识表示（因为主要注意力都用于学习代码模式），（b）代码优先模型可能在自然语言理解上较弱（10%的语言数据不足以维持完整的NLU），（c）代码优先模型可能对代码特有的模式（如缩进结构、变量命名约定、API使用模式）有更深的理解。

子问题 2：2T token代码数据的规模效应

2T token是一个巨大的投资——估计需要数十个A100 GPU集群训练数周。这个规模的”代码优先训练”是否遵循预训练的scaling law？2T token之后是否仍有正收益？是否有收益递减的拐点？

子问题 3：仓库级理解的实现方法

如何在预训练中将跨文件依赖注入模型？如何在推理时高效地检索相关文件？这两种机制（训练时依赖注入 vs 推理时依赖检索）是否互补？

Before-This-Paper Pain Points

  1. 代码模型的”单文件近视”：现有代码模型（Code Llama, StarCoder）将所有代码文件视为独立文本——忽略了软件工程的基本现实：代码是相互关联的（import、继承、调用）。
  2. “通用优先”路线的天花板：虽然Code Llama通过在LLaMA上微调取得了不错的性能，但其知识地基（LLaMA）是为自然语言设计的——再多的代码微调也无法改变知识组织的基本模式。
  3. 开源代码模型的性能落后于闭源：在DeepSeek-Coder发布前，开源代码模型在HumanEval等基准上落后GPT-4约30个百分点。社区需要一个”缩小差距”的突破。

数据与任务定义

训练数据

  • 总量：2万亿token（约10倍于StarCoder的代码训练量）
  • 组成：
    • 87% 代码（GitHub公开仓库，涵盖Python、Java、JavaScript、C++、Go、Rust等100+种语言）
    • 10% 代码相关自然语言（GitHub Markdown、README、Commit messages、Issues、PR讨论）
    • 3% 通用自然语言（StackExchange技术问答）
  • 数据处理：去重（文件级和仓库级）、质量过滤（排除自动生成代码、过短/过长文件）、个人信息脱敏
  • 预训练阶段：早期87%代码+3%Markdown（纯代码阶段），后期引入剩余10%的自然语言和代码相关文本（”语言回归”阶段）

模型尺寸

  • 1.3B（轻量，适合本地IDE集成和边缘设备）
  • 5.7B（中等，性能与效率的平衡）
  • 6.7B（最优单GPU部署尺寸——A100 40GB可容纳）
  • 33B（旗舰，追求最佳性能）
  • 架构：基于LLaMA的decoder-only Transformer + RoPE位置编码 + SwiGLU激活 + Grouped Query Attention

评测基准

  • HumanEval：164道Python手写编程题，pass@1（功能正确性）
  • MBPP：974道Python编程题，pass@1
  • DS-1000：1000道数据科学编程题（Pandas, NumPy, Matplotlib, SciPy, Scikit-learn, TensorFlow, PyTorch），pass@1
  • MultiPL-E：HumanEval的多语言翻译版（C++, Java, JavaScript, Rust, Go, PHP等），pass@1
  • CodeContests：竞赛编程题（Codeforces级别），pass@1
  • APPS：从入门到竞赛级别的编程题
  • LiveCodeBench：最新发布的编程题（防止数据泄露）
  • CrossCodeEval：仓库级代码生成评测

方法主线

机制流程：DeepSeek-Coder的完整6步链路

Step 1：从零代码预训练——87%代码数据

  • 输入：随机初始化的Transformer权重 + 2T token代码数据
  • 操作：
    1. 使用标准自回归语言建模目标训练模型：
      L = -sum_t log P(token_t | token_{<t})
    2. 训练分为两个阶段：
      • Phase 1（前70%的训练）：87%代码 + 10% Markdown + 3% StackExchange
      • Phase 2（后30%的训练）：增加自然语言混合比例到85/15，引入”语言回归”——确保模型不遗忘语言理解
    3. 优化器：AdamW + 余弦学习率调度 + 梯度裁剪
    4. 分布式训练：数据并行 + 张量并行（对33B模型），使用DeepSeek自研的训练框架（HAI-LLM）
  • 输出：预训练的DeepSeek-Coder基础模型
  • 目标：建立一个以代码为根基、兼顾语言理解的基础模型

Step 2：FIM训练——填充中间的能力注入

  • 输入：预训练模型的中间checkpoint + FIM格式化的代码数据
  • 操作：
    1. 在预训练的后期阶段（后20-30%），将部分训练数据重组为FIM格式：
    2. 模型被训练为从 <fim_prefix> 和 <fim_suffix> 预测 <fim_middle>
    3. FIM的三种模式（随机选择）：
      • PSM (Prefix-Suffix-Middle)：先前缀、后后缀
      • SPM (Suffix-Prefix-Middle)：先后缀、此前缀（增加多样性）
      • 标准自回归（无FIM）：保持续写能力
    4. FIM数据比例：约50%的批次使用FIM格式，50%使用标准格式
  • 输出：支持FIM的代码模型
  • 目标：使模型能在给定前后文的情况下精确补全中间代码

Step 3：仓库级训练——跨文件依赖注入

  • 输入：同一仓库中的多个相关文件
  • 操作：
    1. 解析每个源文件的import语句和函数调用，构建文件间的依赖关系图：
    2. 在训练时，将依赖文件的代码作为额外的前缀条件注入：
    3. 依赖选择策略：不是注入整个依赖文件（太长），而是：
      • 仅注入被引用的函数/类的定义
      • 最多注入N个依赖（N=5-10，防止上下文过长）
      • 按调用频率排序（最常用的依赖优先）
    4. 在推理时，模型学会”当我看到一个import语句，我应该预期依赖文件中的API”
  • 输出：具备仓库级理解能力的模型
  • 目标：训练模型在跨文件上下文中理解代码——这是软件工程的本质

Step 4：指令微调——对话式编程能力

  • 输入：预训练模型 + 精心构建的代码指令数据（1B+ token）
  • 操作：
    1. 收集和构造代码指令数据，涵盖：
      • 代码生成：”写一个函数来…”
      • 代码解释：”解释这段代码做了什么”
      • 代码调试：”这段代码有什么bug”
      • 代码优化：”如何优化这个算法”
      • 仓库级任务：”在这个项目中，找到所有使用函数X的地方并替换为Y”
    2. 指令数据来源：手动编写 + 开源数据集（如Evol-Instruct的代码版本）+ GPT-4生成的高质量指令
    3. SFT训练：标准因果语言建模，仅对回答部分计算损失
    4. 保留基础模型版本（DeepSeek-Coder-Base）和指令微调版本（DeepSeek-Coder-Instruct）
  • 输出：DeepSeek-Coder-Instruct
  • 目标：将代码生成能力包装为对话式编程接口

Step 5：推理时的仓库级检索

  • 输入：用户查询 + 目标文件 + 仓库文件树
  • 操作：
    1. 构建仓库级索引——对仓库中的所有文件进行BM25索引或语义嵌入索引
    2. 当用户查询涉及特定文件时，自动检索该文件依赖的其他文件
    3. 相关文件选择策略：
      • 直接依赖（import关系）：强制加入（高优先级）
      • BM25相关：使用查询文本检索top-k（k=5-10）
      • 语义相似：使用代码嵌入检索语义相关的文件
    4. 将检索到的相关文件代码片段拼接到prompt，放在目标文件之前
    5. 16K上下文窗口用于容纳跨文件上下文
  • 输出：带有跨文件上下文的增强prompt
  • 目标：在推理时模拟训练中的仓库级依赖结构

Step 6：解码策略与后处理

  • 输入：增强prompt + DeepSeek-Coder-Instruct模型
  • 操作：
    1. 对于代码生成：greedy decoding (T=0) 用于pass@1评测，nucleus sampling (T=0.8, p=0.95) 用于pass@k
    2. 停止词检测：函数/类定义结束符、文件结束、多余的空白行
    3. 代码格式化：可选的后处理——应用black/autopep8进行一致的格式
    4. 对于FIM填充：在推理时使用FIM格式的prompt，模型预测 <fim_middle> 部分
  • 输出：生成的代码（单函数或跨文件补丁）
  • 目标：高质量、可运行的代码生成

深度分析

“代码优先” vs “通用优先”——一个知识组织理论

这两个策略的根本差异可以通过”知识组织的建筑类比”理解：

  • 通用优先（Code Llama）：先建一座通用语言的大厦（LLaMA 7B-70B），然后在大厦的顶楼加建一个”代码套间”。代码能力建立在对语言能力的理解和推理之上——“语言能力是地基，代码能力是上层建筑”。优势：自然语言能力强，可以进行流畅的代码解释和讨论。劣势：代码知识被组织为自然语言知识的”延伸”，而非独立的知识体系——可能效率不高。

  • 代码优先（DeepSeek-Coder）：从零开始，用87%的砖块（代码token）建造一座”编程大厦”，然后用13%的砖块在周围建造”语言设施”。代码知识是地基，语言能力是附加的。优势：代码知识的内部表示更紧凑、更高效——模型的大部分参数都用于编码编程模式。劣势：语言能力相对弱——不能很好地进行代码之外的自然语言任务。

实证支持：DeepSeek-Coder-6.7B (74.8% HumanEval) >> Code Llama-13B (42.7%)，同时参数量仅为一半。在”每参数效率”上，代码优先训练在编程任务上具有2-3倍的优势。

2T token代码数据的计算投入与回报

2T token的训练是一个巨大的计算投资——使用DeepSeek自建的HAI-LLM训练框架（支持高效的数据并行+张量并行+流水线并行），在数十个A100 GPU集群上训练估计需要数周时间。

估算：33B参数模型，2T token，A100 GPU。

  • FLOPs：约6 × 33B × 2T = 约396 × 10^21 FLOPs ≈ 400 ZFLOPs
  • A100 (bf16)：312 TFLOPs
  • GPU小时：400 × 10^21 / (312 × 10^12 × 3600 × GPU利用率0.5) ≈ 720,000 GPU小时
  • 使用256块GPU：约117天

这解释了为什么DeepSeek的”Coder优先”策略不是其他团队可以轻易复制的——它需要巨大的前期算力投资。但回报也是显而易见的——33B模型的性能接近GPT-4（在HumanEval上仅差7.7pp）。

仓库级理解的技术难度——不只是”塞更多文件”

仓库级代码生成的难点不在于”把更多文件放进上下文”（这是简单的），而在于：

  1. 选择正确的文件：一个100文件的项目中，只有3-8个文件与当前查询真正相关。错误选择文件（包含不相关或误导性的代码）比没有额外上下文更糟糕——它引入噪声而非信号。

  2. 提取文件的相关部分：即使一个文件是相关的，它可能包含数千行代码——其中90%与当前查询无关。需要智能地提取：仅相关函数/类/变量定义。

  3. 处理跨文件的一致性：生成的代码需要与依赖文件中的API签名和类型定义一致。如果文件B定义了 def process(data: List[int]) -> Dict[str, float]，文件A中对该函数的调用必须匹配。

DeepSeek-Coder通过”训练时依赖注入”（在预训练中见过了这种跨文件模式）+ “推理时结构检索”（利用import图和BM25来智能选择上下文）的双重策略来解决这些挑战。

为什么DeepSeek-Coder在DS-1000上的优势最大

DS-1000（数据科学编程）评测的是”使用特定库API解决数据科学问题”的能力。这类任务的本质是”API知识回忆 + API使用模式”——恰好是”代码优先训练”的最大优势：

  • 在2T token代码数据中，Pandas、NumPy、Matplotlib等库的API在大量notebook、脚本、项目中反复出现
  • 代码优先模型在预训练中”看”这些API的次数可能比通用模型多10-100倍
  • 结果：对API的签名、参数默认值、常见使用模式的”内化”远超通用模型

在HumanEval上，DeepSeek-Coder vs GPT-4的差距为7.7pp。在DS-1000上差距为11.6pp——GPT-4在DS-1000上的额外优势可能来自：（a）更大的模型容量存储了更丰富的API知识，（b）更强的推理能力处理需要多步API链式调用的复杂问题，（c）可能的训练数据中包含更多数据科学相关内容（GPT-4的训练细节未公开）。

与后续版本的关系

DeepSeek-Coder-v2（2024年6月发布）进一步提升了性能——使用更大的模型（236B MoE架构）和更多的训练数据，在HumanEval上达到约90% pass@1，进一步缩小了与闭源模型的差距。v2的架构调整（从密集模型转向MoE）代表了”参数效率”的优化——在相同的推理成本下获得更高的质量。

局限

  1. 非代码任务的显著退化：87%代码数据训练的代价是自然语言能力的显著下降。在MMLU上，DeepSeek-Coder-33B得分约38.4，而Code Llama-34B约48.1——差距约10pp。对于需要”编程+讨论”混合场景的用户（如”解释这段代码的设计模式并讨论替代方案”），DeepSeek-Coder的语言能力不足可能成为瓶颈。

  2. 训练成本的”富者愈富”问题：2T token从零训练的算力成本（估计>50万美元）使得只有少数组织能复现和验证——学术团队和小公司无力参与”代码优先”路线的竞赛。这加剧了AI研究中的算力不平等。

  3. 仓库级理解的检索瓶颈：推理时的跨文件检索（BM25 + import图）可能：（a）遗漏语义相关但无显式import关系的文件（如配置文件、常量定义文件），（b）检索到错误文件并引入误导性信息，（c）在超大型仓库（>1000文件）中检索效率低。

  4. 数据泄露风险——GitHub训练的固有矛盾：2T token中几乎肯定包含了评测基准的答案（尽管进行了去污染处理）。”从GitHub用代码训练的模型”和”评测该模型在编程题上的表现”之间存在固有的循环论证风险——训练数据中可能包含了HumanEval问题的解答作为公共代码片段。

  5. 最新语言特性和框架的覆盖缺失：训练数据截止时间（约2023年中）意味着模型不受Python 3.12+的新特性、2024年的新框架版本（如React 19）、或最新的API变更的影响。这是一个持续的问题——代码模型需要定期重新训练以跟上语言和框架的演进。

  6. 仅英文自然语言的良好支持：虽然代码覆盖100+种语言，但自然语言部分（10% Markdown + 3% StackExchange）以英文为主。对中文、日语等非英文编程社区的代码注释和文档的理解能力较弱。

  7. “代码正确性”的评测盲区：与所有基于pass@k的评测一样，DeepSeek-Coder在HumanEval等基准上的高分不能反映代码质量维度（安全性、时间复杂度、可维护性、是否有文档）。79.3%的pass@1意味着模型能”写一个通过测试的函数”，但可能这个函数使用了O(2^n)的算法或忽略了边界条件。

可复用洞见

  1. “领域优先”训练 > “通用预训练+微调”：

    • 洞见：在目标领域有足够的数据（>1T token）和算力（>100K GPU小时）时，从零开始的领域优先训练能产生比”通用预训练+域内微调”更深层的领域知识组织。这体现在”每参数效率”的2-3倍优势。
    • 为什么泛化：通用预训练分配了大量参数容量给”通用语言理解”——这些容量在领域任务中可能是”浪费的”（冗余的语言能力）。领域优先训练将几乎所有参数容量都分配给领域特定的模式和知识。
    • 如何具体应用：（a）评估目标领域的数据量和质量是否足以支撑从零训练（>100B token通常是门槛），（b）选择”领域数据占比”——DeepSeek的87/13比例是一个好的起点但可能需要根据领域调整，（c）在训练后期加入”通用数据回归”阶段防止灾难性遗忘。

  2. 仓库级理解 = 显式依赖图建模：

    • 洞见：跨文件代码生成的关键不是”更多上下文”，而是”更结构的上下文”——显式建模文件间的import/调用关系，并将这些关系作为上下文组织的依据。
    • 为什么泛化：这个原则适用于任何需要理解”关联实体网络”的场景——不仅是代码，还包括知识图谱、文档链接、微服务依赖。
    • 如何具体应用：（a）在训练前构建项目的依赖图（import图、调用图、继承树），（b）在训练时将依赖关系作为上下文组织的结构先验，（c）在推理时使用依赖图引导相关文件的检索——优先检索有显式依赖关系的文件。

  3. FIM训练的长期价值——不仅是代码补全：

    • 洞见：FIM训练不仅提升代码补全性能——它还增强了模型对代码结构的理解（因为被mask的中间部分迫使模型学习前后文如何约束代码逻辑）。
    • 为什么泛化：任何”在给定上下文中填充中间部分”的任务都可以从FIM风格的结构化训练中获益——文本填充、模板补全、配置生成。
    • 如何具体应用：（a）为FIM设置足够大的上下文窗口（>8K）以捕获有意义的结构上下文，（b）FIM数据占总训练数据的40-60%——在这个比例范围内，FIM不会损害标准自回归性能，（c）使用多种FIM格式（PSM, SPM）增加多样性。

  4. 多尺寸模型家族的战略价值：

    • 洞见：DeepSeek-Coder提供1.3B到33B的多个尺寸——不同尺寸服务于不同的部署场景：1.3B用于IDE本地插件，6.7B用于单GPU服务器，33B用于云API。
    • 为什么泛化：单一模型尺寸无法满足所有部署场景的需求——轻量场景需要小模型（低延迟、低成本），重量场景需要大模型（高质量）。
    • 如何具体应用：（a）在开发模型系列时，规划和训练至少3个尺寸（轻量/平衡/旗舰），（b）确保不同尺寸的模型在关键能力上共享相同的架构和训练数据（以保持能力画像的一致性），（c）为用户提供”性能阶梯”——从小模型开始，如果质量不足则升级。

我的笔记

DeepSeek-Coder是2024年初最重要的开源代码模型之一。它在技术路线上的核心选择——“代码优先”训练——是一个有争议但有充分实验支撑的设计决定。33B参数就超越了许多更大的通用模型，证明了领域特化训练的显著有效性。

DeepSeek-AI的研究风格与OpenAI有明显不同——DeepSeek更强调模型效率和领域深度，而非追求”通才”式的通用性。DeepSeek-Coder和DeepSeek-V2/Chat等通用模型的互补策略（专用代码模型+通用对话模型并行）是一个务实的方案——每个模型专注于其擅长的领域，通过API或模型路由聚合。

仓库级代码理解是DeepSeek-Coder最具前瞻性的能力——它预见了AI编程助手从”智能代码补全”到”智能项目协作”的演进。后续的Devin、SWE-agent、Cursor等AI软件工程Agent都严重依赖这种跨文件理解能力（无论是在代理逻辑层面还是基座模型层面）。

从中国AI产业的角度，DeepSeek-Coder是中国公司在全球代码生成领域的重要里程碑——证明了”从零训练+开源”的路线可以产生与国际顶级团队竞争的质量。在DeepSeek-Coder之前，中国AI在代码生成领域的贡献主要集中在应用层（如阿里通义灵码）；DeepSeek-Coder证明了中国团队也可以在基础模型层做出世界级的工作。

前瞻性判断

  1. “领域优先训练”将在更多领域被尝试——不仅是代码，还有数学、科学、医学等领域。专门的科学模型（如”Science LLM”）将采用类似的策略。
  2. 仓库级理解将成为代码模型的标配——未来的代码模型将在预训练中内置项目级别的上下文理解，而不是作为推理时的附加功能。
  3. 代码模型将在”质量”（而非”正确性”）上进行评测——未来的评测将从”通过的测试数量”扩展到”代码的安全性、效率和可维护性”等多维度。
  4. DeepSeek-Coder的架构可能被多次复制——在算力充足的前提下，”代码优先从零训练”的策略将吸引更多团队尝试。

后续问题

  1. DeepSeek-Coder的”代码优先”训练策略在视频、3D、科学计算等其他领域是否同样有效？87/13的代码/语言比例是否适用于其他模态？

  2. 仓库级理解能否从”检索相关文件”升级为”理解整个仓库的全局语义图”——通过代码的embedding聚类和代码调用图分析构建项目的”心智模型”？

  3. 如何量化”代码质量”（不只是功能正确性），使代码模型不仅能生成”通过测试的代码”，还能生成”优雅、高效、安全的代码”？
