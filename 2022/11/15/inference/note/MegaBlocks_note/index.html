MegaBlocks: Block-Sparse MoE运算——消除Token丢弃与零填充的权衡

date: 2022-11-15

MegaBlocks: Block-Sparse MoE的系统层革命

核心信息

MegaBlocks 将 MoE 计算重新表述为 block-sparse 矩阵运算，从根本上解决了传统 MoE 实现中负载不均衡导致的”token 丢弃 vs 零填充”两难问题。传统方法必须通过填充（将 tokens 补齐到统一数量，浪费计算 15-50%）或丢弃（通过 capacity_factor 截断，损失训练数据）来处理专家的自然不均衡负载。MegaBlocks 利用 block-sparse GEMM（基于 NVIDIA CUTLASS 的 Sparse Toolkit stk），让每个专家自然处理不同数量的 token——不填充、不丢弃。训练速度比 Tutel 快 40%、比 dense Transformer 快 2.4 倍，且完全消除了 capacity_factor 超参数。Mixtral 8x7B 明确将 MegaBlocks 列为致谢对象。

原文摘要翻译

我们提出了 MegaBlocks，一个面向 MoE（Mixture-of-Experts）模型的高效稀疏训练系统。MegaBlocks 将 MoE 计算重新表述为 block-sparse 运算，使用块稀疏矩阵乘法处理自然不均衡的专家分配，无需为负载均衡进行填充或丢弃 token。通过基于 CUTLASS 构建的稀疏计算库 stk，MegaBlocks 实现了 Variable-Sized Batched GEMM——不同专家可处理不同数量的 token，而非传统的统一批量。MegaBlocks 与 Megatron-LM 深度集成，在 8-64 专家的 GPT-MoE 上实现了比 Tutel 快 40% 的训练速度，且在负载严重不均衡时加速更显著（+70%）。MoE 训练首次可以在零 token 丢弃和零计算浪费的情况下进行。

创新点

  1. Block-Sparse MoE 计算范式 — 抛弃传统的”token 填充 + dense GEMM”或”token 丢弃 + capacity_factor”方法，将每位专家的 FFN 计算表达为 block-sparse 矩阵乘法——只计算实际分配的 token 块，跳过零填充区域。这是对 MoE 计算的根本性重新抽象。

  2. Sparse Toolkit (stk) — 高效的 GPU 稀疏计算库 — 基于 NVIDIA CUTLASS 构建，实现了 Variable-Sized Batched GEMM——每个 expert 的 FFN 可以接受不同数量的 token 作为输入，输出对应不同数量的 output tokens。块大小固定为 128，匹配 A100 TensorCore 的硬件 tile 尺寸。

  3. 消除 capacity_factor 超参数 — capacity_factor 是 MoE 训练中最敏感的超参数之一（决定”多少 token 可以被丢弃”）。MegaBlocks 完全不需要它——block-sparse 天然处理不均衡，无需容量上限。这直接降低了 MoE 训练的门槛和调参复杂度。

  4. 系统性速度基准与集成 — 与 Megatron-LM 深度集成（drop-in 替换），支持 3D 并行（数据/专家/流水线）。vs Tutel +40%，vs Fairseq MoE +2.1x，vs Dense Transformer +2.4x，且速度优势在负载不均衡时更大。

一句话总结

MegaBlocks 以 block-sparse 矩阵乘法取代 token 填充/丢弃，从根本上解决了 MoE 负载不均衡的计算效率问题——这不是算法改进，而是让 MoE 的算法优势在 GPU 硬件上真正高效兑现的系统层创新，capacity_factor 宣告过时。

研究问题

核心挑战与子问题

子问题1：Token 填充的效率损失有多严重？

传统 MoE 实现（Tutel, Fairseq MoE）的”token 填充”策略：将所有专家的输入 token 数填充到统一大小（取所有专家中最大 token 数的那个 expert），然后用 dense GEMM 处理。这个策略的根本缺陷在于 MoE 的负载天然不均衡——某些专家收到的 token 可能是其他专家的 2-3 倍。容量因子 capacity_factor 限制了每个专家可处理的 tokens 数，但即使 capacity_factor=1.25（一个常用设置），仍有约 25% 的位置被填充为零——浪费了 25% 的计算 FLOPs。

量化在真实训练中的浪费：对于 8 专家 GPT-MoE，Tutel 的实现平均浪费约 15-20% 的 FLOPs。当某些专家严重过载时（如”通用语言”专家在文本数据集上天然收到更多 token），浪费可达 40-50%。对于 100B 参数规模的训练（约 100 万 GPU 小时），15% 的浪费 = 15 万 GPU 小时 ≈ $300K cloud 成本（按 $2/GPU 小时）。

子问题2：Token 丢弃的质量损失。

Switch Transformer 的 token 丢弃方法：设置 capacity_factor（如 1.0），当某专家的输入 token 数超过 capacity_factor × (tokens_per_expert) 时，过剩 token 被丢弃——它们通过残差连接绕过 MoE 层（失去了一次 FFN 处理机会）。

量化质量损失：capacity_factor 从 2.0 降到 1.25 增加了约 0.05-0.1 PPL（在 Switch Transformer 的实验中）。当 capacity_factor=1.0 时，约 10-15% 的 token 被丢弃——这对语言建模 PPL 有可测量的影响（PPL 增加约 0.1-0.2），虽然看似微小，但在大规模训练中这些”失去的 FFN 处理”累积的梯度信号损失是实质性的。

更关键的是超参数敏感性：capacity_factor 从 1.0 到 1.5 需要细粒度调优——设置太高浪费计算，设置太低丢失训练信号。这大大增加了实验周期（每新的 expert 数量、top-K、或 batch size 可能需要重新优化 capacity_factor）。

子问题3：Block-sparse GEMM 在 GPU TensorCores 上的实现效率。

MegaBlocks 的核心工程挑战：如何在 GPU TensorCores（张量核心，优化的矩阵乘法单元）上高效执行不规则大小的矩阵乘法——每个专家处理不同数量的 token 导致每个 GEMM 操作有不同的输入矩阵维度。

TensorCores 被设计为高效处理固定大小的 tile（如 128×128 的矩阵块）。非规则的矩阵大小不能直接映射到 TensorCore 操作。MegaBlocks 的解决策略：将所有专家 FFN 组合成一个大 sparse matrix，然后在 block-sparse 级别（以 128×128 tile 为粒度）调度 TensorCore GEMM。

块大小 128 的选择：64 太小→稀疏索引开销占比大（>10%）；256 太大→块内零填充浪费增加（当块部分填充时）；128 是 A100 TensorCore tile 的天然簇（每 SM 上的 TensorCore 处理 128×128 的 BF16 matmul 约为 8 个连续的 warp 协作），也是最优的”索引开销 vs 填充浪费”平衡点。

子问题4：分布式训练中的 block-sparse 通信开销。

在专家并行（expert parallelism）设置中，token 需要在 GPU 间 all-to-all 传递（因为不同专家的参数分布在不同 GPU 上）。这需要：(a) token permutation（按专家重新排列 token）；(b) all-to-all 通信（发送 token 到持有目标专家的 GPU）；(c) block-sparse GEMM（本 GPU 的专家处理接收到的 token）；(d) token unpermutation（恢复原始 token 顺序）。

MegaBlocks 引入的额外开销集中在 (a) 和 (d) 的转换步骤——在 permuted token buffer 和 block-sparse CSR 格式之间转换。这些转换的额外开销占训练时间的约 5-8%。对比 Tutel 的 15-50% 填充浪费（在 GEMM 本身），5-8% 的转换开销是净节省——因为 GEMM 加速（40%+）远超转换开销。

子问题5：为什么 block-sparse 抽象是 MoE 计算的”正确”范式？

MegaBlocks 的哲学贡献往往被忽视：MoE 的负载不均衡不是”需要被修正的问题”（传统方法试图通过填充/丢弃来强迫均衡），而是 MoE 架构的”自然属性”（不同 token 需要不同专家，某些专家的”受众”天然更多）。当一个架构的自然行为不被实现所允许时，问题不在于架构——而在于实现。

Block-sparse 运算是处理条件计算（conditional computation）的通用抽象。任何”基于条件选择子集进行计算”的场景（MoE 路由、dynamic layer skipping、conditional attention 等）都可以从 block-sparse 视角重新设计——将条件计算映射为稀疏矩阵乘法，跳过被”条件”排除的块。这是一个比 MoE 更具普适性的计算范式。

数据与任务定义

  • 测试模型: GPT-style MoE Transformer (125M - 2.7B 参数), 8-64 专家/层
  • 训练数据: The Pile (825GB, 语言建模基准)
  • 硬件: NVIDIA A100 80GB 集群
  • 对比系统: Microsoft Tutel, Fairseq MoE, Dense Transformer (等参数和等激活参数两种基线)
  • 速度指标: Tokens/s/GPU, 总 wall-clock 训练时间, GEMM FLOPs 利用率
  • 并行策略: 数据并行 + 专家并行 + 流水线并行的 3D 组合

MoE 配置详情

  • 专家数量: 8, 16, 32, 64（消融 sweep）
  • Top-K 路由: K=1 or K=2
  • 容量因子: N/A (MegaBlocks 不需要) vs 1.25 (Tutel 基线)
  • Global batch size: 约 1M tokens
  • 序列长度: 2048 tokens
  • 专家 FFN 中间维度: 4× 隐藏维度（标准 GPT-3 风格 FFN）

方法主线

完整的机制流程

步骤1: Token 路由与专家分配 — 确定每个 token 的目标专家

输入: 输入 token 序列 X ∈ R^{N×D}（N tokens, D 隐藏维度）

操作:

  • 路由线性层: logits = X W_router（W_router ∈ R^{D×E}, E=专家数量）
  • Top-K 选择: 为每个 token 选择 logits 最高的 K 个专家
  • 加上可选的辅助随机扰动（如 random routing aux loss）
  • 记录每个专家收到的 token 索引列表

输出: expert_tokens[e] = {所有路由到专家 e 的 token 索引}, e = 1..E

步骤2: Token 重排 (Permutation) — 按专家分组 token

输入: expert_tokens[e] 的分配信息

操作:

  • 将输入 tokens X 按专家分组重新排列——连续存储专家 0 的所有 token、然后是专家 1、…
  • 使用 GPU scatter/gather 操作（或 NCCL all-to-all 在分布式设置中）
  • 构建 permuted token buffer: [专家0_tok1, 专家0_tok2, …, 专家1_tok1, …, 专家E_tokN_E]

输出: 重排后的 token buffer（按专家连续分组）

步骤3: 构建 Block-Sparse CSR 表示 — 为 block-sparse GEMM 准备数据

输入: 每个专家的 permuted tokens（不同专家有不同数量的 tokens）

操作:

  • 确定块大小 = 128（匹配 A100 TensorCore tile）
  • 对每个专家: 将其 tokens 按 128 对齐分组 → ceil(N_e / 128) 个 blocks
    • 如果最后一块不足 128 → 填充到 128（仅块内填充，代价小）
  • 构建 CSR（Compressed Sparse Row）索引:
    • Row pointer: 每个输出行（每个输出 token）对应的非零 block 的起始和结束索引
    • Column index: 每个非零 block 对应的专家 ID
    • Values: 每个非零 block 的起始 token 位置（在该专家内的偏移）

输出: Block-sparse CSR 格式的 MoE FFN 输入数据

步骤4: Block-Sparse GEMM — TVariable-Sized Batched GEMM

输入: CSR 格式的输入 tokens + 所有专家的 FFN 权重（W1, W2）

操作:

  • 遍历所有非零 blocks（即所有有 token 分配的 (expert, token group) 对）
  • 对每个非零 block: 调用 CUTLASS TensorCore GEMM（128×128 粒度的矩阵乘法）
    • 输入: tokens[block_start:block_start+128] × W_expert
    • Precision: BF16/FP16（矩阵乘法）, FP32（累加）
  • 跳过零 blocks（无 token 分配的专家 block）— 无计算、无内存访问
  • 每个专家的 blocks 可以独立并行（CUDA stream 并行或 warp-level 并行）

输出: 每个专家的 FFN 输出（仅计算实际分配的 tokens）

步骤5: Token 反向重排 (Unpermutation) — 恢复原始顺序

输入: 各专家的 FFN 输出（按专家分组）

操作:

  • 将 expert-grouped 输出转换回原始 token 顺序
  • 使用之前记录的 token-to-expert 映射的后向转换
  • 将恢复后的输出合并回 MoE 层的残差路径

输出: MoE 层的最终输出（按原始 token 顺序）

Block-Sparse CSR 格式的细节

CSR（Compressed Sparse Row）格式是稀疏矩阵的标准表示。传统 CSR 用于稀疏矩阵的 storage（如表示一个 1% 非零的稀疏矩阵），而 MegaBlocks 将它扩展到 block-sparse 的 GEMM 操作。

定义一个 E 个专家的 MoE FFN 层为一个大的”虚拟”矩阵 M ∈ R^{N×E×d_ff}（所有专家的权重组装）。该矩阵只在”每个 token 被路由到的 K 个专家”的位置有非零块。CSR 格式仅存储这些非零块，跳过零块。

块大小 128 的重要性：TensorCores 调用一次可以处理 128×128 的 BF16 矩阵乘法——所以 128 是 CSR 的”原子单位”。如果一个 token group 不满 128，填充到 128（成本小）；如果超过 128，拆分为多个 blocks。

深度分析

1. Block-sparse 是 MoE 计算的”正确”抽象

MegaBlocks 的根本贡献是重新定义了 MoE 计算的”正确抽象”。在 MegaBlocks 之前，MoE 的计算被建模为”多个大小相同的 dense GEMM”（因此需要填充或丢弃来强制统一）。MegaBlocks 揭示了这个模型的根本缺陷——它不是”MoE 的合理近似”，而是”对 GPU 实现便利性的错误让步”。

Block-sparse 抽象将 MoE 的”天然不均衡”从问题转为特征——不再需要通过约束（capacity_factor）或伪装（填充）来应对，而是直接通过计算抽象来包容。抽象级别的提升消除了对两个超参数的需求（capacity_factor, expert buffer size）和一种训练不稳定性（token 丢弃的随机性）。

这个洞见超越了 MoE：”如果计算的自然分布是不规则的，不要通过人为规则化来适应实现——而是通过改变实现来适应自然分布。” 这个原则适用于任何条件计算场景。

2. MegaBlocks 与 Switch Transformer 容量因子的共演

MegaBlocks 使 capacity_factor 这个超参数完全过时。而 capacity_factor 在 2020-2022 年是 MoE 训练中最核心的调优维度之一。

这一进步与 DeepSeek-V3 的”无辅助损失”负载均衡形成了有趣的技术呼应。两者从不同方向推进了 MoE 训练的自由度：

  • MegaBlocks 解放了”容量约束”——token 不再被容量限制，每个 token 必然获得其所需的专家处理
  • DeepSeek-V3 解放了”均衡约束”——专家不再被辅助损失强制均衡，专家专业化可以更自然

两者结合将使 MoE 训练进入一个”无约束”的时代——既没有 token 丢弃、也没有负载均衡的辅助损失惩罚。这是一个正在快速实现的对 MoE 训练的愿景。

3. MegaBlocks 与 FlashAttention 的类比

两者共享核心的设计哲学：为硬件重新设计算法/计算格式。FlashAttention 通过分块 softmax 使 attention 在 SRAM 限制下高效；MegaBlocks 通过 block-sparse GEMM 使 MoE 在不规则负载下高效。两者都认识到”计算上最优”（最小 FLOPs）不等于”硬件上最优”（最快 wall-clock 时间），并接受了为实现硬件效率而进行非零的”浪费”（FlashAttention 的 recomputation, MegaBlocks 的 CSR 索引开销）。

这种”硬件感知算法设计”是 GPU 编程的成熟模式，但在 ML 研究中仍不普遍。大多数 ML 论文用 FLOPs 评估效率，但 MegaBlocks 清楚：GPU 的瓶颈通常不是 FLOPs（计算量），而是 memory bandwidth（内存带宽）和 launch overhead（kernel 启动开销）。Block-sparse 的策略降低了 memory 浪费（不加载零块），同时保持了内存访问的模式友好（连续的 block 访问）。

4. MegaBlocks 在 Mixtral 8x7B 训练中的角色

Mixtral 8x7B 是第一个大规模公开验证 MegaBlocks 有效性的模型。Mixtral 的团队在论文中致谢了 MegaBlocks 对其高效训练的贡献，主要有三个方面:

(a) 零 token 丢弃 — Mixtral 可以充分利用所有训练数据，不必担心 10-15% 的 token 在 MoE 层丢失——这对珍贵的高质量训练数据（如 code 和 math 数据）尤其重要。

(b) 高效的负载不均衡处理 — Mixtral 的 8 个专家在训练中表现出显著的专业化偏斜（某些专家在代码数据上收到 2-3x 的负载），MegaBlocks 高效处理了这种不均衡，无需浪费计算或丢弃 token。

(c) 消除 capacity_factor 超参数 — 在 Mixtral 的开发中，不需要花费宝贵的实验周期来调优 capacity_factor——直接使用 MegaBlocks 即可。

这使得 Mixtral 的训练比使用传统 MoE 系统的方案更快、更简单、质量更高。

局限和实践挑战

  1. 块大小的架构敏感性。 最优块大小（128）是针对 A100 的 TensorCore tile 尺寸（128×128 BF16 matmul = 8 warps 协作）优化的。对于不同的 GPU 架构，最优块大小可能不同——H100 的 TensorCore tile 尺寸相同但计算能力更强，256 可能更好；消费级 GPU（RTX 4090）的 TensorCore 较弱（仅 ada 一代），较优块大小可能不同。每个新 GPU 架构需要重新 profile 和验证最优块大小。

  2. CSR 索引的额外内存开销。 Block-sparse CSR 格式需要额外的索引内存（row pointers + column indices），占激活内存的约 5-10%。虽然对比 Tutel 的 15-50% 填充浪费仍是净节省，但对于内存已经极度紧张的大规模训练（如 70B+ models），这 5-10% 的额外内存可能成为限制（需要更激进的内存优化或更细粒度的 rematerialization）。

  3. 消费级 GPU 上的加速效果有限。 MegaBlocks 的主要效率优势来自利用 TensorCores 的 block-sparse GEMM。在消费级 GPU（RTX 3090/4090）上，TensorCore 的性能乘数较小（~2x vs FP32）且内存带宽瓶颈更大——block-sparse GEMM 的加速比从 1.4x（A100）降到约 1.1-1.2x。这对个人开发者和学术研究者（通常使用消费级 GPU）的采用有影响。

  4. 与框架版本的集成脆弱性。 MegaBlocks 与 Megatron-LM 的深度集成依赖特定版本的 Megatron-LM 接口。当 Megatron-LM 升级时（如新版本的 APEX/GradAccum 接口），MegaBlocks 的集成可能需要对应的维护更新。长期维护一个”第三方插件”的成本会随时间累积——如果 MegaBlocks 不成为 Megatron-LM 的官方一部分或缺乏持续的社区维护。

  5. 推理优化远不如训练成熟。 MegaBlocks 主要针对训练优化（高吞吐、大 batch）。在推理场景下（低 latency、小 batch 甚至 batch=1），block-sparse CSR 格式的动态 kernel 启动和 CSR 遍历的开销占比更大——因为总计算量小了，但索引的固定成本不变。推理场景可能需要不同的稀疏执行策略（如预计算路由模式、persistent kernels 替代动态 kernel 启动）。

  6. Permutation/Unpermutation 的固定开销。 Token 重排和反向重排需要约 5-8% 的训练时间开销——这在训练中是划算的（因为 GEMM 省了 30-50%），但在推理中就不划算了（GEMM 本身的时间短，CSR 处理和 permute 的比例增加）。未来的优化方向可能是将 permute 和 GEMM 合并为一个融合 kernel（fused permute-sparse-GEMM）。

  7. 对路由模式变化不敏感的”刚性”块划分。 当前的 128-token 块固定划分不感知路由模式的变化。当路由将两个”属于不同专家分配模式”的 token 分到同一块时（如块内一部分 token 路由到专家 A，另一部分到其他专家），这个块需要部分处理——引入了复杂性。动态块划分（adapting block boundaries to routing patterns）可能进一步提升效率，但增加了实现复杂性。

可复用洞见

  1. “不均衡不是 bug 而是 feature——不要对抗它，适应它” — 当算法天然产生不均衡的输出时，改变实现来高效处理不均衡，而不是通过限制或伪装来伪装均衡。这个原则适用于 MoE、dynamic routing、conditional computation、and 任何”不同输入需要不同计算量”的场景。

  2. 块稀疏是可以处理不规则计算的通用框架 — 任何条件计算场景（MoE routing, dynamic layer skipping, conditional attention, early exit, etc.）都可以从 block-sparse 视角重新设计——将条件计算的 IF-ELSE 逻辑映射为稀疏矩阵的”加载/跳过”决策。Block-sparse 提供了从”逐元素条件判断”到”块级硬件友好调度”的抽象阶梯。

  3. 系统层的创新的实际影响常常大于算法层 — MegaBlocks 没有提出新的路由算法、新的专家架构、或新的训练目标——它的贡献完全在”让 MoE 在 GPU 上高效运行”这一系统层面。但实际影响（+40% 训练速度、消除 critical 超参数）可能超过许多”更好路由算法”的论文——因为一个”在硬件上高效工作的次优算法”胜过一个”理论上更优但无法高效实现的算法”。

  4. “消除超参数”是降低技术门槛的高价值贡献 — capacity_factor 的消除不仅提升了效率，更降低了 MoE 训练的进入门槛——不需要理解”容量因子”、不需要调优它、不需要在”丢 token vs 浪费计算”之间做痛苦折中。这种”降低复杂度”的工程价值常常被低估，但在技术的广泛 adoption 中至关重要。

  5. GPU 的瓶颈通常是 memory bandwidth 而非 compute FLOPs — CSR 索引的 5-10% 开销对比 15-50% 的 memory 浪费节省，直观地证明了 GPU 上的瓶颈常在于”移动数据”而非”计算数据”。Block-sparse 的根本贡献是降低了内存浪费——不加载零 blocks = 不浪费 memory bandwidth = 更快的实际 wall-clock 时间。

  6. “在现有成熟库之上构建” vs “从零实现自定义 kernel” — MegaBlocks 依赖 CUTLASS 的 block-sparse GEMM（而不是自己实现一个全新的 sparse GEMM kernel），大大降低了开发和维护成本。借用社区已验证、已优化的组件，然后在之上构建自己的创新——这是系统研究和开源生态中的最佳实践。

我的笔记

MegaBlocks 是一篇”系统论文”的典范——它不引入新的数学概念或算法理论，而是通过精巧的系统工程让已经存在的概念（MoE）在真实的硬件上高效运行。它的核心思想（”把专家负载不均衡视为 MoE 的自然属性而非缺陷”）是一种极为重要的”范式转变”——从”适应硬件限制”到”让硬件适应算法特性”。

这种范式转变在计算机科学史上反复出现。早期的数据库系统强迫所有数据符合固定格式的表格（因为硬件限制），直到 NoSQL 运动说”不——数据可能是非结构化的，让数据库适应数据而不是反着来”。早期的大数据处理强迫对所有数据块做相同操作（因为 MapReduce 模型限制），直到 Spark 的 RDD 弹性分布式数据集允许更灵活的数据处理。MegaBlocks 对 MoE 训练做了类似的事——“不要再强迫 token 数量适应 GEMM 维度，让 GEMM 适应 token 数量的自然不均衡”。

MegaBlocks 与 DeepSeek-V3 的 bias-based 负载均衡之间的协同进化是我最喜欢的”技术趋势”之一。两者从完全不同的方向（系统层 vs 算法层）朝着同一个目标推进——让 MoE 训练从人为约束中解放。MegaBlocks 解放了 capacity 约束（token 不用再被丢弃或填充），DeepSeek-V3 解放了 balance 约束（专家不用再被辅助损失强制均衡）。这两个解放的结合效果（”无约束 MoE”）是极具潜力的——可以让专家更自由地专业化（更高质量）、同时不浪费计算（更高效）、不需要调优临界超参数（更易用）。

Mixtral 8x7B 的致谢暗示了 MegaBlocks 在业界的影响力已经超出了论文的可见度。Mixtral 是第一个大规模验证了”零 token 丢弃”训练可行性的开源模型，而它在背后”默默支撑”的技术是 MegaBlocks——这让我想到许多”幕后英雄”式的系统论文：它们的名字不常出现在产品新闻中，但它们的代码是那些明星产品跑起来的关键。从学术角度来看，这类论文的 citation 可能不如算法论文多（因为系统论文的引用者主要是在”实际构建”的人，而非在”写论文引用”的人），但它们的实际影响力可能是同等或更大的。

“block-sparse”作为一种通用计算范式，让我联想到它可能在 MoE 之外的更多场景找到应用。任何”条件计算”——不是所有输入都需要走所有计算路径——都可以从这个角度来优化。例如：diffusion 模型中的”resampling steps”优化（某些 patch 可以跳过不需要的 denoising 步）、多模态模型中的”conditional fusion”（根据 textual context 选择视觉 features）、甚至操作系统的中断响应（根据当前负载选择性地处理 I/O events）。Block-sparse 是一种过于强大的计算抽象，它的应用应该远超 MoE 训练。

最后，MegaBlocks 也让我反思学术界”novelty”(新颖性) 的标准。严格来说，block-sparse GEMM 不是 MegaBlocks 发明的（CUTLASS 早就有），variable-size batched GEMM 也不是（这是 GPU computing 中的常见模式）。MegaBlocks 的贡献是”将这些已有部件 cleverly assembled into a compelling solution for a critical problem”——这不是”来自象牙塔的原始创新”，而是”来自对真实系统痛点的深刻理解的实用解决方案”。在系统研究领域，往往后者比前者更有价值。

后续问题

  1. Block-sparse 范式能否推广到 MoE 以外的条件计算架构？如 dynamic layer skipping、conditional token merging、routing-based contrastive learning？

  2. FP8/FP4 等更低精度下的 block-sparse GEMM 的精度损失如何量化？低精度下稀疏块的数值稳定性是否受块大小的影响？

  3. 消费级 GPU（RTX 4090, 未来 RTX 5090）上 MegaBlocks 的性能如何？是否足够服务于个人开发者的 MoE 实验？

  4. 能否与 vLLM 的 PagedAttention 结合，设计一个”unified sparse execution engine”——同时处理 attention 的 page 稀疏和 MoE expert 的 block 稀疏？

  5. 动态块划分（adaptive block sizing based on routing patterns）能否理论上进一步提高效率？如何在不增加过多实现复杂性的前提下实现？

  6. MegaBlocks 与 DeepSeek-V3 的 bias-based 无辅助损失负载均衡组合后，MoE 训练的工程体验能简化到什么程度？”无约束 MoE”的终极形态是什么？
