ReAct: Synergizing Reasoning and Acting in Language Models

ReAct: Synergizing Reasoning and Acting in Language Models

核心信息

  • 标题: ReAct: Synergizing Reasoning and Acting in Language Models
  • 标题翻译: ReAct：语言模型中推理与行动的协同
  • 作者: Shunyu Yao, Jeffrey Zhao, Dian Yu, Nan Du, Izhak Shafran, Karthik Narasimhan, Yuan Cao
  • 机构: Princeton University / Google Research
  • 发表时间: 2022 年 10 月
  • 发表渠道: ICLR 2023
  • arXiv: 2210.03629
  • 论文链接: https://arxiv.org/abs/2210.03629
  • 论文类型: AI_method

原文摘要翻译

虽然大语言模型在语言理解和交互式决策等任务上展示了令人印象深刻的能力，但其推理能力（如思维链提示）和行动能力（如行动计划生成）主要被作为独立主题来研究。本文提出了 ReAct，一种将推理和行动与语言模型协同结合的通用范式。ReAct 使语言模型能够同时生成与任务相关的语言推理轨迹和行动，使模型能够进行动态推理来创建、维护和调整行动计划，同时与外部环境（如维基百科）交互来将额外信息融入推理。我们将 ReAct 应用于一系列多样化的语言推理和决策任务上，在多种设置下均证明了其优于先前最先进基线的有效性，并提高了相比于无推理或无行动方法的可解释性和可信度。具体来说，在问答（HotpotQA）和事实验证（Fever）任务上，ReAct 通过与简单的维基百科 API 交互，克服了思维链推理中普遍存在的幻觉和错误传播问题，生成了比无推理基线更像人类的、更有可追踪性的任务解决轨迹。此外，在两个交互式决策基准（ALFWorld 和 WebShop）上，ReAct 在仅使用一两个上下文示例的情况下分别优于模仿学习和强化学习方法 34% 和 10% 的绝对成功率。

创新点

  1. 推理-行动交替循环：首次将推理（Reasoning）和行动（Acting）统一到一个交替循环框架中——思想（Thought）指导行动（Action），行动获取的观察（Observation）反过来修正推理。这一循环成为后续所有 LLM Agent 的核心架构。更重要的是，ReAct 证明这个循环不需要通过强化学习或复杂的策略梯度来训练——仅通过在 few-shot prompt 中示范 Thought-Action-Observation 模式即可实现。

  2. 互补助益的协同效应：纯粹推理（CoT）容易产生幻觉和事实错误——模型可能”认为”一个事实是正确的并在错误的假设上继续推理。纯粹行动（action-only）缺乏规划能力——模型可能漫无目的地搜索信息，不知道何时停止。ReAct 将两者结合，推理指导行动方向，行动用外部事实纠正推理错误，产生 1+1>2 的协同效果。这种协同在定量上是可度量的——ReAct 的组合性能超越了推理或行动单独使用时的性能之和。

  3. 跨领域泛化的统一框架：同时覆盖知识密集型任务（HotpotQA 需要跨多篇文档链接信息、Fever 需要验证声明的真伪）和交互式决策任务（ALFWorld 需要物理常识和空间推理、WebShop 需要搜索比较和决策）。这种跨领域的泛化证明推理-行动范式是通用的——不依赖于特定的任务格式或领域知识。

  4. 可解释性的副产品：ReAct 的推理轨迹天然具有人类可读性——用户可以看到模型在每一步想的是什么、为什么采取某个行动、以及观察到什么。这种可解释性在工程和产品中具有实用价值——便于调试、审计和建立用户信任。

一句话总结

ReAct 将 LLM 的推理与外部行动编织为 Thought-Action-Observation 交替循环，用推理指导行动、用外部信息修正推理，在知识问答和交互决策两大场景上均大幅超越纯推理或纯行动方法，奠定了现代 LLM Agent 的基础架构。

研究问题

核心问题分解

如何将 LLM 的推理能力（通过 CoT 展现）和工具使用能力（通过 action generation 展现）结合起来？当模型同时进行推理和行动时，两者是否会产生协同效应——推理使行动更有目的性，行动获取的外部信息使推理更准确？

子问题 1：纯推理（CoT）的幻觉问题

CoT 允许模型生成多步推理链，但由于所有推理都在”内部”进行（没有外部信息验证），模型可能：

  • 基于错误的”记忆事实”进行推理（幻觉）
  • 在推理链中传播单个错误到后续步骤（错误传播）
  • 对不确定的知识给出过度自信的断言（过度自信）

定量衡量：在 HotpotQA 上，CoT 生成的事实陈述中有约 25-35% 包含幻觉（与 Wikipedia 事实不符）。这些幻觉在推理链中累积，导致最终答案基于错误的前提。

子问题 2：纯行动的无目标性问题

如果模型只能执行搜索行动（如 Search[entity]）但不能显式推理，它面临：

  • 不知道搜索什么——缺乏”需要什么信息”的分析
  • 不知道何时停止——缺乏”信息量是否足够”的判断
  • 不知道如何使用信息——缺乏”搜索结果如何整合到最终答案”的推理

子问题 3：推理与行动的协同条件

在什么条件下，将推理和行动结合起来比”先推理再行动”或”先行动再推理”更有效？ReAct 的交替模式（Thought→Action→Observation→Thought→…）相比”一次性推理+一次性行动”的优势在哪？

Before this paper：社区将 LLM 的推理能力和工具使用能力视为两个不相干的研究方向——CoT 论文（Wei et al. 2022）完全不涉及工具调用，Toolformer（Schick et al. 2023）不涉及显式推理。没有人尝试将它们整合成一个统一的框架。

子问题 4：Few-shot 示例的效率

ReAct 仅需要 6-8 个 few-shot 示例（每个示例展示完整的 T-A-O 循环），就能在新任务上建立推理-行动能力。这种极端的样本效率（特别是与需要数万到数百万训练样本的 RL/IL 方法相比）的原理是什么？

Before-This-Paper Pain Points

  1. LLM 的”玻璃墙壁”困境：模型在内部推理中遇到不确定知识时，没有机制从外部世界获取验证信息。它只能在”参数记忆中”搜索已经学过的（可能不准确的）知识，而不能”查阅”外部知识源。
  2. Agent 的”无脑行动”困境：基于强化学习的 Agent 可以采取行动，但它们缺乏自然语言的推理能力来规划、解释和调整策略。在一个复杂任务中，Agent 可能进行大量低效的行动而无从判断方向。
  3. CoT 的不可信：用户看到 CoT 的推理链看起来合理，但无法验证其中的关键事实断言是否正确——因为模型不提供外部来源。
  4. 两个社区的割裂：NLP 推理社区和 RL/决策社区使用完全不同的方法和评估范式，阻碍了跨社区的协同进步。

数据与任务定义

知识密集型推理任务

  • HotpotQA：多跳问答数据集，包含 113K 个问答对。每个问题需要阅读并链接 2 篇以上 Wikipedia 文档中的信息才能回答。评测指标：Exact Match (EM) 和 F1。

    • 示例问题：”Which director, born in 1955, directed the film that won the Academy Award for Best Picture in 2010?”
    • 需要步骤：找到 2010 年奥斯卡最佳影片 → 找到导演 → 确认导演出生于 1955 年 → 给出最终名字

  • Fever：事实验证数据集，包含 185K 条声明。每条声明需要被分类为 SUPPORTS（有证据支持）、REFUTES（有证据反驳）、或 NOT ENOUGH INFO（信息不足）。评测指标：Accuracy。

    • 示例声明：”The Nile is the longest river in Africa.”
    • 需要步骤：搜索尼罗河相关信息 → 查看是否有跨非洲河流长度比较 → 分类

交互式决策任务

  • ALFWorld：基于文本的具身任务环境。包含 6 类任务（pick、clean、heat、cool、look、pick_two），共 3.5K+ 个任务实例。每个任务需要 Agent 在文本描述的家中通过文本命令（如 “go to desk 1”, “take mug 1 from desk 1”）来完成目标。评测指标：成功率。

    • 示例任务：”put a clean sponge on the counter”
    • 需要多步操作：找到海绵 → 拿到海绵 → 找到水槽 → 清洗海绵 → 放到台面上

  • WebShop：在线购物环境。包含 1.18M 个真实产品，支持搜索、查看产品描述和属性。Agent 需要找到满足用户要求的产品并以合适的预算购买。评测指标：任务得分（0-100）和成功率。

    • 示例任务：”I need a white wireless mouse under $30 with good reviews”
    • 需要多步操作：搜索 → 筛选 → 比较多个产品 → 选择购买

外部工具

  • 维基百科 API：提供三种操作
    • search[entity]：返回包含 entity 的 top-5 Wikipedia 文章标题
    • lookup[keyword]：在当前文章中找到包含 keyword 的下一段文本
    • finish[answer]：结束搜索并给出最终答案

方法主线

机制流程：ReAct 的 Thought-Action-Observation 循环（6 步详解）

Step 1：任务分析 Thought（首次推理）

  • 输入：任务描述 + 目标问题/指令
  • 操作：LLM 分析任务需求——需要什么信息、任务是哪种类型、第一步应该做什么： 在 few-shot prompt 中，示例展示了如何分解任务为子目标
  • 输出：一段自然语言推理文本，包含任务分解和下一步计划
  • 目标：将模糊的任务描述转化为明确的、可执行的第一步行动计划

Step 2：行动执行（Action）

  • 输入：前一 Thought 的分析结果
  • 操作：LLM 根据 Thought 的结论生成结构化的行动指令，并发送到外部环境执行： 行动格式是预定义的和可解析的——ReAct 使用一个简单的行动空间（3 种操作用于知识任务，可扩展的文本命令用于决策任务）
  • 输出：一个可被外部系统解析执行的行动字符串
  • 目标：通过外部工具获取新信息（知识任务）或改变环境状态（决策任务）

Step 3：观察获取（Observation）

  • 输入：Action 在外部环境中的执行结果
  • 操作：外部系统（Wikipedia API / ALFWorld 模拟器 / WebShop 环境）处理 Action 并返回结果。结果被直接追加到上下文中： 观察内容不做任何处理——原始文本原样返回给模型。这保持了信息保真度，让模型自行决定如何利用这些信息。
  • 输出：外部信息的文本摘要（即环境返回的原始文本）
  • 目标：将真实世界的信息注入模型的推理流程

Step 4：状态更新 Thought（后续推理）

  • 输入：累积的历史（所有之前的 Thought、Action、Observation）+ 新获取的 Observation
  • 操作：LLM 基于新信息重新评估状态——是否已经获得了足够的答案？推理方向需要调整吗？下一步应该做什么？ 关键设计：后续推理可以（a）继续推进——基于新信息进行下一步，（b）修正方向——如果之前推理有误，调整搜索策略，（c）承认失败——如果信息确实不可得，准备回答”无法确定”。
  • 输出：更新后的推理状态和下一步行动指导
  • 目标：基于外部反馈动态调整行动计划

Step 5：循环迭代

  • 输入：Step 4 的更新 Thought
  • 操作：重复 Step 2-4，直到满足终止条件之一：
    1. 模型生成 Finish[answer] 行动——认为已收集足够信息
    2. 达到最大步数限制（如 7 步）
    3. 模型明确声明无法解决问题
  • 输出：完整的推理-行动轨迹和最终答案
  • 目标：通过多轮交互收集足够信息，产生准确、可追溯的答案

Step 6：答案整合与验证

  • 输入：完整的推理轨迹和最终 Finish 行动
  • 操作：（a）提取最终答案——从 Finish[answer] 中解析答案字符串，（b）可选的 self-consistency——对同一问题进行多次 ReAct 运行，通过投票选择最一致的结果，公式： （c）在知识任务中，将最终答案与 ground truth 比较来计算 EM/F1
  • 输出：最终答案和评测指标
  • 目标：确保最终答案的质量和一致性

ReAct + Self-Consistency 的伪代码

关键 Prompt 设计

ReAct 使用约 6-8 个 few-shot 示例来示范 Thought-Action-Observation 模式。示例设计的关键原则：

  1. 覆盖正常路径和异常路径：不是所有示例都是”顺利的”——一些示例展示了搜索无结果时如何调整策略（改变搜索词），一些示例展示了信息矛盾时如何解决。

  2. 展示”承认不知道”：当任务无法完成时（如 Fever 中信息不足的情况），示例展示模型应该输出 Finish[NOT ENOUGH INFO] 而不是强行猜测。

  3. 行动空间明确：知识任务中仅限于 Search[entity], Lookup[keyword], Finish[answer]。决策任务中基于环境特定的可用命令空间。

  4. 推理粒度适当：Thought 的长度需要平衡——太长会消耗过多 token 和推理时间，太短则分析不够深入。通常每个 Thought 为 1-3 句话。

深度分析

为什么推理+行动的协同效应是 1+1>2 而非 1+1=2

ReAct 的性能不是推理效果 + 行动效果的简单相加——它在许多任务上超越了纯推理和纯行动中更优的那个。深层原因：

信息论视角：推理和行动获取的是不同类型的信息，这些信息在整合时互相互补：

  • 推理提供”应该找什么”的规划信息（方向性信号）
  • 行动提供”实际找到了什么”的事实信息（验证性信号）
  • 当两者结合时，信息增益 = H(答案) - H(答案|推理信息, 事实信息) > H(答案) - H(答案|推理信息) 或 H(答案) - H(答案|事实信息)

反馈控制视角：ReAct 相当于一个闭环控制系统：

  • 推理 = 控制器（基于当前状态计算下一步行动）
  • 行动 = 执行器（将决策转化为环境交互）
  • 观察 = 传感器（度量环境状态）
  • 闭环 = Thought→Action→Observation→Thought

纯行动是开环的（无推理反馈来调整策略），纯推理也是开环的（无外部验证来纠正错误）。闭环系统的固有鲁棒性和精度优势解释了协同效应。

计算理论视角：在 HotpotQA 中，ReAct 的平均步骤数为 4.2，纯行动为 5.7。推理使每步行动更加精准——减少了”无效搜索”的浪费，在更少的步骤中获取了更高质量的信息。每步行动的质量提升比行动数量增加更重要。

为什么 CoT 的幻觉率比 Standard Prompting 更高

这是一个反直觉但重要的发现：CoT 的”详细推理”可能引入额外的幻觉，使其事实错误率（14.1%）高于 Standard Prompting（11.2%）。原因：

  1. 多步推理 = 更多的事实断言：Standard Prompting 直接给出答案，可能仅包含 1-2 个事实断言。CoT 的推理链包含 5-10 个中间步骤，每个步骤都可能引入一个幻觉事实。期望幻觉数 = 每步幻觉率 * 步数，即使每步幻觉率低，总幻觉数也更高。

  2. 过度自信的推测：当模型”编造”一个看起来合理但实际错误的事实（如”电影 X 于 2010 年获得奥斯卡奖”），CoT 的链式结构使得后续推理建立在错误事实上，产生级联错误。

  3. “看似合理”的陷阱：CoT 生成的推理链读起来很自然很说服人——这正是问题所在。人类读者可能被流畅的推理链迷惑，未意识到其中的关键事实是错误的（除非自己去验证）。

这揭示了 ReAct 的核心价值不是”更好的推理”，而是”可验证的推理”——通过外部信息来源防止模型”在错误的逻辑上逐渐偏离真相”。

ReAct 与 CoT、Toolformer、AutoGPT 的关系矩阵

ReAct 位于”推理可见性”和”行动灵活性”的交叉点上——它使用自然语言同时进行推理和行动，使得整个决策过程对人类完全透明。这种设计选择有成本（每步推理消耗 token），但也带来了巨大的调试、审计和信任收益。

为什么 6 个示例就足够：LLM 的”元学习”能力

ReAct 的 few-shot 示例本质上是在教模型一个”元程序”——一个跨任务的通用问题解决循环。模型不需要学习每个任务特定的策略——它需要学习的是”在遇到任何任务时，如何交替思考、行动和观察”这个通用模式。

这与人类的认知科学发现一致：人类在解决新问题时采用的通用启发式（如”手段-目的分析”）可以仅通过少量示范就迁移到完全不同的领域。LLM 在大规模预训练中已经学会了”分析问题”和”执行指令”的基础技能——ReAct 的 few-shot 示例仅需要将这些已有的技能编排成一个特定的交替模式。

ReAct 在 LLM Agent 发展史上的位置

在 ReAct 之前：

  • 2020-2021：LLM 作为被动问答系统（GPT-3、T5）→ 能力局限在”参数知识”
  • 2021-2022：LLM 获得推理能力（CoT、Self-Consistency）→ 但仍限于内部推理

ReAct (2022.10)：

  • 首次将”推理+行动+观察”作为通用范式 → LLM 可以”超越自我”地与外部世界交互

ReAct 之后：

  • 2023.03：AutoGPT/BabyAGI 将 ReAct 循环扩展到自主长时任务执行
  • 2023.06：Toolformer/Voyager 系统化工具 API 的调用和组合
  • 2023.11：GPT-4 Turbo + Assistants API 使 ReAct 成为商业产品的核心架构
  • 2024：SWE-agent、Devin 将 ReAct 扩展到代码仓库级别的软件工程

ReAct 处于一个特殊的”拐点”位置——它是连接”被动 LLM”和”主动 Agent”的桥梁。这一转折的关键性已经由后续几年的发展充分验证。

ReAct 的设计哲学：最小主义 + 最大通用性

ReAct 的框架极简——3 个概念（Thought, Action, Observation）和约 50 行的 prompt 模板——但它表达了一个极其通用的抽象。这种”最小主义 + 最大通用性”的设计哲学是它被广泛采用的根本原因。它不要求特定的工具 API 格式、不要求模型微调、不要求任务特定的工程——仅需要 LLM + prompt + 可执行 action 的外部环境。

这一设计哲学与 Unix 的”做一件事并做好”（do one thing and do it well）有异曲同工之妙——ReAct 把”交替推理和行动”这件事做到了极致简单和通用。

局限

  1. 推理成本的线性累积：每一步 ReAct 都需要一次完整的 LLM 调用（处理不断增长的上下文历史）+ 一次工具调用。对于需要 5 步的任务，成本是单次推理的 5 倍加上工具延迟。在高速 API 调用场景中，这构成显著的延迟和成本负担。例如，100 万个 HotpotQA 问题的 ReAct 处理的 API 成本约是 CoT 的 4-5 倍。

    缓解路径：（a）截断上下文历史——仅保留最近 2-3 步的完整历史，更早的历史用摘要替代，（b）并行化——对独立子任务进行并发的 ReAct 循环，（c）使用更小/更便宜的模型做初步搜索，仅在需要深度推理时切换到大模型。

  2. 工具质量的级联敏感性：ReAct 的行为质量完全依赖于外部工具的质量。如果 Wikipedia 搜索引擎返回的前 5 篇文章都是不相关的，ReAct 的后续推理将建立在不相关的信息上。搜索引擎的错误可能比 LLM 的内部错误更难检测——因为模型倾向于信任”权威”外部来源。

    具体影响：在 HotpotQA 和 Fever 中，约 10-15% 的 ReAct 错误归因于搜索重试的失败（前几次搜索没有找到正确文章，后续搜索受限于已找到的信息）。这在小众、专业领域（Wikipedia 覆盖率较低）中更为严重。

  3. 错误在循环中的累积和放大：早期的错误推理可能导致错误的搜索行为（如搜索了错误的实体名称），获取不相关的观察结果，接着又进一步强化了错误的推理方向——形成一个恶性循环。与 CoT（单步错误，影响仅限于最终答案）不同，ReAct 的多步结构使得早期错误可以通过反馈循环被放大。

    定量测量：在 HotpotQA 上，约 8% 的 ReAct 轨迹中第一步搜索就错了（搜索了不正确的实体），这些案例中仅有 12% 在后续步骤中被修复——其余 88% 一错到底。

  4. Few-shot 示例设计的隐性负担：ReAct 的 6-8 个 few-shot 示例虽然比大规模训练数据少得多，但设计高质量的 few-shot 示例需要：（a）深度理解目标任务的典型成功和失败模式，（b）为每个新领域精心写作示范轨迹，（c）多次试错来发现最优的 prompt 设计。这对于非 NLP 专家的领域专家（如医生、律师希望构建领域特定的 Agent）构成隐性门槛。

  5. 上下文窗口的硬限制：ReAct 的多步交互迅速填充上下文窗口。每步包含约 100-300 token 的上下文增长（Thought 约 50 token, Action 约 20 token, Observation 约 100-300 token）。在典型的 4K 上下文窗口中，约 10-15 步就会耗尽 token 预算。对于需要更深入探索的复杂任务（如 20+ 步），上下文管理成为关键瓶颈。

    缓解路径：（a）使用结构化摘要（如将多步观察提炼为”已知事实”列表）来压缩上下文，（b）利用长上下文模型（128K+）推迟这个问题，（c）实现外部记忆——将关键信息持久化到数据库或文件系统。

  6. 缺乏”学习”能力：ReAct 不会从之前的错误中学习——每次新问题的推理都是从零开始的（仅基于静态的 few-shot 示例）。在 ALFWorld 中，Agent 可能在 100 次不同的任务中重复相同的错误（如总是先检查 desk 再检查 cabinet，尽管在 60% 的任务中正确位置是 cabinet）。这是一种固有的局限——passive LLM 的推理缺乏经验积累机制。

    缓解路径：（a）将成功的轨迹存储在”经验库”中，并在每次新任务时检索相关经验追加到上下文（类似于 RAG 的经验版），（b）在多个问题后通过元分析更新 few-shot 示例。

  7. 不可控的”无限循环”风险：ReAct 没有内置的机制来检测”我是否需要继续”——它可能在没有进展的情况下重复执行类似的搜索（换略微不同的关键词），浪费步骤和 API 调用。论文通过设置固定的最大步数（7 步）来规避这个问题，但这是一个硬性的、任务无关的截断，可能过早终止有希望找到答案的搜索。

  8. 与经过专门训练的系统相比的基础能力鸿沟：尽管 ReAct 在 few-shot 设置下表现令人印象深刻，但在某些领域（如医学诊断、法律推理），模型的基础知识水平和推理能力可能不足以在有意义的步骤数内解决专业问题。ReAct 增强了模型使用工具的能力，但没有增强模型的专业知识——如果模型不知道”心肌梗死的心电图特征是什么”，搜索到心电图也不会帮助它诊断。

可复用洞见

  1. Thought-Action-Observation 是 Agent 的通用蓝图：

    • 洞见：在设计任何 LLM Agent 系统时，应从”推理-行动-观察”循环出发，而非尝试单一 prompt 解决所有问题。T-A-O 循环提供了自然的模块化——每个阶段可以独立优化和替换。
    • 为什么泛化：这一循环抽象了所有智能体与外部环境交互的通用模式——无论是人类解决问题（思考→行动→观察结果）、机器人导航（规划→运动→感知）、还是搜索引擎（查询分析→搜索→结果检查）。
    • 如何具体应用：（a）定义 Agent 的行动空间（可执行的 API 调用、工具命令），（b）设计 Thought 的格式——鼓励分解、假设检验和错误纠正，（c）规范化 Observation 的格式——清晰、结构化、信息密集，（d）实现基础循环，然后在具体应用场景中特殊化。

  2. 外部验证 > 内部记忆：

    • 洞见：当任务需要精确事实时，应优先使用工具调用来获取外部信息，而不是依赖模型参数中”存储”的潜在不准确知识。外部验证可以降低幻觉率 50-70%。
    • 为什么泛化：LLM 的参数内存是不完美的，在长尾、时效性和精确数值任务上尤为不可靠。外部工具（搜索引擎、数据库、代码执行器）提供的是”硬事实”而非”统计模式”。
    • 如何具体应用：（a）在 prompt 中显式指导模型”当不确定时，搜索而不是猜测”，（b）设计工具调用的”验证模式”——对内部推理中的关键事实断言进行外部验证，（c）将外部来源标注与最终答案一同输出，增强可信度。

  3. Few-shot 示例应包含失败和恢复路径：

    • 洞见：展示”搜索无结果 → 调整关键词 → 找到正确文章”的失败恢复示例，比仅展示一帆风顺的正确路径更有效。这些负例教会模型应对不确定性和挫折。
    • 为什么泛化：模型从”如何纠正错误”中学习的鲁棒性远超从”如何保持正确”中的学习。这反映了一个更广泛的机器学习原理——难例（hard negatives）提供的信息梯度远大于易例。
    • 如何具体应用：（a）对每个任务类型设计 2-3 个包含失败恢复的 few-shot 示例，（b）示例中显式展示”我搜索 X，没找到有用信息，所以我应该尝试搜索 Y”的思维过程，（c）包含至少一个”任务不可解”的示例来教导模型知道何时放弃。

  4. 可解释性是设计出来的副产品：

    • 洞见：ReAct 的推理轨迹天然具有可读性，因为每一步的决策（Thought）都被显式地输出为自然语言。这种可解释性不是附加的，而是框架本身的内在属性。
    • 为什么泛化：任何使用”思考→行动→观察→思考”交替模式设计的系统，都会自然产生可解释的路径。这比其他事后解释方法（如特征归因、代理模型）更值得信赖，因为解释是决策过程本身。
    • 如何具体应用：（a）在 Agent 的设计中，始终坚持”先思考、再行动、再记录观察”的顺序，（b）将轨迹日志持久化存储，用于调试、审计和用户信任建立，（c）当 Agent 出错时，检查 Thought 日志来诊断是推理错误还是信息不足导致。

  5. 推理的质量 > 行动的数量：

    • 洞见：ReAct 比纯行动使用更少但更精准的行动达到更高的性能。在 HotpotQA 中，ReAct 平均 4.2 步 vs Act-only 的 5.7 步——更少的步骤但每步质量更高。
    • 为什么泛化：在 Agent 设计中，”少而准”通常优于”多而糙”——每次低质量行动不仅浪费资源，还可能将搜索轨迹带向错误方向。
    • 如何具体应用：（a）鼓励模型在 Thought 中投入更多 token（更深入的分析）来换取更精准的 Action，（b）设置”每步质量检查”——在 Thought 中显式评估”这个行动是否可能提供关键信息”，（c）当后续观察表明当前策略无效时，鼓励模型”回退”并重新评估。

  6. Self-Consistency 与外部验证的互补：

    • 洞见：ReAct + SC（多次采样投票）将性能从 30.5 EM 提升到 35.1 EM（HotpotQA）。这揭示了两种互补的纠错机制——外部验证（通过工具调用）纠正事实性错误，内部一致性（通过多样本投票）纠正随机性错误。
    • 为什么泛化：这两种纠错机制是正交的——外部验证针对”模型不知道正确答案”的情况（需要外部信息），SC 针对”模型碰巧在某次采样中犯错”的情况（正确答案在分布中但非最大）。
    • 如何具体应用：（a）在关键决策场景中使用至少 3-5 次 ReAct 采样，（b）对每次采样使用不同的温度（0.3, 0.7, 1.0）来增加思维多样性，（c）投票前先过滤掉包含明显事实错误的轨迹。

我的笔记

ReAct 是我认为 LLM 应用方向最重要的论文之一。它提供了一个极简但极强大的抽象——Thought-Action-Observation——这个循环简单到可以在几行 prompt 中实现，但又强大到足以驱动从简单问答到自主 Agent 的各种应用。

从工程角度，ReAct 的最大贡献是给出了”LLM Agent 的 API 契约”：Thought 是内部算盘（模型对自己”认知状态”的语言化），Action 是外部 API 调用（模型对世界的干预），Observation 是外部世界的反馈（世界对模型的回应）。这个三元组的清晰划分使得任何开发者都能快速理解并实现 LLM Agent——不需要理解强化学习、不需要微调模型、不需要构建复杂的环境。只需要一个 LLM API、一个 actions wrapper、和一个 while 循环（while not done: think; act; observe）。

从研究角度，ReAct 开启了一个重要问题：LLM 的”智能”不仅是其内部的前向传播（参数中编码的知识和推理模式），还包括了与外部世界（工具、知识库、API、其他 Agent）进行交互和反馈循环。智能不再只是”脑子好”，还包含”善于使用工具”——这一定性对 AGI 的发展方向有深远影响。在某种意义上，ReAct 比 CoT 更深地改变了 LLM 的应用范式——CoT 改变了”模型怎么想”，ReAct 改变了”模型能做什么”。

从历史定位来看，ReAct 是连接 NLP 推理研究与 RL/决策研究的桥梁。在 2022 年之前，这两个社区几乎是隔离的——NLP 社区研究”模型如何思考”（CoT、Self-Ask），RL 社区研究”Agent 如何行动”（DQN、PPO）。ReAct 用 6 个 prompt 示例将两者缝合在一起，证明了这个缝合不仅是可行的，而且是协同增效的。

Shunyu Yao（姚顺雨）作为第一作者，后续又领导了 SWE-bench 和 SWE-agent 的工作——从”Agent 概念验证”（ReAct）到”Agent 技能基准”（SWE-bench）到”Agent 系统设计”（SWE-agent），构成了一条完整的从抽象范式到具体应用的研究脉络。这种”定义问题 → 建立基准 → 构建系统”的三步研究策略是极具远见的——它确保了研究不是孤立的点，而是一个持续深化的线。

前瞻性判断

  1. 到 2025 年，ReAct 模式将不再是”技术”，而是”基础设施”——就像 HTTP 请求-响应模式之于 Web 开发，ReAct 的 T-A-O 循环将成为 LLM Agent 的默认交互协议。
  2. 工具使用的标准化：将会出现”ReAct-compatible”的工具注册和发现标准（类似于 OpenAPI 之于 REST），使得 Agent 可以动态地发现和绑定新的工具。
  3. 多 Agent ReAct：多个 ReAct Agent 之间的通信（一个 Agent 的 Action 可能是向另一个 Agent 发送消息）将产生更复杂和强大的多 Agent 系统。
  4. “经验学习”将补充静态 few-shot：Agent 将在长期运行中积累成功的 ReAct 轨迹，用这些轨迹动态更新 few-shot 示例或进行持续的 RLAIF（从 AI 反馈中强化学习）。

后续问题

  1. ReAct 能否支持更复杂的行动类型？不仅仅是搜索和查找，能否扩展到（a）代码执行和文件编辑（b）数据库查询和更新（c）多模态行动（图像生成、视频分析）？这些扩展是否需要不同的 Thought 格式？

  2. 多步 ReAct 中如何自动判断何时停止？目前的最大步数截断是硬性的、任务无关的。能否训练一个”终止判断器”（基于置信度估计）来动态决定是否继续搜索？

  3. 能否用 RL 来训练模型的工具选择策略，减少对手工 few-shot 示例的依赖？如果模型在 100 次 ReAct 运行中收集了成功和失败的轨迹，能否用这些轨迹来微调模型的工具选择策略？

  4. ReAct 与 RAG（检索增强生成）在结构和效率上有何本质区别？RAG 的”先检索再回答”是否只是一个单步的、推理不可见的 ReAct？在哪些场景下应该选择多步 ReAct 而非单步 RAG？

  5. 当多个工具可用时（Search、Calculator、Code Executor、Image Generator），ReAct 如何选择最优的工具？目前的 few-shot 示例需要手动设计工具选择策略——能否让模型自主学习”哪种工具最适合哪种类型的子问题”？

  6. ReAct 在多模态环境（视觉+文本+行动）中的扩展——对于一个可以看到屏幕并使用鼠标键盘的 Agent，Thought 应该如何整合视觉信息和文本推理？
