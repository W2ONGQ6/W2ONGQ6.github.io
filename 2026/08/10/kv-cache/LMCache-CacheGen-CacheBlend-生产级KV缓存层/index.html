LMCache 与 CacheGen / CacheBlend：生产级 KV 缓存层

LMCache 与 CacheGen / CacheBlend：生产级 KV 缓存层

本文是 KV Cache 全方位技术指南 专题的深剖篇之一。SGLang HiCache 和 Mooncake Store 解决的是「把 KV 卸载到多级存储、跨实例共享」。这一篇看 LMCache——vLLM production stack 的 KV 缓存层，以及它背后两项让人眼前一亮的研究：CacheGen（把 KV 压成紧凑比特流做存储/传输）和 CacheBlend（突破「只能复用前缀」的限制，复用任意位置的 KV chunk）。如果说前缀缓存是「省重复的开头」，那 CacheBlend 就是要「省重复的中间段」——这对 RAG 多文档场景是质的飞跃。

一、LMCache 是什么

LMCache 的定位一句话：

把 KV cache 从「用完即弃的临时张量」变成可持久化、可跨引擎共享、可监控、可变换的「知识」。

目标是降 TTFT、提吞吐，尤其面向长上下文 agentic、多轮对话、RAG 这些「有大量可复用上下文」的场景。它的几个关键特性：

  • vendor-neutral（厂商中立）：跨引擎、跨硬件、跨存储。面向 vLLM production stack，也被 NVIDIA Dynamo 在 2025 年集成。
  • 多级存储：GPU 之外可下沉到 CPU RAM、本地盘（SSD）、Redis/Valkey、Mooncake、InfiniStore、S3 兼容对象存储、NIXL、GDS。
  • 独立 daemon 运行：与推理引擎「无 fate-sharing」——引擎崩了，缓存还在。
  • 与 vLLM 集成：面向 vLLM V1、支持多模态。

一点说明：LMCache 通过 vLLM 的 KV connector 接口接入引擎——这是 vLLM 侧的机制，本文按常识引用（LMCache 自身 README 未逐字出现「KV Connector」字样）。

但 LMCache 真正的技术亮点，是它背后的两项研究：**CacheGen（压缩）**和 CacheBlend（非前缀复用）。这两个才是它区别于「单纯卸载/分层」缓存的核心。

二、前缀缓存的天花板：为什么只能复用开头

先理解一个根本限制。vLLM 的自动前缀缓存、SGLang 的 RadixAttention 都只能复用前缀。为什么？

因为 KV Cache 的每个 token 的 K/V，是它看着前文所有 token 算出来的（causal attention）。

  • 一个 chunk 如果放在开头，它看到的前文和缓存时一样 → KV 正确 → 可复用。
  • 同一个 chunk 如果放在中间（前面还有别的 chunk），它此刻该看到的前文变了，但缓存里的 KV 是「当初它在开头时」算的 → KV 是错的 → 直接复用会掉质量。

这就是 RAG 的痛点：你检索出 3 篇文档拼进 prompt，只有第 1 篇能命中前缀缓存，第 2、3 篇即使之前见过，也因为「不在开头」而无法复用，只能重算。CacheBlend 就是来解决这第 2、3 篇的。

三、CacheGen：把 KV 压成比特流

CacheGen（SIGCOMM’24）解决的是「KV 太大，存和传都贵」——把 KV Cache 编码成紧凑比特流，用于存储与网络传输。

3.1 三步编码

  1. Delta（差分）：对相邻 token 的 KV 求差。利用「token 局部性」——相邻 token 的 KV 相似，delta 的方差比原值低 2.4–2.9×，更好压。
  2. 按层量化（layer-wise）：对 delta 分层量化。
  3. 算术编码（arithmetic coding）：无损压缩。

3.2 两个精妙设计

① 分组 + anchor：每 10 个连续 token 一组，组内首 token 作 anchor 独立压缩、用 8-bit（因为它的精度会影响整组 delta 的分布），其余存为对 anchor 的 delta。

② 浅层给更多 bit：层分早/中/晚三组，量化 bin 越靠后越大（即浅层精度更高）。依据是一个重要观察——

LLM 输出质量对浅层 KV 的损失比深层更敏感。

所以把比特预算优先给浅层。这和后面 PyramidKV 的逐层预算、KV 量化的分层策略是同一种「不同层不平等对待」的智慧。

③ channel-layer 分组的算术编码：按「channel-layer」组合离线 profile 概率分布（而非按 token 位置），同一 LLM 可复用。这个分组比全局单一分布最多再省 53% 比特。

3.3 流式自适应

context 切 chunk（默认 1.5K token），每 chunk 离线预编码成多个可独立解码的量化档 + 文本兜底。运行时按上一 chunk 实测吞吐估带宽，选「压缩损失最小且预期延迟仍在 SLO 内」的档；带宽过低时降档，甚至改发原文本让 LLM 重算。

3.4 收益

而对输出质量「影响可忽略」。

四、CacheBlend：非前缀复用的钥匙

CacheBlend（EuroSys’25）是这篇的重头戏——它让「中间段 chunk」的 KV 也能复用。核心思路：大部分 KV 直接复用，只选择性重算一小撮「错得最离谱」的 token。

4.1 HKVD：高偏差 token

定义 HKVD（High-KV-Deviation）tokens——把某个 chunk 的「复用 KV」和「完整 prefill 应得的 KV」对比，偏差最大的那些 token。

Insight 1：重算这些高偏差 token，对减少整体注意力偏差的贡献最大。

关键发现是注意力的稀疏性：只有约 10–15% 的 token，其 KV 偏差远高于其他。所以——

论文报告：更新比例 <15% 时通常即可匹配完整 prefill 的质量。这就把「复用 vs 质量」的矛盾化解了：复用 85%+ 的 KV，只补算 15% 的关键 token。

4.2 gradual filling：逐层筛出 HKVD

怎么知道哪些 token 是 HKVD？不可能真去做完整 prefill（那就没意义了）。CacheBlend 用一个逐层收敛的技巧，依据是——

Insight 2：某层偏差最高的 token，在下一层大概率也偏差最高（跨层相关性）。

做法：

  1. 第一层按 attention deviation 选 r1%（略高于目标 r）；
  2. 在下一层只重算这些 token；
  3. 收窄到 r2%（略低于 r1）；
  4. 逐层收敛，最终选出「不只第一层、而是多层都高偏差」的 HKVD token。

位置正确性用 RoPE 旋转矩阵一次性修正（开销可忽略）。

4.3 与 KV 加载的流水化

重算和「从慢速存储加载 KV」可以重叠。双线程 pipeline：第 层的 selective recompute 与第 层的 KV load 并行，每层前 synchronize。

一组实测数字很能说明问题（Llama-7B、4K 上下文）：

重算被加载完全掩盖——等于「免费」修正了质量。（Llama-70B 则相反：重算 7ms、load 仅 4ms，load 掩盖不住重算，所以 loading controller 会取「重算延迟=load 延迟」的比例与经验值 r*≈15% 的较大者动态调整。）

4.4 收益

五、三者定位对比：LMCache / HiCache / Mooncake

这三个经常被放一起，但侧重点不同，理清楚很重要：

组件 本质 独特能力
Mooncake Store 分布式 KV 存储引擎 get/set + RDMA 高速搬运 + 副本/淘汰
SGLang HiCache 分层缓存控制器/编排层 HiRadixTree 跨层页表 + 可插拔后端（Mooncake/3FS/NIXL 作后端）
LMCache vendor-neutral 的 KV 缓存层 CacheGen（压缩传输）+ CacheBlend（非前缀复用）

一句话区分：

  • HiCache 是「指挥官」——决定 KV 放哪层、何时搬，后端可插 Mooncake/3FS；
  • Mooncake Store 是「仓库」——负责高效存取和搬运；
  • LMCache 独特在**「压缩」和「任意位置复用」**——不只是把 KV 卸载/分层，而是让 KV 更小、更能被复用。

三者不是纯竞品，很多时候是互补层（HiCache 可以把 LMCache 或 Mooncake 当后端）。

六、典型场景

CacheGen + CacheBlend 收益最大的场景，都有「大量可复用但不在开头的上下文」这个共性：

  • RAG（多文档拼接）：CacheBlend 的主场。检索出的多篇文档，无论拼在什么位置都能复用 KV。
  • 多轮对话：历史轮次的 KV 卸载 + 压缩存储，下一轮快速取回。
  • 共享系统提示：长 system prompt 的 KV 压缩后跨请求共享。

一句话总结 LMCache：它把 KV 缓存做成了可压缩（CacheGen）、可任意位置复用（CacheBlend）、可跨引擎持久化的「知识层」——尤其是 CacheBlend 用「复用 85%+KV、只重算 15% 高偏差 token」一举突破了前缀缓存的天花板，把 RAG 多文档的 KV 复用从「只能复用开头」变成「哪都能复用」。
