Mooncake：以 KVCache 为中心的分离式推理架构

Mooncake：以 KVCache 为中心的分离式推理架构

本文是 KV Cache 全方位技术指南 专题的深剖篇之一。前面 vLLM 和 SGLang 两篇讲的是「单引擎内部如何管好 KV Cache」。这一篇我们把视角拉高到整个集群：Moonshot AI（Kimi）的 Mooncake 把 KVCache 从「引擎内的临时张量」升格为集群级的一等公民——用 Prefill/Decode 分离 + 一个池化的分布式 KVCache 存储 + 以 KVCache 为中心的全局调度，在高度过载的真实负载下最大化有效吞吐（goodput）。它也是本站分布式存储专题与 KV Cache 专题的交汇点：当 KV 缓存被池化、被 RDMA 互联、被跨实例共享，它就变成了一个「存储问题」。

一、出发点：goodput 才是硬道理

Mooncake 是 Kimi 背后的服务平台，论文标题就点明了它的哲学——「A KVCache-centric Disaggregated Architecture」。它要解决的不是「理想负载下的峰值吞吐」，而是一个更残酷的现实：

线上请求经常处于「高度过载」状态——不是每个请求都能被服务。此时该优化的不是吞吐，而是 goodput（有效吞吐）：在满足延迟 SLO 的前提下，真正被完整服务完的请求量。

这个视角的转变很关键。传统吞吐（throughput）会把「跑了一半被拒的请求」也算进算力消耗，但它对用户毫无价值。Mooncake 的整个设计——分离、池化、调度、拒绝——都围绕一个目标：别把算力浪费在最终无法满足 SLO 的请求上。

它把 GPU 集群里「没被充分利用的 CPU、DRAM、SSD」池化成一个分离式 KVCache 存储池，再用一个 KVCache-centric 的调度器（Conductor）统筹全局。下面逐块拆解。

二、Prefill / Decode 分离

2.1 为什么要拆

LLM 推理天然分两个阶段，特征截然不同：

阶段 做什么 特征
Prefill（预填充） 并行处理整个 prompt，生成首 token 与全量 KV 计算密集、可并行、决定 TTFT
Decode（解码） 自回归逐 token 生成 访存密集、串行、决定 TBT

一个常见说法：「prefill 算力密集、decode 访存密集」是这个领域（DistServe/Splitwise 等）的通识总结——严格说这不是 Mooncake 论文的逐字表述，但它准确描述了两阶段的差异，本文按通识引用。

vLLM 这类基线把两者耦合在同一批次里跑。问题是：一个长 prompt 的 prefill 会抢占正在进行的 decode，导致 decode 的 TBT 抖动（长上下文场景尤其严重）。

2.2 拆成两个池

Mooncake 把集群拆成 prefill 节点池和 decode 节点池，各自独立调度、独立扩缩容。请求先在 prefill 池算完 KV、吐出首 token，再把 KVCache 传给 decode 池继续生成。两个阶段互不抢占，各自的 SLO（TTFT / TBT）可以独立保证。

这就引出一个核心问题：KVCache 怎么在 prefill 节点、decode 节点、以及跨请求之间流转和复用？ 答案是 Mooncake Store。

三、Mooncake Store：池化的分布式 KVCache

Mooncake Store 是把 KVCache「存储化」的核心组件——它把散落在各节点的 CPU DRAM 和 SSD 池化成一个分布式 KV 存储池。

3.1 分页存储与寻址

  • KVCache 在 CPU 内存里以 paged blocks（分页块） 存储——和 vLLM 的 PagedAttention 一样，块是管理粒度。
  • 每个 block 的 hash 由「自身内容 + 其前缀」共同决定。这个设计是复用的关键：相同前缀的请求会算出相同的 block hash，于是能命中同一份缓存（内容寻址 + 前缀链，和 vLLM 的自动前缀缓存同源）。
  • GPU↔CPU 的传输由一个叫 Messenger 的 GPUDirect RDMA 组件负责（每实例一个独立进程）。

3.2 副本与淘汰策略

热点极度倾斜是 KVCache 的固有特性。论文的 trace 分析给出很有意思的数字：

  • 超过 50% 的 cache block 从未被复用，而某些 block 被访问上万次。
  • 容量从 1,000 提到 50,000 blocks 时，命中率从 30% 升到 50%，再往上收益递减。

对策：

  • 支持 LRU / LFU / 基于特征的淘汰策略（其数据上 LRU 最好）。
  • 复制热点 block，避免所有请求都去挤同一个节点造成传输拥塞。
  • 仓库版还提供可编程的 per-object 生命周期：副本数、preferred segments、soft/hard pin，以及 DRAM + SSD/NVMe 多级缓存。

3.3 开源状态

Mooncake Store 已于 2025-03 开源，底层的 Transfer Engine 更早（2024-11）开源。二者都在 github.com/kvcache-ai/Mooncake（Apache-2.0），并已进入 PyTorch 生态。

四、Transfer Engine：RDMA 搬运底座

KVCache 在节点间流转，搬运效率就是命脉。Transfer Engine 是 Mooncake 的统一数据搬运层：

  • 统一接口做批量搬运，屏蔽底层介质差异。
  • 传输层覆盖 TCP、RDMA、AWS EFA、NVMe-oF、NVLink、Ascend 等。
  • 支持多网卡带宽聚合、拓扑感知路由、自动故障切换。

实测带宽（论文数字）：

大对象走 striping（条带化）+ 并行 IO + 端到端 zero-copy。这套底座和 3FS 全链路 RDMA、USRBIO 零拷贝的思路完全一致——在 TiB/s 量级的 KV 搬运面前，TCP 协议栈的拷贝和中断是扛不住的。

五、Conductor：以 KVCache 为中心的全局调度

Conductor 是 Mooncake 的全局调度器，也是「KVCache-centric」这个定语的落点。它根据当前 KVCache 的分布与各节点负载来分派请求，并在有益时主动复制/迁移 block。

5.1 prefill 节点选择（cache-aware，Algorithm 1）

一个请求进来，Conductor 怎么选 prefill 节点？核心是**「哪台机器已经缓存了最多我需要的前缀」**：

  1. 对输入切块、算 block hash；
  2. 与各 prefill 实例的缓存比对，求前缀命中长度；
  3. 估算每台的「prefill 执行时间 + 排队时间」，得到每台的预期 TTFT；
  4. 选 TTFT 最短的实例。

其中 prefill 时间用离线实测数据预测。若没有任何实例能满足 SLO，直接返回 HTTP 429——这是 goodput 哲学的直接体现：与其接一个注定超时的请求浪费算力，不如早拒。

5.2 复用最大化 + 热点迁移

Conductor 用启发式的自动热点迁移：不需要精确预测未来，而是把热点 block 复制到多台。当某实例过载时，有一个漂亮的判据：

由 kvcache_balancing_threshold 控制「传远端前缀 vs 本地重算」的取舍——传输和重算谁快用谁，这是分布式 KV 复用的核心权衡。

六、面向 SLO 的过载调度与 early rejection

6.1 两个 SLO：TTFT 与 TBT

  • TTFT（Time To First Token）：请求到达 → 首 token，prefill 阶段指标。
  • TBT（Time Between Tokens）：相邻 token 之间的间隔，decode 阶段指标。

SLO 用「单请求 baseline 的倍数」表示。比如 TTFT_P90 = 4x 意为 90% 请求的 TTFT 不超过单请求基线的 4 倍。端到端实验用 TTFT_P90=10x, TBT_P90=5x。

6.2 为什么要「早拒」

关键洞察：goodput 只算完整完成的请求。如果一个请求做完了 prefill（消耗了算力），却在 decode 阶段因过载被拒——那 prefill 的算力就白烧了。所以拒绝要尽量前移，在 prefill 之前就决定。

朴素的 early rejection 依据「prefill 池与 decode 池中较大的负载」提前拒。但它有个坑：

6.3 反相波动与预测式拒绝

朴素做法会引发 prefill 与 decode 负载之间的显著反相波动（anti-phase fluctuations）——因为它按「当前」decode 负载调度，存在滞后，形成振荡循环（prefill 机器少时更严重）。

Prediction-based early rejection 解决这个：预测「prefill 完成之后」的 decode 负载，再决定接不接。分两级——

  • request-level：预测每个请求的输出长度（成本高、精度低）；
  • system-level：预测某时刻整体 batch 数 / TBT 状态（精度要求低，更适合过载）。

七、CPP 与 layer-wise 传输

7.1 Chunked Pipeline Parallelism（CPP）

为了降长 prompt 的 TTFT，Mooncake 把每 X 个 prefill 节点组成一个流水线组：请求 token 切成 chunk（每块通常 >1000 token），不同 chunk 在不同节点上并发处理。

  • 好处：跨节点通信只发生在流水线 stage 边界，可与计算重叠，提高 MFU（算力利用率）；
  • 天然适配长短上下文混合；
  • 论文称这是据其所知首个在推理阶段应用流水线加速的工作。

7.2 Layer-wise prefill（传输/计算重叠）

用异步 launch/wait 把 KVCache 传输与计算逐层重叠：某层做 attention 前等待该层 KV load 完成并触发下一层 load，attention 后 launch 该层 store。目标是最小化 KVCache 占用的显存，让执行时间 ≈ max(load 时间, 标准 prefill 时间)。

收益是：prefill 调度可以几乎忽略显存大小——只要装得下单个请求就行。这和 3FS 的 layer-wise 重叠、CacheBlend 的流水化重算是同一个「用重叠掩盖 IO」的套路。

九、与 vLLM/SGLang/DistServe 的关系

  • vLLM：基线（耦合式 PD）。Mooncake Store 已正式接入 vLLM，提供 MooncakeConnector（PD 分离）与 MooncakeStoreConnector（集群级 KV 池化）。
  • SGLang：也已接入——用 Transfer Engine 做 PD 分离，用 Mooncake Store 作 HiCache 的外部存储后端。
  • DistServe / Splitwise / TetriInfer：共享「PD 分离」洞见。论文明说 Splitwise 在其早期开发中激励了进展；DistServe 为每阶段优化资源分配与并行策略以最大化 goodput。
  • 与纯缓存工作（如 AttentionStore）的区别：Mooncake 不是一个独立缓存，而是「内存高效的缓存存储 + cache-aware 调度」的结合。

十、和分布式存储的交汇：KV 即存储

这是 Mooncake 最值得玩味的地方，也是它同时属于 KV Cache 专题和分布式存储专题的原因：

Mooncake Store 与 3FS 都在把 KV 变成可持久化、可跨实例共享的「存储」。

两者是同一趋势的不同层：

  • 3FS 是 DeepSeek 的通用高性能分布式文件系统（RDMA + NVMe），面向训练与推理的底层高吞吐存储；
  • Mooncake Store 是专为 KVCache 设计的存储引擎（get/set + RDMA 搬运 + 副本/淘汰）；
  • 上层的 SGLang HiCache 则是编排层，可以把 Mooncake Store 或 3FS 当作可插拔后端。

三者叠起来，正好是一个金字塔：

这解释了为什么本站会把 3FS、RapidFS 这些「文件系统」和 Mooncake、HiCache 这些「推理组件」放在一起看——在 LLM 推理的尺度上，KV 缓存的量已经大到必须用分布式存储的思路来对待。这也是 RocksDB 那句「上层负责分布式、底层复用存储引擎」的又一次印证。
