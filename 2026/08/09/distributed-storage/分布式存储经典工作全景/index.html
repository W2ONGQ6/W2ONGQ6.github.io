分布式存储经典工作全景 —— 从文件、复制到云原生数据库

写在前面：分布式存储的核心不是“把数据放到多台机器”

把一份数据复制到多台机器并不难；真正困难的是：节点宕机、网络分区、请求重试和并发写入同时发生时，系统仍要对用户兑现某种可解释的承诺。文件系统承诺 POSIX，数据库承诺事务和 SQL，对象存储承诺 key–value 与耐久性，日志系统承诺顺序追加和可回放——不同系统的外观差异，最终都来自它们选择兑现的语义不同。

因此，本篇不按产品名堆砌，而按一条问题链组织重要工作：

先解决“如何在会坏的机器上保存大数据” → 再解决“副本如何达成一致” → 再解决“数据和请求如何分片、定位、扩容” → 接着解决“读写延迟与事务如何共存” → 最后在云与 NVMe 条件下，把本地 LSM、对象存储、共识组和无状态计算组合成现代系统。

一、总时间线：每一代系统都在重写一个边界

时期 代表工作 重画的边界 留下的问题
1980s–1990s NFS、AFS、LFS、LSM-Tree 远程文件访问、客户端缓存、追加写 单点元数据、跨机一致性与随机写放大
2001–2006 Chord、GFS、BigTable、Ceph/CRUSH 去中心定位、分布式文件与宽表、算法化放置 强一致事务昂贵，副本协调复杂
2007–2014 Dynamo、Spanner、Raft 最终一致的高可用 KV、全球事务、可理解共识 语义与成本难以兼得
2011–2018 RocksDB、FoundationDB、TiKV 高性能本地 LSM、事务层与存储层解耦、Raft 分片 运维、热点、跨地域延迟仍复杂
2018 至今 JuiceFS、对象存储表格式、3FS 云原生组合、对象存储 POSIX 化、为 NVMe/RDMA 重设路径 多云一致性、成本与治理成为新瓶颈

这张表有一个很重要的阅读顺序：不要先问“Ceph 和 JuiceFS 谁更强”，而要先问“它们各自把哪一层交给了谁”。Ceph 自己管理对象、放置、恢复和多种接口；JuiceFS 将数据放在对象存储、把元数据交给外部数据库、由富客户端重建文件语义；3FS 则针对 AI 训练重新设计数据链和 RDMA 路径。它们的差异首先是架构分工，而不是功能清单。

二、文件系统的起点：缓存、追加写与“大文件优先”

2.1 NFS 与 AFS：远程文件访问首先是缓存一致性问题

工作：Sun NFS（1984）；Carnegie Mellon AFS（1980s）。

中文摘要：NFS 让远程目录看起来像本地目录，以 RPC 和无状态服务端换取简单故障恢复；但客户端缓存会带来陈旧读，因此早期 NFS 采用 close-to-open 一类较弱语义。AFS 则用 callback 机制：服务器在其他客户端修改文件时主动撤销本地缓存。两者共同揭示了一个后来反复出现的事实：文件系统性能很大程度取决于客户端敢缓存多少，而缓存得越激进，一致性协议就越复杂。

这正是 POSIX 在分布式环境里昂贵的原因。rename、fsync、原子追加、文件大小可见性等看似普通的调用，背后都要求元数据与数据副本在特定时刻达成协调。后来的 CephFS、JuiceFS 和 3FS 并不是“重新发明文件”，而是在更大规模、更高吞吐环境下重新选择缓存与一致性的边界。

2.2 LFS 与 LSM-Tree：把随机写改写为顺序追加

论文：Rosenblum, M. and Ousterhout, J. “The Design and Implementation of a Log-Structured File System.” SOSP 1991；O’Neil, P. et al. “The Log-Structured Merge-Tree.” Acta Informatica 1996.

🏆 里程碑

中文摘要：LFS 的洞察是，磁盘写入常常比读取更昂贵且更随机；因此系统不在原位置修改，而是把更新顺序追加到日志尾部，后续再通过 cleaner 回收旧段。LSM-Tree 将这一想法用于键值索引：内存 MemTable 接收写入，刷盘形成有序不可变 SST，后台 compaction 把多个层级合并。写入因此转化为顺序 IO，代价则转移为读取时需要查多层文件、后台 compaction 消耗带宽、空间/写/读放大彼此制约。

这条“追加写 + 后台整理”的技术线贯穿今天的 RocksDB、LevelDB、Cassandra、HBase、TiKV，甚至也能在 Kafka 日志和对象存储上的 Copy-on-Write 文件系统中看到。理解 LSM 的 RUM 三角（Read/Update/Memory）后，就能理解为什么没有一种 compaction 策略能在所有负载下都最优。

三、Google 与 Ceph：从中心元数据到算法化数据放置

3.1 GFS（2003）：把故障当成常态

论文：Ghemawat, S. et al. “The Google File System.” SOSP 2003.

🏆 里程碑

中文摘要：GFS 以一个 Master 管理命名空间和 chunk 元数据，多个 ChunkServer 保存大块文件的副本；客户端只从 Master 获取位置，随后直接读写数据节点。它面向的是大文件、顺序读、批量追加与频繁故障，而不是通用 POSIX 负载。三副本、租约和 record append 共同保证：即使节点不断失效，系统仍能持续写入并恢复数据。

GFS 的真正贡献是承认规模会改变设计前提。单 Master 在元数据量远小于数据量时可以极其简单高效，数据复制则被视为软件责任而不是昂贵硬件的附属能力。它直接启发 HDFS，也把“集中元数据会不会成为瓶颈”这一问题留给了后来的 CephFS、分布式元数据服务和外部 KV 元数据引擎。

📄 Google Research

3.2 BigTable（2006）：文件之上需要可分裂的结构化索引

论文：Chang, F. et al. “Bigtable: A Distributed Storage System for Structured Data.” OSDI 2006.

中文摘要：BigTable 将数据表示为按 row key 排序的稀疏多维映射，并将表切为 tablet。它把 SSTable 文件放在 GFS 上，借助 Chubby 协调 tablet server、schema 和元数据。这个设计说明，分布式存储不能只解决“文件在哪”；一旦需要按 key 查找、范围扫描和在线更新，就必须再引入分片、索引、元数据和协调协议。

BigTable 催生 HBase 等宽表系统，也影响了现代数据库的分层：底层文件负责耐久与有序扫描，上层负责把逻辑键空间划分为可迁移的分片。热点 key、tablet split 和 metadata root 的管理，都是此后所有 range-sharded 数据库必须面对的问题。

📄 Google Research

3.3 Ceph 与 CRUSH（2006）：不靠中心查表，靠规则定位

论文：Weil, S. A. et al. “CRUSH: Controlled, Scalable, Decentralized Placement of Replicated Data.” SC 2006.

🏆 里程碑

中文摘要：传统分布式文件系统往往依赖中心元数据服务告诉客户端“数据在哪”。CRUSH 的回答是：给定对象名、集群拓扑和放置规则，客户端可以算法化地计算对象应落在哪些 OSD，而不必查询中心位置表。CRUSH Map 将机架、主机、磁盘等故障域编码进规则，使副本或纠删码分片能主动跨故障域放置。

Ceph 在 CRUSH 之上加入 RADOS、Placement Group、OSD 和 Monitor：PG 让对象映射和恢复管理具有合适粒度，MON 维护集群 map，OSD 在故障后自治恢复。它的核心价值不是“提供块、文件、对象三种接口”，而是用同一个对象层和放置机制支撑三种语义。代价是 PG 数量、恢复流量、CRUSH 规则和小对象开销都需要精细运维。

📄 CRUSH 论文

四、复制的一次分叉：Dynamo 的可用性与 Spanner 的事务

4.1 Dynamo（2007）：宁可冲突，也不要拒绝写入

论文：DeCandia, G. et al. “Dynamo: Amazon’s Highly Available Key-value Store.” SOSP 2007.

🏆 里程碑

中文摘要：Dynamo 面向购物车等“写入可用性优先”的服务。它用一致性哈希在虚拟节点间分布 key，用 N/R/W quorum 控制读写副本数，以 vector clock 识别并发版本，以 sloppy quorum 和 hinted handoff 在部分节点不可用时继续接受写入，再通过 anti-entropy 修复副本差异。它没有让所有副本在写入时立即达成单一顺序，而是把一部分冲突交给读取端或业务逻辑合并。

这项工作最重要的贡献是把一致性从“系统全局的开关”改写为可按业务选择的策略。Dynamo 不是宣称最终一致性总是更好，而是清楚展示了：当跨地域可用性比单 key 的立即一致更重要时，允许短暂分歧可以避免网络分区把写路径整体拒绝。Cassandra、Riak 等系统继承了这条路线；但账户、库存、唯一约束等业务通常不能仅靠应用层合并冲突。

📄 论文 PDF

4.2 Spanner（2012）：用时间和 Paxos 让全球事务可解释

论文：Corbett, J. C. et al. “Spanner: Becoming a SQL System.” SIGMOD 2017；Spanner 初始系统论文发表于 OSDI 2012。

🏆 里程碑

中文摘要：Spanner 选择了与 Dynamo 相反的方向：用 Paxos 复制每个分片，以 TrueTime 提供带不确定性界的物理时间，再以 commit wait 确保外部一致性（external consistency）。这使跨分片事务不仅能串行化，而且能与真实时间顺序一致：若事务 A 在事务 B 开始前已向客户端返回，那么 B 的读不会看到一个早于 A 的世界。

Spanner 证明强语义不是不可能，而是要为它建立昂贵基础设施：全球复制组、2PC、Paxos、时间 API 和等待预算缺一不可。它直接影响 CockroachDB、YugabyteDB、TiDB 等 NewSQL 系统，但各系统对全局时钟、复制协议和跨地域延迟的取舍不同。这里最重要的教训是：事务隔离级别、共识和时钟精度必须作为一个整体理解。

📄 Google Research

4.3 Raft（2014）：把共识变成可工程化的模块

论文：Ongaro, D. and Ousterhout, J. “In Search of an Understandable Consensus Algorithm.” USENIX ATC 2014.

🏆 里程碑

中文摘要：Paxos 提供了强大的安全性证明，但工程实现长期容易出错。Raft 以强 leader、任期、日志匹配和多数派提交为中心，将共识拆成领导者选举、日志复制和成员变更。Leader 只追加日志，Follower 只接受来自 Leader 的复制；当一条日志被多数副本持久化，才可以提交给状态机。这样的限制减少了状态空间，也让线性一致读、快照和流水线复制更容易落地。

Raft 并不自动解决分片、事务或热点问题；它只保证一个复制状态机组对操作顺序达成一致。现代分布式数据库通常会把数据切为许多 range/shard，每个分片一个 Raft group，再在跨分片事务上叠加 2PC、MVCC 与时间戳服务。把“Raft 能做什么”与“数据库还需要什么”分开，是理解 TiKV、CockroachDB 和 braft 的关键。

📄 USENIX 论文

五、本地引擎成为标准件：RocksDB、FoundationDB 与 TiKV

5.1 RocksDB：将 LSM 的权衡工程化

工作：Facebook RocksDB（2012 起）。

中文摘要：RocksDB 在 LevelDB 基础上面向多核、SSD 和服务端负载扩展：写入先进入 WAL 与 MemTable，flush 后变成 SST，后台 compaction 控制层间重叠。Bloom filter、block cache、prefix filter、column family、写组提交与多种 compaction 策略共同决定读放大、写放大、空间放大和尾延迟。

它在分布式存储中的地位类似“发动机”：TiKV、CockroachDB 的部分版本、Ceph BlueStore 的周边组件以及大量状态服务都会把复杂的本地持久化交给它。这样上层可以把精力放在复制、事务与分片；代价是 compaction 写停顿和磁盘放大仍会向上层传播，不能因为底层是 RocksDB 就忽略文件布局和资源隔离。

📄 RocksDB

5.2 FoundationDB：把事务层与存储层彻底分离

工作：FoundationDB（2012 起，开源于 2018）。

中文摘要：FoundationDB 将“提供严格串行化事务”的责任集中在一层事务处理架构中，底层存储服务器只保存有序 KV 数据。客户端通过代理读取、计算 read/write conflict range，事务系统用全局顺序与冲突检测决定提交；分片和迁移则在不改变客户端事务接口的情况下进行。它展示了一个强有力的分层思想：上层不需要直接面对复制、数据迁移和冲突细节，只要面对一套有序 KV + 事务 API。

这条路线特别适合作为元数据底座。JuiceFS 可以把 inode、目录项和 slice 映射交给事务型 KV；3FS 也使用 FoundationDB 作为无状态元数据服务的事务来源。它们不是“把文件存进 FDB”，而是把最需要原子性的小而热的元数据交给 FDB，把大数据放进对象存储或自管 NVMe。

📄 FoundationDB

5.3 TiKV：Raft 分片与 MVCC 的可扩展组合

工作：TiKV（PingCAP，2016 起）。

中文摘要：TiKV 将键空间切为多个 Region，每个 Region 由一个 Raft group 复制；PD 负责调度、时间戳与热点迁移，RocksDB 负责单机持久化，MVCC 负责多版本读取，跨 Region 事务再叠加 2PC。它把前文四项重要工作——LSM、本地 KV、Raft、事务时间戳——组合成一个可横向扩展的事务存储层。

TiKV 的价值在于说明现代分布式数据库不是某个单独算法的胜利，而是分层组合的结果：Raft 解决副本顺序，MVCC 让读写并发，2PC 处理跨分片原子性，调度器处理 Region 迁移与热点。任何一个层的延迟、倾斜或故障都会成为整条事务路径的上限。

📄 TiKV

六、云原生存储：把“大数据”和“小元数据”放在不同的地方

6.1 对象存储与 JuiceFS：数据面、元数据面、客户端三分

工作：S3 风格对象存储；JuiceFS（2021 起）。

中文摘要：对象存储天然适合大量不可变对象、跨 AZ 耐久和弹性容量，却没有目录、随机写、原子 rename 或 POSIX 缓存一致性。JuiceFS 的架构将三层拆开：对象存储保存大块数据，Redis/MySQL/TiKV/FoundatonDB 等元数据引擎保存 inode 与目录事务，富客户端通过 Chunk/Slice/Block 映射、缓存和后台 compaction 将两者重新拼成文件系统。

这种组合式设计的关键不是“把对象存储挂载成目录”，而是承认不同数据有不同访问规律：大数据追求低成本耐久，小元数据追求低延迟原子性，客户端缓存追求读写性能。它也带来新的边界：数据文件和元数据提交顺序、垃圾回收、缓存失效以及对象存储的列表/重命名语义，都必须由系统明确处理。

📄 JuiceFS 文档

6.2 3FS：为 AI 训练重新安排复制、元数据与网络路径

工作：DeepSeek 3FS（2025）。

中文摘要：3FS 面向大规模 AI 训练与 KV Cache 卸载，选择与 JuiceFS 不同的路径：元数据依托 FoundationDB 事务而保持无状态扩展，数据副本采用 CRAQ 链式复制，存储服务直接管理 NVMe，并以 RDMA 和用户态 IO 降低 CPU 与内核路径开销。它试图解决的不是通用云文件共享，而是在高并发、大吞吐训练负载中把网络、SSD 和 GPU 集群的带宽真正利用起来。

它说明硬件变化会再次改写存储设计：当 NVMe、RDMA 和 AI checkpoint/embedding/KV cache 成为主负载时，传统“中心元数据 + TCP + 通用文件缓存”的最优点会移动。但 3FS 也没有绕开分布式存储的基本约束：复制链仍要处理故障与恢复，FoundationDB 仍是元数据一致性的根，应用仍必须理解其 POSIX 与耐久性边界。

七、把经典工作连成一张图

这张图也解释了三个常见误会：

  1. Raft 不是数据库：它只为一个复制状态机确定操作顺序；分片、索引、事务和查询还需额外设计。
  2. 对象存储不是文件系统：它提供对象与 key，目录、随机写、rename 和 POSIX 一致性需要上层重建。
  3. 最终一致不等于不可靠：Dynamo 式系统以冲突处理换取分区时可写；但若业务需要唯一性、余额或跨记录不变量，就应选择事务或显式协调。

八、小结：选系统之前，先选语义和失败模型

分布式存储没有“万能最优解”。如果数据是海量追加日志，GFS/HDFS/Kafka 的思路自然；如果需要对象级弹性与低成本耐久，对象存储加元数据层更合适；如果要多副本线性一致读写，Raft/Paxos 组是核心；如果要跨分片不变量，则必须为 2PC、MVCC 和时间戳服务支付代价。

经典工作的真正价值，不在于记住每个系统的组件名，而在于学习它们如何明确地回答同一组问题：故障时还能否写？读到的是哪个版本？数据由谁决定位置？副本何时可见？元数据和大块数据谁负责？ 能把这些问题逐一说清，面对 Ceph、TiKV、JuiceFS、3FS 或任何新系统时，就不会只停留在宣传语层面。
