RocksDB 架构与实现深度解析

RocksDB 架构与实现深度解析

本文是「分布式存储系统」专题的一块关键拼图。前面的系统里 RocksDB 无处不在：3FS 用它存 chunk 元数据、Ceph 的 BlueStore 用它存元数据、TiKV/MyRocks/Kafka Streams/Flink 都把它当本地持久化底座。可以说，RocksDB 是分布式存储世界的「本地存储引擎标准件」——上层系统在它之上叠加复制、分片、事务，就长成了各式各样的分布式系统。这一篇我们把它彻底讲透：从 LSM-Tree 的写入路径、SST 文件格式，到 Compaction 的三种策略、序列号与快照的 MVCC、列族与事务，看它如何用「一切皆追加 + 后台合并」把《数据库原理》里的 LSM-Tree 理论落成工业级实现。

一、RocksDB 是什么

RocksDB 是一个嵌入式的、持久化的 key-value 存储引擎库，用 C++ 写成，key 和 value 都是任意字节串。要点全在这句话里：

  • 嵌入式（embedded）：它是一个 library 而非 server——直接链接进宿主进程，没有网络协议、没有独立进程。你的程序 #include 它、调 API，数据就落在本地磁盘。
  • 持久化：数据落盘，崩溃可恢复（靠 WAL）。
  • 基于 LSM-Tree：写入优化的存储结构，专为 SSD/Flash 和服务端负载设计。

它 2012 年从 LevelDB 1.5 fork 出来（Facebook/Meta 主导），也借鉴了 HBase 的思路，目标是把 LevelDB 改造成能扛生产级服务端负载的引擎：多线程 compaction、列族、事务、备份、丰富的调优旋钮和工具（sst_dump/ldb/db_bench/db_stress）。

为什么它成了「标准件」？ 因为分布式存储系统真正难的是复制、分片、共识（这些《分布式系统原理》讲过），而「单机怎么把 KV 高效、可靠地落盘」是个可以复用的子问题。RocksDB 把这个子问题解决得足够好，于是大家都拿它当地基——上层负责「分布式」，RocksDB 负责「存储」。

二、LSM-Tree 骨架：MemTable / WAL / SST

RocksDB 的一切都建立在 LSM-Tree（Log-Structured Merge-Tree） 之上。三个核心构件，数据在每一层都保持有序：

2.1 MemTable（内存写缓冲）

新写入先落 MemTable（内存中的有序结构）。一个 active（当前可写）+ 零或多个 immutable（写满后冻结、等待刷盘）。写满（超过 write_buffer_size，默认 64MB）就冻结成 immutable，换一个新的 active 继续接收写入，后台线程把 immutable 刷成 SST。

MemTable 有多种实现（memtable_factory）：

实现 结构 特点
SkipList（默认） 跳表 读写均衡；唯一支持并发插入；支持全序全库扫描
HashSkipList 哈希桶 + 跳表 「哈希 + 二分」，适合前缀范围查询，需 prefix_extractor
HashLinkList 哈希桶 + 有序链表 「哈希 + 线性查找」，适合每个前缀行数少
Vector 向量线性查找 适合随机写密集的批量装载

2.2 WAL（预写日志）

MemTable 在内存里，进程一崩就没了。所以每次写入同时顺序追加到 WAL（Write-Ahead Log）。崩溃重启时重放 WAL 恢复未刷盘的 MemTable。一旦对应的 MemTable 安全刷成了 SST，那段 WAL 就能删除。这就是《数据库原理》里 WAL「先写日志再改数据」 的经典落地。

2.3 SST（有序不可变文件）

MemTable 刷盘产物是 SST（Sorted String Table） 文件——磁盘上有序、不可变的 KV 文件，默认用 Block-based Table 格式（§4）。刷出的第一站是 L0，之后靠 Compaction 逐层向下合并（§6）。

刷盘触发：① 单个 MemTable 超过 write_buffer_size；② 跨列族总量超过 db_write_buffer_size（刷最大的）；③ WAL 总量超过 max_total_wal_size（刷最老数据对应的 MemTable，以便回收 WAL）。

三、写路径详解

一次写入的完整旅程，也是理解「LSM 为什么写得快」的关键：

关键点：写入只碰内存和顺序日志，不做任何随机磁盘 IO。SST 的生成、层间合并全丢给后台线程。这就是 LSM「把随机写变成顺序写」的核心——对照《数据库原理》的 B-Tree（原地更新、随机写）vs LSM（追加写、顺序写） 之争，RocksDB 站在 LSM 这边，用写放大换写吞吐。

3.1 WriteBatch 与原子性

多个操作可以打包进一个 WriteBatch，db.Write(batch) 原子地写入——要么全成功、要么全失败。WriteBatch 本质是一个 append-only 的 std::string，把一串操作序列化进去。

3.2 组提交（Group Commit）

并发写入者排成一个队列，队头的写入者成为 leader，代表整个组把 WAL + MemTable 写完。这样 N 个并发写只需一次 WAL fsync，大幅降低同步开销——和《数据库原理》里数据库的组提交是同一招。

3.3 流水线写（Pipelined Write）

enable_pipelined_write=true（5.5+）更进一步：前一个写入者写完 WAL 后，下一个写入者立即开始写自己的 WAL，同时前一个写入者还在做 MemTable 插入——让「WAL 写」和「MemTable 插入」在相邻组之间重叠。官方测得约 30% 吞吐提升。

注意别混淆：「流水线写」（相邻组之间重叠 WAL/MemTable）和「并发 MemTable 插入」（allow_concurrent_memtable_write，同一组内并行插入，仅 SkipList 支持）是两个不同机制。

四、SST 文件格式

理解 SST 的内部结构，才能理解读路径为什么快、Bloom Filter 装在哪。默认的 Block-based Table 格式（继承自 LevelDB）：

  • BlockHandle = (offset, size)，是文件内的「指针」。Footer 定长放在文件末尾，含 metaindex_handle、index_handle 和 magic number（0x88e241b785f4cff7）。
  • Data Block：排序的 KV 对，可选压缩。
  • Index Block：二分查找结构，把「查找 key」映射到「包含它的 data block」。可以是单块，也可分区（partitioned index）：顶层索引 → 索引分区，避免大文件索引块过大。
  • Filter Block：Bloom Filter。6.6+ 的 format_version=5 用更快更准的实现（64 位哈希、可扩展到十亿级 key）。
  • 范围删除 Block：range tombstone 单独存——因为它们没法内联二分查找（§8）。
  • 属性 Block：数据大小、索引大小、条目数、data block 数等，支持用户自定义属性。

压缩推荐配置：最底层用 ZSTD（90% 数据住在这，压缩比优先）+ 其他层用 LZ4（速度优先）。这是「热层快、冷层省」的分层压缩思路。每个 block 带校验和。

五、读路径与 Bloom Filter

5.1 Get 的查找顺序

一次点查 Get(key) 按「新数据优先」的顺序逐层找：

一旦在某层找到（或找到 tombstone 墓碑），就停。这解释了为什么 LSM 读会「放大」——最坏情况要翻遍所有层。这正是《数据库原理》RUM 猜想里「写优化的代价是读放大」的体现。

5.2 Bloom Filter：跳过不含 key 的 SST

每个 SST 带一个 Bloom Filter。查某层某文件前，先问 Bloom：「这个 key 肯定不在」还是「可能在」。若至少一个探测位为 0，则 key 一定不存在，直接跳过该文件，不用读它的 data block。

这对否定查找（negative lookup） 是决定性优化——查一个不存在的 key，靠 Bloom 几乎不碰磁盘。位数与假阳性率的权衡：

bits/key 假阳性率
4.9 10%
9.9（默认约 10） 1%
15.5 0.1%
  • Full Filter（默认）：整文件一个过滤器，每个 key 的探测落在一条 CPU cache line 内，比已废弃的 block-based filter 快。
  • Whole-key（默认，仅点查） vs Prefix filter（prefix_extractor，用于 Seek/范围扫描）。
  • Ribbon Filter（6.15+）：比 Bloom 省约 30% 空间，代价是 3–4× CPU——空间换时间的另一个选择。

5.3 点查 vs 迭代器

Get（点查）能充分吃 Bloom 红利；迭代器（NewIterator，范围扫描） 则要跨所有层/MemTable 做归并，Bloom 帮不上普通范围扫（但 prefix bloom 能加速 Seek）。读放大随层数增长，是 LSM 的固有代价，靠 Compaction 控制层数、靠 Bloom 减少无效 IO。

六、Compaction：LSM 的心脏

Compaction（合并）是 LSM 最核心也最微妙的部分：它决定了写放大、读放大、空间放大三者的平衡——正是《数据库原理》RUM 猜想（Read-Update-Memory 不可能三角） 的工程战场。RocksDB 提供三种策略。

6.1 Leveled Compaction（默认）

层级结构：

  • L0：直接从 MemTable 刷来的文件，彼此可重叠（因为各自独立刷出）。
  • L1 ~ Ln：每层是一个有序 run，切成互不重叠的 SST 文件，可在整层做二分查找。
  • 每层目标大小指数增长，max_bytes_for_level_multiplier 默认 10（即每层是上一层的约 10 倍）。

触发与选择：L0 文件数达到 level0_file_num_compaction_trigger（常见 4）触发 L0→L1；某层超过目标大小则挑文件合并进下一层的重叠区间，层层级联。按得分（score） 挑最该合并的层：非零层 score = 层大小 / 目标大小；L0 score = max(文件数/触发阈值, 总大小/base)。

动态层级（level_compaction_dynamic_level_bytes，8.4 起默认 true）：从最后一层反推各层目标，保证约 90% 数据在最后一层、9% 在倒数第二层，空间放大更优。

Leveled 的取舍：读放大低、空间放大低（默认动态层级下额外空间约 10%），但写放大高（常常 >10，因为数据要逐层被重写）。

6.2 Universal Compaction（size-tiered）

  • 目标：降低写放大，代价是读放大和空间放大变高。
  • 数据是一组按写入年龄排序的有序 run（R1 最新 → Rn 最旧），合并相邻 run。
  • 挑选顺序（命中即止）：① 年龄（周期性）；② 空间放大 超过 max_size_amplification_percent 就全量合并成一个 run；③ 相邻 run 的大小比例触发；④ run 数超阈值。
  • 因为每次合并都把更新「指数级地推近最终 run」，写放大更低。缺点：run 更多 → 读 IO 和 CPU 更高；全量合并时磁盘占用可能翻倍。

6.3 FIFO Compaction

像缓存：总大小超 max_table_files_size 就丢最老的文件，支持 TTL。适合时序/缓存类、可容忍老数据丢失的场景。

6.4 三者对比（RUM 三角的三个顶点）

策略 写放大 读放大 空间放大 适用
Leveled 高 低 低 读多写少、通用（默认）
Universal 低 高 高 写多、能容忍空间/读代价
FIFO 极低 — — 时序/缓存、老数据可丢

子合并（sub-compaction）：max_subcompactions（默认 1）> 1 时把一次 compaction 按 key 区间切给多线程并行，加速大合并。

七、序列号、快照与 MVCC

这是 RocksDB 实现一致性读和上层事务的基石，也是它和《数据库原理》MVCC 章节的直接呼应。

7.1 全局序列号（Sequence Number）

每一次写入都被赋予一个全局单调递增的序列号（seqno）。内部 key 的结构是：

同一个用户 key 的多次写入，靠 seqno 区分版本——新版本 seqno 更大。查找时，同一 key 的多个版本按 seqno 从大到小排，读到第一个满足条件的即最新版本。

7.2 快照（Snapshot）= 一个序列号

一个快照本质就是一个 seqno。带快照读时，只返回 seqno ≤ 快照 seqno 的版本——于是得到一个一致的、可重复的读视图，这就是 MVCC。

代价：持有一个快照会钉住 compaction——不能丢弃那些仍被快照可见的旧版本，直到快照释放（ReleaseSnapshot）。快照拿着不放会导致旧版本堆积、空间膨胀，是常见的坑。

这套「seqno + 多版本 + 快照读」和《数据库原理》讲的 MVCC「写不覆盖、追加新版本、按时间戳读合适版本」 完全同源——只不过这里的「时间戳」是全局递增的 seqno。也和 JuiceFS 的「新 slice 逻辑覆盖旧 slice」、3FS 的 chunk copy-on-write 是同一个思想母题。

八、删除的三种姿势

LSM 里「删除」不是真的抹掉数据（数据在不可变 SST 里），而是写一个墓碑（tombstone）标记，真正的回收发生在 compaction。RocksDB 有三种删除：

删除方式 机制 适用
Delete 写一个普通 tombstone；compaction 时在「确保没有更老版本」的层才真正丢弃 通用删除
SingleDelete 针对「只写过一次」的 key，tombstone 与那唯一的 Put 相互抵消，避免墓碑堆积 key 只 Put 一次再删（写多次则行为未定义）
DeleteRange 一个 range tombstone 表示 [start, end) 整段删除，存在范围删除 meta block 批量删一段连续 key，避免逐个删

为什么 SingleDelete 重要：普通 Delete 的墓碑要等到 compaction 抵达最底层、确认无更老版本才能清。若一个 key 被反复 Put/Delete，墓碑和旧版本会长期共存，拖慢读。SingleDelete 让「写一次、删一次」的 key 干净抵消。

DeleteRange 则把「删一个前缀下的一百万个 key」从一百万次 Delete 变成一条范围墓碑——它有 seqno、随 flush/compaction 正常流动、在最底层 compaction 时才真正丢弃。这些 tombstone 单独放在 SST 的范围删除块里，因为它们表示的是区间、无法内联进按点二分的 data block。

九、列族（Column Families）

列族（Column Family，CF） 是 RocksDB 3.0 起的多命名空间机制。每个 KV 属于且仅属于一个 CF；不指定则进 default CF。核心设计一句话：

列族之间共享 WAL，但各有独立的 MemTable 和 SST。

这个设计带来两个好处：

  • 共享 WAL → 跨列族原子写：Write({cf1,k1,v1}, {cf2,k2,v2}) 可原子提交，得到跨 CF 的一致视图。
  • 独立 MemTable/SST → 各自配置、快速删除：不同 CF 可有不同的 compaction 策略、压缩、Bloom 配置；drop 一个 CF 很快。

一个运维坑：老 WAL 只有在它涵盖的所有 CF 都已 flush 后才能删。若某个 CF 一直没写、不 flush，会拖住 WAL 回收——所以要用 max_total_wal_size 触发陈旧 CF 的自动刷盘。

ColumnFamilyOptions（每 CF）与 DBOptions（每实例）分离；以读写方式 DB::Open 时必须列出所有已存在的 CF。

十、事务与并发控制

RocksDB 在 WriteBatch 原子性之上提供两种事务 DB，都支持 BEGIN/COMMIT/ROLLBACK，提交前修改不可见：

10.1 悲观事务（TransactionDB）

对写入的 key 加锁检测冲突，拿不到锁就报错；提交「只要 DB 可写就保证成功」。用 PointLockManager，每 CF 默认 16 个锁条带（lock stripe）。适合高并发/高冲突场景。

10.2 乐观事务（OptimisticTransactionDB）

不加锁，提交时校验：检查涉及的 key 有没有被别的写入者动过（比对最新 seqno 与写入时看到的 seqno）。适合低冲突、大量非事务写 + 少量事务的场景。这正是《数据库原理》里 OCC（乐观并发控制） 的实现——和 FoundationDB（3FS 的元数据引擎）、TiKV 的乐观路径同源。

10.3 冲突检测的关键：GetForUpdate

普通 Get() 不做冲突追踪；GetForUpdate() 才是「建立读-写冲突」的唯一方式。配合 SetSnapshot() 可把保证收紧为「事务开始以来无人写过」。

10.4 两阶段提交（2PC）

Prepare（只写 WAL）→ Commit 支持分布式事务的 2PC——这是上层分布式数据库（如 TiKV 支撑的 TiDB）能在本地 RocksDB 上实现跨节点事务的基础。写策略有 WriteCommitted（默认）、WritePrepared、WriteUnprepared 三种。

十一、MANIFEST 与版本管理

SST 文件一堆、还在不断被 compaction 增删——「当前到底哪些 SST 是活的」 这件事怎么保证崩溃一致？答案是 MANIFEST。

文件系统不提供跨多文件的原子一致性，所以 RocksDB 自己用一个事务日志记录状态变更：

  • MANIFEST = { CURRENT, MANIFEST-<seqno>* }。CURRENT 是个特殊文件，指向当前最新的 MANIFEST 日志。
  • 一个 Version = 某个时刻的 DB 状态（活跃 SST 集合 + 元数据）。MANIFEST 日志是一串 VersionEdit 记录，每条记录一次增量变更。
  • VersionEdit 记录类型：kNewFile（加文件：层号、文件号、大小、最小/最大 key、最小/最大 seqno）、kDeletedFile、kLogNumber（最新 WAL）、kLastSequence、kColumnFamilyAdd/Drop 等。
  • 原子组（atomic group，5.16+）：一组 edit 要么全应用要么全不应用——「RocksDB 从不应用部分原子组」，用于原子 flush 和多 CF 摄入。

重启恢复流程：读 CURRENT → 找到最新 MANIFEST → 重建当前 Version（知道哪些 SST 是活的）→ 重放比记录的 log number 更新的 WAL。源码里 VersionSet::LogAndApply 负责追加 VersionEdit 并装配新 Version（这两个名字是源码级的，wiki 未直接出现）。

这套「CURRENT 指针 + 增量 VersionEdit 日志」本身就是一个小型的 WAL + 检查点机制——用日志把「多文件状态变更」做成原子的，和《数据库原理》崩溃恢复一章的思想一致。

十二、Merge Operator 与 BlobDB

12.1 Merge Operator：读-改-写的一等公民

想给一个计数器 +1，传统做法是 Get → 加一 → Put，两次 IO + 一个竞态窗口。RocksDB 的 Merge Operator 把它变成一次 Merge：

  • Merge 不立即计算，只把操作数（operand）压栈；
  • 在下次 Get / flush / compaction 时惰性合并（像逐个应用一样）。

两种接口：AssociativeMergeOperator（操作数与 Put 同格式、可按序合并，如计数器）和通用 MergeOperator（FullMerge + PartialMerge）。典型用途：计数器、追加、JSON 字段更新。它把「读-改-写」的读省掉了，对写密集的增量更新是巨大优化。

12.2 BlobDB：键值分离（WiscKey 思路）

LSM 的痛点之一：大 value 反复被 compaction 搬运，写放大惊人。BlobDB（受 WiscKey 论文启发）把大 value 存进独立的不可变 blob 文件，LSM 树里只留一个小指针：

代价是 blob 文件里会积累不再被引用的垃圾，靠 GC（集成进 compaction） 回收。Integrated BlobDB（现代实现）用标准 rocksdb::DB API，支持列族、事务、检查点、备份。关键旋钮：enable_blob_files、min_blob_size（多大的 value 才分离）、blob_file_size、enable_blob_garbage_collection、blob_garbage_collection_age_cutoff（默认 0.25，重定位最老 25% 的文件）。推荐配 Leveled compaction 用。

这是「大 value 场景」下对 LSM 写放大的针对性优化——3FS 用 RocksDB 存的是小 chunk 元数据，用不上；但存大 value 的 KV 服务能显著获益。

十三、调优旋钮与写停顿

RocksDB 以「旋钮多」著称，理解几个核心的就能应对大多数场景。

13.1 写停顿（Write Stall）

当 compaction/flush 跟不上写入速度，RocksDB 会主动刹车（降速甚至完全停写），避免读放大和空间失控。触发条件（任一 CF 满足即拖累整库）：

维度 降速（slowdown） 停写（stop）
immutable MemTable 数 — ≥ max_write_buffer_number
L0 文件数 level0_slowdown_writes_trigger（常见 20） level0_stop_writes_trigger（常见 36）
待 compaction 字节 soft_pending_compaction_bytes hard_pending_compaction_bytes

降速时把写入速率降到 delayed_write_rate（每写 sleep ~1ms）；完全停写则阻塞直到 compaction 追上。WriteOptions::no_slowdown=true 可让被限流的写直接返回 Status::Incomplete() 而非阻塞。

写停顿是 RocksDB 运维最常见的性能问题——通常是 compaction 带宽/线程不够，或 L0 触发阈值设置不当。

13.2 核心旋钮速查

旋钮 默认/推荐 作用
write_buffer_size 64MB 单 MemTable 大小；越大刷盘越少、写放大越低
max_write_buffer_number 2 最多几个 MemTable（含 immutable）
max_bytes_for_level_multiplier 10 层间大小倍率
level_compaction_dynamic_level_bytes true(8.4+) 动态层级，优化空间放大
max_background_jobs 推荐 6 后台 flush/compaction 线程
max_subcompactions 1 单次 compaction 的并行度
Bloom bits_per_key ~10 每 key 过滤位数，越多假阳性越低、越占内存
block_cache 大小 按内存定 缓存热 data block + 索引/过滤块

版本提示：level_compaction_dynamic_level_bytes 在 8.4 之前默认 false；level0_*_trigger、target_file_size_base(常见 64MB)、max_bytes_for_level_base(常见 256MB) 等具体默认值随版本变化，生产前请对照你所用版本的 advanced_options.h 核对。

13.3 调优即在 RUM 三角内选点

每个旋钮都是在《数据库原理》RUM 猜想的三角里挪动位置——没有免费的午餐，只有对负载的匹配。

十四、谁在用 RocksDB

RocksDB 是分布式存储的「本地引擎标准件」，串起了本专题的许多系统：

系统 用 RocksDB 做什么 上面叠加了什么
3FS 每块 SSD 上存 chunk 元数据 CRAQ 链式复制 + 自管裸盘
Ceph BlueStore 存对象元数据、分配信息 RADOS + CRUSH + 副本/EC
TiKV 本地 KV 持久化 Raft 复制 + 分片 + Percolator 事务
MyRocks MySQL 的存储引擎 SQL 层
Kafka Streams / Flink 流处理的状态存储（state backend） 流计算 + checkpoint
CockroachDB（早期） 本地 KV 后改用自研 Go 版 Pebble

为什么都选它？ 因为它把「单机 KV 持久化」这个可复用子问题解决得足够好：嵌入式（无需独立服务）、LSM 写优化、原子 WriteBatch、列族、事务/2PC、检查点——一个完整的本地持久层。上层系统只需专注真正难的分布式部分（复制、分片、共识），存储交给 RocksDB。这本身就是「组合优于自造」在存储引擎层的体现——和 JuiceFS/3FS 把元数据事务下推给 FDB/TiKV 是同一种智慧。
