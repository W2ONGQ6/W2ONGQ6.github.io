大数据-02：YARN —— "资源与计算解耦"这一步棋

一、引子：Hadoop 1.0 的结构性缺陷

上一篇讲到，Hadoop 用 HDFS + MapReduce 解决了”单机存不下、算不动”的问题。但在实际的大规模生产集群里运行一段时间后，工程师们发现了一个根本性的设计缺陷——资源管理和计算逻辑被焊死在同一个组件里。

这个组件叫 JobTracker。

JobTracker 身兼几职

在 Hadoop 1.0（也叫 MRv1）的架构里，JobTracker 负责以下所有事情：

  • 资源管理：追踪集群中每个节点有多少可用的 slot（Map slot 和 Reduce slot）；
  • 作业调度：决定哪个任务在哪个节点的哪个 slot 上运行；
  • 作业监控：跟踪每个任务的运行状态，处理失败重试；
  • 心跳管理：接收所有 TaskTracker（工作节点）的心跳上报。

一个进程，四种职责。这在小集群里还能应付，但随着集群规模扩大到几百、上千台节点，问题就暴露出来了：

问题一：单点瓶颈（Scalability）

所有 TaskTracker 每隔几秒都要向 JobTracker 发心跳。集群有 1000 台节点，每秒就有数百个心跳涌入，JobTracker 既要处理心跳、又要做调度决策、又要维护作业状态，CPU 和内存都承受巨大压力。据当时的工程经验，MapReduce 1.0 在超过 4000 个节点时扩展性就已经很吃力了。

问题二：单点故障（Availability）

JobTracker 是单点。它挂掉，整个集群所有正在运行的作业全部失败，必须等 JobTracker 重启后手动重提交。在一个 7×24 小时的生产环境里，这几乎是不可接受的。

问题三：资源利用率低（Utilization）

Hadoop 1.0 的资源单位是 slot，而且 Map slot 和 Reduce slot 是分开的、不可互换的。一个作业的 Map 阶段跑完了，Map slot 空出来了，但这些 slot 不能给 Reduce 用，更不能给其他类型的作业用。结果是集群里常常一边有资源闲置，一边有作业排队等待。

问题四：只能跑 MapReduce（Flexibility）

最致命的一点：JobTracker 的设计是与 MapReduce 的执行模型深度绑定的。它管理的 slot、它处理的任务生命周期、它理解的 map/reduce 两阶段——全都是为 MapReduce 量身定做的。如果你想在这个集群上跑一个图计算（如 Giraph）、或者一个内存计算框架（如早期的 Spark），几乎是不可能的，要么自己维护一套独立集群，要么对 Hadoop 做深度侵入式修改。

这就是 Hadoop 1.0 留下的历史账单：一个好用的分布式存储（HDFS），配上一个设计上有天花板的计算框架管理系统（MRv1 的 JobTracker）。

二、YARN 的核心思想：解耦

面对上述问题，Hadoop 社区在 2012 年前后推出了 YARN（Yet Another Resource Negotiator，另一个资源调度器），作为 Hadoop 2.0 的核心改进之一。

YARN 的设计哲学，用一句话概括：

把”资源管理”从”计算框架”里剥离出来，让集群的资源层变成一个通用的操作系统层。

具体来说，YARN 把原来 JobTracker 的职责拆成了两个相互独立的部分：

  1. 资源管理（Resource Management）：由全局的 ResourceManager 负责，管全集群的资源；
  2. 作业管理（Job Management）：由每个作业自己的 ApplicationMaster 负责，管自己这个作业的任务调度和状态。

这个拆分，表面上看只是把一个大进程拆成了两个，但其意义远不止于此——它把”集群是什么框架的集群”这个问题的答案，从”MapReduce 的集群”变成了”通用计算集群”。计算框架不再是特权居民，而是普通应用。

这是整个大数据生态后来百花齐放的前提。我们后面会反复回到这一点。

三、YARN 的架构：四个核心角色

整体架构示意

下面逐一介绍四个核心角色。

3.1 ResourceManager（RM）：全局资源大管家

ResourceManager 是整个 YARN 集群中唯一的全局资源管理者。它内部有两个关键子模块：

Scheduler（调度器）：纯粹负责资源分配。它接收来自 ApplicationMaster 的资源请求，结合当前集群各节点的资源状况，决定把哪些资源（Container）分配给哪个请求。注意，Scheduler 只管”分配”，不关心任务的执行、监控和重试——这些都是 ApplicationMaster 的事。

ApplicationsManager（应用管理器，注意和 ApplicationMaster 区分）：负责接受客户端提交的新应用，为其分配第一个 Container 来启动 ApplicationMaster，并在 AM 失败时负责重启它。

ResourceManager 在高可用（HA）模式下可以配置主备节点，通过 ZooKeeper 做主备切换，从而解决 Hadoop 1.0 时代 JobTracker 的单点故障问题。

3.2 NodeManager（NM）：单机资源守卫

每台工作节点上运行一个 NodeManager。它的职责：

  • 定期向 ResourceManager 发心跳，上报本节点当前可用的资源（CPU、内存），以及本节点上各 Container 的运行状态；
  • 根据 ResourceManager 的指令，启动和停止 Container；
  • 监控 Container 的资源使用，如果一个 Container 超过了分配给它的内存限额，NodeManager 会将其杀死（防止一个任务拖垮整台机器）；
  • 管理本地磁盘缓存，如分布式缓存（DistributedCache）中的文件。

NodeManager 只是本机资源的执行者，它不理解任务的业务逻辑，不知道也不关心 Container 里跑的是 MapReduce 的 Map 任务还是 Spark 的 Executor。

3.3 ApplicationMaster（AM）：每个作业的”小 JobTracker”

ApplicationMaster 是 YARN 设计中最精妙的部分，也是解耦得以成立的关键。

每提交一个应用（Application），YARN 就会启动一个对应的 ApplicationMaster，它运行在集群的某个 Container 里。AM 的职责是：

  • 向 ResourceManager 申请本作业所需的资源（以 Container 的形式提出请求，指定需要的 CPU 核数、内存量、数据本地性偏好等）；
  • 与 NodeManager 协作，启动具体的任务 Container；
  • 监控任务的运行进度，处理任务失败的重试；
  • 作业完成后释放所有资源，注销自己。

这里有一个关键的设计思想：AM 是框架相关的。MapReduce 有自己的 MRAppMaster，Spark on YARN 有自己的 SparkYarnClient 和 AM，Flink on YARN 有自己的 Flink AM。每个计算框架自己实现 AM，把本框架的调度逻辑封装在 AM 里，YARN 不需要理解这些细节。

这就是解耦的精髓：YARN 提供统一的资源层，框架各自实现自己的 AM，双方通过 Container 这个抽象接口交互。

3.4 Container：资源抽象单元

Container 是 YARN 分配资源的基本单位。一个 Container 代表集群上某个节点的一组资源，包含：

  • 指定量的内存（以 MB 为单位）；
  • 指定数量的虚拟 CPU 核（vcore）。

（较新版本的 YARN 还支持 GPU 等其他资源类型。）

Container 是一个逻辑概念，在实现层面对应操作系统的进程（以及可选的 cgroup 隔离）。任何东西都跑在 Container 里：ApplicationMaster 本身是一个 Container，每个 Map 任务是一个 Container，每个 Spark Executor 是一个 Container。

与 Hadoop 1.0 的 slot 不同，Container 的大小是动态指定的——不同的任务可以申请不同规格的 Container，不再受限于固定的 Map slot / Reduce slot 划分，资源利用率因此大幅提升。

四、一个作业的完整生命周期

把四个角色的互动串起来，以一个 MapReduce 作业为例，描述从提交到完成的全过程：

几个值得注意的细节：

数据本地性（Data Locality）：AM 在向 RM 申请 Container 时，会携带数据本地性偏好。对于 Map 任务，AM 会告诉 RM”我希望这个任务跑在存有对应 HDFS 数据块的节点上”。RM 的 Scheduler 在做分配决策时会尽量满足这个偏好，实在不行才退而求其次（rack-local 或 off-rack）。这是”移动计算而非移动数据”思想的具体实现。

心跳驱动：YARN 的资源分配是心跳驱动的，而不是推送式的。NodeManager 向 RM 发心跳，RM 在心跳响应里携带分配决策。这个设计简化了 RM 的实现，但也意味着资源分配有一定的延迟（心跳间隔通常是秒级）。

ApplicationMaster 的容错：如果某个 AM 崩溃，ResourceManager 会感知到（心跳超时），并重新启动一个新的 AM。新 AM 启动后可以通过读取已完成任务的输出来恢复作业状态，避免全部重跑。

五、调度器：多租户下的取舍

YARN 的 Scheduler 是可插拔的，官方提供了三种实现，分别针对不同的业务场景：

5.1 FIFO 调度器

先进先出（First In First Out）。提交早的作业优先获得所有可用资源，后提交的作业必须等前面的作业完全完成后才能开始。

优点：实现简单，不需要任何配置。

缺点：不适合生产环境的多租户场景。一个大作业独占资源时，大量小作业（比如报表、Ad hoc 查询）只能无限等待，集群利用率和用户体验都差。

实用场景：开发调试，或完全受控的单作业流水线。

5.2 Capacity 调度器（容量调度器）

Capacity Scheduler 是 Hadoop 社区的默认调度器，由 Yahoo! 主导开发。

核心思想：把集群资源按比例划分成若干队列（Queue），每个队列有保证的最低资源容量（capacity）。不同的业务团队/部门使用不同的队列，互不干扰，各有保障。

主要特性：

  • 容量保证：每个队列保证能使用不低于 capacity 比例的资源。
  • 弹性扩展：某个队列暂时闲置时，其资源可以借给其他繁忙队列使用，但一旦本队列有新作业进来，借出的资源会被逐步归还。
  • 层级队列：队列可以嵌套，形成树状结构（如 root → engineering → ml_team）。
  • 作业优先级：队列内部可以配置基于 FIFO 或优先级的调度。
  • ACL 控制：每个队列可以配置哪些用户/组有权提交作业。

适合场景：大型企业，多个部门共享同一个集群，需要对不同部门的资源使用进行隔离和配额管理。

5.3 Fair 调度器（公平调度器）

Fair Scheduler 由 Facebook 开发并贡献给社区。

核心思想：让所有提交的作业公平地共享集群资源，使每个作业在统计上都能获得相等份额的资源。

主要特性：

  • 动态公平：当集群只有一个作业时，它独占所有资源；当有新作业提交时，一部分资源会从正在运行的作业里”抢占”（preemption）回来分配给新作业，最终达到各作业资源均等。
  • 抢占（Preemption）：这是 Fair Scheduler 和 Capacity Scheduler 的重要区别之一。Fair Scheduler 支持强制抢占——如果某个作业长期未获得公平份额，调度器可以杀死其他作业的 Container 来”强制腾出”资源（这有一定代价，需要谨慎配置）。
  • 队列机制：同样支持队列，队列内按公平策略调度；跨队列之间也可以配置权重（weighted fair）。
  • 最小份额保证：可以为队列配置最低资源保证，防止小作业被完全饿死。

适合场景：交互式分析、Ad hoc 查询等延迟敏感型场景，希望每个用户的作业都能快速得到响应，而不是排在一个大批处理作业后面无限等待。

三种调度器对比

实际生产中，Capacity Scheduler 更常见于需要强资源隔离和 SLA 保证的企业场景；Fair Scheduler 更受开发者喜爱，因为它能让每个用户的 Ad hoc 查询都快速得到响应。

六、解耦的深远意义

说清了架构和调度器，现在我们回到最重要的问题：YARN 的解耦，究竟带来了什么？

6.1 计算框架退化为”YARN 上的一个应用”

这是最直接的好处。在 YARN 的世界里，没有任何计算框架是”原住民”——MapReduce、Spark、Flink、Tez、Storm、Giraph，全都是 YARN 上的普通应用，通过实现 ApplicationMaster 接口来接入 YARN 的资源层。

它们共享同一套物理资源（CPU、内存、网络），无需各自维护独立的集群。一家公司不再需要”一个跑 MapReduce 的集群”+”一个跑 Spark 的集群”，而是维护一个 YARN 集群，按需跑任何框架。这在资源利用率和运维成本上都是巨大的节省。

6.2 生态爆发的基础设施前提

更深一层：没有 YARN 的解耦，Spark、Flink 几乎不可能以今天这个规模繁荣起来。

原因很简单：推广一个新的计算框架，最大的障碍不是框架本身的代码有多好，而是它能跑在哪里。如果每个新框架都要求用户建一套独立的集群，迁移成本就是天文数字，绝大多数企业根本不会去尝试。

YARN 把这个障碍移除了。当 Spark 的 YARN 支持成熟后，任何已经有 Hadoop/YARN 集群的企业，都可以零额外基础设施成本地试用 Spark——只需要提交一个 Spark 应用到已有的 YARN 集群，几分钟后就能看到结果。这极大地降低了生态中新框架的试用门槛和推广成本。

从这个角度看，YARN 不是 Hadoop 的一个内部改进，而是整个大数据生态的”公共操作系统层”——它让后来的 Spark、Flink 站在了一个统一的资源基座上，而不是各自为战。

6.3 架构思想：分离关注点（Separation of Concerns）

YARN 的解耦是一个经典的”分离关注点”设计。在此之前，”这个集群能跑什么”和”这个集群的资源怎么分配”是同一个问题；在此之后，它们成了两个完全独立的问题，由不同的组件分别负责、分别演进。

这种分离带来了另一个好处：各层可以独立优化。YARN 的 Scheduler 可以单独改进公平性算法，不影响 Spark；Spark 可以在不动 YARN 的情况下优化自己的 AM 实现和 Executor 管理。正交性使系统更健壮、更易演进。

6.4 YARN 的局限与 Kubernetes 时代的演进

YARN 解决了”多框架共存”的问题，但它本身也有局限：

  • 容器模型相对简单：YARN 的 Container 是进程级隔离，没有 Docker 容器那样的镜像封装和环境一致性保证，部署新框架时依然需要在所有节点上预装依赖；
  • 主要面向批处理和长运行服务：YARN 对微服务、在线推理等低延迟服务的调度支持相对有限；
  • 生态绑定：YARN 是 Hadoop 生态的一部分，对于完全基于云原生的新架构，引入整套 Hadoop 显得笨重。

这些局限催生了另一种思路：用 Kubernetes（K8s）来做大数据的资源调度。K8s 提供了更标准的容器化、更丰富的资源类型（GPU、TPU）、更好的多租户隔离（Namespace）和更活跃的云原生生态。

从 Spark 2.3 开始，Spark 官方支持 Kubernetes 作为部署模式（取代或并行于 YARN）；Flink 的 Kubernetes Operator 也日趋成熟。越来越多的新平台选择直接基于 K8s 而不是 YARN。

但这并不意味着 YARN 被抛弃。对于已经有大规模 Hadoop 集群的企业，YARN 依然是主力资源调度层，而且稳定性和调度效率经过多年生产验证，短期内不会消失。YARN 和 K8s，代表的是”Hadoop 生态内资源调度”和”云原生资源调度”两条路线，在相当长的时间内会并行存在。

从历史的角度看，YARN 做的事情在当时是正确且必要的：在 Hadoop 成为事实标准的年代，它用解耦打开了多框架共存的大门。K8s 后来做了类似的事，只是在更彻底的容器化和云原生语境下重新做了一遍。

七、小结：YARN 解决了什么，又留下了什么

YARN 的出现，是大数据演进链条上一个承上启下的关键节点。

它解决的问题：

  • JobTracker 单点瓶颈 → ResourceManager + HA 支持，集群可扩展到数万节点；
  • 资源计算耦死 → 解耦，任意框架都可以作为 YARN 应用运行；
  • 固定 slot 利用率低 → 动态 Container，资源分配更灵活；
  • 只能跑 MapReduce → 多框架共存成为可能，生态开放。

它没有解决（也不打算解决）的问题：

  • MapReduce 的慢：YARN 让 MapReduce 以外的框架能跑起来，但 MapReduce 本身每一步都要把中间结果落回 HDFS 的问题依然存在。迭代计算、机器学习、交互式查询，MapReduce 仍然太慢、太难用。
  • 流式计算的缺失：YARN 本质上还是个面向批处理的资源调度器，实时流处理需要专门的计算框架。

这两个悬而未决的问题，分别指向了大数据演进链条上的下两站：Spark（用内存计算打破磁盘瓶颈，解决”慢”和”难用”）和 Kafka + Flink（解决流式计算问题）。

YARN 完成了它的历史使命：把资源层从计算层解放出来，为后续的百花齐放搭好了舞台。接下来登场的，是这个舞台上最耀眼的主角之一——Spark。
