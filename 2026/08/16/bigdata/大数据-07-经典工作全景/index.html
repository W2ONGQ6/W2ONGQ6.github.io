大数据-07：经典工作全景 —— 从 Google 三驾马车到湖仓与流批统一

写在前面：一条技术史，不是一串产品名

大数据领域最容易被误读成一张产品清单：Hadoop、Hive、YARN、Spark、Kafka、Flink、Iceberg……似乎每隔几年就多一个新名字。但真正推动系统演进的不是“发明了一个更酷的框架”，而是上一代架构在规模、延迟、一致性或易用性上碰到了不可回避的边界。

这篇文章把重要工作放回它们出现时的矛盾中。读完后，应能回答：它解决的是哪一种瓶颈、改变了哪一层抽象、为什么仍会留下下一道难题，以及它在今天的湖仓/实时数仓架构中留下了什么。

一、总时间线：五层抽象轮流成为瓶颈

时期 重要工作 解决的核心问题 留下的下一道难题
2003–2006 GFS、MapReduce、BigTable 如何在廉价且会故障的机器上存、算、查海量数据 批处理僵硬，资源与计算耦合
2006–2012 Hadoop、Hive、YARN、Mesos、Borg 将 Google 的思想开源化，并让多个计算框架共享集群 磁盘中间结果慢；SQL 和交互分析仍受限
2010–2015 Dremel、Spark、Presto、Parquet/ORC 通过列存、内存与 DAG/MPP 执行提高分析速度 流处理仍多依赖批式思维
2011–2016 Kafka、MillWheel、Dataflow、Flink 让连续、乱序、可重放的数据流可正确计算 裸文件存储没有事务和演进能力
2016 至今 Hudi、Iceberg、Delta Lake、Lakehouse 让对象存储/数据湖具备表、ACID、增量与时间旅行 多引擎互操作、成本和治理成为新重点

先把数据分散到多机，再把计算移到数据旁；接着把资源从计算框架中解耦，把磁盘流水线变成内存 DAG；随后让无界事件流具备时间和一致性语义；最后把裸文件重新组织成可事务化的表。

二、Google 三驾马车：定义分布式数据处理的基本问题

2.1 GFS（2003）：先承认机器会坏

论文：Ghemawat, S. et al. “The Google File System.” SOSP 2003.

🏆 里程碑

中文摘要：GFS 的重要性不在于“把文件拆成块”，而在于它彻底改变了系统的默认前提：机器故障不是异常，而是大规模集群中的日常事件。它把大文件切成 64 MB chunk，以单个 Master 管理元数据、多个 ChunkServer 保存数据副本；客户端只向 Master 查询元数据，随后直接与数据节点传输内容，避免让控制面成为数据面的瓶颈。

更深的设计选择是主动放弃通用文件系统语义。GFS 假设大文件、顺序读和追加写才是主要负载，因此用跨机器副本而非昂贵硬件解决可靠性，用 record append 支持海量日志写入。这种“根据真实工作负载重写抽象”的思路，后来贯穿 HDFS、Kafka 和湖仓表格式。

📄 Google Research

2.2 MapReduce（2004）：把并行与容错从业务代码中拿走

论文：Dean, J. and Ghemawat, S. “MapReduce: Simplified Data Processing on Large Clusters.” OSDI 2004.

🏆 里程碑

中文摘要：MapReduce 将离线计算归结为 Map、Shuffle、Reduce 三步。用户只描述“单条记录如何变换”和“同一 key 的值如何归约”，运行时负责切分输入、把任务调度到数据附近、按 key 分区、在失败后重跑任务，并用 speculative execution 缓解慢节点。这第一次让工程师能在数千台机器上写并行程序，而不必自己处理 RPC、重试和数据分片。

它的决定性贡献是 data locality：与其把 TB 级数据搬到计算节点，不如把计算任务派到数据副本所在节点。代价同样深远：阶段间中间结果必须物化到磁盘，Shuffle 既昂贵又僵硬；复杂算法被迫拆成多轮作业。这正是 Spark 试图打破的瓶颈。

📄 Google Research

2.3 BigTable（2006）：文件系统之上需要结构化随机访问

论文：Chang, F. et al. “Bigtable: A Distributed Storage System for Structured Data.” OSDI 2006.

🏆 里程碑

中文摘要：GFS 擅长保存大文件，MapReduce 擅长批量扫描，但搜索索引、网页元数据和用户画像还需要按键查询与范围扫描。BigTable 将数据组织为按 row key 有序的稀疏多维映射 (row, column family:qualifier, timestamp) → value，通过 tablet 分片扩展，并把 SSTable 文件存放在 GFS 上。它不是关系数据库替代品，而是面向海量、稀疏、半结构化数据的宽表系统。

它的影响有两条支线：HBase、Cassandra 等 NoSQL 系统直接继承宽表思想；“文件层负责耐久、上层元数据负责组织和索引”的分层思想，则在 Iceberg、Hudi、Delta Lake 中以分析表的形式重新出现。

📄 Google Research

三、从单一框架到共享平台：Hadoop、Hive、YARN

3.1 Hadoop / HDFS：把三驾马车变成开源基础设施

工作：Hadoop Common、HDFS 与 Hadoop MapReduce（Apache Hadoop 生态，2006 起）。

🏆 里程碑

中文摘要：Hadoop 将 GFS 与 MapReduce 的思想做成开源基础设施：HDFS 用 NameNode 管理文件到 block 的映射、DataNode 保存多副本数据；MapReduce 按 InputSplit 切分任务，并尽可能把 Map 调度到本地或同机架副本。它真正改变的不是某一项算法，而是让企业能够以相对低的成本部署 PB 级离线数据平台，并形成 Hive、HBase、Oozie、Sqoop 等完整生态。

Hadoop 1.x 的局限也很典型：JobTracker 同时承担资源管理和 MapReduce 控制，使集群只能服务一种计算模型。当 SQL、机器学习和流处理开始共存时，资源层必须从 MapReduce 中独立出来。

📄 Apache Hadoop

3.2 Hive（2009）：让分布式计算回到 SQL

论文：Thusoo, A. et al. “Hive—A Warehousing Solution Over a Map-Reduce Framework.” VLDB 2009.

中文摘要：Hive 为 HDFS 文件建立表、分区、schema 和 Metastore，使分析师可以通过 HiveQL 描述查询，由编译器翻译成 MapReduce、Tez 或 Spark 执行计划。它解决的不是计算能力，而是人机接口问题：在数据规模增长后，不能要求每一个指标、报表和临时分析都由工程师重写一份分布式 Java 程序。

Hive 奠定了现代湖仓的一个核心事实：表不等于数据文件，表是“文件 + schema + 分区 + 元数据”的逻辑对象。早期 Metastore 不保证文件级事务，且查询性能仍受 MapReduce 限制，但这层“表的幻觉”成为 Parquet、Iceberg 和多引擎 SQL 互操作的共同起点。

📄 VLDB 论文

3.3 Mesos、YARN 与 Borg：资源管理从计算框架中独立出来

论文：Hindman, B. et al. “Mesos.” NSDI 2011；Vavilapalli, V. K. et al. “Apache Hadoop YARN.” SoCC 2013；Verma, A. et al. “Large-scale Cluster Management at Google with Borg.” EuroSys 2015.

中文摘要：Mesos 采用两级调度：中心 master 向各 framework 分配 resource offer，framework 自己决定如何分配任务；YARN 将资源管理抽为 ResourceManager/NodeManager，让每个应用持有 ApplicationMaster；Borg 则展示了 Google 如何在统一集群中处理长期服务与批作业、优先级、配额和超卖。三项工作实现不同，却共同完成了一次抽象迁移：集群不再“属于 MapReduce”，而成为多个工作负载共享的资源池。

YARN 对 Hadoop 生态尤其关键。Spark、Tez、Flink 不需要重新建设机器管理系统，就能作为 YARN application 运行；调度器也不必理解 SQL、机器学习或流计算的业务语义。资源解耦为生态繁荣创造条件，同时也带来更复杂的控制面，并在云原生时代与 Kubernetes 形成新的分工。

📄 Mesos | YARN | Borg

四、交互分析的突破：列式存储、DAG 与内存计算

4.1 Dremel（2010）：PB 级 SQL 首先要能少读数据

论文：Melnik, S. et al. “Dremel: Interactive Analysis of Web-Scale Datasets.” VLDB 2010.

🏆 里程碑

中文摘要：Dremel 证明了 PB 级交互式查询不一定要等待传统 MapReduce 批作业。它采用树形服务架构，并使用面向嵌套记录的列式编码：查询只读取所需列，聚合可以在服务树上并行合并。它的关键不是某个 SQL 方言，而是把“全表扫描”拆成“列裁剪 + 分布式聚合 + 共享存储上的并行读取”。

Dremel 对开源生态的影响体现在两个方向：Parquet 的嵌套列式编码受其启发，Presto/Trino 等 MPP 查询引擎延续了交互式 SQL 的目标。它说明大数据计算并非只有 MapReduce 路线：面对报表与探索分析，延迟、并发和列选择往往比通用批处理吞吐更重要。

📄 Google Research

4.2 Spark / RDD（2012）：把重复计算从磁盘搬到内存与血统图

论文：Zaharia, M. et al. “Resilient Distributed Datasets: A Fault-Tolerant Abstraction for In-Memory Cluster Computing.” NSDI 2012.

🏆 里程碑

中文摘要：Spark 的 RDD 把分布式数据集定义为不可变、可分区、可通过确定性 transformation 重建的集合。它允许中间结果缓存于内存以加速迭代机器学习、交互分析和多次复用，同时用 lineage（血统）而非每次都复制或落盘来恢复丢失分区。只要知道一个 RDD 是由哪些父 RDD 经过什么操作得到的，失败分区就可以沿依赖链局部重算。

Spark 进一步用 DAG 调度取代固定的 Map→Reduce 两阶段：窄依赖可以在同一 stage 流水执行，只有宽依赖才需要 shuffle 边界。这使它既能减少无意义落盘，也能把 SQL、机器学习、图计算和流处理放进同一套运行时。它仍不能消除数据倾斜、shuffle、GC 和缓存失控；这些问题说明瓶颈只是从磁盘转移到了内存、网络和执行计划。

📄 NSDI 论文

4.3 Parquet / ORC 与 Presto：格式和引擎必须协同

工作：Apache ORC（2013）、Apache Parquet（2013）、Presto（Facebook，2013）。

中文摘要：列式格式之所以成为分析系统的默认选择，不是因为“按列存更现代”，而是因为 OLAP 查询经常只访问宽表中的少数列。Parquet/ORC 通过列裁剪、分块统计信息、字典/RLE/压缩编码，减少读盘、网络传输和解码成本；Presto 则代表共享存储之上的 MPP SQL 引擎，尽量把计算下推到 worker 并避免把所有中间状态写回 HDFS。

这阶段给出了一个长期有效的经验：性能来自语义层、优化器、文件布局和执行器的共同工作。表有清晰 schema 和分区，文件有列统计和合理大小，优化器才能做谓词下推与列裁剪；否则即使换成更快引擎，仍是在扫描不该扫描的数据。

📄 Parquet | ORC | Trino

五、无界数据的革命：Kafka、Dataflow 与 Flink

5.1 Kafka（2011）：消息队列升级为可重放的数据事实日志

论文：Kreps, J. et al. “Kafka: A Distributed Messaging System for Log Processing.” NetDB 2011.

🏆 里程碑

中文摘要：Kafka 的核心抽象是分区化、持久化、仅追加的 commit log。生产者按 partition 追加记录，broker 持久化并复制，消费者组只保存自己读到哪个 offset，因此多个下游可以以各自速度独立读取、失败后重放，甚至从历史 offset 重新构建状态。它与传统“消息被一个消费者取走后即消失”的队列模型不同，更接近一条可以反复读取的数据河流。

Kafka 解决流系统的输入与解耦问题，却不负责业务状态计算。窗口聚合、乱序事件、跨 topic 一致提交仍要由流处理器完成。这种分工让 Kafka 成为 Kappa 架构的骨架：把原始事件长期保存，计算逻辑可以在需要时重放，而不必维护独立的批处理回填链路。

📄 Apache Kafka 文档

5.2 MillWheel 与 Dataflow：难点不是“持续运行”，而是时间语义

论文：Akidau, T. et al. “MillWheel.” VLDB 2013；Akidau, T. et al. “The Dataflow Model.” VLDB 2015.

🏆 里程碑

中文摘要：MillWheel 将有状态流计算的核心问题讲得很清楚：记录可能重复、延迟、乱序甚至在失败恢复后重新投递，因此系统必须把状态、持久化、watermark 和触发机制作为一等公民。Dataflow 则进一步给出统一模型，用 what / where / when / how 四个维度分离计算逻辑、窗口位置、结果触发时机和结果修正方式。

event time 不是机器收到消息的时间，而是事件在业务世界发生的时间；watermark 也不是“绝不会再有旧数据”的证明，而是系统基于观测作出的进度估计。允许迟到、更新先前结果、在正确性和低延迟之间取舍，都是业务语义而非单纯实现细节。Flink、Beam 及多数现代流平台都直接或间接继承了这一框架。

📄 MillWheel | Dataflow Model

5.3 Flink：把状态一致性和事件时间做成运行时能力

工作：Apache Flink（2014 起）；Carbone, P. et al. “Apache Flink: Stream and Batch Processing in a Single Engine.” IEEE Data Engineering Bulletin, 2015.

🏆 里程碑

中文摘要：Flink 的世界观是“批是有界的流”。DataStream 以事件为基本处理单位，watermark 推进事件时间，状态后端保存算子状态；checkpoint barrier 在数据流中传播，并借助分布式快照协议把所有算子状态与 source offset 对齐。恢复时，作业从一致快照继续，才有可能在端到端 sink 配合下实现 exactly-once。

它解决的不是“比 Spark 更快”这样简单的问题，而是把无界、乱序、长期运行的计算放进一套可推理的状态模型。exactly-once 也不是免费标签：source 必须能回放，状态必须持久化，sink 必须支持幂等或事务提交，checkpoint 频率还会影响延迟与成本。理解这些前提，才能避免把“开启 exactly-once”误当成系统绝对不重不丢。

📄 Apache Flink

六、从文件集合回到可事务化的表：三大数据湖表格式

6.1 Delta Lake（2020）：用事务日志把对象存储变成可靠表

论文：Armbrust, M. et al. “Delta Lake: High-Performance ACID Table Storage over Cloud Object Stores.” VLDB 2020.

🏆 里程碑

中文摘要：数据湖的原始形态是一组 Parquet 文件。单个文件可高效扫描，却无法回答“并发写入完成了吗”“当前表由哪些文件构成”“能否回到昨天版本”。Delta Lake 通过有序事务日志记录文件级 add/remove 操作：写入先生成数据文件，再原子提交对应元数据版本；读者只读取某个已提交快照引用的文件集合，因此不会看到半完成写入。

这为 ACID、time travel、schema enforcement/evolution、MERGE/UPDATE/DELETE 奠定基础。它说明湖仓不是把数据库复制到对象存储，而是在不可变文件之上建立 MVCC 式表元数据层。事务粒度通常是文件而非行，文件大小、compaction 和分区策略仍直接决定写放大与查询性能。

📄 VLDB 论文

6.2 Apache Hudi：把增量写入和变更捕获带进数据湖

工作：Apache Hudi（Uber，2016 起）。

中文摘要：Hudi 的起点是典型的增量数据难题：用户、订单、行为事件并不总是只追加，迟到数据和更正记录会反复修改历史分区。它将表区分为 Copy-on-Write 与 Merge-on-Read：前者写入时合并并重写 base file，读快但写成本高；后者先追加 delta log，读取时再合并，写快但读路径更复杂。围绕两类表，Hudi 提供 upsert、索引、compaction、cleaning 和增量查询。

它将“变更数据”从 ETL 边角问题提升为表格式的一等能力。对流批统一而言，关键不只是新数据能否写入，而是下游能否准确读取某个 commit 之后发生的变更；这正是 CDC、实时数仓和特征平台所需要的接口。

📄 Apache Hudi

6.3 Apache Iceberg：用开放表规范解决多引擎互操作

工作：Apache Iceberg（Netflix，2018 起）。

中文摘要：Iceberg 将重点放在表规范和元数据树，而不是绑定某一个计算引擎。它以 metadata file、manifest list、manifest file 分层记录快照、数据文件和分区信息；查询引擎可在计划阶段读取文件级统计，避免扫描无关文件。隐藏分区让用户按逻辑列过滤，不必把物理目录结构写进 SQL；分区演进则允许历史数据与新数据使用不同布局。

Iceberg 回应 Hive 分区目录和 Metastore 的长期脆弱性：大量分区会使元数据操作缓慢，重命名列、修改分区策略或多引擎并发写都容易出问题。它不替代 Spark/Flink/Trino，而是为它们提供共同、可版本化的表接口。选择 Iceberg、Hudi 或 Delta 的关键区别，通常在多引擎开放性、写入模式和增量读取需求，而非“谁更像数据库”。

📄 Apache Iceberg 规范

七、把重要工作重新连成一张架构图

最容易混淆的三组概念必须分开：

  1. Kafka 不是 Flink：Kafka 持久化并分发事件日志；Flink 维护状态、时间与窗口并计算结果。
  2. Parquet 不是 Iceberg：Parquet 定义单个文件如何按列编码；Iceberg 定义一张表在某个快照中有哪些文件、如何提交与演进。
  3. Spark/Flink 不是数据湖：前者是计算引擎，后者是存储与表层。引擎可替换，表快照和数据文件才是不同工作负载共享的长期资产。

八、小结：真正的主线是抽象边界不断重画

  • GFS/HDFS 将可靠存储从单机磁盘提升为集群能力；
  • MapReduce/Spark 将并行与容错从业务逻辑提升为运行时能力；
  • YARN/Mesos/Borg 将资源分配从单一框架提升为共享基础设施；
  • Kafka/Dataflow/Flink 将时间、状态和恢复从应用补丁提升为流系统语义；
  • Iceberg/Hudi/Delta 将事务、版本和演进从数据库专属能力提升为数据湖表能力。

现代数据平台看似组件更多，逻辑反而可以更简单：把事件留在可回放日志中，把批与流计算建立在一致的时间/状态语义上，把长期数据资产保存为可版本化的开放表。每一层只承担自己的职责，整条链才不会再次耦死。
