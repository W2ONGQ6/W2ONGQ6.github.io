引子：单机的墙

大数据这个词听上去很宏观，但它的起点非常具体——2000 年代初，互联网公司第一次遭遇了一道单机无法翻越的墙。

Google 的爬虫每天产出几十 TB 的网页数据。这些数据要存下来，还要被索引、被搜索、被实时服务。问题是：

  • 一块硬盘的容量，撑死几百 GB（彼时）；
  • 一台机器的内存，处理不了百亿网页的倒排索引；
  • 一个 CPU，就算跑一年也排不完如此规模的 PageRank。

这就是”单机的墙”：存不下，算不动。

Scale-Up vs Scale-Out

面对这堵墙，工程师本能的第一反应是 scale-up（纵向扩展）——换更大的机器，更多的内存，更快的磁盘。这条路走了一段时间，但很快碰到三个硬上限：

  1. 成本指数级上升：最顶配的服务器比普通服务器贵十倍，但性能只提升两三倍。边际收益迅速衰减。
  2. 单点故障：越贵的机器，一旦宕机损失越大。
  3. 物理极限：单机性能存在摩尔定律以外的物理上限，内存带宽、总线速度、单磁盘 IOPS，都有天花板。

唯一的出路是 scale-out（横向扩展）：用成百上千台廉价的商用机器（commodity hardware），通过软件层把它们组成一个逻辑上统一的大机器。

这个思路说起来简单，但要真正做到”几千台机器协同工作，对外表现得像一台超大机器”，需要解决一系列从未被系统性解决过的问题：

  • 数据怎么分散存在多台机器上，又能被快速读取？
  • 某台机器随时可能宕机，数据怎么保证不丢？
  • 计算任务怎么拆分下发，结果怎么汇总？
  • 部分节点失败时，整个作业怎么继续？

Google 的工程师们，用三篇论文给出了答案。

Google 三驾马车：理论蓝图

2003—2006 年，Google 陆续发表了三篇论文，彻底改变了大规模数据处理的面貌。

GFS（2003）：解决”存不下”

Google File System 是一个运行在廉价商用机器集群上的分布式文件系统。它的核心设计哲学有几点，每一点都是对现实环境的直接回应：

① 大文件为主，小文件不是优化对象
GFS 的典型使用场景是几百 MB 到几十 GB 的大文件（爬虫产出的网页、日志、索引文件）。块（chunk）大小设为 64MB，远大于传统文件系统的 4KB 块。好处是大幅减少元数据量——元数据全放在内存里，一台 Master 就能管理 PB 级数据。

② 副本（Replication）而非 RAID
每个 chunk 默认在三台不同机器上保存副本。这与 RAID 的思路不同：RAID 是同机多盘冗余，防不了整机故障；三副本跨机器甚至跨机架，单节点宕机对可用性无影响，天然容忍节点失效。

③ 追加写（append）而非随机写
网页爬取、日志记录，都是持续追加数据，极少修改已写入内容。GFS 针对”一次写入、多次读取”的访问模式做了深度优化，放弃了通用 POSIX 文件系统的随机写语义。

④ 单 Master 管理元数据，简化设计
文件到 chunk 的映射、chunk 的位置，统一由一台 Master 节点维护。这是故意的简化：分布式 Master 会带来一致性噩梦，单 Master 只要放在内存里（元数据远比数据小），读写都极快，且逻辑简单。

MapReduce（2004）：解决”算不动”

光能存还不够，还要能算。Google 的 MapReduce 论文提出了一个优雅的分布式计算范式。

它的核心思想可以用一句话概括：把计算拆成两类操作——Map（映射/变换）和 Reduce（归约/聚合）——让框架自动处理并行、分发、容错，用户只管写业务逻辑。

这个抽象来自函数式编程（Lisp 里的 map 和 reduce），但被 Google 工程化成了一套可以在数千台机器上自动并行的运行时。

为什么是 Map + Reduce 这两步？因为这两步覆盖了大量数据处理模式：

  • Map：对每条输入记录独立做转换，输出中间键值对。无副作用，天然可并行。
  • Reduce：把相同 key 的所有中间值聚合起来。覆盖了统计计数、求和、Top-N 等高频需求。

中间有个关键步骤——Shuffle：把 Map 输出的中间结果，按 key 分组，发给对应的 Reducer。这是整个框架最复杂的部分，也是性能瓶颈所在（后面细说）。

BigTable（2006）：解决”查不快”

GFS 解决了大文件存储，但直接在 GFS 上做随机读写效率很低。Google 的 BigTable 在 GFS 之上构建了一个稀疏的、多维的、有序的分布式”宽表”。

BigTable 的关键设计是按 row key 字典序排列，范围查询（scan）高效；列族（column family）按需存储稀疏数据，不浪费空间。这是后来 HBase 的直接原型。

HDFS：GFS 的开源化

2006 年，Doug Cutting 和 Mike Cafarella 在雅虎工程师的支持下，用 Java 把 GFS 的思想实现为开源项目，这就是 HDFS（Hadoop Distributed File System）。

HDFS 和 GFS 的核心架构几乎一一对应：Master 变成了 NameNode，ChunkServer 变成了 DataNode，chunk 变成了 Block。

NameNode / DataNode 架构

NameNode 是什么？
NameNode 维护两类核心数据（全在内存）：

  1. 文件系统命名空间：文件树结构，文件→block 列表的映射；
  2. block 位置映射：每个 block 存在哪几个 DataNode 上（这部分不持久化到磁盘，而是由 DataNode 启动时上报重建）。

DataNode 是什么？
DataNode 是真正存数据的工作节点。它做三件事：

  1. 按 NameNode 指示存储 block；
  2. 每隔固定时间向 NameNode 发心跳，证明自己还活着；
  3. 周期性汇报自己持有哪些 block（block report）。

NameNode 的单点问题
这里有个明显的设计脆弱点：NameNode 是单点。如果 NameNode 宕机，整个集群无法读写任何文件。早期 Hadoop 靠 Secondary NameNode（实际上是”checkpoint 助手”，不是热备）来缓解，Hadoop 2.x 才引入了真正的高可用（HA）NameNode（Active/Standby 双节点 + ZooKeeper）。这个短板值得记住——分布式系统里的”单点元数据”是反复出现的痛点。

Block 分块与多副本

HDFS 默认 block 大小为 128MB（Hadoop 2.x 起，早期是 64MB）。一个 5GB 的文件会被切成约 40 个 block。

为什么要设这么大的 block？两个理由：

  1. 减少元数据：40 个 block 的元数据 vs 5GB 文件被切成 4KB 小块产生的 1.3M 条元数据，NameNode 内存压力天壤之别。
  2. 减少寻址开销：顺序读一个大 block，磁盘寻道开销摊薄到可忽略不计；如果 block 很小，大量时间浪费在磁盘寻道上。

代价是：HDFS 对小文件非常不友好。100 万个 1KB 文件，block 数仍是 100 万，NameNode 要存 100 万条元数据，内存告急，却只存了约 1GB 数据。这是 HDFS 长期以来的”小文件问题”。

“一次写入、多次读取”的设计取舍

HDFS 明确声明它针对”write-once, read-many”工作负载优化：

  • 不支持对已写入数据的随机修改（只支持追加，且早期版本连追加都不支持）；
  • 不提供 POSIX 语义的文件锁；
  • 不保证毫秒级写入延迟。

这些限制换来了：

  • 超高的顺序读吞吐（大 block + 流式读）；
  • 简单可靠的副本同步模型；
  • 极低的元数据成本。

对于”先存下来，再批量处理”的大数据离线分析场景，这些取舍是值得的。但对于需要低延迟随机读写的 OLTP 场景，HDFS 天生不适合。

MapReduce 计算模型

HDFS 解决了”存”的问题，MapReduce 解决”算”的问题。

三阶段：Map → Shuffle → Reduce

“移动计算，而非移动数据”

MapReduce 有一个极其重要的设计原则：data locality（数据本地性）。

在分布式集群里，数据和计算节点都是分散的。有两种做法：

  • 移动数据：把数据从存储节点传到计算节点；
  • 移动计算：把计算代码（Map/Reduce 函数）发送到数据所在的节点，就地执行。

网络带宽是集群最稀缺的资源（磁盘 IO 或内存 IO 要快得多）。在 GB 量级的数据面前，传输数据的网络开销远大于传输几 KB 代码的开销。

所以 MapReduce 的 JobTracker 调度 Map Task 时，优先把 Task 分配到持有对应 block 的 DataNode 上（或至少同机架），让计算在数据旁边执行，最大化利用本地磁盘 IO，最小化网络传输。

容错：任务失败就重算

分布式集群中节点随时可能宕机。MapReduce 的容错机制简单粗暴但有效：重算。

  • Map Task 失败：JobTracker 检测到（心跳超时），在另一台机器上重新启动该 Task，重新读取相应的输入 block。因为 Map 是无副作用的纯函数（同样输入必然产生同样输出），重算结果幂等。

  • Reduce Task 失败：同样重算。但 Reduce 依赖 Map 的中间输出，若 Map 中间结果还在，直接重新拉取；若对应 Map Task 所在节点也挂了，则先重跑 Map Task，再重跑 Reduce Task。

  • Straggler（掉队者）：某台机器因磁盘老化、负载过高，导致某个 Task 运行特别慢。MapReduce 会在接近结束时，对尚未完成的 Task 启动推测执行（speculative execution）——在另一台机器上并行执行同一个 Task，谁先完成就用谁的结果，另一个取消。

这种容错机制的前提是”计算是纯函数，重算代价可接受”。这个前提在批处理中完全成立，但给后来的”交互式查询”和”迭代算法”埋下了性能隐患。

MapReduce 的两大短板

Hadoop + MapReduce 在 2008—2012 年统治了大数据处理领域，但它骨子里的两个结构性缺陷，从一开始就存在，并最终催生了整个后续演进。

短板一：慢——每步中间结果必须落盘

这就是为什么 Hadoop 上跑机器学习是”炼狱级”体验，也是 Spark 内存计算后来能秒杀 MapReduce 的根本原因。

短板二：难用——万物皆 Map/Reduce 的编程模型

MapReduce 的抽象虽然优雅，但能力有限。很多现实中的数据处理逻辑，根本无法自然地映射到”一个 Map + 一个 Reduce”的范式上。

例子：多表 Join

SQL 里一行 JOIN，在 MapReduce 里需要：

  1. 用一个 MapReduce 作业读两张表，按 join key 分组；
  2. 在 Reducer 里手动实现 join 逻辑；
  3. 如果是多表 join，可能需要多个 MapReduce 作业串联。

例子：SQL 中一个常见的”按天分组、再 Top-N”查询

正是”慢 + 难用”这两大短板，驱动了整个大数据生态的演进：

  • Hive 出现，是为了让人用 SQL 描述逻辑（翻译成 MR），解决”难用”；
  • Pig 出现，是为了提供更高层的数据流语言，解决”难用”；
  • YARN 出现，是为了解耦资源管理和计算，让不同引擎可以共存；
  • Spark 出现，是为了用内存计算根治”慢”，同时用 DAG + 高层 API 解决”难用”。

小结：基石已立，裂缝已现

Hadoop 在 2006—2012 年完成了一件历史性的工作：把 Google 三篇论文中描述的分布式存储和计算能力，以开源的形式交到了整个工业界手中，让不依赖 Google 内部基础设施也能处理 PB 级数据成为现实。

这是真正的基石。没有 HDFS 的廉价可靠存储，后来的 Hive、HBase、Spark 就没有数据基础。没有 MapReduce 对”分布式计算是怎么回事”的示范，后来的 DAG 引擎就缺少参照系。

但裂缝从一开始就存在，且随着业务需求复杂化而扩大：

问题 根源 后续方案
每步落盘，迭代慢 MapReduce 的执行模型 Spark（内存 RDD + DAG）
编程模型僵硬，难用 Map/Reduce 两步抽象层次太低 Hive/Pig（高层语言），Spark（丰富 API）
资源管理与计算耦死 MR 1.0 的 JobTracker 包办一切 YARN（解耦资源管理）
只能批处理，无实时 落盘 + 调度开销决定分钟级延迟 Flink/Spark Streaming

Hadoop 告诉我们：分布式的代价是复杂性（副本同步、网络 Shuffle、容错重算），而复杂性换来的是规模——当数据大到单机存不下，这个代价不是选择题，是必答题。

下一篇，我们讲 YARN——那个把 MapReduce 从”资源霸主”降格为”普通应用”的关键一步，也是整个大数据生态从”Hadoop 独大”走向”百引擎共舞”的枢纽。
