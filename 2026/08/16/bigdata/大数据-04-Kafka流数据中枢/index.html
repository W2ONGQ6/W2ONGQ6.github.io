引子：为什么讲 Flink 之前先讲 Kafka

在板块三里，我们看到 Spark 用内存计算打破了 MapReduce 的磁盘瓶颈，把批处理速度提升了一两个数量级。但 Spark 有一个基因层面的局限：它是批处理原生的，流处理只能靠”微批（micro-batch）”来模拟——把数据流切成一个个小批次，按固定间隔触发一次批计算。

微批能凑合用，但它有一道无法逾越的延迟下限——批的时间间隔。想要真正的毫秒级流处理，微批帮不到你。这就引出了板块五的主角 Flink。

然而，在谈 Flink 如何计算之前，有一个更基础的问题必须先解决：数据从哪里来？

流式计算的本质是持续处理到来的事件。这意味着你需要一条”河流”，而不是一个”水桶”：

  • 数据源源不断地生产，不能因为计算引擎短暂宕机就永久丢失；
  • 多个下游消费者（Flink 作业、实时报表、数仓同步……）需要各自独立消费，互不干扰；
  • 如果计算出了 bug，需要从几小时前的某个时间点**重放（replay）**数据来修正结果；
  • 吞吐量必须能跟上生产侧的高并发写入。

传统消息队列（如 RabbitMQ）无法满足这些需求——它的语义是”消费即删除”，消息一旦被取走就从队列里消失，既不能回放，也难以支持多个独立的消费者各自维护进度。

Kafka 正是为了填补这个空白而生的。它不把自己定位成消息队列，而是一个分布式的、分区的、持久化的提交日志（distributed, partitioned, persistent commit log）平台。这个定位的转变，是流式时代最重要的基础设施革命之一。

核心抽象：提交日志（Commit Log）

理解 Kafka 的钥匙只有一个词：commit log。

数据库领域早就有 commit log（也叫 WAL，Write-Ahead Log）的概念——数据库在把数据改写到实际存储之前，先把操作追加写到一条日志里。这条日志有几个关键属性：

  1. 追加写（append-only）：永远在末尾追加，不修改已有的记录；
  2. 有序：日志里的每条记录都有一个单调递增的序号；
  3. 持久化：落盘，机器重启后仍在；
  4. 可重放：给你一个起始位置，你可以从那里开始重新”消费”整条日志。

Kafka 把这个抽象搬到了分布式消息领域，并以此为基础构建了整个系统。

与传统消息队列的根本差异

这个差异看似微小，实则颠覆了消息中间件的使用范式：

  • 消息不再是”易消耗品”，而是持久的历史记录；
  • 消费进度由消费者持有（offset），而不是由 broker 管理；
  • 同一批数据可以被多个消费者独立消费，互不影响；
  • 回放（replay）成为一等功能，只需把 offset 重置到某个历史位置即可。

这正是流式基础设施所需要的”河流”特质：水流过去了，但河床记得，你可以逆流而上。

架构详解

Topic、Partition 与 Offset

Topic 是逻辑上的数据分类，类似数据库的表名。一个 Kafka 集群里可以有成百上千个 Topic，每个 Topic 对应一类业务数据（用户行为日志、订单事件、传感器数据……）。

Partition 是 Topic 的物理分片，每个 Topic 在创建时被划分为若干个 Partition。每个 Partition 就是一条独立的 commit log：

Offset 是 Partition 内每条消息的序号，单调递增，从 0 开始。消费者通过记录”我消费到了哪个 Partition 的哪个 Offset”来跟踪自己的进度。

Partition 的存在让 Kafka 天然具备了水平扩展能力：不同 Partition 可以分布在不同的 Broker（节点）上，读写负载随 Partition 数量线性增长。

Producer：写入与分区路由

Producer 把消息写入指定 Topic。写入时需要决定消息落入哪个 Partition，路由策略有三种：

  • 指定 key：对 key 做哈希，相同 key 的消息落入同一 Partition，保证局部有序（如同一用户的所有事件顺序到达）；
  • 轮询（round-robin）：无 key 时默认轮询各 Partition，最大化吞吐；
  • 自定义 Partitioner：业务自定义路由逻辑。

Producer 默认批量发送——在本地累积一批消息后一次性发出，减少网络往返。批量大小和等待时间（batch.size、linger.ms）可调，是吞吐与延迟的权衡旋钮。

Consumer Group：并行消费与负载均衡

这是 Kafka 设计里最精妙的一个机制。

每个 Consumer 属于一个 Consumer Group。Kafka 保证：一个 Partition 在同一时刻只能被同一 Consumer Group 内的一个 Consumer 消费。

这个约束带来了自然的并行消费模型：

A、B、C 三个 Consumer Group 各自维护独立的 offset，互不干扰——同一批数据被三个下游”各取所需”，而 Kafka 不需要为此复制数据。这正是”解耦生产者与消费者”的精髓。

当 Consumer Group 内的消费者数量发生变化（节点宕机或扩容），Kafka 会触发 Rebalance：重新分配哪个消费者负责哪些 Partition。Rebalance 期间消费暂停，这是一个已知的延迟开销，较新版本的 Kafka 引入了增量式 Rebalance（Incremental Cooperative Rebalancing）来缩短暂停时间。

Broker 与 ISR 副本机制

Broker 是 Kafka 的服务端节点。一个 Kafka 集群由多个 Broker 组成，每个 Broker 存储若干 Partition 的数据。

单个 Partition 的数据只存在一台机器上显然不可靠。Kafka 为每个 Partition 维护多个副本（replica），其中一个是 Leader，其余是 Follower：

  • 所有读写请求都走 Leader；
  • Follower 从 Leader 异步拉取数据进行同步。

ISR（In-Sync Replicas，同步副本集合） 是核心的可靠性机制。ISR 是一个动态集合，包含”与 Leader 保持充分同步”的副本。判定标准是：Follower 在一定时间窗口内（replica.lag.time.max.ms）没有落后 Leader 超过阈值，就保持在 ISR 内；否则被踢出。

当 Producer 写入消息时，可以要求 Broker 等待 ISR 内所有（或指定数量）副本确认后再返回成功（acks=all）。这保证了即便 Leader 立刻宕机，ISR 内任意一个 Follower 晋升为新 Leader 后数据也不丢失。

这是 Kafka **”不丢消息”**承诺的底层实现：不是单点落盘，而是多副本 ISR 的集体确认。

ZooKeeper 与 KRaft

早期（2.x 及以前），Kafka 依赖 ZooKeeper 存储集群元数据（Broker 列表、Topic 配置、Partition Leader 信息、Consumer Group offset 等）。ZooKeeper 是一个独立的分布式协调服务，运维 Kafka 意味着同时运维两套系统。

从 Kafka 3.x 开始，社区推出了 KRaft 模式（Kafka Raft Metadata mode）：用 Kafka 内置的 Raft 协议自管理元数据，彻底去除 ZooKeeper 依赖。KRaft 模式在 3.3 起成为生产可用选项，在 4.0 起 ZooKeeper 模式已被移除。

KRaft 的好处不只是减少运维复杂度，更关键的是它解决了 ZooKeeper 成为扩展瓶颈的问题：ZooKeeper 在管理超大规模 Partition 时会成为性能瓶颈，KRaft 把这个上限大幅提高。

为什么快：四个设计决策的叠加

Kafka 能在普通机械磁盘上实现极高吞吐，是四个设计决策共同作用的结果。每一个单独看都不新鲜，但叠加在一起，就形成了”磁盘也能很快”的经典案例。

1. 顺序写磁盘

磁盘的随机 IO 很慢（寻道时间），但顺序 IO 可以达到接近内存的吞吐——现代机械硬盘的顺序写速度通常在 100–200 MB/s 量级，远高于随机写的几 MB/s。

Kafka 的 commit log 是 append-only 的：每次写入都追加到文件末尾，从不修改已有位置。这让 Kafka 的写入天然是顺序 IO，完美地规避了磁盘最贵的那部分开销。

与之对比，传统消息队列（如 RabbitMQ 的某些存储模式）需要维护复杂的索引结构，导致写入存在随机 IO；Kafka 用极简的追加写换来了极高的写入速度。

3. 批量压缩

Producer 在本地积累一批消息，打包成一个 batch 再发送。Broker 将整个 batch 作为一个单元落盘，Consumer 拉取也是按 batch 拉取。

批量处理有两重收益：

  • 减少网络往返次数：一次 RTT 传输大量消息，而不是每条消息一次 RTT；
  • 压缩率更高：相同类型的消息批在一起，重复字段多，压缩率远高于逐条压缩。

Kafka 支持 Snappy、LZ4、ZSTD 等压缩算法，实际使用中消息体积可以压缩到原始大小的 20%–50%，既节省网络带宽，也节省存储空间。

4. Page Cache 优先

Kafka 几乎不自己管内存缓存，而是将大量数据操作委托给操作系统的 Page Cache（内核管理的磁盘缓冲区）。当 Broker 写入消息时，数据先进 Page Cache；当 Consumer 消费近实时的数据时，很可能直接从 Page Cache 命中，根本不需要真正读磁盘。

这个设计有一个微妙的好处：Page Cache 在 Kafka 进程重启后仍然存在（它属于操作系统），而进程内自管的 JVM 堆缓存重启即清空。对于运行数月不停的生产集群，这意味着更稳定的缓存命中率。

交付语义：消息究竟会丢还是重复？

流式系统里，”消息不丢不重”是一个经典难题。Kafka 将其拆解为三个层次：

At-Most-Once（最多一次）

消息最多被处理一次，可能丢失，不会重复。

实现方式：Producer 发出后不等确认（acks=0），Consumer 拉取后立刻提交 offset，再处理消息。如果处理中途崩溃，消息丢失。

适用场景：对丢失容忍但对重复零容忍的场景（如日志采样）。

At-Least-Once（至少一次）

消息至少被处理一次，不会丢失，但可能重复。

实现方式：Producer 开启重试（acks=all + retries>0），Consumer 处理完消息后再提交 offset。如果处理成功但 offset 提交失败，崩溃恢复后会重新处理同一批消息。

这是绝大多数生产场景的默认选择，下游需要做幂等处理来应对重复。

Exactly-Once（精确一次）

消息恰好被处理一次，既不丢失也不重复。

这是最难实现的语义，Kafka 通过两个机制来支撑：

幂等 Producer（Idempotent Producer）：每个 Producer 实例有全局唯一的 Producer ID（PID），每条消息带有单调递增的序列号（Sequence Number）。Broker 检测到重复序列号时直接丢弃，从而去除 Producer 重试导致的重复写入。启用方式：enable.idempotence=true。

Kafka 事务（Transactions）：Producer 可以在一个原子事务里向多个 Topic/Partition 写入消息——要么全部成功，要么全部回滚。Consumer 端可以设置 isolation.level=read_committed，只读取已提交事务的消息，过滤掉中间状态。

这两个机制组合，使 Flink 等流引擎能在 Kafka-to-Kafka 的处理链路上实现端到端的 exactly-once——这是 Flink checkpoint 与 Kafka 事务深度配合的基础，板块五会详细展开。

Kafka 在数据架构中的角色

解耦：生产者与消费者的完全分离

没有 Kafka 的世界里，生产者和消费者必须直接对接：A 服务调 B 服务的接口，B 挂了 A 就堵死；B 需要扩容，A 的调用逻辑要跟着改。

有了 Kafka 之后：

生产者只管写入，不关心谁在消费；消费者只管从自己的 offset 读取，不关心谁在生产。双方通过 Kafka 这层”日志”完全解耦，独立部署、独立扩展、独立故障。

可重放：修复 bug 的超能力

传统消息队列消费即删除，一旦消费者处理时存在 bug，那批消息永久丢失，无法回头。

Kafka 的消息保留在日志里（默认 7 天，可调），任何时候都可以：

  1. 把消费者的 offset 重置到某个历史时间点；
  2. 重新消费那段时间的所有数据；
  3. 把修复 bug 后的正确结果写入下游。

这个”时间旅行”能力在生产环境里价值巨大——它把”数据处理错了怎么办”从一个灾难级问题变成了一个日常运维操作。

Kappa 架构是 Lambda 的简化版，去掉批处理层，只保留流处理层：

当需要重新计算时，直接从 Kafka 历史日志重放，用流处理引擎处理完整历史数据。这成立的前提，正是 Kafka 的长期保留能力——日志足够长，Kappa 就能替代批处理层。

没有 Kafka 这条可重放的”数据河流”，Kappa 架构是无法成立的。

Kafka 作为 Flink 的典型 Source/Sink

Flink 与 Kafka 的配合几乎是现代流式架构的标准范式：

  • Flink 作为 Consumer：Flink 作业的每个并行实例对应若干 Kafka Partition，天然并行；Flink 的 checkpoint 时机与 Kafka offset 提交绑定，实现端到端 exactly-once；
  • Flink 作为 Producer：Flink 计算结果写回 Kafka 的下游 Topic，供其他系统消费；
  • 可重放 + 可恢复：Flink 作业失败后从 checkpoint 恢复，重置 Kafka offset 到对应位置，从那里重新消费，保证状态一致性。

这个组合的深度整合，是”真正的流式计算”成为可能的基础设施前提，也是板块五要深入展开的内容。

小结

Kafka 在大数据发展主线上解决的是一个基础设施级的问题：如何为流式计算提供一条”持续、可靠、可重放”的数据供给。

它的核心贡献可以归结为三点：

  1. 用 commit log 重新定义消息中间件：从”消费即删除的队列”升级为”持久化的、可多消费者独立消费的分布式日志”，让消息不再是易耗品，而是历史记录。

  2. 用顺序写、零拷贝、批量压缩、Page Cache 四个机制的叠加，在普通磁盘上实现了极高吞吐，证明了”存储介质的快慢不全由硬件决定，访问模式同样关键”。

  3. 用 Consumer Group + offset 机制实现了生产者与消费者的彻底解耦，以及多下游的并行独立消费，让同一份数据可以同时服务实时计算、批量同步、风控分析等多个截然不同的场景。

Kafka 把”数据河流”这个问题解决了。河床铺好、水流稳定、可以随时回溯。现在，流式计算引擎终于有了一个足够稳固的数据基础。

数据就位，下一步是如何正确地计算它——这正是板块五 Flink 要回答的问题：event-time、watermark、exactly-once 状态，以及”批是有界的流”这一统一世界观。
