大数据-05：Flink —— 真正的流式与批流统一

一、引子：Spark 微批的天花板

上一篇讲 Kafka 时，我们建立了”数据是持续流动的河流”这一认知。现在的问题是：谁来消费这条河流？ Spark Streaming 是第一个广泛使用的答案，但它留下了一道裂缝，这道裂缝最终逼出了 Flink。

微批是什么

Spark Streaming 并不是”真正的”流处理。它的做法是把时间轴切成一段一段的小批次（比如每 500ms 一批），每个批次触发一个普通的 Spark 批处理作业，结果看上去像是在”持续处理”，但本质是批处理的快速轮转。这种设计被称为微批（micro-batch）。

微批的好处是显而易见的：Spark 的批处理引擎可以直接复用，容错机制、调度机制全都天然继承，工程实现代价很低。在 Spark Streaming 出现之前，真正的流处理要么依赖 Storm（无状态、exactly-once 很难做到），要么自研，Spark Streaming 以相对低的延迟（秒级）换来了工程上的极大简化，一度被认为足够用了。

裂缝在哪里

问题出在两个地方，而且它们相互关联：

第一，延迟的天花板。微批的最低延迟受限于批的间隔。间隔设得越小（比如 100ms），每个批次的调度开销占比越高，系统负担急剧上升；设得越大，延迟越高。这意味着微批在毫秒级延迟的场景下力不从心。金融风控、实时推荐、IoT 告警，这些场景对延迟的敏感度比秒级要高得多。

第二，event-time 的噩梦。这是更本质的问题，值得细讲。

现实数据的乱序问题

设想一个典型场景：你在统计每分钟的用户点击量。用户的每一次点击，设备会记录一个时间戳——这叫事件时间（event-time），即事件真正发生的时刻。数据从设备发出，经过网络、消息队列，到达你的流处理系统时，已经过了一段时间——这叫处理时间（processing-time）。

在理想情况下，两者差距很小，可以忽略。但现实中：

  • 用户手机处于弱网环境，点击事件攒了 30 秒才一起上报
  • 某个 Kafka partition 的消费者短暂落后，追赶时一次性涌入大量旧数据
  • 不同地区的数据中心，时钟可能有几十毫秒的偏差
  • 设备离线后重新上线，把离线期间产生的事件一次性补发

结果是：一个”应该属于 12:00:00–12:01:00 这个窗口”的事件，可能在 12:01:30 才到达你的处理系统。

Spark Streaming 在这里遇到了根本性困难。微批是按处理时间切割的，它根本不知道”某个批次的数据里，有些事件的 event-time 其实属于上一个窗口”。你可以在 Spark Streaming 里手动补偿，但代码极其复杂，而且往往无法精确。

这就是 Spark 微批的天花板：它没有一等公民的 event-time 语义。

二、流式原生：Flink 的 DataStream 模型

Flink 不是从批处理改造而来的，它从一开始就是为流式计算设计的。这个基因差异导致了截然不同的架构选择。

一次一个事件

Flink 的基本执行单元是单条记录，而不是批次。一条数据进入系统，就立刻被处理，产生输出（或更新状态），然后等待下一条。这叫做真流式（true streaming）或事件驱动（event-driven）。

这个区别不仅是延迟的量变，而是整个处理模型的质变。在 Flink 里，延迟可以做到毫秒级甚至亚毫秒级，因为中间没有”等凑批”这一步。

三、时间语义：event-time 与 watermark（重点）

这是 Flink 最核心、也最能体现其设计哲学的部分。理解了 event-time 和 watermark，就理解了 Flink 为什么比微批”正确”。

三种时间语义

Flink 明确区分三种时间：

时间类型 含义 优缺点
processing-time 数据到达处理系统的时刻（系统时钟） 实现简单，但在数据乱序时语义不正确
ingestion-time 数据进入 Flink source 的时刻 介于两者之间，较少使用
event-time 事件真正发生的时刻（数据里的时间戳字段） 语义正确，能正确处理乱序，但需要等待迟到数据

为什么 event-time 才是正确的？

考虑一个统计”每小时下单量”的报表。如果用 processing-time，那么 23:59 下的单、由于网络延迟在 00:01 到达系统，就会被算到下一个小时——报表数据是错的。如果用 event-time，则按订单里的创建时间戳来分桶，无论何时到达，都会被正确地计入对应小时。

event-time 的代价：你必须等待。你永远不知道”这个时间窗口的所有数据是否都到了”，因为网络上可能还有迟到的数据在路上。这就是 watermark 要解决的问题。

Watermark：界定”迟到”的时钟

Watermark 是一个特殊的标记，随数据流一起流动，含义是：

“截至目前，event-time 在 W 之前的数据，我已经看到足够多了，可以认为不会再有新的了。”

换句话说，watermark(W) 是 Flink 对”当前 event-time 进度”的一个保守估计。当 watermark 推进到 W 时，Flink 会触发所有结束时间 ≤ W 的窗口计算。

四、状态与容错：有状态流计算与 exactly-once（重点）

流处理最难的不是计算本身，而是如何在分布式环境下保证计算结果的正确性。Flink 的答案是：有状态算子 + 分布式快照。

什么是有状态流计算

不是所有的流处理都需要状态。一个简单的 map(event -> event.userId.toUpperCase()) 是无状态的，每条数据独立处理，不依赖历史。

但稍微复杂一点的场景都需要状态：

  • 聚合（窗口求和、计数）：需要记住这个窗口目前已经累积了多少
  • 连接（join 两条流）：需要缓存一条流里的数据，等另一条流的对应数据到达
  • 去重（exactly-once 语义）：需要记住哪些事件已经处理过了
  • 机器学习（在线学习）：需要维护模型的中间状态

Flink 把算子维护的数据叫做状态（State）。每个算子实例有自己的状态，按 key 分片（和 keyBy 对应），状态可以是键值对（ValueState）、列表（ListState）、Map（MapState）等多种形式。

容错的挑战

在分布式系统里，节点随时可能崩溃。如果一个有状态的算子崩溃了：

  • 重启之后，它的状态是什么？ 如果状态丢失，则这个算子从空状态重新开始，会漏掉已处理的数据（at-most-once）
  • 如果从 Kafka 重新消费，重放数据，会不会重复处理某些事件，导致计数偏高（at-least-once）
  • 能不能做到精确一次（exactly-once），即每条数据恰好被处理一次，状态和输出都正确？

exactly-once 是流处理里最难的保证，Flink 用分布式快照来实现它。

Chandy-Lamport 分布式快照

理解 Flink 的 Checkpoint 机制，需要先理解 Chandy-Lamport 算法（1985 年提出，是分布式系统的经典算法）。

Chandy-Lamport 算法解决的问题是：如何在一个分布式系统运行过程中，不停止系统、不全局同步，拍一张一致的”全局快照”？

直觉上，”一致的全局快照”意味着：如果你把快照里各节点的状态拼在一起，它应该对应某一个合法的系统状态（就像你按了暂停键那一刻的快照）。难点在于，各节点的时钟不同步，你没法让所有节点”同时”记录状态。

Chandy-Lamport 的解法是引入一个**标记（Marker）**在消息通道里传播。当一个节点收到 Marker 时，它立刻记录自己的状态；同时，Marker 之前通道里”在路上”的消息，也要被记录进快照（因为这些消息的发出发生在快照之前，但还没被接收）。

Flink 的 Checkpoint 机制与 Barrier

Flink 用 Barrier 来实现类似 Chandy-Lamport Marker 的功能。

Barrier 是一种特殊记录，由 JobManager 周期性地注入到每个数据源（Source）的数据流中。

几个关键点：

Barrier 对齐（Barrier Alignment）：当一个算子有多个上游时，它必须等到所有上游的同一个 Barrier 都到达，才能触发快照。在等待期间，已经到达的那个上游的后续数据会被缓冲，以确保快照的一致性。这个等待过程叫做 Barrier 对齐。

为什么对齐能保证 exactly-once？

  • Barrier 对齐确保：快照里的状态，对应的是”处理了 Barrier 之前所有数据、但没有处理 Barrier 之后任何数据”的系统状态
  • 如果发生故障，从这个一致的快照恢复，然后从对应的 Kafka offset（也存在快照里）重新消费 Barrier 之后的数据
  • 由于 Barrier 之后的数据尚未被计入快照状态，重放这部分数据不会造成重复
  • 由于 Barrier 之前的数据已经被计入快照状态，恢复后不会重新处理，也不会漏掉

State Backend

状态需要持久化存储，Flink 支持多种 State Backend：

  • HashMapStateBackend：状态存在 TaskManager 的 JVM 堆内存里，快照时序列化到远端存储（如 HDFS、S3）。适合状态较小的场景，访问速度快。
  • EmbeddedRocksDBStateBackend：状态存在本地的 RocksDB（嵌入式 KV 存储），支持超大状态（可以远超内存大小），快照时将 RocksDB 的 SST 文件上传到远端。适合状态极大的场景（如数十 GB 的状态），访问速度相对慢一些，但支持增量快照，快照效率更高。

五、世界观之争：”批是有界的流” vs “流是连续的批”

这不只是哲学问题，而是决定了两个系统在批流统一上的能力边界。

Spark 的世界观：流是连续的批

Spark 诞生于批处理，流处理是后来加上去的。它的自然思路是：把无界的流切成一段一段的有界批次，复用批处理引擎。这就是微批。

这个世界观有一个内在矛盾：批和流是两种不同的执行模式。Spark Streaming（基于 RDD 的 DStream API）和 Spark 批处理是分开的；后来虽然有了 Structured Streaming（基于 DataFrame），但底层仍然是微批（或基于连续处理的实验性模式），在 event-time 语义、延迟、状态管理上都有不同程度的妥协。

Flink 的世界观：批是有界的流

Flink 的出发点完全相反：流是第一公民，批只是流的一个特例——有界（bounded）的流。

这个视角的优雅之处在于：

  • 流式引擎天然可以处理有界数据（数据耗尽时作业结束）
  • 批处理和流处理共享同一套 API、同一套执行引擎、同一套状态管理和容错机制
  • 不需要为批处理和流处理分别维护两套代码

这一视角的实际意义：你可以用完全相同的 Flink SQL 或 DataStream 代码，既处理实时的 Kafka 数据流，又处理 HDFS 上昨天的历史数据——代码不变，只换数据源。

六、架构演进：Lambda → Kappa → 批流统一

理解了 Flink 的设计哲学，我们就可以理解它如何推动了数据架构的演进。

Lambda 架构：两套代码的维护地狱

Lambda 架构是在 Flink 成熟之前，业界最流行的大数据架构模式，由 Nathan Marz 提出（约 2011 年）。它的思路是：同时跑两套管道，用准确性换延迟。

  • 批处理层：定期（如每天）对全量数据跑一次准确的批处理，产出”完全正确”的历史视图
  • 速度层：实时消费 Kafka，产出”最近几小时的近似结果”（因为流处理难以做到完全精确）
  • 服务层：查询时合并批处理视图（历史部分）和速度层视图（近期部分）

Lambda 架构解决了”既要低延迟、又要准确”的矛盾，但代价极高：

  1. 两套代码：同一个业务逻辑（比如”按页面统计点击量”）需要用 Spark 写一遍批处理逻辑，再用 Storm/Spark Streaming 写一遍流处理逻辑
  2. 两套逻辑难以保持一致：批处理和流处理的语义细节（如边界处理、去重逻辑）一旦不同步，就会出现”批流结果对不上”的问题，调试极为痛苦
  3. 运维成本翻倍：两套系统各自的部署、监控、调优、故障处理

Kappa 架构：一套流式代码

Kappa 架构由 Jay Kreps（Kafka 的作者）于 2014 年提出，核心思想是：把批处理层干掉，只用流处理层来做一切。

Kappa 架构的前提是两点：

  1. Kafka 能长期保存数据（或者 S3 等对象存储上有数据备份），以便需要时可以重放
  2. 流处理引擎足够精确，event-time 语义正确、exactly-once 有保证——这正是 Flink 提供的

有了 Flink，Kappa 架构变得可行：批处理和流处理不再是两套系统，而是同一套 Flink 作业跑在不同的数据源上。日常时，它消费 Kafka 实时数据；需要历史回算时，换个 Source 读 HDFS/S3 上的历史文件，代码逻辑完全不变。

Flink 的批流统一 API

Flink 1.9 之后，DataStream API 和 DataSet API（批处理专用 API）开始走向合并，最终在 Flink 1.12 实现了DataStream API 的批流统一：同一段 DataStream 代码可以运行在流模式（处理无界流）或批模式（处理有界数据，带批量优化）。

七、小结：Flink 完成了计算侧的批流统一

回顾一下 Flink 的核心贡献，以及它在大数据发展主线里的位置：

Flink 解决了什么？

问题 Flink 的答案
Spark 微批延迟高 真流式，一次一个事件，毫秒级延迟
event-time 处理复杂 一等公民的 event-time + watermark 机制
分布式容错难保证 exactly-once Chandy-Lamport 分布式快照 + Barrier 对齐
批流两套代码维护地狱 “批是有界的流”世界观，DataStream/SQL 批流统一
Lambda 架构复杂度高 支持 Kappa 架构，一套代码处理实时+历史

Flink 在发展主线里的位置：

但还有一个问题没解决：计算统一了，存储层还是割裂的。

Flink 作业跑完，数据写到哪里？写到 HDFS 上的 Parquet 文件？那就没有 ACID，没法更新，批流两个作业写同一份数据会打架。写到数据库？吞吐量撑不住大数据量。

这就是下一篇要讲的问题：存储层的革命——从 Hive 到 Parquet，从 Parquet 到 Iceberg/Hudi/Delta Lake，最终实现湖仓一体。计算侧和存储侧的批流统一，要在板块六才能真正收束。
