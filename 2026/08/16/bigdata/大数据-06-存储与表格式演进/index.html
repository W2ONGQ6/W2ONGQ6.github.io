大数据-06：存储与表格式演进 —— 从文件到湖仓一体

一、引子：计算飞奔，存储原地踏步

读到本篇，你已经跟随这条主线走了很远：HDFS 解决了”存不下”，MapReduce/YARN 解决了”算不动”，Spark 解决了”磁盘太慢”，Kafka 提供了可靠的数据流，Flink 实现了真正的流式处理与批流统一。计算层的每一场革命都紧接着上一代的短板，逻辑清晰，势如破竹。

然而，翻回头看存储层，却发现它几乎停在原地。从 Hadoop 诞生，到 Spark 大行其道，整整十年里，数据依然是 HDFS 上一堆裸文件——无论你的计算引擎多么先进，最终要读写的，还是那些散落在 NameNode 目录树下的 /user/hive/warehouse/orders/dt=2024-01-01/ 文件夹。

这并非无伤大雅的小事。裸文件方案积累了三宗根本性的罪：

第一宗罪：没有 SQL，难用。HDFS 原生只有文件系统 API——put、get、ls。分析师无法说”给我过去 30 天来自北京用户的订单总金额”，他必须先写一段 Java/Python 代码，明确告诉 MapReduce 去哪个目录、读哪些文件、如何解析。这对熟悉 SQL 的数据分析师是一道不可逾越的门槛。

第二宗罪：行存不适合分析，慢。早期数据通常以文本（CSV、JSON）或行式二进制（SequenceFile）格式存储——一行记录连续存放，这很自然，因为写入时数据是一行行来的。但分析型查询（OLAP）的特征是宽表少列：一张订单表有 200 个字段，但一个分析查询往往只需要 5 个。行存会强迫你把 200 个字段全部读进内存，再丢掉 195 个——95% 的 IO 是浪费。

第三宗罪：没有 ACID，无法更新。文件一旦写入 HDFS，实际上是不可修改的。你想更正一条错误的订单记录？需要把整个分区文件读出来，修改，再写回去，手动替换。并发写入没有隔离机制——两个 ETL 任务同时写同一个目录，会产生数据重叠或不完整的文件，下游读到的数据可能是半截。更别提”回滚”——一旦写坏，只能靠备份恢复。

这三宗罪，就是存储层三十年演进的驱动力：

下面，我们沿着这条线，逐层讲透每一步为什么不够、下一步解决了什么。

二、Hive：在文件上套一层”表的幻觉”

2.1 Hive 的诞生背景

2008 年，Facebook 的数据工程师面临一个现实困境：公司每天产生海量日志数据，Hadoop 集群在跑，但使用门槛极高——每一个分析任务都要求工程师编写 Java MapReduce 程序。数据分析师懂 SQL，不懂 Java；即便懂，每个分析问题都从零写 MapReduce 也是效率灾难。

Hive 的解法很朴素：不改变底层存储（HDFS + 文件），但在上面套一个”表”的抽象，允许用 SQL（HiveQL）来描述查询意图，由 Hive 编译器把 SQL 翻译成 MapReduce（后来也支持 Tez、Spark）提交执行。

2.4 Hive 解决了什么、留下了什么

Hive 的贡献是决定性的：它让 SQL 进入了 Hadoop 生态，让数据分析师不需要学 Java 就能分析大数据，直接催生了整个”数仓”层面的大数据应用。

但 Hive 有两个根本性局限，源于它的”套皮”本质：

其一，仍然是 HDFS 文件，没有事务。Hive 的表只是 Metastore 里的元数据加上 HDFS 上的文件。写入一条记录，本质上是往某个目录 append 一个文件；删除一条记录，需要重写整个分区。Hive 3.x 引入了有限的 ACID 支持（基于 delta file 方案），但性能开销大、使用场景受限，并未被广泛采用于高并发更新。

其二，性能受限于执行引擎和存储格式。早期 Hive 用 MapReduce，延迟以分钟计。即便后来换成 Tez 或 Spark，查询依然受限于读取全量列的行式存储。

这两个局限，分别指向了下面两个方向的补丁：列式存储解决性能，表格式解决 ACID。

三、Parquet 与 ORC：列式存储与分析性能的飞跃

3.1 行存 vs 列存：一个直觉模型

在理解列式存储之前，先想清楚一张简单的表在磁盘上可以怎么排列。

读一行很快，适合 OLTP（事务型系统，如电商下单、银行转账），因为事务操作通常是”找到这一行，更新这一行”。

列式存储（Column-Oriented）按列排列，每列连续：

读一列很快，适合 OLAP（分析型查询），因为分析查询通常是”统计某几列的聚合值，忽略其他列”。

3.2 列存为什么适合 OLAP——三个关键机制

机制一：列裁剪（Column Pruning）

分析查询 SELECT city, SUM(amount) FROM orders WHERE status='paid' 只用到 city、amount、status 三列。

  • 行存：必须把所有 5 列全读进内存，再丢掉不需要的 2 列。读了 5 列的 IO，用了 3 列。
  • 列存：只读 city、amount、status 三列的磁盘块，order_id 和 user_id 的块完全不读。

数据越宽（列越多），列裁剪的收益越大。生产环境中宽表动辄几百列，列裁剪可以把 IO 缩减 90% 以上。

机制二：高压缩率（Encoding + Compression）

同一列的数据类型一致、值域相近，压缩效果远好于行存：

  • status 列只有几种枚举值（paid/pending/cancelled），可以用字典编码：用整数 0/1/2 替代字符串，再 RLE（Run-Length Encoding）压缩连续相同值。
  • user_id 列是递增整数，可以用 Delta 编码：只存相邻差值，大幅降低存储空间。
  • 数值列可以利用 ZSTD、Snappy 等通用压缩算法，列内数据分布一致，压缩比远高于混杂行数据。

更小的磁盘占用，意味着同样的 IO 带宽能读取更多逻辑数据，查询吞吐直接提升。

机制三：谓词下推（Predicate Pushdown）

Parquet/ORC 为每个列块（Row Group）存储统计元数据：min 值、max 值、null 计数，有时还有 Bloom Filter。

当查询条件是 WHERE amount > 1000 时，查询引擎在读取数据之前，先读列块的统计信息：如果某个 Row Group 中 amount 列的 max 值是 500，那么这整个 Row Group 一定不包含满足条件的行，直接跳过，不读磁盘。这就是谓词下推到存储层。

这三个机制叠加，让列式存储在 OLAP 场景下比行存快 5x～50x，具体取决于查询的列选择率和过滤条件。

3.3 Parquet vs ORC：两者的选择

Parquet 和 ORC 都是列式存储格式，原理相同，差异在于细节：

维度 Parquet ORC
起源 Cloudera + Twitter，2013 Hortonworks，2013，为 Hive 优化
生态支持 Spark、Flink、Arrow、Pandas 等广泛支持 Hive 生态最成熟，Spark 也支持
嵌套结构 原生支持（Dremel 编码），对 JSON 类嵌套数据友好 支持，但实现略有不同
典型压缩 Snappy（默认）、ZSTD、GZIP ZLIB（默认）、Snappy、ZSTD
适用倾向 Spark/Flink 生态，现代数据湖 Hive 重度用户，纯 ORC 仓库

现代数据湖和湖仓架构（Iceberg/Delta/Hudi）几乎都默认使用 Parquet，因为 Arrow 生态的支持使跨引擎互操作更简单。ORC 在纯 Hive 环境中仍然广泛使用。

列式存储彻底解决了”行存太慢”的问题。但它还是文件——你仍然无法 UPDATE 一行、无法在两个 writer 并发写入时保证原子性、无法回滚到昨天的状态。这就到了表格式的故事。

四、数据湖表格式革命：Iceberg、Hudi 与 Delta Lake

4.1 为什么需要表格式——数据湖的阿喀琉斯之踵

在表格式出现之前，整个大数据生态有一个奇特的分裂：

  • 传统数据仓库（Teradata、Redshift、Snowflake 等）有 ACID、有 schema 管理、有事务，但是封闭、昂贵、不开放——数据被锁在专有系统里，格式不透明，换引擎需要迁移数据。
  • 数据湖（HDFS/S3 上的 Parquet 文件）开放、廉价、灵活——任何引擎都能读，格式标准开放，但没有 ACID、没有事务、没有统一 schema 管理。

两者在根本上是对立的。Databricks 的论文（2020）把这个矛盾总结为：数据湖是廉价的、开放的，但靠不住的（cheap, open, unreliable）；数据仓库是可靠的，但昂贵的、封闭的（reliable, expensive, proprietary）。

表格式的设计目标，就是在数据湖的文件之上，用一个开放的元数据层，把数据库的可靠性搬过来，同时保留数据湖的开放性。

4.2 核心思想：在文件之上加一层”事务日志”

理解三大表格式的本质，关键是理解它们共同的思想——把”表是什么状态”的信息从文件名/目录结构里分离出来，放进一个结构化的元数据层。

传统 Hive 的”表状态”记录方式：

这个方式有根本性问题：目录列举（ls）是 NameNode 的操作，对于几百万个文件的大表极慢；两个 writer 同时往目录写文件，没有协调机制，可能互相覆盖；你无法知道”昨天这张表长什么样”。

表格式的思路：

写操作的原子性来自元数据的原子提交：写数据文件（不可变的 Parquet 文件），然后原子替换一个元数据指针。如果提交失败，旧版本的元数据还在，表状态回到提交前——ACID 中的 A（原子性）天然保证。

时间旅行来自历史快照的保留：每次写操作产生一个新的快照，旧快照不立即删除，你可以用 AS OF TIMESTAMP 或 VERSION AS OF N 来查询任意历史版本。

下面逐一看三个主要表格式的具体实现思路。

4.3 Apache Iceberg：以”表规范”为核心

Iceberg 诞生于 Netflix，2018 年开源。它的设计目标是成为一个跨引擎的开放表规范——任何引擎（Spark、Flink、Presto、Trino、Hive）只要实现了 Iceberg API，就能读写 Iceberg 表，且语义保证一致。

这个结构带来几个关键能力：

隐藏分区（Hidden Partitioning）：Hive 要求用户在写 SQL 时显式指定分区字段（WHERE dt = '2024-01-01'），且分区字段必须是物理列。Iceberg 允许定义”分区变换”——例如对 event_time 列做 days(event_time) 变换，写入时自动分区，读取时查询引擎根据过滤条件自动推断跳过哪些分区，用户完全不感知分区的存在。这解决了 Hive 中”忘写分区条件导致全表扫描”的常见性能陷阱。

Schema 演进：可以安全地 ADD COLUMN、DROP COLUMN、RENAME COLUMN、MODIFY TYPE，旧文件按旧 schema 读，新文件按新 schema 读，引擎透明处理兼容性。而 Hive 的 schema 变更有时需要重写数据或修改文件头。

ACID 与并发控制：基于乐观并发控制（OCC）——多个 writer 可以并发写，提交时检查是否有冲突（如两个 writer 都修改了同一批文件），有冲突则后一个提交失败并重试。不会有”脏读”或文件互相覆盖的问题。

时间旅行：保留历史 snapshot，可以 SELECT * FROM orders FOR SYSTEM_TIME AS OF '2024-01-01 00:00:00'，或 FOR SYSTEM_VERSION AS OF 12345（snapshot id）。

4.4 Apache Hudi：以”增量更新”为核心

Hudi（Hadoop Upserts Deletes and Incrementals）诞生于 Uber，2016 年起用，2019 年开源。它的核心设计出发点是：数据湖中有大量的 upsert（update or insert）场景——比如数据库 CDC 同步（数据库里的行被更新了，数据湖也要反映），或者订单状态变更（从 pending 变成 paid）。

Hudi 围绕增量数据处理设计了两种存储类型：

Copy-On-Write（COW）：每次 upsert，找到含有待更新记录的 Parquet 文件，复制一份新文件（包含更新后的版本），原文件标记为旧版本。读取时只读最新文件。写放大（Write Amplification）较高，但读性能最优（纯 Parquet，无需合并）。

Merge-On-Read（MOR）：增量写入到小的 delta log 文件（Avro 格式），base 文件（Parquet）不动。读取时”实时合并”base 文件和 delta log——这叫 Snapshot 读，延迟稍高；也可以仅读 delta log 获得”增量读”，只拿上次 checkpoint 后的变化数据。定期 Compaction 任务合并 base 和 delta，还原成纯 Parquet。

Hudi 的 Timeline（时间轴）是它的事务日志，记录所有操作（commit/deltacommit/compaction/rollback）的历史，是 ACID 和时间旅行的基础。

Hudi 还引入了 Record-Level Index（记录级索引）的概念，默认使用布隆过滤器（Bloom Filter）记录每个文件包含哪些 record key，使 upsert 时能快速定位需要更新的文件，而不是扫描全表。

Hudi 的增量查询能力也是区别于 Iceberg 的一个设计重点——你可以精确地查询”某个时间点之后新增/更新的行”，这对 CDC 同步、下游实时更新场景非常友好。

4.5 Delta Lake：以”生态整合”为核心

Delta Lake 由 Databricks 开发，2019 年开源，是三者中与 Apache Spark 绑定最深的方案。它的设计哲学是在 Spark 生态内提供最一流的 ACID 和可靠性体验，与 Databricks 平台深度集成。

Delta Lake 的元数据层是一个 Transaction Log（事务日志），存储在表目录的 _delta_log/ 子目录下：

每个 JSON commit 文件记录了这次操作”添加了哪些文件、移除了哪些文件”（add/remove actions）。重建当前表状态，只需从最近一个 checkpoint 开始，重放后续的 commit log。

Delta Lake 的核心能力：

  • ACID 事务：基于乐观并发控制，支持多个并发写入（需要处理 conflict resolution）。
  • 可扩展元数据（Scalable Metadata）：对于有数百万文件的超大表，Delta Lake 利用 Spark 自身来并行处理元数据操作，而不是单点 Metastore——这是它在超大规模场景下的一个重要工程优化。
  • 时间旅行：SELECT * FROM orders VERSION AS OF 5 或 TIMESTAMP AS OF '2024-01-01'。
  • Z-Order 聚合：Delta Lake 支持 OPTIMIZE ... ZORDER BY (col1, col2) 命令，把相关数据聚合到同一批文件中，配合 Data Skipping（基于文件级 min/max 统计），对多列过滤查询有显著加速效果。
  • Change Data Feed（CDF）：类似 Hudi 的增量读，可以读取指定版本区间内的行级变化（插入/更新/删除），便于下游增量处理。

三者的定位总结：

Iceberg Hudi Delta Lake
设计重心 开放表规范，跨引擎 高效 upsert / CDC 同步 Spark 生态深度集成
特色能力 隐藏分区、schema 演进 Record-Level Index、增量读 Z-Order 优化、Databricks 平台
引擎生态 Spark/Flink/Trino/Hive Spark/Flink Spark（最优），Flink 支持中
社区 Apache 顶级项目 Apache 顶级项目 Linux Foundation 项目

三者都在积极互相借鉴，差异在缩小。在技术选型时，更重要的是你的主力引擎和核心场景：CDC 写多用 Hudi，多引擎互操作优先选 Iceberg，Databricks/Spark 重度用户选 Delta Lake。

五、湖仓一体：两条线的最终汇合

5.1 “湖仓一体”这个词在说什么

Lakehouse（湖仓一体）这个概念由 Databricks 在 2020 年的论文中正式提出，但它描述的是一种架构范式，而非特定产品。它的目标是：

在同一套存储系统上，同时获得数据湖的开放性与低成本，以及数据仓库的ACID 可靠性与性能。

两条路线向中间汇聚，交汇点就是湖仓一体：以开放格式（Parquet）存储在廉价对象存储（S3/ADLS/GCS）上，用表格式（Iceberg/Delta/Hudi）提供 ACID 和事务语义，让多种计算引擎（Spark/Flink/Trino/DuckDB）直接读取，无需数据迁移。

5.2 存储侧的批流统一：与 Flink 的遥相呼应

这里有一条深层的对应关系，值得细说。

板块五讲的 Flink：批流统一发生在计算层。Flink 的世界观是”批是有界的流”——同一套代码，同一个算子，既能处理实时流数据，也能处理有界的批数据。Lambda 架构里”批处理一套代码、流处理一套代码”的分裂，被 Flink 在计算层化解了。

湖仓一体（表格式）：批流统一发生在存储层。在表格式之前：

  • 实时流数据写入 Kafka，或写到单独的实时数仓（Druid/ClickHouse），这是”流存储”；
  • 历史批量数据存 HDFS/S3 上的 Parquet 文件，这是”批存储”；
  • 批流两套存储，数据需要定期同步，存在不一致窗口，运维成本极高。

有了湖仓一体（以 Iceberg 为例），Flink 可以直接把流数据实时写入 Iceberg 表（Flink-Iceberg connector），同时 Spark/Trino 对同一张 Iceberg 表做批量分析查询——流写批读，发生在同一张表上，不需要”流存储同步到批存储”这道工序。

更进一步，Flink 的 Streaming Lakehouse 正在成为实践方向：Flink 流式消费 Kafka，实时写入 Iceberg 表（支持分钟级延迟的”近实时”入湖），下游分析直接查 Iceberg——彻底消灭了 Lambda 架构中两套存储、两套代码的双重负担。

5.3 湖仓一体的技术架构层次

这个四层架构的关键特征：每一层都是开放标准，可以被不同产品替换，层与层之间通过开放 API 交互。这和传统数据仓库”打包售卖整个栈”的思路截然不同——湖仓一体的本质是关注点分离（separation of concerns）：存储便宜、格式开放、协议标准、引擎可换。

六、结语：收束整条主线

6.1 五个瓶颈，五次突破——一条完整的因果链

回顾这六个板块走过的路：

每一步都不是凭空冒出的技术创新，而是被上一代的短板逼出来的。YARN 不是因为工程师突然想解耦，而是 Hadoop 1.0 的资源焊死逼到了扩展性极限；Flink 不是因为有人想写新框架，而是 Spark 微批在高实时性业务下真的不够用；Iceberg 不是为了发论文，而是 Netflix 在 HDFS 上的 Petabyte 级数据真的管不住了。

技术演进的驱动力永远是真实的痛点，不是美好的愿景。 读懂每个工具在补谁的短板，就能在纷乱的技术新闻里保持清醒，不会因为每个月都有新框架出现而迷失。

6.2 展望：三个仍在演进的方向

专题收官，但技术演进远未停止。以下三个方向值得持续关注：

方向一：实时湖仓（Streaming Lakehouse）

Flink 流写 Iceberg、Hudi 的 MOR 模式、Delta Lake 的 Streaming Update——这些都是”近实时”湖仓的实践，但延迟还在分钟级。下一步是真正的秒级乃至毫秒级流式入湖，同时保证 ACID 和查询性能，需要更高效的小文件合并机制（Compaction）和 metadata 写入路径的优化。

方向二：流批进一步融合——统一 API 与统一 Catalog

Flink 的批流统一是计算层的统一，湖仓一体是存储层的统一，但元数据层还没完全统一。不同的 catalog（Hive Metastore、Iceberg REST Catalog、Unity Catalog、AWS Glue）之间的互操作仍有摩擦。Apache Gravitino 等项目在尝试构建统一的 metadata 层，让一张 Iceberg 表能被 Spark/Flink/Trino 用完全一致的方式注册和读取，而不需要各引擎各自维护表注册。

方向三：AI 与数据栈的融合

现代 AI 训练管道大量消耗存储层的数据——特征数据、训练集、评估集都存在数据湖里。Iceberg 的时间旅行让”用昨天的特征版本复现上周的训练结果”成为可能；Delta Lake 的 Change Data Feed 让特征工程管道能增量更新；向量数据库（pgvector、Milvus）与数据湖的集成也在加速——AI 正在成为数据栈演进的新驱动力，一如过去每一代技术的出现都由真实的业务压力驱动。

大数据这条主线，没有终点，只有下一个瓶颈在等待被突破。
