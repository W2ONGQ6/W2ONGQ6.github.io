写在前面：不要把大数据学成”工具堆”

学大数据最常见的误区，是把它学成一份工具清单：HDFS、MapReduce、YARN、Hive、Spark、Kafka、Flink、Iceberg……每个都会一点，却说不清它们为什么依次诞生、彼此在解决对方的什么问题。结果是记住了一堆组件名，遇到选型却抓瞎。

本专题换一个讲法：用一条”内在发展逻辑”把整个生态串起来。这条逻辑的驱动力只有一个——旧方案的瓶颈，逼出了新方案。每一代技术，都是在补上一代的短板：

单机存不下、算不动（数据爆炸）→ 分布式存储与计算（GFS/MapReduce → Hadoop）→ MapReduce 把资源管理和计算耦死了 → 解耦（YARN）→ MapReduce 磁盘 IO 太慢、只能批处理 → 内存计算与 DAG（Spark）→ 微批仍有延迟、批流两套代码太痛 → 真正的流式（Flink，以 Kafka 为数据中枢）→ 存储层跟不上：没有 ACID、批流存储割裂 → 表格式革命（Hive → Parquet → Iceberg/Hudi/Delta）→ 湖仓一体收敛。

读懂这条链，你就能把任何一个组件准确地安放到它在版图中的位置，也能明白为什么现代数据栈长成今天这样。

六个板块与内在因果

板块一：起源与基石 —— 分布式存储与计算的诞生

一切始于一个朴素的事实：当数据大到单机存不下、单核算不动，唯一的出路是把它摊到成百上千台廉价机器上。Google 的三篇论文（GFS、MapReduce、BigTable）给出了理论蓝图，Hadoop 则是它的开源实现——HDFS 负责”存”（分块 + 多副本容错），MapReduce 负责”算”（Map 分、Reduce 合）。这一层要讲清：为什么必须分布式、HDFS 如何用副本换容错、MapReduce 的”移动计算而非移动数据”思想，以及它埋下的两个致命短板——慢（每步落盘）和难用（万物皆 Map/Reduce）。这两个短板，正是后面所有故事的起点。

板块二：资源调度 —— YARN 与”解耦”这一步棋

Hadoop 1.0 有个结构性缺陷：MapReduce 既管计算，又管集群资源分配，两者焊死在一起。这意味着一个集群只能跑 MapReduce，且扩展性受限于 JobTracker 单点。YARN 的意义是”解耦”——把资源管理（ResourceManager）从计算框架里剥离出来，计算框架退化为 YARN 上的一个”应用”。这一步看似朴素，却是整个生态的枢纽：正因为资源层被抽象出来，Spark、Flink 才能和 MapReduce 跑在同一个集群上。没有 YARN 的解耦，就没有后面的百花齐放。

板块三：Spark —— 用内存计算打破磁盘瓶颈

MapReduce 最大的痛点是慢：每一步的中间结果都要写回 HDFS，一个迭代算法（如机器学习）要反复读写磁盘几十次。Spark 的核心创新是 RDD（弹性分布式数据集）+ 内存计算：中间结果尽量留在内存里，迭代计算快上一两个数量级。同时它用 DAG 执行引擎取代僵硬的 Map-Reduce 两段式，把整个计算流程作为有向无环图优化调度，并提供远比 MapReduce 友好的 API（还有 Spark SQL、MLlib、GraphX）。Spark 一举解决了”慢”和”难用”，成为批处理的事实标准。但它有个基因缺陷——它是批处理原生的，流处理只能靠”微批”（micro-batch）模拟，这就为下一场变革埋了伏笔。

板块四：Kafka —— 流式时代的数据中枢

在讲 Flink 之前，必须先讲 Kafka——因为真正的流式计算，需要一个能持续、可靠、可重放地供给数据的”河流”。Kafka 用**分布式、分区、持久化的提交日志（commit log）**抽象，把”消息队列”升级为”流数据平台”：数据以 append-only 日志形式存储，消费者按 offset 自主消费、可回放。它解决了流式架构的基础设施问题——数据如何解耦生产者与消费者、如何保证不丢、如何支持多个下游各取所需。Kafka 是 Lambda/Kappa 架构的骨架，是 Flink 等流引擎最典型的数据源。

板块五：Flink —— 真正的流式与批流统一

Spark 的微批有个天花板：延迟受限于批的间隔，且”事件时间”语义难以精确处理。现实中数据是乱序到达的（网络延迟、设备离线），要正确地按”事件真正发生的时间”开窗聚合，微批很吃力。Flink 的哲学正好相反——它是流式原生的：一次处理一个事件，用 event-time + watermark 处理乱序，用分布式快照（Chandy-Lamport）实现精确一次（exactly-once）的状态一致性。更关键的是它的世界观：批只是”有界的流”（和 Spark”流是连续的批”恰好相反）。这一视角让 Flink 天然支持批流统一，从根上化解了 Lambda 架构”批一套代码、流一套代码”的维护地狱，催生了更简洁的 Kappa 架构。

板块六：存储与表格式演进 —— 从文件到湖仓一体

计算引擎一路狂奔，存储层却长期停留在”HDFS 上一堆文件”的原始状态，暴露出三个问题：没有 SQL（难用）、行存不适合分析（慢）、没有 ACID（并发写、更新、回滚都做不到）。这一层的演进依次补齐：Hive 给 HDFS 文件套上表和 SQL；Parquet/ORC 列式存储让分析型查询只读需要的列、压缩率更高；Iceberg/Hudi/Delta Lake 这批”数据湖表格式”则把数据库才有的 ACID 事务、时间旅行、schema 演进、增量更新带到了数据湖上。终点是湖仓一体（Lakehouse）——用一套存储同时服务批与流、数仓与数据湖，与 Flink 的批流统一在存储侧遥相呼应，整条主线在此收束。

系列文章导航

按发展主线顺序阅读，每一篇的短板恰好由下一篇解决：

  1. 大数据-01：起源与基石 —— 从 Google 三驾马车到 Hadoop
    分布式存储与计算的诞生：HDFS 存、MapReduce 算；埋下”慢 + 难用”两大短板。
  2. 大数据-02：YARN —— “资源与计算解耦”这一步棋
    把资源管理从计算里剥离，让 Spark/Flink 得以与 MapReduce 共存——生态爆发的前提。
  3. 大数据-03：Spark —— 用内存计算与 DAG 打破磁盘瓶颈
    RDD 内存计算 + DAG 引擎，快一两个数量级；批处理王者，但流处理只能微批。
  4. 大数据-04：Kafka —— 流式时代的数据中枢
    持久化 commit log 提供可重放的”数据河流”，是流式架构的骨架与 Flink 的典型数据源。
  5. 大数据-05：Flink —— 真正的流式与批流统一
    event-time + watermark + exactly-once；”批是有界的流”→ 批流统一 → Kappa 架构。
  6. 大数据-06：存储与表格式演进 —— 从文件到湖仓一体
    Hive→Parquet→Iceberg/Hudi/Delta 给数据湖带来 ACID 与时间旅行；湖仓一体在存储侧收束批流。
  7. 大数据-07：经典工作全景 —— 从 Google 三驾马车到湖仓与流批统一
    集中梳理 GFS、MapReduce、BigTable、YARN、Spark、Kafka、Dataflow/Flink 和三大表格式，并说明它们如何沿同一条瓶颈链演进。

一张图看懂发展主线

一句话总结：大数据的历史，是”存储—计算—资源—流批—表格式”五个层面轮流成为瓶颈、又轮流被突破的历史。理解每个组件在补哪一代的短板，就不会在工具堆里迷路。

说明：本专题聚焦主流开源大数据生态的发展脉络与设计思想，而非某个组件的 API 手册。版本细节会变，但”被瓶颈逼着演进”的内在逻辑长期稳定。

阅读建议：按板块顺序读，能看清每一代技术”为何出现、解决了什么、又留下什么”；这条因果链本身，就是最好的知识地图。
