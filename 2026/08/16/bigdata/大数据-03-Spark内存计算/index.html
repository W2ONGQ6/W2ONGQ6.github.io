一、引子：MapReduce 慢在哪、难用在哪

上一篇讲 YARN 时留下一个悬案：YARN 完成了”解耦”，让 Spark、Flink 得以和 MapReduce 共存于同一个集群。但为什么非得把 MapReduce 换掉？它具体慢在哪，又难用在哪？

1.1 慢的根源：每一步都要落盘

MapReduce 的执行模型可以用一句话概括：Map 产出中间结果写本地磁盘，Reduce 从所有 Mapper 拉数据再写 HDFS，下一步 Job 再从 HDFS 读。

用文字描绘一个三步迭代的数据处理流程：

每一步的结果都要经历一次序列化写磁盘 → 网络传输 → 反序列化读磁盘的完整循环。磁盘 IO 和网络传输的延迟，是内存读写的成百上千倍。

这对于只跑一次的 ETL 任务还可以忍受，但对于迭代算法来说是灾难。机器学习里的梯度下降、图算法里的 PageRank，都需要反复在同一份数据上迭代几十上百次。用 MapReduce 做机器学习，意味着每轮迭代都要把整个中间状态写回 HDFS 再读回来——磁盘 IO 把绝大部分时间都吃掉了。

1.2 难用的根源：万物皆 Map/Reduce

MapReduce 的 API 只有两个原语：Map 和 Reduce。业务逻辑必须被强行压进这两个框里。

  • Join 两张表：要把两边的 key-value 同时塞进一个 Reduce，手写分发逻辑。
  • 多步聚合：每一步都是一个独立的 MapReduce Job，作业之间靠 HDFS 传递中间结果。
  • 排序 + 过滤 + 聚合：在同一个 Job 里揉在一起，逻辑拆不开、测试难、调试更难。

Hive 用 HQL 给 MapReduce 套了一层 SQL 方言，缓解了”难写”的问题，但生成的执行计划本质上还是 MapReduce，慢的问题一分未解。

这是板块三要解决的核心矛盾：既要快，又要易用。

二、RDD：Spark 的计算原语

Spark 的回答是 RDD（Resilient Distributed Dataset，弹性分布式数据集）。这是 2012 年 Matei Zaharia 在 UC Berkeley 博士论文中提出的抽象，也是整个 Spark 体系的逻辑地基。

2.1 RDD 的三个核心属性

1. 不可变（Immutable）

RDD 一旦创建就不能修改。所有操作都是从一个 RDD 生成一个新的 RDD，而不是在原地改写。这个设计和函数式编程一脉相承——不可变对象天然没有并发写入问题，任意分区可以在任意节点上独立计算，不需要任何同步。

2. 分区（Partitioned）

每个 RDD 被切分为若干分区（Partition），分区是调度的最小单位。每个分区会被分配到集群的某个节点上计算，多个分区可以在不同节点上并行运行。分区数决定了并行度。

3. 血统（Lineage）

每个 RDD 都记得自己是从哪个父 RDD、经过什么操作变化而来的。这条”变换链”就是血统，也叫依赖图。

血统的价值在后面容错一节展开。

2.2 Transformation 与 Action：惰性求值

RDD 的操作分两类：

Transformation（转换）：从一个 RDD 生成另一个 RDD，惰性执行——调用时只记录”我打算这样变换”，不触发任何实际计算。

常见 Transformation：

算子 语义
map(f) 对每个元素应用 f，1:1 变换
flatMap(f) 对每个元素应用 f，结果展平（1:N）
filter(f) 过滤满足 f 的元素
groupByKey() 按 key 分组（会触发 shuffle）
reduceByKey(f) 按 key 聚合，先本地预聚合再 shuffle
join(other) 按 key 做内连接（会触发 shuffle）
sortByKey() 按 key 全局排序（会触发 shuffle）
union(other) 合并两个 RDD
distinct() 去重（会触发 shuffle）

Action（动作）：触发实际计算，返回结果到 Driver 或写到外部存储。

常见 Action：

算子 语义
collect() 拉回全量数据到 Driver
count() 统计元素个数
take(n) 取前 n 个
saveAsTextFile(path) 写出到文件系统
reduce(f) 在 Driver 端规约
first() 取第一个元素

为什么要惰性求值？ 因为 Spark 需要在触发 Action 之前，拿到完整的计算图，才能做全局优化——合并多次过滤、消除冗余的 shuffle、决定最优的 Stage 划分。如果每个 Transformation 立即执行，就失去了优化的窗口。

2.3 容错：靠血统重算，而非落盘

MapReduce 的容错方案是检查点（checkpoint）：每一步结果写到 HDFS，某个 Task 失败了就从最近的 HDFS 检查点重启。这保证了容错，却也是落盘的直接原因——为了容错，不得不写磁盘。

RDD 的容错思路完全不同：利用血统重算（lineage recomputation）。

某个分区的数据丢失了（节点宕机），Spark 不需要从 HDFS 重新读整个数据集，它直接顺着血统往上追溯——找到这个分区的”父分区”，重新执行那段 Transformation，就能还原出丢失的分区。

这个方案的前提是：Transformation 是纯函数式的（相同输入，相同输出），因此”重算”是安全的。RDD 的不可变性正是为此服务的——正因为不可变，重算的结果才能保证等价于原来的结果。

血统的代价：如果血统很长（几十步），某个分区丢失后重算的代价很高。对于这种情况，Spark 提供了显式的 checkpoint() 操作，把 RDD 物化到 HDFS，切断过长的血统。这是用户主动选择的权衡，而非框架强制。

三、内存计算：为什么快一两个数量级

3.1 中间结果驻留内存

RDD 的 Transformation 是惰性的，所有中间 RDD 只是计算计划里的一个节点。当 Action 触发执行时，Spark 的执行器（Executor）在内存中流水线式地处理分区数据：

  • 读取输入分区数据到内存。
  • 在内存中执行所有 Transformation（filter、map、flatMap 等窄依赖操作可以直接串联，不产生落盘）。
  • 遇到 shuffle 边界时，把 shuffle 数据写到本地磁盘（这一步无法避免，但只在 shuffle 边界发生，而非每一步）。
  • Shuffle 读取对端写下的数据，继续在内存中处理。

对比 MapReduce：每一步（即每个 MapReduce Job）都要把结果写回 HDFS，下一步再从 HDFS 读。Spark 只在 shuffle 边界落盘，其余全在内存里流转。

3.2 cache 与 persist

如果一个 RDD 会被多次使用（迭代算法、多次查询同一基础数据集），可以显式告诉 Spark 把它保留下来：

cache() 是 persist(StorageLevel.MEMORY_ONLY) 的简写。persist 提供了更细的控制：

StorageLevel 含义
MEMORY_ONLY 只存内存，内存不够则不缓存该分区（重算）
MEMORY_AND_DISK 内存不够的分区溢写到磁盘
MEMORY_ONLY_SER 序列化后存内存（更省空间，CPU 换内存）
DISK_ONLY 只写磁盘
OFF_HEAP 堆外内存（减少 GC 压力）

实际调优时，ML 迭代训练通常用 MEMORY_AND_DISK——内存放不下的分区落磁盘，总好过每轮都重算。

3.3 内存管理：统一内存模型

Spark 1.6 引入了统一内存管理（Unified Memory Manager）。Executor JVM 堆内存大致分为：

  • Execution Memory（执行内存）：shuffle、join、sort、aggregation 的临时数据。
  • Storage Memory（存储内存）：cache/persist 的 RDD 数据。
  • 两者共享同一个内存池，可以动态借用——执行内存不够时可以占用存储内存（evict 缓存），存储内存不够时也可以借用执行内存。

这比早期静态划分（Spark 1.5 以前固定各 60%/40%）灵活得多，但内存压力大时 cache 可能被 evict，需要结合 StorageLevel 策略做权衡。

四、DAG 执行引擎：把计算构建成有向无环图

4.1 从两段式到 DAG

MapReduce 的执行模型是僵硬的两段式：Map → Shuffle → Reduce，不多也不少。任何计算都必须压进这个模子，哪怕你的逻辑只需要一次 Map，也要付出 Shuffle 的代价。

Spark 的执行模型是 DAG（有向无环图）：把整个计算（从输入 RDD 到最终 Action）表示为一张有向无环图，节点是 RDD，边是 Transformation。DAGScheduler 拿到这张图后，负责把它划分成 Stage，Stage 再切分成 Task，分发到 Executor 执行。

4.2 宽依赖与窄依赖：Stage 的划分边界

Stage 的划分依据是依赖类型：

窄依赖（Narrow Dependency）：父 RDD 的每个分区，至多被子 RDD 的一个分区依赖。数据不需要跨节点传输，可以在同一个 Executor 上流水线执行。

典型窄依赖算子：map、filter、flatMap、mapPartitions、union（一对一或多对一，但不需要 shuffle）。

宽依赖（Wide Dependency）：父 RDD 的一个分区，可能被子 RDD 的多个分区依赖。数据必须跨节点重新分发（Shuffle），是 Stage 的边界。

典型宽依赖算子：groupByKey、reduceByKey、join（默认）、sortByKey、distinct。

Stage 0 包含所有窄依赖操作（flatMap、map），可以在一个 Task 里流水线完成。Stage 1 在 Shuffle Read 之后继续处理（reduceByKey 的聚合部分），最终写出结果。

同一个 Stage 内的操作**流水线化（pipeline）**执行：一个分区的数据进来，依次经过所有窄依赖算子，不产生任何临时落盘。

MapReduce 要实现同样的逻辑，需要至少两个独立的 MapReduce Job，中间结果写 HDFS 传递。Spark 的 DAG 调度器把它们融合在一张图里，全局优化，减少中间落盘。

4.4 Catalyst 优化器（Spark SQL 层的 DAG 优化）

如果用 Spark SQL / DataFrame API，还会经过 Catalyst 优化器的进一步处理。Catalyst 是一个基于规则和代价的查询优化器，工作分四个阶段：

  1. 解析（Analysis）：把 SQL 文本或 DataFrame 操作解析成未解析的逻辑计划。
  2. 逻辑优化（Logical Optimization）：应用规则优化逻辑计划——谓词下推（把 filter 提前，减少数据量）、列剪裁（只读需要的列）、常量折叠、子查询合并等。
  3. 物理计划生成（Physical Planning）：把逻辑计划转换为物理计划，选择 join 算法（BroadcastHashJoin vs SortMergeJoin）、决定是否广播小表等。
  4. 代码生成（Code Generation）：利用 Tungsten 引擎把物理计划编译成 JVM 字节码，消除虚函数调用开销，充分利用 CPU 缓存局部性。

Catalyst 的存在让 Spark SQL 的性能往往优于手写 RDD 代码——用户写的声明式 SQL 被优化器重写后，执行计划可能与人工调优的 RDD 程序相当甚至更好。

五、Spark 生态：统一的大数据栈

MapReduce 解决的是”把数据跑一遍”，生态极度单薄。Spark 的野心是用一套引擎覆盖批处理、SQL 查询、流处理、机器学习、图计算，形成统一栈，消除多套系统带来的运维复杂度和数据搬迁成本。

5.1 Spark SQL / DataFrame

核心价值：把声明式 SQL 和结构化数据（DataFrame）带入 Spark 计算体系。

5.2 Structured Streaming：微批流处理

Structured Streaming 是 Spark 2.0 引入的流处理模型，建立在 DataFrame API 之上。它的核心思想是把流当成一张无界的表——新数据持续追加到表的末尾，流式查询就是对这张不断增长的表持续运行的批处理查询。

Structured Streaming 的实现机制：每隔一个触发间隔（trigger interval），Spark 把该间隔内到达的新数据当成一个”微批”（micro-batch），在内部以一次小的批处理 Job 来执行，结果增量合并到输出。

这个模型有一个直接的好处：Spark SQL 的所有优化（Catalyst、Tungsten）直接复用，不需要另起炉灶。批处理代码和流处理代码几乎可以互换，运维统一。

但是——这里要点出一个重要的设计约束，留到下一节展开。

5.3 MLlib：分布式机器学习

MLlib 是 Spark 内置的分布式机器学习库。它的意义在于：ML 训练本质上是迭代算法，每轮迭代需要遍历整个训练集。把训练集 persist 在内存里，每轮迭代直接从内存读，相比 Mahout（基于 MapReduce 的前辈）快了一两个数量级。

MLlib 支持常用算法：线性回归、逻辑回归、决策树、随机森林、K-means 聚合、协同过滤（ALS）、朴素贝叶斯等，以及特征工程 Pipeline（Pipeline、Transformer、Estimator 的组合）。

5.4 GraphX：图计算

GraphX 是 Spark 的图处理 API，提供了属性图（Property Graph）抽象——顶点和边都可以携带任意属性。内置算法包括 PageRank、连通分量、最短路径、三角计数等。GraphX 的底层依然是 RDD，利用 Spark 的内存计算优势做迭代图算法。

这里不深入展开——GraphX 在今天实际使用中已逐渐被 GraphFrames（基于 DataFrame API 的图框架）取代，后者更好地接入了 Catalyst 优化器。

六、Spark 的基因缺陷：批处理原生，流是后来者

讲完 Spark 的优势，必须直视它的设计根源，以及从这个根源生长出来的内在局限。

6.1 世界观：流是连续的小批

Spark 诞生于批处理场景。它的核心抽象 RDD 是一个静态的、有界的数据集。当 Spark 要做流处理时，它的思路是：把一条连续的数据流切成一个个小的时间窗口，每个窗口对应一批数据，对每批数据跑一次批处理 Job。

这就是 微批（micro-batch） 模型。在 Spark Streaming（DStream API）时代这一点很明显；Structured Streaming 用”无界表”重新包装了这个概念，但底层执行机制（默认 Trigger.ProcessingTime）仍然是微批。

Spark 的世界观：流 = 连续的批。

6.2 微批的两个根本性局限

局限一：延迟受批间隔限制。

微批模型下，一条数据的处理延迟至少是一个批间隔。把批间隔设小（比如 100ms）可以缩短延迟，但批 Job 的调度开销（Stage 调度、Task 序列化分发、JVM 启动等）是有下限的。在实际工程中，Spark Structured Streaming 的端到端延迟通常在秒级，很难做到真正的毫秒级低延迟。

对于大多数离线报表、分钟级实时大屏来说，这个延迟完全够用。但对于金融风控（需要毫秒内决策）、高频交易、实时推荐等场景，秒级延迟是不可接受的。

局限二：Event-time 语义处理吃力。

真实世界的数据是乱序到达的：移动设备可能在网络恢复后一次性上报几分钟前的事件；物联网传感器可能有几秒的时钟偏移；后端服务在重启后可能重放历史日志。

“事件时间”（event-time）指的是事件实际发生的时间，区别于 Spark 收到数据的”处理时间”（processing-time）。如果要按事件真正发生的时间做窗口聚合（比如”每分钟用户点击次数，按点击发生的时刻而非服务器收到的时刻统计”），就必须处理乱序。

Structured Streaming 提供了 Watermark 机制来处理乱序——声明”我愿意等待最多 X 时间的迟到数据，超过 X 的就丢弃或不更新”。但这个机制在微批模型下有内在的精度问题：

  • Watermark 的推进以批为粒度，粒度太粗，对乱序的响应存在一个批间隔的滞后。
  • “恰好一次”（exactly-once）语义在状态 checkpoint 上更复杂，实现和调优的认知成本高。
  • 有状态算子（stateful aggregation）在内存压力大时容易出现性能抖动。

这些不是 Spark 团队的工程疏忽，而是微批世界观的先天约束——你始终是在用批处理模拟流处理，总有一层不完美的抽象在中间。

6.3 两套代码的维护成本：Lambda 架构的痛

在 Spark 成为批处理标准之后，行业里形成了一种常见的架构模式——Lambda 架构：

Lambda 的逻辑是合理的：批处理保证准确性（全量重算可以纠正历史错误），速度层保证低延迟，两者互补。

但它的工程代价是：同一套业务逻辑要用两套代码实现，批处理一套（Spark batch），流处理一套（Spark Streaming 或 Storm）。两套代码要保持语义一致——这在实际工程中极难保证：一侧修了 bug，另一侧忘了改；两侧对某个边界情况的处理方式有微妙差异；业务逻辑变了，两边都要同步更新……

这个痛点，正是 Flink 的登场动机之一。Flink 的设计哲学是流式原生、批是有界的流，从根上统一了批和流的执行路径，从根上消除了”两套代码”的问题。这是下两个板块的主题。

七、小结：Spark 在历史坐标中的位置

回顾一下这条逻辑链：

Spark 是大数据生态里里程碑式的作品。它用一个足够优雅的抽象（RDD）把内存计算、容错、惰性优化统一起来，把批处理的生产力提升了一个数量级，并用一套引擎覆盖了 SQL、ML、图计算等多个场景。在今天，Spark 依然是离线批处理和数仓 ETL 最主流的选择。

但它是批处理时代的产物。流处理的世界，需要一个从流出发、批只是特例的新框架。这个框架，就是 Flink。在此之前，我们需要先看清 Flink 最重要的数据来源——Kafka，以及它如何把”数据流”这件事变成了一个稳固的基础设施。
