Agent-02：前沿模型 —— 为 agentic 而生的军备竞赛

一、引子：通用 LLM 当 agent 的三大先天不足

板块一讲清楚了 agent 的能力基石：把 LLM 套进”感知—决策—行动—反馈”循环，配上工具调用和记忆模块，ReAct 模式就跑起来了。听上去很美——但 2023 年的大量工程实践迅速揭示了一个残酷事实：

通用 LLM 并不擅长当 agent。

不是它不聪明，而是它的训练目标从来不是”干完一件事”，而是”把下一个 token 猜对”。这个目标差异，导致了三种在 agent 场景里特别致命的先天不足。

1.1 多步跑偏（goal drift）

一个真实任务往往需要 10～50 步工具调用。通用 LLM 在第 3 步还好，到第 15 步时常常已经”忘了”最初的目标，开始沿着中间某个子问题的惯性一路走偏。人类研究者把这叫做 goal drift——目标在多轮推理中悄悄漂移。

预训练语料里大量的”单轮问答”让模型对”短期目标对齐”极度敏感，但对”跨越几十步保持长期一致性”几乎没有训练信号。

1.2 工具调用格式易错（tool alignment gap）

工具调用要求模型输出严格符合 schema 的 JSON 或函数签名——字段名不能打错、类型不能混淆、必填参数不能遗漏。通用 LLM 见过大量代码，但那些代码往往是人类写的，有冗余、有注释、可以模糊理解；而工具调用要的是机器可解析的精确输出，差一个引号就报错。

更麻烦的是，不同工具的 schema 差异很大。模型需要在运行时动态理解”这次用的是哪个工具的格式”，而不是靠记忆某个固定模板——这需要专门的对齐训练，不是 few-shot prompting 能完全覆盖的。

1.3 长程失忆（context amnesia）

早期主流模型的上下文窗口是 4K～32K token。一个中等复杂的编程任务，光是代码文件加上工具调用历史，就能把窗口塞满。当上下文溢出，模型实际上只能看到最近的一段历史——早期建立的关键信息（比如”这个函数要保持向后兼容”）就从视野里消失了。

即使上下文够长，通用 LLM 也没有经过”在超长序列中精准检索关键信息”的专项训练，注意力容易被中间无关内容稀释，出现 lost in the middle 问题。

这三个问题不是 bug，是设计哲学上的错位。修复它们，需要的不是更好的 prompt，而是重新设计训练目标。这正是 2025–2026 这场”agentic 模型军备竞赛”的起点。

二、什么是”为 agentic 训练”

从”答得对”到”干得完”，训练目标的切换涉及四个核心维度。

2.1 长程强化学习（long-horizon RL）

传统 RLHF 的奖励信号来自人类对单轮回复的偏好评分。agentic 训练则需要延迟奖励：在整个任务结束（测试通过、任务完成、用户确认）时才给出一个奖励，然后反向传播到任务开始前的每一步决策。

这就是 long-horizon RL——模型必须学会”哪些中间步骤对最终成功有贡献”，而不是只优化当前这一步看起来有多顺滑。实现难点在于：任务轨迹极长，信用分配（credit assignment）问题变得极为困难；需要大量真实或仿真的多步任务环境来生成训练数据。

2.2 工具调用对齐（tool-use alignment）

在大量真实工具调用轨迹上做监督微调（SFT），再用 RL 进一步优化”格式正确且语义合理”的工具调用。关键是覆盖多样化的工具 schema——不能只训练几个固定工具，而要让模型泛化到任意新工具。

部分厂商还引入了”工具调用失败恢复”训练：当工具返回错误时，模型需要正确地解析错误、修正参数、重试，而不是慌乱输出无关内容。

2.3 超长上下文建模

把有效上下文从 32K 扩展到 128K、512K、1M token，不只是把位置编码拉长那么简单。需要：

  • 稀疏注意力或分块注意力：避免全量 attention 的二次复杂度。
  • 长序列精准召回训练：在超长序列中放入关键信息，专门训练模型在任意位置精准召回，消除 lost-in-the-middle 问题。
  • KV cache 工程：超长上下文下缓存管理成为性能瓶颈，需要 prefix caching、跨请求复用等工程手段。

2.4 防跑偏与防失忆的行为训练

这是最难量化但最重要的一层。具体手段包括：

  • 目标锚定训练：在训练中故意引入”中途干扰”（如插入无关工具调用结果），训练模型保持对原始目标的追踪。
  • 自我反思（reflection）强化：在多步任务中训练模型定期”回头看”——“我的当前状态离目标还有多远？”
  • Minimal footprint 原则：Anthropic 等厂商明确将”只请求必要权限、只做任务要求的事情”纳入 agentic 训练，减少模型在自主执行时的过度行动风险。

这四个维度共同定义了”为 agentic 训练”的内涵。下面看各家是怎么落地的。

三、闭源双雄

3.1 Anthropic Claude Opus 4.x：agentic coding 的新标杆

基准定位

Claude 系列在 2025 年确立了 agentic coding 的行业标杆地位。Opus 4.5 在 SWE-Bench Verified（将真实 GitHub issue 作为闭环任务的评测集）上达到 80.9%（截至 2026 年中，以官方为准），意味着在近千个真实软件工程任务中，有超过八成能被模型自主解决。这不是问答题，是让模型在真实代码库里自己找到 bug、写好修复、跑通测试——这个数字的含义远比”代码题准确率”沉重得多。

版本演进

  • Opus 4.5：初次确立 agentic coding 标杆，配合 Claude Code 工程外壳大规模部署。
  • Opus 4.7（2026 年 4 月 16 日）：进一步强化长程自主执行能力，减少多步任务中的 goal drift。
  • Opus 4.8（2026 年 5 月 28 日，截至 2026 年中的当前旗舰）：主打 agentic coding、长程自主、1M 上下文三个方向同步推进。

关键创新点

  1. 1M 上下文 + 精准召回：1M token 在 agent 场景里意味着整个代码库、完整历史轨迹、所有工具返回都能放进上下文，从根本上缓解长程失忆问题。但 Anthropic 不止是把窗口拉大——他们专门训练了长序列中的精准召回能力，使模型在超长上下文中依然能准确找到关键信息。

  2. Minimal footprint 原则：Anthropic 在 agentic 训练中明确引入行为约束——模型被训练为”只请求完成任务必要的最小权限、只做任务要求的操作、优先询问而非假设”。这是安全性与自主性之间精心校准的平衡，也是 Claude 在企业生产环境里被信任的重要原因。

  3. 并行子代理协作：Claude Opus 4.x 经过专门训练来扮演”orchestrator”角色——把大任务拆成子任务，分发给并行运行的子代理（subagent），聚合结果后继续推进。这对应板块三要讲的多智能体 harness 架构，模型本身的训练必须支持这种协作模式。

  4. 错误恢复训练：工具返回错误时，Opus 4.x 被训练为能够解析错误信息、修正调用参数、优雅重试，而不是陷入错误循环或直接放弃任务。

在竞赛中的意义

Claude Opus 系列的意义不只是榜单数字。它是第一个被大规模工程化部署（通过 Claude Code）、在真实生产环境里跑了大量 agentic 任务、并把工程经验反哺回模型训练的闭源系统。这个”训练—部署—反馈—再训练”的飞轮，使它在 agentic coding 这个垂直方向上积累了显著的数据优势。

3.2 OpenAI GPT-5.x + Codex：通用智能与专项编程的双线并进

两条产品线的分工

OpenAI 在 2026 年采取了双线并进策略：GPT-5.x 系列追求通用强智能，Codex 系列专攻编程 agent 场景。两条线不是竞争关系，而是在不同 agent 任务上各自优化。

GPT-5.5（2026 年 4 月 23 日）

  • 1M 上下文：与 Claude 同步进入超长上下文时代。
  • Terminal-Bench 2.0 约 82.7%（截至 2026 年中，以官方为准）：Terminal-Bench 考察的是模型在终端环境里自主完成系统操作任务的能力——安装依赖、配置环境、调试运行——这比 SWE-Bench 更接近真实的 DevOps agent 场景。

GPT-5.1-Codex-Max

  • SWE-Bench Verified 约 77.9%（截至 2026 年中，以官方为准）：专为编程 agent 场景优化的版本，在 SWE-Bench 上的表现证明了专项训练的价值。
  • Codex 系列定位：OpenAI Codex 系列的产品化目标是”云端编程 agent”——用户描述需求，Codex 在隔离的云端环境里自主完成代码编写、测试、修复的完整循环，最终以 PR 的形式交付结果。这是一个典型的”把 agent 能力封装成 API”的思路。

关键创新点

  1. 隔离执行环境（sandboxed execution）：Codex 系列的一个重要工程选择是让模型在完全隔离的云端沙箱里执行代码——不连接生产系统，不影响用户本地环境。这在安全性上做了明确的权衡：降低自主性的同时大幅降低风险。

  2. 原生 Responses API：OpenAI 推出的 Responses API 提供了标准化的工具调用、状态流转和中断恢复接口，让第三方 harness 能更容易地把 GPT-5.x 接入多步 agent 工作流。DeepSeek V4 后来也宣布原生支持这一 API，这本身就说明了它成为了行业事实标准之一。

  3. 多模态 agent 能力：GPT-5.x 系列在视觉输入上的强化，使得”看截图调试 UI bug”、”读图表写分析报告”这类任务成为可能，拓宽了 agent 的输入感知边界。

在竞赛中的意义

GPT-5.x 系列的竞争意义在于”通用智能溢出到 agentic”——它不像 Codex 系列那样专项优化，但强大的通用能力使它在”非编程的复杂多步任务”（如深度研究 agent、计算机操作 agent）上保持领先。Terminal-Bench 的高分说明：通用推理能力越强，对任意新类型工具的泛化就越好，这是专项训练模型难以复制的。

四、开源追赶

开源阵营的 2026 年可以用一句话概括：在 agentic coding 这个最具可测量性的子赛道上，开源与闭源的差距从”显著”压缩到了”需要仔细看基准才能区分”。这背后有深刻的结构性原因，后面会分析。先看各家的具体打法。

4.1 DeepSeek V4：开源 + 1M + MoE 的三重意义

基本信息

DeepSeek V4 于 2026 年 4 月 24 日发布预览版，采用 MIT 开源协议——这意味着任何人都可以商业使用、部署、微调。

架构上采用 MoE（混合专家模型）：

  • V4-Pro：1.6T 总参数 / 49B 激活参数
  • V4-Flash：284B 总参数 / 13B 激活参数

原生支持 1M token 上下文。后续版本（0731、0813 等迭代版本）专门针对 agentic 场景做了增强。

关键创新点

  1. MoE 在 agentic 场景的效率优势：1.6T 总参数意味着模型的”知识容量”接近甚至超过稠密模型的顶级水平；但每次推理只激活 49B 参数，推理成本大幅降低。对于 agentic 任务（一次任务可能需要几十到几百次 LLM 调用），推理成本是真正的生产瓶颈——MoE 在这里的优势比单轮对话场景更加显著。

  2. 原生多框架兼容：DeepSeek V4 原生支持 Claude Code 协议、OpenAI Codex API 接口、Responses API——这是一个非常明确的信号：它不只是想做一个”能用”的开源模型，而是要无摩擦地嵌入现有的 agent 生态，替换闭源模型。对于已经在用 Claude Code 或 Codex 的工程团队，切换到 DeepSeek V4 的工程成本接近于零。

  3. 持续的 agentic 专项迭代：0731、0813 等后缀版本号说明 DeepSeek 在以接近两周一个版本的频率专门针对 agentic 场景做迭代，而不是等待下一个大版本。这种快速迭代能力是开源模式的固有优势——部署在自己服务器上的用户可以直接升级，不需要等 API 提供商的版本切换。

  4. 可本地部署：对于数据合规要求严格的企业（金融、医疗、政府），能否在内网部署是硬性前提。DeepSeek V4 的开源使这成为可能，而这个市场闭源 API 天然无法进入。

在竞赛中的意义

DeepSeek V4 的意义不只是”又一个强模型”，而是重新定义了 agentic 模型的成本曲线。当 1M 上下文的开源 MoE 模型达到接近闭源旗舰的 agentic 能力，它就把整个行业的”合理成本”锚点往下拉了一档。任何闭源厂商的定价，都需要在这个新基准线上重新论证其溢价的理由。

4.2 Kimi K2.5 / K3：Agent Swarm 理念与开源权重的双重押注

K2.5（2026 年 1 月 27 日）

Kimi K2.5 的核心亮点是两个：

  1. HLE with tools 50.2%（截至 2026 年中，以官方为准）：HLE（Humanity’s Last Exam）是目前已知最难的学术测试集，用 with tools 模式跑到 50.2%，说明 K2.5 在工具辅助下的推理能力达到了很高的水平。这里的关键词是”with tools”——它不是背答案，是在真实推理过程中调用工具来辅助解题，这正是 agentic 能力的一种体现。

  2. “Agent Swarm”理念：K2.5 明确提出并推广了 Agent Swarm 概念——将复杂任务分解为多个专项子任务，用一群协作的小 agent 而非单一大 agent 来完成。这个架构理念影响了后来整个行业对多 agent 协作的讨论范式。

K2.6：在 K2.5 基础上的进一步迭代，持续强化 agentic 任务上的稳定性。

K3（2026 年 7 月 16 日）

K3 是 Kimi 系列一个里程碑式的节点：开源权重，总大小 594GB（MXFP4 精度）。

这里有几个值得关注的细节：

  • MXFP4 精度：Microscaling FP4 是一种比 FP8 更激进的低精度格式，在保持模型质量的同时大幅压缩权重体积和推理内存占用。594GB 已经是很大的体积，如果用标准精度会更大得多——K3 在推理效率上做了明确的工程选择。
  • 开源权重的战略意义：月之暗面把 K3 开源，意味着研究社区可以在此基础上做 agentic 专项微调、安全评估、本地部署。这是在向 DeepSeek 的开源路线靠拢，也是在建立生态护城河的一种方式——让”Kimi 兼容”成为开源社区的一个标准。

在竞赛中的意义

Kimi 系列的贡献在于两个层面：Agent Swarm 理念层面的概念输出，和大权重开源层面的生态布局。K2.5 的 HLE with tools 成绩说明月之暗面在超高难度推理+工具调用的结合上找到了正确方向；K3 的开源则说明它在”影响开源生态走向”上有明确野心。

4.3 Qwen3 系列：高频迭代下的全面对标

基本情况

阿里 Qwen3 系列在 2025–2026 采取了非常密集的迭代策略，Qwen3-Next-80B-A3B、Qwen3.6、Qwen3.8 等版本持续推出（截至 2026 年中，以官方为准）。命名中的 A3B 意味着 3B 激活参数——和 DeepSeek 一样，Qwen3 也采用了 MoE 架构来平衡能力与效率。

关键特点

  1. 开源 + agentic/coding 强：Qwen3 系列在 coding benchmark 上的表现持续对标甚至超越同量级的闭源模型，是工程团队在”想要一个开源编程 agent 底座”时的主流选项之一。

  2. 全系列覆盖：从小参数（适合端侧或低成本部署）到大参数（对标旗舰级能力），Qwen3 系列形成了完整的产品矩阵，适应不同计算预算的 agent 部署场景。

  3. 工具调用生态：Qwen3 系列对 OpenAI 兼容接口、function calling 格式有良好支持，与主流 agent 框架（LangChain、LlamaIndex 等）的集成相对顺畅。

在竞赛中的意义

Qwen3 代表的是”以量取胜”策略在模型领域的实践——高频发布、覆盖全场景、保持与闭源的技术追平。对生态的影响是：它让”在阿里云上部署本土开源 agent”成为一个技术上完全可行且性价比高的选项，这对于中国市场尤其重要。

4.4 智谱 GLM-4.5 / GLM-5：中文 agentic 的本土路线

定位

GLM 系列（智谱 AI）在 GLM-4.5、GLM-5 迭代中重点强化了 agentic coding 能力，同时在中文长文本处理、中文工具调用场景上有针对性的优化（截至 2026 年中，以官方为准）。

关键特点

  1. 中文场景的原生优化：相比其他模型主要针对英文 benchmark 优化，GLM 系列在中文指令理解、中文代码注释、中文错误信息处理等方面有更细致的训练。对于以中文为主要工作语言的开发团队，这种原生优化减少了”翻译摩擦”。

  2. 与 AgentBench 等中文评测的对齐：智谱较早地参与了中文 agent 评测体系的建设，GLM 系列的迭代方向与这些评测高度对齐，形成了本土评测驱动开发的闭环。

  3. GLM-5 的 agentic 架构：GLM-5 在模型架构上引入了更强的工具调用稳定性和多步任务跟踪能力，是 GLM 系列从”强大的对话模型”向”可靠的 agent 底座”转型的标志。

在竞赛中的意义

GLM 系列的意义更多体现在市场层面而非纯技术层面：它是国内最早完成”从通用 LLM 向 agentic 模型”转型叙事的本土模型之一，对中国企业客户的说服力来自语言和合规两个维度，这是任何海外模型都难以复制的优势。

五、格局与意义：为什么 2026 开源快速逼近闭源

5.1 三个结构性原因

原因一：agentic coding 是可测量的

SWE-Bench、Terminal-Bench 这类闭环任务评测的成熟，使得”模型在 agentic coding 上到底有多好”第一次有了相对客观的度量。可测量意味着可优化——开源模型的迭代可以精确地对着这些指标打。当目标明确，资源充足的开源团队（DeepSeek、阿里、月之暗面背后都有充足的算力和数据）能以极快的速度追赶。

原因二：训练数据的同质化

agentic 训练所需的核心数据——GitHub 上的真实代码库、真实 issue 的解决轨迹、工具调用序列——是公开可获取的。这与通用对话 RLHF 的高质量人工标注不同，后者存在更高的数据壁垒。当训练数据的质量差异收窄，闭源与开源之间最重要的护城河之一就变薄了。

原因三：MoE 降低了大参数的门槛

DeepSeek V4 的 1.6T 总参 / 49B 激活，Qwen3 的 A3B 激活——MoE 架构使得”拥有大参数量的知识容量”与”推理时的实际计算成本”解耦。这让开源团队能够训练出知识容量媲美闭源旗舰的模型，同时保持可接受的推理成本。

5.2 闭源的剩余优势

差距的收窄不意味着消除。截至 2026 年中，闭源模型在以下方面仍有优势：

  • 非编程的复杂 agentic 任务：深度研究 agent、计算机操作 agent 等场景，通用推理能力的差距比 coding 场景更难通过专项训练弥补。
  • 安全与对齐训练：Minimal footprint、拒绝有害工具调用、在多步任务中保持行为可预期——这些训练需要大量人工审核和闭环反馈，开源模型在这里的投入仍然有限。
  • harness 与模型的协同优化：Claude 的 Opus 系列与 Claude Code，GPT-5.x 与 Codex API——闭源模型与其 harness 是深度共同优化的，模型知道 harness 的工作方式，harness 也针对模型的行为模式做了精确设计。这种协同在开源生态里很难复制。

5.3 对生态的影响

这场军备竞赛对整个 agent 生态的影响可以用三个词概括：降本、加速、分化。

  • 降本：开源模型把推理成本的参考基准拉低，倒逼整个市场重新定价。
  • 加速：多路并行的激烈竞争使模型能力提升速度远超单一垄断情形。
  • 分化：不同场景的最优模型选择开始分化——编程 agent 可能用 DeepSeek V4，中文企业场景可能用 GLM，需要最强通用推理的场景用 Claude/GPT。”一个 API 统治所有 agent 场景”的局面正在瓦解。

六、小结：有了好模型，为什么生产可靠性仍然不够

经过这场军备竞赛，到 2026 年中，我们已经拥有了一批真正为 agentic 训练过的强大模型：SWE-Bench Verified 上 80%+ 的成绩、1M token 的上下文、原生工具调用、开源可部署。

听上去，agent 的问题应该差不多解决了？

并没有。

拿一个 SWE-Bench 80% 的模型去跑真实公司里的工程任务，你很快会发现：成功率远不是 80%。原因不在模型本身，而在于 SWE-Bench 的任务是被精心挑选、边界清晰、有标准测试集的——它测的是模型在”理想条件下”的能力上限。真实工程任务是混乱的：代码库有历史债务、测试覆盖率不全、需求是隐式的、失败时没有明确的错误信息。

在这个现实与理想的鸿沟里，harness 工程才是决定生产可靠性的关键变量。

同一个 Opus 4.8 模型，接上一个设计粗糙的 harness，任务成功率可能是 30%；接上 Claude Code 这种深度设计过的 harness，成功率可以翻倍甚至更高。差的不是模型，而是上下文工程、失败恢复机制、权限系统、跨会话记忆管理——这些统称为 harness 的工程层。

下一篇（板块三）就是要讲透这一层：好的 harness 到底在解决模型的哪些具体短板，以及为什么”让模型成为可靠 agent”这件事，最终落在了工程而非模型上。
