一、引子：Agent 不是新模型，而是 LLM + 循环

在理解 Agent 之前，先想清楚”静态 LLM”到底缺什么。

一个标准的 LLM 推理过程是：给定输入 token 序列，输出一段文字，然后停止。这个架构在问答、写作、代码补全上已经非常强大，但它有三个根本局限，恰好堵死了”自主执行复杂任务”的路：

局限一：单步、无状态。 每次调用是独立的。模型不知道自己上一步做了什么，不知道环境现在是什么状态，也不能主动去拿新信息。问”查一下今天天气再帮我写邮件”——它只能假装知道天气，或者承认不知道，但它无法真正”去查”。

局限二：无法与环境交互。 LLM 是文字处理器，输入输出都是 token。它不能执行代码、不能读文件、不能调 API、不能打开浏览器。换句话说，它的”行动”只存在于文字层面，落不到现实世界。

局限三：不能自我纠错。 单次推理一旦输出就结束了。如果中间哪步出了错——前提假设错误、工具结果异常、中途遇到意外——模型没有机会回头检查、重试或重新规划。

Agent 要解决的，正是这三个局限。它的本质不是换一个更大的模型，而是给 LLM 套上一个”感知—决策—行动—反馈”的循环（loop）：

这个循环是 Agent 的骨骼。循环运行多少轮，取决于任务复杂度；每轮里 LLM 负责”想”，外部工具/环境负责”做”，结果再喂回给 LLM。

本文的任务是讲清楚支撑这个循环的四大能力——ReAct（执行框架）、Planning（规划）、Tool Use（工具使用）、Memory（记忆）、Reflection（反思）——并且讲清楚每个能力”解决了什么问题、创新在哪里、上限在哪里”。这是理解后面一切的地基。

二、ReAct：Reasoning + Acting 交替，Agent 的骨架

2.1 纯 Chain-of-Thought 的瓶颈

2022 年 CoT（Chain-of-Thought）论文展示了一件令人振奋的事：让模型在给出最终答案之前先”一步步推理”，准确率大幅提升。但 CoT 有一个致命约束——它是封闭的：整条推理链都在模型脑子里，无法访问外部信息，无法执行代码，无法验证中间结论。碰到需要”查资料再推理”或”计算再推理”的任务，CoT 只能在幻觉里绕圈。

2.2 ReAct 的核心思路

2022 年 Yao 等人的论文 ReAct: Synergizing Reasoning and Acting in Language Models 提出了一个简洁但深刻的改变：把”想（Thought）”和”做（Action）”交替嵌入同一个 token 序列，并在每次 Action 之后把环境返回的 Observation 也写进序列，供下一轮 Thought 参考。

  1. Thought 让 LLM 显式表达推理意图，为后续 Action 提供语义锚点，也让轨迹可解释。
  2. Observation 把真实环境反馈写回上下文，打通了模型与外部世界的信息通道——这是 CoT 做不到的。

2.3 为什么”边想边做”优于纯 CoT

原始论文的对比实验显示，在 HotpotQA（多跳问答）、Fever（事实核查）等任务上，ReAct 显著优于 CoT-only 和 Act-only（只行动不思考）。直觉上很好理解：

  • 只 CoT：推理正确但没有实际信息，容易产生幻觉。
  • 只 Act：盲目行动，不知道为什么这样做，遇到岔路不会推断。
  • ReAct：推理指导行动，行动结果更新推理，形成一个有方向的搜索过程。

2.4 ReAct 是几乎所有 Agent 的骨架

从 2023 年之后的主流 agent 框架（LangChain Agent、AutoGPT、Claude Code、OpenAI Assistants）到 2025–2026 的各类 coding agent，都可以看到 ReAct 结构的影子：一个主循环，Thought 在 LLM 内部完成，Action 发出工具调用，Observation 接收结果，写回上下文，再次调用 LLM。它是 Agent 骨架，不是可选项。

三、规划（Planning）：长程任务的骨架上加肌肉

3.1 为什么单靠 ReAct 不够

ReAct 解决了”一步步走”的问题，但在复杂长程任务上，光靠逐步反应（reactive）远远不够。想象一个任务：”帮我调研竞品、写一份 20 页的分析报告、生成可视化图表、发邮件给团队”。如果没有全局规划，ReAct 很容易在某一步陷入局部循环，或者执行完一半才发现前面的结构不对，需要整体返工。

规划（Planning）的核心价值是：在行动之前把任务拆解成子目标序列，形成一个可执行的计划，并在执行过程中动态调整。

改进版加入了重规划（Replanning）：每个子目标执行完，检查结果是否符合预期，如果偏差超过阈值，就重新调用规划器修改后续子目标。

3.3 任务分解的技巧

任务分解本身是个难题。几个实用策略：

递归分解：把大任务分解为子任务，再对复杂子任务继续分解，直到每个叶节点都足够原子（可以在一个 ReAct 循环内完成）。

依赖图：有些子任务之间有依赖关系（B 必须在 A 完成后执行），有些是并行的（C 和 D 互相独立）。显式地建模成 DAG（有向无环图），可以安全地并行执行独立子任务，大幅提速。

3.4 Tree-of-Thoughts：把规划变成搜索

2023 年的 Tree of Thoughts (ToT) 论文把规划推进了一步：它把推理过程建模为在一棵思维树上的搜索，而不是一条单链。每个节点是一个”中间思路状态”，从当前节点可以扩展出多个子节点（不同的下一步思路），然后用 LLM 对各个子节点打分（评估”这条路走下去有多大希望”），再用 BFS 或 DFS 策略选择继续探索哪条分支。

ToT 的意义在于：它让 LLM 从”贪心地一路走到底”变成了”有回溯的搜索”。在需要全局最优的问题（数学证明、代码生成中的设计决策）上，ToT 比 CoT 强很多。代价是推理成本高——每个节点都需要 LLM 评分。

3.5 规划的现实局限

规划能力目前的主要瓶颈是计划的准确性：LLM 生成的计划可能遗漏关键步骤，或者对执行难度估计不准。特别是在执行深处遇到意外时，重规划的代价很高。这就是为什么板块二（前沿模型）要专门讲”为 agentic 训练的模型”——它们会在 long-horizon 任务上做专门的微调，提升计划质量。

四、工具使用（Tool Use）：把 LLM 接到外部世界

4.1 Function Calling 的本质

工具使用解决了 LLM 和外部世界之间的物理隔离问题。其核心机制是 function calling（函数调用），OpenAI 在 2023 年 6 月将其引入 GPT-4，随后成为行业标准。

它的本质是：在 LLM 的输入中描述一组可用工具（工具名称、参数 schema、用途描述），让 LLM 在需要时输出一个结构化的”调用意图”而不是自然语言。外部 runtime 解析这个意图，执行真实工具，把结果返回给 LLM。

这里有一个关键设计：LLM 的输出不再是最终答案，而是一个”下一步做什么”的指令。执行权在 runtime，LLM 负责决策。这个分离是 agent 可靠性的重要基础——工具真正执行前可以插入权限检查、沙箱隔离等安全层。

4.2 工具生态带来的能力飞跃

有了可靠的工具调用，LLM 能做的事情从”生成文字”扩展到几乎一切：

  • 检索增强（RAG）：搜索向量库或互联网，把实时信息喂给模型，消灭知识截止日期的限制。
  • 代码执行：生成代码然后真正运行，看到真实结果——调试、数据分析、自动化任务。
  • 文件系统/数据库操作：读写文件、查询数据库，agent 因此能处理真实业务数据。
  • 浏览器/GUI 操作：通过 computer use API 操控网页和桌面应用，打开了”自动化一切人机界面”的可能。
  • API 调用：对接任意第三方服务（天气、支付、日历、邮件……），让 agent 能融入已有的数字基础设施。

4.3 工具调用的可靠性挑战

工具使用不是万能的，有几个现实挑战：

格式错误：LLM 有时生成的 JSON 不合法，或者参数名拼错，导致 runtime 无法解析。这在早期 GPT-4 时代是常见问题，现代模型好很多，但未完全消除。解决方案包括：用 grammar-constrained decoding 强制输出合法 JSON，或者在 runtime 层做自动修复重试。

工具选择错误：有多个工具时，LLM 可能选错工具（比如该用精确数学库却去搜索互联网）。缓解方案：给工具加清晰的描述和示例，限制同时可见的工具数量。

并发工具调用：复杂任务里经常需要同时调多个工具（并行搜索多个关键词）。现代模型支持在单次响应中输出多个工具调用，runtime 并行执行，再把所有结果一起返回。这对延迟优化很重要。

工具结果的置信度：工具返回的信息不一定可信（搜索结果可能过时、代码执行可能有 side effect）。模型需要有一定的怀疑精神，不能盲目信任工具输出。

五、记忆（Memory）：让 Agent 不失忆

5.1 上下文窗口的本质局限

LLM 的”工作记忆”就是上下文窗口（context window）。当前顶级模型的上下文窗口已经达到 100K–200K token，但这依然是有上限的。更重要的是：上下文窗口在每次会话结束后就清空了。一个需要跨天、跨会话工作的 agent，没有持久化记忆就是失忆症患者——每次启动都从零开始。

记忆系统要解决两个问题：（1）当前会话内，如何在有限上下文里高效管理信息；（2）跨会话，如何持久化并检索过去的经验。

5.2 记忆的四种类型

借鉴认知科学，agent 的记忆可以分成四类：

类型 类比 存储位置 特点
短期记忆 工作记忆 上下文窗口 快速访问，容量有限，会话结束即消失
长期记忆 情景记忆 向量数据库（如 Chroma、Faiss、Weaviate） 持久化，语义检索，容量无上限
实体记忆 语义记忆 结构化存储（KV 或图数据库） 存储关于特定实体（人、项目、文件）的属性
程序记忆 程序性记忆 代码/函数定义 通过工具调用固化的”技能”

5.3 记忆的三个阶段

无论哪种长期记忆，完整的记忆系统都经历三个阶段：

存储（Storage）：把什么信息写入长期记忆？一个重要设计决策。如果全部写入，检索噪声大；只写重要信息，需要判断”什么重要”。常见策略：对话摘要写入（而非逐字写入）、关键结论和决策写入、错误经验写入。

反思（Consolidation）：写入前，对原始信息做抽象和提炼。类似人类睡眠中的记忆巩固。将原始轨迹（”搜索了 A，返回了 B，发现 B 不对，改用 C”）提炼为结论性知识（”在任务 X 中，工具 C 比 B 可靠”）。

利用（Retrieval）：需要记忆时，用当前任务的语义相似度从向量库检索，把最相关的 K 条记忆注入上下文窗口。检索质量直接影响 agent 的表现——检索到无关记忆比没有记忆更有害（浪费上下文、引入噪声）。

5.4 为什么长程 Agent 必须有记忆

没有记忆的 agent 在长程任务上会犯两种错：一是重复劳动——每次都重新探索已经解决过的子问题；二是忘记约束——早期确认的设计决策在上下文被截断后消失，导致后期工作与早期矛盾。

记忆系统是把 agent 从”一次性工具”变成”长期协作伙伴”的关键。这正是 Claude Code 等生产级 agent 花大力气做跨会话记忆（CLAUDE.md、项目记忆文件）的原因——工程决策和项目上下文沉淀下来，agent 才能像熟悉代码库的人类工程师一样工作，而不是每次都重新读一遍所有文件。

六、反思（Reflection）：闭环纠错，自主性的关键

6.1 没有反思的 Agent 会怎样

前面四个能力（ReAct、Planning、Tool Use、Memory）已经让 agent 能”走下去”。但走下去不等于走对。特别是在开放任务里，agent 很容易陷入一个错误假设，然后在错误的方向上越走越远——每一步都合理，但整体偏了。

反思（Reflection）要解决的是：agent 如何识别自己的错误，并从中学习、纠正。这是自主性的关键——能自我纠错的系统，才不需要人类时刻监督。

6.2 Reflexion：从失败轨迹中提炼语言反思

2023 年 Shinn 等人提出的 Reflexion 是这个方向最有代表性的工作。它的核心思路是：

  1. Agent 尝试完成任务，产生一条完整轨迹（Thought-Action-Observation 序列）。
  2. 如果任务失败（或者评估器认为结果不够好），让一个”反思 LLM”分析这条轨迹，用自然语言总结”哪里出了问题、下次应该怎么做”。
  3. 把这条反思文字存入记忆（持久化）。
  4. 下次再执行相同或类似任务时，把历史反思注入上下文，引导 agent 避开同样的坑。

Reflexion 在 HumanEval（编程任务）上通过多轮反思迭代，最终通过率显著高于单次尝试——这说明”反思+重试”比”一次出对”更可靠，也更符合人类解决复杂问题的方式。

6.3 Self-Refine：迭代精炼输出

另一个思路是 Self-Refine（2023）：对同一个任务，让模型先生成一个初始输出，然后让同一个（或另一个）模型对这个输出打分并提出改进建议，再根据建议生成新版本，循环若干轮。

Self-Refine 不需要外部评估器或真实执行结果，只用 LLM 自身的判断力来迭代，适用于开放生成任务（文本、代码、摘要）。弱点是：如果 LLM 本身对”好”的判断有系统性偏差，Self-Refine 会把偏差放大而非纠正。

6.4 反思的三个层次

可以把反思分成三个层次，由浅到深：

即时反思（Immediate）：在当前任务执行中，发现单步错误立即重试。例如工具调用格式错误，runtime 报错，LLM 立刻重新生成正确调用。最浅，但最常用。

轨迹反思（Trajectory）：任务结束后（无论成功还是失败），对整条执行轨迹做复盘，提炼经验存入记忆。Reflexion 属于这一层。

元反思（Meta）：跨任务地分析自己的系统性弱点（比如”我在涉及时间计算的任务上总是出错”），修改自己的工作方式。这一层目前主要由人类来做（比如通过 prompt 优化或 fine-tuning），agent 完全自主的元反思还是研究前沿。

6.5 反思的局限

反思的有效性高度依赖反思质量本身。如果 LLM 生成的”反思”是错误的（对失败原因的误判），那这条反思非但没帮助，还会在未来污染上下文。此外，反思增加了每个任务的计算开销——每次失败都要额外调用 LLM 来分析。在高频、低容错的生产场景里，反思的收益和代价需要权衡。

七、小结：四大能力正交但需协同

回顾一下这五个机制，它们之间的关系：

ReAct 是骨架，定义了 Thought-Action-Observation 的基本节拍。

Planning 是肌肉，在骨架上加上长程方向感——知道整体要走哪里，而不是每步只看眼前。

Tool Use 是手脚，让 agent 真正能碰触外部世界，而不只是在 token 空间里打转。

Memory 是海马体，让 agent 能从历史中学习，而不是每次从零开始。

Reflection 是前额叶，让 agent 能审视自己的行为，识别错误，迭代改进。

这五个能力不是互相替代的，而是正交的——缺少任何一个，agent 在某类任务上就会明显变弱。但它们协同工作也面临工程挑战：记忆检索如果太慢，会成为每步推理的瓶颈；反思如果每步都触发，计算成本倍增；工具太多，LLM 的选择准确率下降。

这些上限，正是后续要突破的瓶颈。板块二（前沿模型）要讲的，是 Anthropic、OpenAI、DeepSeek 等如何在训练阶段就把这四个能力内化到模型权重里——让模型天生更擅长当 agent，而不是靠 prompt 技巧”外挂”这些能力。板块三（Harness 工程）要讲的，是当模型能力就位之后，如何通过工程手段把这四个能力在生产环境里稳定地发挥出来。

这是整个专题的内生逻辑起点：静态 LLM 加上循环，造就了 Agent 雏形；雏形暴露的上限，推动着接下来的一切演化。
