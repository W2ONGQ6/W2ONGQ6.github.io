Agent-05：应用与评测 —— 能力落地与"考卷"的进化

一、引子：模型 + harness 就位，应用随之爆发

板块三讲完了 harness 工程的核心结论：同一个模型，换一套 harness，任务成功率可以差出几十个百分点。上下文工程、跨会话记忆、失败即关闭的权限系统——这些工程实践把一个”聪明但不可靠”的模型，变成了一个”能在生产环境里自主跑完任务”的 agent。

这个转变，是应用爆发的真正起点。

在此之前，agent 的演示往往止步于”惊艳的 demo + 不堪用的实际体验”。根本原因不是模型不行，而是缺少那层把模型能力转化为可靠行为的工程外壳。当 Claude Code、Codex CLI、Cursor 等工具在 2025 年把 harness 做扎实之后，整个生态迅速翻页——不再是”这个 AI 能不能干这件事”，而是”这个 AI 能干多复杂的这类事”。

与此同时，评测也被倒逼着进化。原来的”开环问答”——给一道题，看模型答案对不对——已经越来越难区分”真会干”和”会蒙”。当 agent 真的开始自主操作代码库、浏览网页、执行终端命令，考卷也必须跟着变成”闭环任务”：把 agent 扔进真实环境，看它能不能从头到尾自己干完。

这一板块就是要讲清楚这两件事：应用如何落地，评测如何进化——以及两者之间那条更深的因果链。

二、编程智能体：最成熟的落地

2.1 为什么编程是 agent 最先突破的场景

三个结构性原因让编程成为 agent 的第一个真实战场：

验证闭环天然存在。 代码写完之后，有编译器、有测试套件、有 linter——这些工具能给出明确的”对/错”反馈，不需要人类裁判。这个特性对 agent 极其宝贵：它可以在本地反复试错，把”写→运行→看报错→改→再运行”这个循环跑几十次，而不需要每次都等人来告诉它哪里错了。

工具调用高度结构化。 编程任务的工具集相对固定：读文件、写文件、运行命令、搜索代码库。每个工具的输入输出都有明确的格式和语义，比”帮我订一张机票”这类任务的工具集简单得多。这让 harness 的工具描述和错误处理可以做到相当精确。

训练数据天然丰富。 互联网上有海量的代码、问题-解决方案对话、GitHub issue + PR。模型在预训练阶段就吸收了大量”问题描述 → 代码修改”的模式，agentic 微调阶段只需要在这个基础上强化”多步执行”的部分，而不是从零开始建立领域知识。

2.2 SWE-bench 破 80%：这个数字意味着什么

SWE-bench 是当前编程智能体领域最有说服力的基准。它的设计思路很直接：从 GitHub 上的真实开源项目中抽取 issue（问题报告），每个 issue 都附带一套验收测试——模型需要自主定位问题、修改代码，直到测试通过。

“Verified”子集经过人工筛选，确保每个任务的问题描述清晰、验收测试确实对应问题，去掉了原始集合里的噪声样本，是更公平的比较基准。

截至 2026 年中（以官方为准），前沿模型在 SWE-bench Verified 上的解题率如下：

模型 SWE-bench Verified 解题率
Claude Opus 4.5 ~80.9%
GPT-5.1-Codex-Max ~77.9%
Gemini 3 Pro ~76.2%

突破 80% 意味着什么？它意味着模型能独立修复真实代码库中超过四分之三的真实 bug，不是玩具问题，不是精心设计的教学案例，而是真实开源项目的真实 issue，有真实的测试套件来验收。

这是一个质变，不只是量变。2023 年的早期 agent 在 SWE-bench 上的解题率只有个位数，2024 年突破 30% 已经被认为是里程碑，2025 年底冲到 60%+，现在到了 80%+。这条曲线背后是模型侧（更好的代码理解和生成）与 harness 侧（更精准的上下文管理、更稳定的工具调用循环）共同提升的结果。

但更重要的是，这个数字重新定义了”AI 辅助编程”这件事的边界。过去，AI 辅助编程的上限是”给你补全一段代码”；现在，它能做到”给我一个 issue，我自己改好，你来合并 PR”。这不是辅助，是协作。

2.3 主流编程智能体的工程形态

Claude Code 是 Anthropic 把 harness 工程做得最极致的产品化工具。它在 CLI 层面集成了完整的上下文工程管道：CLAUDE.md 作为项目级指令注入点，自动感知 Git 状态、测试配置、代码风格；权限系统默认拒绝所有有破坏性的操作，每次写文件、执行命令都需要明确授权或预先配置白名单；多代理模式允许把复杂任务拆解成并行子任务，由多个 agent 实例同时处理不同模块，最后汇总。

Codex CLI（OpenAI）的定位是”在终端里直接运行的轻量 agent”。它的设计哲学偏向开放性：工具链更灵活，用户可以自定义工具集；沙箱隔离保证每个会话的文件操作不会污染宿主环境；与 GPT-5.x 系列模型深度集成，在代码生成和工具调用的对齐上有明显的专项优化。

Cursor 走的是另一条路：它把 agent 能力嵌进 IDE，而不是让用户切换到终端。这带来了一个重要的上下文优势——光标位置、当前编辑的文件、打开的标签页、最近的编辑历史，都自然地流入 agent 的上下文，不需要手动描述”我现在在做什么”。代价是把 agent 变成了 IDE 功能的一部分，重度集成反而限制了它在 IDE 之外的使用。

三种形态背后是三种关于”agent 应该在哪里活”的判断：终端（Claude Code）、终端+灵活工具链（Codex CLI）、IDE 原生（Cursor）。目前看，这三个方向都在持续演进，用户群体的选择也在分化。

三、深度研究（Deep Research）：多步检索-综合-成文

3.1 什么是深度研究任务

深度研究（deep research）代表了另一类重要的 agent 应用形态。与编程任务不同，它的验收标准不是”测试通过没有”，而是”报告写得全不全、准不准、逻辑是否自洽”——这是一个更难形式化的目标。

一个典型的深度研究任务长这样：给 agent 一个开放式问题，比如”梳理 2023–2026 年大型语言模型在推理能力上的主要进展，重点分析思维链训练和验证器设计的演化”。然后让它自主搜索文献、抓取网页、阅读 PDF、交叉验证来源，最终输出一份有引用、有结构、有判断的研究报告。

这个任务的难点在于：它的”正确答案”是分布式的，散落在数十篇论文和技术博客里，而且这些来源之间存在矛盾和不一致。Agent 需要做的不是”检索然后粘贴”，而是真正地”读懂、综合、判断”。

3.2 深度研究 agent 的内部机制

深度研究 agent 通常跑一个迭代式的”搜索-阅读-综合”循环：

初始规划阶段： 拿到问题后，agent 先做一次分解——把大问题拆成若干子问题，生成初始搜索计划。这一步的质量很大程度上决定了后续能不能覆盖到关键信息。

迭代检索阶段： 执行搜索，阅读结果，提取关键信息，更新”已知”和”待解”的状态。关键是这个过程是迭代的：每一轮搜索的结果会更新 agent 对问题的理解，进而触发新的搜索。一个好的深度研究 agent 能跑 10–30 轮检索，每轮都更接近全面覆盖。

交叉验证阶段： 对于关键事实（数字、日期、归因），agent 会主动搜索第二个来源来确认。这个步骤在早期 agent 里往往缺失，是”听上去有理但其实在编”的主要根源。

综合成文阶段： 把散落的信息组织成有结构的报告。这一步对长程上下文的要求极高——agent 需要在写报告的同时，还能随时”回忆”前面收集到的某个细节。

深度研究任务是 GAIA 基准（通用助手任务）着重考察的能力之一，后面评测部分会详细介绍。

3.3 深度研究的实际局限

当前深度研究 agent 的能力边界是清晰的：它在”广度优先的信息汇总”上已经超过了普通人的效率，但在”需要深度领域直觉的判断”上仍然明显弱于领域专家。

具体说：让 agent 写一篇”梳理某个技术领域近年进展”的综述，它能做到比一个新进入该领域的研究生快几十倍，覆盖面甚至更广。但如果问它”这篇论文的实验设计有什么根本性缺陷”，它的判断质量会明显下降，因为这需要的不是信息汇总，而是领域内化的批判性思维。

这个边界并不是 agent 的失败，而是它在信息处理效率上的真实优势被清晰地圈了出来。

四、计算机操作（Computer Use）与企业 agent

4.1 Computer Use：GUI 自动化的范式升级

Computer Use 的核心思路是：让 agent 直接操作计算机屏幕，就像人类操作一样——截图、识别 UI 元素、点击、输入、滚动。

这听上去像是传统 RPA（机器人流程自动化）的升级版，但有一个根本区别：传统 RPA 靠的是”找到特定坐标/元素的固定脚本”，一旦 UI 布局变化，脚本就失效了。基于视觉理解的 Computer Use agent 靠的是”理解屏幕上的语义”——它看到一个按钮，知道那是”提交”，而不是坐标 (342, 187)。这让它能应对 UI 的动态变化，也能处理没有 API 的遗留系统。

Anthropic 在 2024 年底发布的 Claude computer use 功能是这个方向的重要里程碑。它能接受截图作为输入，输出鼠标和键盘操作指令，配合沙箱环境实现对浏览器、文件管理器、各类 GUI 应用的自主操控。这打开了一整类过去因”没有 API 接口”而无法自动化的任务场景。

4.2 为什么 Computer Use 比看上去更难

Computer Use 的挑战远比”看截图点按钮”复杂：

视觉-语义对齐问题。 同一个”确认”操作，在不同应用里可能是绿色的”OK”按钮、蓝色的”Confirm”、回车键，或者对话框右上角的勾选图标。Agent 需要理解当前 UI 的语义结构，而不是靠外观特征的字面匹配。

多步骤状态跟踪。 填写一个复杂表单可能需要 20 步操作，中间任何一步的 UI 状态都可能影响后续步骤的判断。Agent 需要维护”到目前为止做了什么、当前处于哪个状态、接下来应该做什么”的完整心理模型。

错误恢复机制。 点错了一个按钮，弹出了意外的对话框，或者页面加载超时——这些情况在真实操作中频繁发生。Agent 需要能识别”我偏离了预期路径”，然后决定是回退、重试还是换个路径。

操作不可逆性。 误删了一个文件，误提交了一个表单，误发了一封邮件——Computer Use 的操作往往有真实后果。这要求 harness 层面有严格的权限控制和操作确认机制，而不能”用最快路径完成任务”。

4.3 企业 agent：从单点自动化到工作流编排

Computer Use 是企业 agent 的一个组件，而不是全部。企业级的 agent 应用通常覆盖更广的范围：

跨系统的数据流转。 从 ERP 拉一个报告，提取关键数字，填入另一个系统的审批表单，发送通知邮件——这类任务在大公司里每天发生几千次，但每一步都涉及不同的系统和格式。Agent 能把这些拆散的操作串成一个可靠的工作流。

文档处理与知识问答。 合同审查、法务文件摘要、内部知识库问答——这类任务过去要么靠人工、要么靠专门的关键词搜索系统。Agent 能理解文档语义，回答”这份合同里有哪些违约条款对我方不利”这样的问题。

客户服务 agent。 接入工单系统、CRM、产品知识库，自主处理常见问题，必要时生成解决方案草稿交给人类审核。这已经在不少公司的实际生产环境里跑了一年以上。

企业 agent 的落地核心不是技术突破，而是在可靠性和授权边界上的工程约束——谁能批准哪些操作、操作日志如何审计、出错了由谁负责。这些问题比模型能力更难解决，也是当前企业采用率仍然受限的主要原因。

五、评测的进化：从”开环问答”到”闭环任务”

这是整个板块最值得深入的部分。评测的演化，不只是”出了几个新榜单”，而是整个领域对”什么叫真正有能力”这个问题认知的深化。

5.1 开环评测的局限：会背答案的鹦鹉

传统 NLP 评测的范式是开环的：准备一批题目（选择题、填空题、问答对），喂给模型，看输出和标准答案的匹配度。这个范式在评测”模型知道什么”时是有效的——它简单、可复现、容易大规模运行。

但当模型开始被用来做事而不只是回答时，开环评测暴露出了根本性的局限：

静态答案无法验证动态执行。 问模型”如何修复这个 Python 函数的内存泄漏”，它可以给出一个听上去很合理的答案，但那个答案是否真的能解决问题，只有把代码实际跑起来才知道。开环评测没有”运行”这个步骤。

容易被记忆和过拟合。 大模型的预训练语料覆盖极广，很多”标准答案”本身就可能出现在训练数据里。这导致开环评测越来越难区分”真的会”和”背下来了”。

无法衡量多步能力。 一个需要 15 步工具调用才能完成的任务，拆成 15 道独立选择题后，每道题的难度可能都不高。但把这 15 步串起来、在真实环境里执行不出错，这才是 agent 真正需要的能力——而这个能力在开环框架里几乎无法测量。

5.2 SWE-bench：闭环评测的里程碑

SWE-bench 的出现（普林斯顿大学，2023 年末发布，2024–2025 年持续成为主流基准）代表了一个范式转变：把真实的软件工程任务搬进评测框架，用自动化测试取代人类裁判。

它的闭环特性体现在：模型不是”告诉我怎么改”，而是直接去改代码，然后运行测试套件，pass 了才算成功。这个验证链路不需要人类判断，完全自动化，又完全基于真实的工程场景。

SWE-bench Verified 是其精炼版本，经过人工筛选确保任务质量，去掉描述模糊或测试有缺陷的样本。截至 2026 年中（以官方为准），Claude Opus 4.5 在此子集上达到 ~80.9%，GPT-5.1-Codex-Max ~77.9%，Gemini 3 Pro ~76.2%。

但 SWE-bench 的成功也带来了一个熟悉的问题：当所有顶级模型都奔着它优化，这个基准的区分度开始下降。当前沿模型已经能解决 80%+ 的任务，剩余 20% 里的难题到底是什么性质的？SWE-bench 自身的任务分布能不能继续推动模型能力边界？这些问题催生了新的基准。

5.3 DeepSWE：更难、更接近真实工程师的日常

DeepSWE 由 Datacurve 于 2026 年 5 月 26 日发布，共 113 个任务。它的设计出发点是：SWE-bench 里的很多任务已经对顶级模型太简单，需要一个能持续区分前沿能力的难题集。

DeepSWE 的任务有几个特点：任务复杂度更高，往往需要跨多个文件、多个模块的联动修改；问题描述故意保留了一定的模糊性，更接近真实 issue 的风格（人类开发者并不总是把问题描述得很清楚）；部分任务需要先理解项目的整体架构，才能找到正确的修改位置。

113 个任务的规模相对小，但这是设计决策：小而精的任务集可以对每道题做深度的人工标注和验证，确保”通过了就是真的对”，而不是靠运气或者对测试的过拟合。

5.4 Terminal-Bench：终端环境的全栈能力测试

Terminal-Bench（2.0/2.1 版本，截至 2026 年中以官方为准，GPT-5.5 在其上达到 ~82.7%）的定位和 SWE-bench 不同：它考察的不只是”改代码”，而是在终端环境里完成全栈工程任务——包括环境配置、依赖安装、构建调试、运行测试、分析输出、根据输出做判断再操作。

这更接近一个真实工程师在新机器上接手一个陌生项目时会做的事情：没有预配置的 IDE，没有现成的测试环境，需要自己把整个链路搭起来，然后完成任务。

Terminal-Bench 的”终端原生”特性使它对 agent 的工具使用广度要求更高——不只是读写文件和运行 Python，而是使用 curl、git、make、docker、pip、apt 等各种命令行工具，并能根据每个命令的输出正确判断下一步。

5.5 Senior SWE-Bench：区分”能跑通”和”写得好”

Senior SWE-Bench 针对的是 SWE-bench 的一个核心缺陷：测试通过不等于代码写得好。

SWE-bench 的验收标准是测试 pass，但一个通过了测试的解决方案可能有以下问题：硬编码了测试用例的特殊条件（只让这个测试 pass，但对其他输入行为不对）；用了极度 hacky 的方式绕过问题而不是真正修复根因；引入了新的技术债务或破坏了代码风格一致性。

Senior SWE-Bench 的出发点是：真实的高级工程师审查代码时，不只看测试有没有 pass，还看解决方案有没有”工程品味”——是否真正理解了问题根源、是否遵循了代码库的设计惯例、是否做了必要的测试覆盖而不只是让原有测试 pass。

这个基准的评测不再是完全自动化的，需要引入人类评审对”代码质量”维度做判断，这也让它的运行成本显著高于纯自动化基准。但它触碰到了一个重要问题：当 agent 自主提交代码进代码库，测试只是最低门槛，”能不能写出人类工程师愿意维护的代码”才是真正的考验。

5.6 GAIA：通用助手任务的综合测试

GAIA（General AI Assistants，2023 年发布，持续更新）考察的不是编程，而是通用助手场景下的多步任务。典型任务包括：在网上找到某个特定事实（需要多次搜索和交叉验证）、处理文件然后回答关于文件内容的问题、根据一组条件在多个选项中找出唯一答案。

GAIA 的设计哲学是：人类回答这些问题并不难（需要几分钟到几十分钟），但对当前 AI 系统来说却相当挑战。这个差距不是因为问题太难，而是因为它们需要精确的多步执行——每一步都做对，中间不能犯任何会影响最终答案的错误。

GAIA 的三个难度级别对应了不同的任务复杂度：Level 1 只需要少量工具调用，Level 2 需要多步骤和工具组合，Level 3 需要长程规划和复杂的信息综合。前沿 agent 在 Level 1 的表现已经相当好，但在 Level 3 上仍有明显差距，说明”单步执行准确”和”长程任务鲁棒性”之间仍然是不同维度的能力。

5.7 GDPval：对比人类专家胜率

GDPval 的出发点最直接：不用固定的测试集，直接看 agent 和人类专家在同等任务上的胜负。

它让 agent 和人类专家处理同一批任务，然后由独立评审盲判哪一份输出更好、更准确、更有用。这消除了”固定榜单被优化”的问题——因为任务是动态生成的，很难针对性地过拟合。

GDPval 的局限是成本极高：每次评测都需要人类专家参与，无法大规模自动化。但它能回答一个其他基准都回避的问题：在真实工作场景里，agent 到底在哪些任务类型上能打过专家，哪些不行？这个答案对于理解 agent 的实际部署价值比任何自动化榜单数字都更有指导意义。

5.8 “你怎么考它，就决定了它往哪进化”

这些基准的演化轨迹揭示了一个超越技术细节的规律：评测框架本身就是能力方向的选择器。

当行业的主流评测是选择题和填空题时，模型进化的压力就在于”知识覆盖面”和”格式匹配”。当行业的主流评测变成”能不能让测试 pass”时，模型进化的压力就转移到了”多步执行可靠性”和”工具调用精度”。当行业开始用”代码质量”和”专家胜率”来考察，能力进化的方向又会进一步推向”工程判断力”和”领域内化的批判性思维”。

这个规律在技术史上反复出现。ImageNet 基准推动了卷积神经网络的繁荣，同时也埋下了”针对 ImageNet 过拟合”的问题；BLEU 指标推动了机器翻译的量化优化，同时也激励了大量”BLEU 高但人类读起来很奇怪”的模型。每一个被广泛采用的评测基准，都在隐性地定义”什么叫做好的 AI”——直到它自身的局限被下一个基准取代。

这不是评测设计者的失败，而是任何代理指标在被广泛优化后都会偏离它本来想衡量的真实能力——这是 Goodhart 定律在 AI 领域的具体体现。理解了这一点，看到新基准出现时，正确的问题不是”这个数字有多高”，而是”这个基准在对齐什么真实能力，以及它本身会怎么被过拟合”。

六、结语：内生逻辑的闭环

至此，本专题的主线可以画成一个完整的因果环：

静态 LLM 只会生成 token，没有行动能力。为它套上”感知—决策—行动—反馈”的循环，加上工具调用和记忆模块，就有了 agent 雏形（板块一）。

雏形暴露了通用 LLM 的先天不足：goal drift、tool alignment gap、context amnesia。修复这些需要专门的训练目标，于是出现了 agentic 模型军备竞赛（板块二）——Claude Opus 4.x、GPT-5.x、DeepSeek V4、Kimi K2/K3、Qwen3 系列，都在为”长程自主执行”专项优化。

光有好模型仍然不够可靠。同一个模型，harness 做得好和做得差，成功率可以差几十个百分点。于是 harness 工程（板块三）成为生产可靠性的真正决定因素——上下文工程、跨会话记忆、权限隔离、多代理协作，把”聪明但不可靠”变成”可以信赖的协作者”。

当模型和 harness 都就位，应用爆发（本板块）：编程智能体（SWE-bench 破 80%）、深度研究、computer use、企业 agent，一层层落地。与此同时，评测从开环进化为闭环，从”能不能答对”到”能不能在真实环境里干完”——SWE-bench、DeepSWE、Terminal-Bench、Senior SWE-Bench、GAIA、GDPval，每一个新基准都是能力边界被推进后，旧的考卷不再够用的结果。

这个闭环不会停在这里。当前 80%+ 的 SWE-bench 解题率意味着什么也意味着什么仍然做不到：Senior SWE-Bench 揭示的”工程品味”缺口、GDPval 揭示的领域专家级判断力差距，指向了下一阶段的进化方向。

可靠性、成本、安全仍然是横在应用爆发和真正规模落地之间的三道槛：

  • 可靠性：当前最好的 agent 在结构化任务上的成功率已经很高，但面对边缘情况、异常输入、不完整信息时，行为仍然不稳定。这是”能演示”和”能生产”之间的距离。
  • 成本：一次复杂的 agentic 任务可能消耗数千甚至数万 token，加上多次工具调用的延迟，成本比单次问答高出一个量级。大规模部署的经济性仍然需要模型效率和 harness 优化的双重进步。
  • 安全：agent 有行动能力意味着它的错误可以造成真实损害——误删文件、误提交代码、误发邮件。如何在赋予 agent 自主性的同时，保持足够的人类监督和可控的操作边界，是一个至今没有完美答案的工程和制度问题。

这三道槛的突破方向，已经清晰地写在了 2025–2026 的研究议程里。读懂了”能力基石 → 模型 → harness → 应用/评测”这条内生逻辑，你就能把这些进展准确地放到它们该在的位置，而不是在每次新发布面前重新迷失方向。
