KV Cache 优化思想演化史 —— 一条主线串起所有技术

写在前面：为什么需要一条”演化主线”

KV Cache 的优化技术已经多到令人眼花：MQA、GQA、MLA、量化、Token 驱逐、稀疏注意力、PagedAttention、前缀缓存、分离式架构……本专栏为其中每一类都写了专文。但如果只是并排陈列，读者很容易只见树木不见森林——记住了一堆名词，却说不清它们为什么依次出现、彼此是什么关系。

本文是整个 KV Cache 专栏的主线索引。它不重复各篇的技术细节，而是回答一个更根本的问题：

KV Cache 的优化，是沿着一条怎样的思想脉络演化至今的？

答案可以浓缩成一句话：KV Cache 从”自回归解码的一个实现细节”，一步步变成了”整个推理系统的一等公民乃至中心”。 这条演化线上的每一步，都是被上一步遗留的瓶颈逼出来的。读懂这条因果链，你就能把任何一项新技术准确地安放到版图中的位置。

起点：KV Cache 是什么，以及它为什么会成为瓶颈

Transformer 自回归解码时，每生成一个新 token，都要用它的 Query 去和前面所有 token 的 Key、Value 做注意力。如果每步都重算前面所有 token 的 K、V，计算量是 的灾难。

KV Cache 的思想极其朴素：把已经算过的 K、V 缓存下来，下一步直接复用，把每步复杂度从 降到 。这是一个”用空间换时间”的经典交换——而正是这个”空间”，成了此后一切故事的源头。

四条演化主轴：向公式里的每个变量开刀

面对上面那个显存公式，优化思想沿着四条主轴展开——它们分别在攻击公式里的不同因子，彼此正交、可以叠加。这是理解整个领域的核心框架。

主轴 攻击公式里的 核心思想 一句话
轴一：架构缩减 （每 token 的”宽度”） 改造注意力结构，让每个 token 缓存更少 从源头把单 token 变小
轴二：数量削减 （token 的”数量”） 只保留重要的 token / 稀疏访问 不是每个 token 都值得留
轴三：精度压缩 bytes（每个数的”字节数”） 低比特量化 每个数存得更轻
轴四：系统治理 内存的”利用率”与”复用率” 分页、前缀共享、跨请求复用、分离式 缓存不该被浪费，也不该只属于一次请求

前三轴是”让缓存本身更小“，第四轴是”让既有缓存被管得更好、用得更足“。下面沿着”被瓶颈逼着走”的因果顺序逐一展开，并标出每篇专文在演化中的位置。

轴一：架构缩减 —— 从源头削减每个 token 的”宽度”

最釜底抽薪的思路：既然 ，那就改造注意力架构本身，让每个 token 天生就缓存更少的 K、V。这条线是一部清晰的递进史：

  • MQA（Multi-Query Attention）：所有 Query 头共享一组 K、V。缓存直接砍到 ，但表达力受损、质量下降。
  • GQA（Grouped-Query Attention）：折中——把头分组，组内共享 K、V。在”省显存”和”保质量”之间找平衡，成为 Llama 2/3 等主流模型的标配。
  • MLA（Multi-head Latent Attention）：DeepSeek 的杀手锏。不再共享，而是把 K、V 压缩到一个低维潜空间再缓存，用时解压。它既大幅缩减缓存，又几乎不损质量——是这条轴迄今最优雅的答案。
  • CLA / YOCO：进一步跨层共享或”只算一次 KV”，把削减推向层间维度。

这条轴的思想内核：KV Cache 的大小是被模型结构”设计”出来的，那就重新设计结构。它的代价是——必须在预训练阶段就定好，无法对已有模型事后套用。

轴二：数量削减 —— 不是每个 token 都值得留

架构轴要改预训练，成本高。于是另一条思路问：能不能对已有模型，在推理时就把不重要的 token 从缓存里扔掉？ 这条轴的前提，是两个关于注意力的基本发现：

  1. Attention Sink（StreamingLLM）：最初几个 token 吸走了不成比例的注意力，删了模型就崩——所以它们必须留。
  2. Heavy Hitter（H2O）：注意力矩阵 95% 以上是稀疏的，少数 token 贡献了绝大部分注意力——留住它们就够了。

这两个发现直接催生了一整族”该丢什么“的方法：H2O（按累积注意力驱逐）、SnapKV（提示压缩）、PyramidKV（逐层递减预算）、Quest（页粒度稀疏召回）……它们的分歧只在于”如何判定重要性“和”在什么粒度上操作“。

这条轴的思想内核：从”缓存全部”到”缓存值得的”。它引出一个更深的追问——如果稀疏性是注意力的固有属性，为什么要等到推理时才补救？能不能让模型在训练时就学会稀疏？这就顺势推开了下一扇门。

📖 驱逐与稀疏族谱：KV Cache 该丢弃什么：Token 驱逐与稀疏
📖 把稀疏做进训练：可训练稀疏注意力：NSA 与 MoBA —— DeepSeek NSA、Kimi MoBA 让模型原生学会稀疏，是轴二从”事后补救”到”原生能力”的升华。

轴三：精度压缩 —— 每个数存得更轻

前两轴动的是”多少个数”，这一轴动的是”每个数占几个字节”。思想同样直接：把 KV Cache 从 FP16 量化到 8-bit、4-bit 甚至 2-bit。

难点在于 KV 对精度敏感，粗暴量化会崩。关键洞察来自 KIVI：Key 和 Value 的数值分布完全不同——Key 有逐通道的异常值，适合逐通道量化；Value 没有通道结构，适合逐 token 量化。KVQuant、FP8 等沿着”按分布特性分而治之”继续深化。

这条轴的思想内核：不改结构、不删 token，只在”表示精度”上榨空间，且能与前两轴自由叠加。它是最”即插即用”的一条轴。

📖 量化方案详解：KV Cache 量化：KIVI / KVQuant / FP8

轴四：系统治理 —— 缓存不该被浪费，也不该只属于一次请求

前三轴把单份缓存做小了。但真实推理系统里还有两个巨大的浪费：显存碎片和重复计算。轴四的思想跃迁在于——把 KV Cache 当作一个需要被系统性管理的资源，而不是每次请求各自为政的临时数据。这条轴本身又是一段层层递进的演化：

4.1 内存管理：PagedAttention 与前缀共享

PagedAttention（vLLM）把操作系统的虚拟内存分页思想搬进了 KV Cache：缓存不再要求连续大块显存，而是切成固定大小的 block 按需分配，消灭了外部碎片，显存利用率逼近极限。在此之上，前缀缓存让共享同一前缀（如相同 system prompt）的请求复用同一份 KV——第一次”缓存复用”从单请求内跨越到了请求之间。SGLang 的 RadixAttention 用前缀树把这种复用推向自动化、最大化。

4.2 复用的边界突破：从”前缀”到”任意片段”

前缀复用有个硬限制：只能复用相同前缀。但 RAG 场景里，多个文档片段的组合顺序千变万化，前缀几乎从不重合。CacheBlend 打破了这堵墙——支持非前缀的 KV 复用；CacheGen 则把 KV 编码压缩以便低成本存储和网络传输；LMCache 把这些能力整合成一个可挂载到 vLLM 的生产级 KV 缓存层（多级存储 + 复用）。复用的粒度从”前缀”解放到了”任意片段”。

📖 LMCache 与 CacheGen / CacheBlend：生产级 KV 缓存层

4.3 终点：以 KV Cache 为中心重构整个架构

演化的最高潮，是 KV Cache 从”被管理的资源”升格为”架构的组织中心“。Mooncake（Kimi）提出以 KVCache 为中心的分离式架构：把 Prefill 和 Decode 拆成独立资源池（PD 分离），中间用一个跨节点的分布式 KVCache 存储（借 RDMA 高速传输）连接，并围绕缓存命中率做全局调度。至此，KV Cache 不再是某个 GPU 里的一块显存，而是整个推理集群的一等公民——这正好呼应了本文开头那句话。

演化全景：一张因果链

四条轴不是互斥的路线之争，而是可以同时叠加的正交维度：一个生产系统完全可以用 MLA 架构（轴一）+ FP8 量化（轴三）+ PagedAttention 前缀缓存（轴四），三管齐下。

更远的终点：绕过 KV Cache 本身

以上四轴，都是在”Transformer 注意力必然产生 KV Cache“这个前提下做优化。但还有一条更激进的思想：如果换掉注意力这个序列混合原语，KV Cache 的线性增长问题就从根上不存在了。

线性注意力、状态空间模型（Mamba）、RWKV、以及 Attention/SSM 混合架构（如 Jamba），用一个固定大小的循环状态取代随长度增长的 KV Cache——代价是牺牲一部分对历史的精确随机访问能力。这是与本专栏四轴平行的”第五条路”，属于架构范式的更替。
