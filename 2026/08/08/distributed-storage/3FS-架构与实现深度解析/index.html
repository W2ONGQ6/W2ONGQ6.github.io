3FS 架构与实现深度解析

3FS 架构与实现深度解析

本文是「分布式存储系统」专题的又一篇单系统深剖。上一篇《JuiceFS 架构与实现深度解析》讲的是「组合优于自造」的云原生路线——把数据交给对象存储、语义交给事务型 KV。这一篇我们走向另一个极端：DeepSeek 开源的 3FS（Fire-Flyer File System），一个为 AI 训练/推理而生、把 NVMe SSD + RDMA 的硬件红利榨干的高性能分布式文件系统。它不站在对象存储肩上，而是自己直管裸盘、自己实现链式复制，用一套「无状态元数据 + CRAQ 强一致 + 用户态零拷贝 IO」的设计，把聚合读带宽做到了 6.6 TiB/s 的量级。

一、3FS 是什么

3FS 是 DeepSeek 开源（MIT 协议）的高性能分布式文件系统，全称 Fire-Flyer File System。它的设计目标一句话概括：

把成百上千块 NVMe SSD 的总吞吐、成百台存储节点的总网络带宽，聚合成一个对应用「位置无关（locality-oblivious）」的共享存储池，喂饱 GPU 集群的 AI 训练与推理负载。

和 JuiceFS「组合式」的哲学恰好相反，3FS 走的是垂直自研路线：

  • 数据：不用对象存储，而是让每个存储节点直管本地裸 NVMe SSD，自己实现 chunk 分配、复制与容错。
  • 元数据：不自己造分布式事务，而是站在 FoundationDB 肩上——这一点和 JuiceFS 用外部事务 KV 是同源的思路。
  • 一致性：不用 Raft/Paxos 那套多数派共识，而是选了 CRAQ（Chain Replication with Apportioned Queries，带均摊查询的链式复制） 来兑现强一致。
  • 网络：全链路 RDMA（InfiniBand 或 RoCE），配自研 RPC 框架。
  • 客户端：既提供普通的 FUSE 挂载（兼容性优先），又提供绕开 FUSE 的用户态零拷贝 IO 接口 USRBIO（性能优先）。

它诞生于 DeepSeek 的 Fire-Flyer AI-HPC 训练基础设施（arXiv 2408.14158，SC’24）——那套用 1 万张 PCIe A100 逼近 DGX-A100 性能、成本砍半的集群。3FS 就是它的存储底座。理解 3FS 的每一个设计取舍，都要放回这个前提：服务对象是 GPU，敌人是「读带宽不够、随机小读太慢、GPU 空等数据」。

二、整体架构：四大组件 + RDMA 底座

3FS 由四类组件构成，全部通过 RDMA 网络互联：

2.1 Cluster Manager（mgmtd）

管理集群成员变更与配置分发。部署多个，选举出一个 primary，故障时提升另一个顶上。只有 primary 能修改 chain table（复制链的拓扑，见 §6）。配置可以放 ZooKeeper/etcd，但生产中 3FS 干脆把配置存进和文件元数据同一个 KV（FoundationDB），少一个外部依赖。存储/元数据服务都向它发心跳。

2.2 Metadata Service（meta）

无状态——这是关键设计。它实现文件系统的 POSIX 语义（create/lookup/rename/listdir…），但自身不持有任何持久状态，所有状态都落在 FoundationDB 里。因此客户端可以连任意一个 meta 节点，某个节点重启/升级/宕机都能无缝切换。详见 §3。

2.3 Storage Service（storage）

每个存储节点管理若干块本地 SSD，对外暴露一个 chunk store。它用 CRAQ 实现强一致的链式复制（§4），底层用自研的 Chunk Engine（§5）把 chunk 落到裸盘。「write-all-read-any」的链式复制思路，正是为了把 SSD + RDMA 的读吞吐彻底释放出来。

2.4 Client（FUSE + USRBIO）

两种客户端：FUSE 客户端降低接入门槛，绝大多数应用直接挂载即用；USRBIO 原生客户端面向性能关键路径，绕开 FUSE 内核态的开销（§8）。

2.5 为什么全用 RDMA

AI 训练要的是极高聚合带宽 + 低延迟随机读。传统 TCP 协议栈的内核拷贝和中断开销在这个量级下会成为瓶颈。3FS 全链路走 RDMA（InfiniBand 或 RoCE），并自研了一套 RPC 框架：带序列化、包合并、基于模板的反射（C++ 没有原生反射），以及一个两级缓存（线程本地队列 + 全局队列）在最优情况下避免加锁。测试峰值配置里，存储节点用 2×200 Gbps IB，客户端 1×200 Gbps IB。

三、元数据服务：无状态 + FoundationDB 事务

3.1 为什么选 FoundationDB

FoundationDB（FDB）提供一个带 可串行化快照隔离（SSI） 事务的 KV 接口。3FS 选它的核心理由和 JuiceFS 选 TiKV 如出一辙——把「分布式事务」这个硬骨头下推给专业选手：

  • 无状态 meta 服务成为可能：状态全在 FDB，meta 节点可随意重启、升级、故障转移。
  • 自动冲突检测与重试：FDB 追踪每个事务的读写 key 集合，冲突时自动重试。meta 服务因此可以大量并行处理请求，把冲突处理甩给 FDB。

这正是《数据库原理》里 OCC（乐观并发控制）思想的落地——FDB 本身就是工业级 OCC/SSI 的代表。

3.2 元数据在 FDB 里怎么存

两类核心结构：

结构 Key 设计 Value 内容
Inode "INOD" 前缀 + 64 位 inode id（小端编码） 文件：长度、chunk 大小、chain table 范围、shuffle 种子；目录：父 inode id、默认布局；符号链接：目标路径
Directory Entry（dentry） "DENT" 前缀 + 父 inode id + 条目名 目标 inode id + 类型

两个细节很讲究：

  • inode id 用小端编码：让连续分配的 inode 在 FDB 的 key 空间里打散到不同节点，避免热点。
  • dentry 的 key 是「父 inode + 名字」的连续区间：listdir 直接一个范围查询搞定，天然高效。

这和《分布式文件存储与 POSIX 语义》§3.5/§3.11 反复强调的 inode 与目录项分离原则完全一致——rename 只动 dentry、硬链接多个 dentry 指同一 inode，都因此变得自然。

3.3 两个「反直觉但很聪明」的取舍

① 不追踪只读文件描述符。 训练任务会同时打开海量文件，若每个 fd 都去 FDB 登记会把元数据打爆。3FS 干脆只为「写模式」的 fd 维护 file session，只读 fd 完全不记。删除一个仍有活跃写 session 的文件时，真正删除会被延迟（兑现 open-unlink 语义）。

② 文件长度「写时可最终一致」。 多客户端并发写同一文件时，精确长度难实时维护。3FS 让客户端每 5 秒（默认）上报一次自己的最大写入位置；在 close/fsync 时，meta 服务再去向存储端查询最后一个 chunk 的 id 与长度，算出精确文件大小。这些「长度更新任务」通过对 inode id 做 rendezvous hashing（会合哈希）分散到各 meta 服务上，避免单点。

四、存储服务：CRAQ 链式复制

这是 3FS 数据层最核心的一节，也是它和 JuiceFS/Ceph 最不同的地方。3FS 不用多数派共识，而选了 CRAQ。

4.1 什么是链式复制与 CRAQ

链式复制（Chain Replication）：把一个数据分片的多个副本排成一条链——头（head）、中间、尾（tail）。写从头进入，沿链向下传播，到尾提交；读只从尾节点返回，保证强一致。

CRAQ 是它的增强版：允许从链上任意节点读（均摊查询负载），靠给每个对象维护「committed（已提交）/ pending（待定）」两个版本状态来保证一致性——干净（clean）状态直接读本地，脏（dirty，存在 pending）时才去问尾节点权威版本。

3FS 把每个 chunk 复制在一条由若干存储 target 组成的链上。这套「write-all-read-any」在读多写少的 AI 负载下，把读吞吐几乎线性铺满整条链。

4.2 3FS 的写路径（CRAQ 写）

一次 chunk 写在链上的旅程：

  1. 校验链版本：请求携带的 chain version 必须与最新一致（否则拓扑已变，拒绝）。
  2. RDMA 拉数据：head 用 RDMA-Read 把写入数据从客户端拉过来（超时则中止）。
  3. 加锁串行化：获取该 chunk 的锁——所有写在 head 串行化。
  4. 写 pending 版本：读出已提交版本 v，应用更新，作为 pending 版本 u = v+1 暂存（一个 target 可同时持有 committed 和 pending 两个版本）。
  5. 向下传播：若自己是尾，就原子地用 pending 替换 committed，然后向后（向 head 方向）逐跳回 ack；否则转发给后继节点。
  6. 回 ack 收敛：收到 ack 的每个节点用 pending 替换 committed、继续向前回 ack、释放锁。

4.3 3FS 的读路径（与标准 CRAQ 的差异）

  • 若某 target 上只有 committed版本（干净），直接返回它。
  • 若存在 pending（脏）——这里 3FS 和标准 CRAQ 不同：标准 CRAQ 会去问尾节点拿权威的 committed 版本；3FS 则直接返回一个特殊状态码，让客户端自己选择「重试/等待」还是「发起一次放松读」。

这个取舍很有意思：它把「脏读时向尾节点回查」的复杂度和额外延迟去掉了，代价是写入延迟略高（要等链走完），换来读路径极简。对读密集的 AI 负载，这是笔划算的买卖。

4.4 为什么不是 Raft

对比《Raft 实现细节：braft 源码解析》：Raft 的读要么走 leader、要么走 ReadIndex/Lease，读吞吐受 leader 单点限制；而 CRAQ 天生读可分摊到整条链。对「一写、被成百上千 GPU 反复读」的训练数据集，CRAQ 的读扩展性正中下怀。这就是**「按负载选一致性协议」**——不是 Raft 不好，是场景不同。

五、Chunk Engine：SSD 上的「分配即写入」

每块 SSD 上跑一个 Chunk Engine，负责把 chunk 数据落到裸盘。

5.1 结构

  • 数据文件：一组固定的大文件，存放 chunk 的实际字节。
  • RocksDB 实例：存 chunk 的元数据（id、版本号等），用 RocksDB 的 write batch 保证元数据更新的原子性。
  • 内存元数据缓存 + chunk 分配器：get 走 哈希表缓存，返回引用计数的 handle。

5.2 分配即写入（Copy-on-Write）

Chunk Engine 的 update 操作不原地覆盖，而是 allocate-on-write / copy-on-write：

  • 先分配一个新的物理块，把「旧数据 + 本次修改」读-改-写进新块；
  • 再在 RocksDB 里原子地把元数据指向新块；
  • 旧块在其 handle 全部释放前仍可被读。

这套思路是不是很眼熟？它和 JuiceFS 的「新 slice 逻辑覆盖旧 slice」、LSM-Tree 的「追加写 + 逻辑覆盖」、以及《数据库原理》的 MVCC「写不覆盖、追加新版本」是同一个母题——不可变底座 + 版本切换。唯一的例外优化：追加写（append）在已有块末尾就地进行，省去一次拷贝。

5.3 物理块的分级管理

物理块大小分 11 档，从 64 KiB 到 64 MiB 按 2 的幂递增。每档一个资源池，各含 256 个物理文件，用内存位图追踪占用；需要扩容时 fallocate() 一次性创建 256 个新块，减少碎片和系统调用。

六、数据布局与放置：Chain Table 与均衡恢复

6.1 文件如何切分与定位

文件被切成等大的 chunk，跨多条复制链**条带化（stripe）**分布：

  • chunk id = 文件 inode id + chunk 序号。
  • chain table、chunk 大小、stripe 大小都可按目录配置。
  • 创建文件时，按 stripe 大小轮转（round-robin） 选连续的若干条链，再用一个随机种子 shuffle 打乱以求均衡。
  • 客户端 open 时从 meta 拿到布局参数，之后自己独立计算 chunk id 与所属链，无需为每次 IO 查库：

这与 Ceph 的 CRUSH「算法定位、无需查表」 异曲同工（见《Ceph 架构与实现深度解析》）——都追求「客户端算得出数据在哪，不用问中心」。

6.2 Chain Table（复制链拓扑表）

举例：6 个节点（A–F），每节点 1 块 SSD、每 SSD 划 5 个 target = 30 个 target；3 副本 → 10 条链（如 Chain 1 = A1、B1、C1）。每条链有一个版本号，拓扑一变就 +1。可以并存多张 chain table（比如「批处理」和「在线」各一张，落在互斥的节点集合上）。

6.3 均衡恢复：一个漂亮的组合数学问题

朴素布局的坑：若节点 A 的所有链伙伴都固定是 B、C，那 A 一挂，恢复流量全压在 B、C 两台上，把它们打爆。

3FS 的解法：让每块 SSD 和其余每一块 SSD都两两配过对——把它建模成一个 平衡不完全区组设计（Balanced Incomplete Block Design, BIBD），用整数规划求解。这样任一节点故障，它的恢复流量均摊到所有存活 SSD（每台约 ），没有热点。这是《分布式系统原理》里「再平衡要避免热点」思想的一个精致工程实例。

七、读写路径详解

把前几节串起来，看一次完整 IO 怎么走。

7.1 写路径

  1. 元数据准备：open/create 走 meta 服务（FDB 事务），拿到文件布局（chunk 大小、stripe、chain table 范围、shuffle 种子）。
  2. 客户端本地定位：按 §6.1 的公式算出本次写涉及哪些 chunk、每个 chunk 属于哪条链、链的 head 是谁。不查库。
  3. 数据写入 head：客户端把数据准备好（USRBIO 下要先放进共享内存 Iov），存储 head 用 RDMA-Read 拉取。
  4. CRAQ 沿链传播：head 串行化 → pending → 逐跳转发 → tail 提交 → 回 ack（§4.2）。Chunk Engine 用 copy-on-write 落盘（§5.2）。
  5. 长度维护：客户端周期性上报最大写位置；close/fsync 时 meta 向存储查末尾 chunk 得到精确长度（§3.3）。

7.2 读路径

  1. 元数据准备：open 拿布局（只读 fd 不登记，省 FDB 压力）。
  2. 本地定位：算出读区间涉及的 chunk 与链。
  3. read-any：CRAQ 允许从链上任意 target 读，负载被分摊。干净直接返回，脏则按 §4.3 处理。
  4. RDMA 直达：数据经 RDMA 直接 DMA 到客户端缓冲（USRBIO 下直落 Iov，零拷贝）。

这条路径为「海量小随机读」而生：客户端算得出位置、读可分摊到整链、RDMA 零拷贝——正好打中训练 dataloader「反复随机读海量小样本」的痛点。

八、客户端：FUSE 与 USRBIO

3FS 提供两种客户端，是一组经典的**「兼容性 vs 性能」**取舍。

8.1 FUSE 客户端的天花板

FUSE 挂载即用、兼容所有 POSIX 应用，但有硬伤：

  • 内存拷贝开销：FUSE 守护进程碰不到应用内存，必须多一次拷贝，既吃带宽又加延迟。
  • 多线程原始：共享请求队列背后一把自旋锁，并发一高就争抢。
  • 约 40 万次/秒 的 4 KiB 读上限：加并发也顶不上去（锁争抢）。
  • 不支持对同一文件并发写（Linux 5.x），应用只能写多个文件绕开。

对训练 dataloader 这种「小随机读打满」的场景，FUSE 的 40 万 IOPS 天花板远远不够。

8.2 USRBIO：用户态零拷贝环形 IO

USRBIO（User Space Ring Based IO） 是 3FS 的杀手锏，灵感来自 Linux io_uring，实现在 FUSE 守护进程内部（不引入内核模块的风险），并绕开 FUSE 的单次 IO 大小限制。两个核心结构：

结构 作用
Iov 一大块共享内存区，用于零拷贝。IB 内存注册由 FUSE 进程完成；读的数据落进 Iov，写的数据要先放进 Iov。可选 block_size 切块以优化 IB 注册时间。
Ior 一个小的共享环形缓冲。应用入队 IO，FUSE 进程出队处理。io_depth 控制批大小；一个 Ior 只读或只写，不混用；多线程建议各用各的环（共享环会强制同步）。

典型调用序列：

线程模型的铁律：一个线程负责 prep+submit，另一个线程负责 wait。io_depth 语义：0 不控深度、>0 攒够 N 个才发、<0 最多等 -N 个（配 timeout）。

一句话：USRBIO 把 FUSE 的拷贝和锁争抢全绕过，让应用直接和 RDMA + SSD 对话——这是 3FS 能在真实 AI 负载下跑满带宽的关键。

九、一致性模型

9.1 强一致的两块拼图

3FS 的一致性由两部分保证，正好对应元数据和数据：

$$
\text{文件系统强一致} ;\Leftarrow; \underbrace{\text{FDB 的 SSI 事务}}{\text{元数据}} + \underbrace{\text{CRAQ 链式复制}}{\text{数据}}
$$

  • 元数据强一致：所有命名空间操作是 FDB 上的可串行化事务，rename/create/unlink 天然原子。
  • 数据强一致：chunk 一旦经 CRAQ 提交（tail commit），任意节点读到的都是已提交版本。

9.2 一个明确的边界：写时文件长度最终一致

如 §3.3，并发写时文件长度是最终一致的——客户端每 5 秒上报、close/fsync 时才精确化。这是个务实的放松：训练场景「写完再读」的模式下，close 时长度已精确，不影响正确性；但要清楚这个边界的存在。

这和 JuiceFS「只有已 flush/close 的写才跨客户端可见」是同一类合理边界——都把「写入过程中的瞬时视图」这个最难的部分做了工程化放松。

十、故障检测与恢复

10.1 心跳与租约

  • 存储/元数据服务向 mgmtd 发心跳；manager 在 T 秒静默后判定其故障。
  • 反向也有约束：服务若 T/2 秒连不上 manager 就自杀退出——心跳即租约续期，避免脑裂后还对外服务。这正是《分布式系统原理》里租约 + 故障检测的标准套路。

10.2 target 的双重状态

每个存储 target 有一个公开状态（serving / syncing / waiting / lastsrv / offline）和一个仅 manager 可见的本地状态（up-to-date / online / offline）。离线的 target 会被挪到链尾、链版本 +1，manager 广播更新——这样在线部分继续服务，恢复不阻塞读写。

10.3 恢复流程（与正常流量重叠）

服务重启后，先扣住心跳直到自己所有 target 都被标记 offline，再开始追数据：

  1. 前驱节点发 dump-chunkmeta；恢复中的 target 回本地元数据（chunk id、链版本、committed/pending 版本号）。
  2. 前驱逐一比对，只传需要的 chunk：
    • 本地缺 → 传；本地多（远端已删）→ 删；
    • 本地链版本 > 远端 → 传；版本相同但本地 committed ≠ 远端 pending → 传。
  3. 传完发 sync-done → target 变 up-to-date。

注意恢复期的写是整 chunk 替换（full-chunk-replace），不做增量。对比 Ceph：Ceph 靠 PG log 做增量恢复，3FS 则简单粗暴地整块覆盖——又一次「简单换正确性易验证」的取舍。

十一、性能与 AI 场景

11.1 官方性能数字

场景 数字 配置
峰值聚合读带宽 ≈ 6.6 TiB/s 180 节点集群（每节点 16× 14 TiB NVMe + 2×200 Gbps IB），500+ 客户端，且带着后台训练流量
GraySort 排序 110.5 TiB / 30 分 14 秒 = 3.66 TiB/min 25 存储 + 50 计算节点
KVCache 推理读 峰值 up to 40 GiB/s 客户端 1×400 Gbps

6.6 TiB/s 这个数字的含金量在于**「带着后台训练流量还能跑到」**——不是空载峰值，而是生产态吞吐。

11.2 训练场景：喂饱 GPU 的 dataloader

训练的存储痛点是海量小样本的随机读：dataloader 要从数据集里随机抽样本喂给 GPU，若存储跟不上，GPU 就空等。3FS 的应对是本文一路讲下来的组合拳：客户端本地算位置（不查库）+ CRAQ read-any（读分摊全链）+ USRBIO 零拷贝 + RDMA 直达，把小随机读的 IOPS 和带宽同时拉满。

11.3 推理场景：KV Cache 卸载

这是 3FS 和本站另一个专题的交汇点。LLM 推理的 KV Cache 会随上下文变长而撑爆显存，一个思路是把它分层卸载到 CPU 内存乃至外部存储。3FS 正是这一层里**「比 DRAM 便宜、又能扛住高读带宽」** 的外部存储后端，用 SSD 缓存已算好的 attention K/V 张量，避免重算。

这条线在 KV Cache 专题里有实证：SGLang 的 HiCache 三级缓存（GPU→CPU→外部存储）就把 3FS 作为 KVStore 后端。Novita AI 用它跑 Qwen3-Coder-480B 编码 Agent（对话超 25K token），TTFT 下降 56%、吞吐翻倍、命中率从 40% 升到 80%（详见《SGLang KV Cache 技术方案深度解析》§五）。3FS 在这里扮演的角色，就是那个「速度递减、容量递增」金字塔的最底层。

11.4 数据处理：smallpond

3FS 还托起了 DeepSeek 的轻量数据处理框架 smallpond（基于 DuckDB + 3FS）：PB 级、无常驻服务、哈希 repartition + 分区级 SQL + Parquet IO。上面那个 GraySort 成绩就是 smallpond 在 3FS 之上跑出来的——3FS 是它的共享存储层。

十二、POSIX 语义如何落地

沿用本专题的收尾惯例，把文件系统篇逐条讨论的 POSIX 语义，对照看 3FS 的实现：

POSIX 语义 3FS 实现
原子写 / read-after-write CRAQ head 串行化 + tail 提交，提交即强一致可见
写立即可见（强一致） 数据经 CRAQ 提交、元数据经 FDB 事务提交
随机写 / 覆盖写 Chunk Engine copy-on-write（分配新块 + 原子切元数据），追加则就地优化
rename 原子性 FDB 单事务改 dentry，跨目录亦原子
open-unlink 只读 fd 不登记；有活跃写 session 的文件延迟删除
目录操作 / readdir dentry 按「父 inode + 名字」连续 key，范围查询高效列举
stat / size 长度写时最终一致；close/fsync 时向存储查末尾 chunk 精确化
fsync 持久性 CRAQ 沿链写全副本 + Chunk Engine 落盘（RocksDB write batch 原子）
符号链接 inode value 存目标路径
元数据扩展性 无状态 meta + FDB 水平扩展；inode id 小端编码打散热点

一句话：3FS 把「文件语义」交给 FDB 的事务、把「数据强一致」交给 CRAQ、把「落盘」交给自研 Chunk Engine，在自管的 NVMe 裸盘之上兑现了强一致的 POSIX 文件系统——语义靠数据库、数据靠链式复制、性能靠 RDMA + 用户态 IO。

十三、选型、优劣与适用场景

13.1 优势

  • 极致读带宽与低延迟随机读：CRAQ read-any + RDMA + USRBIO，专为 GPU 喂数据设计，聚合读带宽做到 TiB/s 量级。
  • 强一致：元数据 FDB 事务 + 数据 CRAQ，语义干净。
  • 无状态 meta：升级/故障转移无缝，运维友好。
  • 自管裸盘、无双重日志：直接管 NVMe，绕开本地文件系统的双重日志开销（对照《分布式文件存储与 POSIX 语义》§讲的分离式存储写放大控制）。
  • AI 场景实证：训练 dataloader、KV Cache 卸载、smallpond 数据处理全线跑通。

13.2 局限与注意点

  • 硬件门槛高、成本重：要 NVMe SSD + RDMA 网络（IB/RoCE），不是普通云环境随手能上——和 JuiceFS「任意对象存储即可」形成鲜明对比。
  • 运维复杂度高：自管裸盘、CRAQ 链、FDB、RDMA 网络，栈很深，比 JuiceFS 的「组合成熟件」重得多。
  • 写时文件长度最终一致：并发写场景要理解这个边界。
  • POSIX 丰富度不及 JuiceFS：JuiceFS 支持 flock/fcntl、copy_file_range、readdirplus、fallocate、S3 Gateway、CSI 等更全；3FS 聚焦高性能 IO 主路径。
  • 恢复是整 chunk 替换：不做增量（不如 Ceph 的 PG log 精细），大 chunk 恢复流量偏大。
  • 网络限于 RDMA：无原生 TCP 路线（JuiceFS 走 TCP，普适性更强）。

13.3 与其他系统的定位对比

维度 3FS JuiceFS Ceph Lustre
元数据 无状态 meta + FDB 客户端逻辑 + 外部 KV/DB 多 MDS 动态子树 MDS/MDT
数据层 自管 NVMe SSD 对象存储 + 本地缓存 RADOS/BlueStore OST 条带

一句话选型：如果你有 NVMe + RDMA 的高端集群、要为 GPU 训练/推理压榨极致读带宽与随机读性能，3FS 是目前最锋利的开源选择；如果你在通用云环境、要低成本和易运维、能接受对象存储的延迟，JuiceFS 更务实。它俩不是竞品，是光谱的两端——一个把性能推到硬件极限，一个把成本和普适性做到最优。

13.4 它在本专题里的位置

3FS 是本专题三条主线在**「新硬件 + AI 负载」**下的一次全新演绎：

  • 分布式系统原理：一致性没选 Raft 而选 CRAQ（读可分摊的链式复制），故障检测靠心跳 + 租约，再平衡用 BIBD 避免热点——都是原理篇武器库的场景化选型。
  • 数据库原理：元数据事务下推给 FDB 的 SSI/OCC，Chunk Engine 的 copy-on-write 是数据层的 MVCC——处处是数据库思想。
  • 分布式文件系统：用「无状态元数据 + 自管裸盘 + 用户态零拷贝 IO」这条硬核路线，把强一致 POSIX 语义实现在了 NVMe + RDMA 之上，专门服务 GPU。

如果说 JuiceFS 回答的是「云上如何用最省的方式拼出一个文件系统」，那 3FS 回答的是「给定顶级硬件，如何把文件系统的性能推到物理极限去喂 GPU」。
