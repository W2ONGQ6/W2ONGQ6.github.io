数据库原理：存储引擎、事务与查询

数据库原理：存储引擎、事务与查询

本文是「分布式存储系统」专题的第二篇。数据库是分布式存储中语义最丰富、最复杂的一类。本文自底向上讲透数据库的核心机制：数据怎么存（存储引擎与索引）、怎么保证正确（事务、隔离级别、并发控制、崩溃恢复）、怎么查得快（查询处理与优化），最后延伸到分布式数据库与 NewSQL。

本文大致按「存储 → 事务 → 查询 → 分布式」的顺序展开。理解数据库的关键是抓住一条主线：内存快但易失、磁盘持久但慢——数据库的几乎所有精巧设计都是在调和这对矛盾。

二、存储引擎：B-Tree vs LSM-Tree

存储引擎决定数据在磁盘上如何组织。两大流派主宰了现代数据库。

2.1 B-Tree / B+Tree（原地更新派）

传统关系库（MySQL InnoDB、PostgreSQL、Oracle）的选择。

  • 结构：多路平衡搜索树，数据按 key 有序存放在固定大小的**页（page，通常 4–16KB）**中。B+Tree 把所有数据放在叶子节点，内部节点只存索引 key，叶子间用链表相连（利于范围扫描）。
  • 查找：从根到叶 次页访问， 是每页的分支数（很大，所以树很矮，通常 3–4 层就能索引 TB 级数据）。
  • 写入：原地更新（update-in-place）——找到目标页，直接改。页满则分裂（split），页空则合并。
  • 代价：随机写多；每次写要先写 WAL 再改页，存在写放大；页分裂产生碎片。

2.2 LSM-Tree（追加写派）

日志结构合并树，为写密集场景而生（RocksDB、LevelDB、Cassandra、HBase、TiKV）。

  • 写路径：写先进内存的 MemTable（有序结构，如跳表）+ 追加 WAL。MemTable 写满后冻结，顺序刷成磁盘上不可变的 SSTable（Sorted String Table）。
  • 读路径：先查 MemTable，再从新到旧查各层 SSTable。用 布隆过滤器（Bloom Filter） 快速跳过不含该 key 的 SSTable，用块索引定位。
  • Compaction（压实）：后台把多个 SSTable 归并，去除过期/删除（tombstone）的数据，控制层数。有 Leveled（每层大小递增，层内不重叠）和 Tiered（同层堆多个、写放大低读放大高）两种策略。

2.3 三种放大与权衡

理解存储引擎的核心是 RUM 猜想——读放大(Read)、写放大(Write/Update)、空间放大(Memory/space)三者不可兼得：

引擎 写放大 读放大 空间放大 擅长
B-Tree 高（原地改+WAL） 低（一次到叶） 中（页碎片） 读多写少、点查
LSM-Tree 低（顺序追加） 高（多层+compaction） 可高可低（看策略） 写多、顺序写

一句话：LSM 把随机写转成顺序写（对磁盘/SSD 友好），代价是读要查多层、后台 compaction 耗资源。

三、索引

索引是用额外的空间和写开销换取查询速度的数据结构。

3.1 聚簇索引 vs 二级索引

  • 聚簇索引（clustered index）：表数据按主键物理有序存放，主键索引的叶子就是数据行本身（InnoDB）。主键查询极快，但主键更新代价大。
  • 二级索引（secondary index）：叶子存的是「索引列 → 主键」，查询需回表（先查二级索引拿主键，再查聚簇索引拿完整行）。
  • 覆盖索引（covering index）：若查询所需列都在索引里，无需回表，直接从索引返回。

3.2 索引结构

结构 适用
B+Tree 范围查询、排序、点查（通用默认）
哈希索引 仅等值查询，，不支持范围
LSM/SSTable 写密集 KV
倒排索引 全文检索（Elasticsearch/Lucene）
位图索引 低基数列（性别、状态）的分析查询
R-Tree / GiST 空间/多维数据

3.3 索引的代价

索引不是免费午餐：每个索引都会放大写开销（插入/更新/删除都要同步维护所有相关索引）、占用额外空间。索引设计的艺术在于「为高频查询建索引，但不滥建」。

四、事务与 ACID

事务（transaction）是数据库把「一组操作」当作一个不可分割的逻辑单元的抽象。它的保证由 ACID 四个字母概括。

字母 含义 由谁保证
A — 原子性（Atomicity） 事务要么全做，要么全不做，不存在中间状态 undo 日志（回滚）
C — 一致性（Consistency） 事务把数据库从一个合法状态带到另一个合法状态（约束不被破坏） 应用 + 约束 + 前三者
I — 隔离性（Isolation） 并发事务互不干扰，效果如同串行 并发控制（锁/MVCC）
D — 持久性（Durability） 一旦提交，即使崩溃也不丢 redo 日志（WAL） + fsync

关键澄清：ACID 里的 C（一致性）与 CAP/分布式里的 C（线性一致性）不是同一个概念。ACID 的 C 是「不破坏应用定义的不变量（如账户余额非负、外键有效）」，很大程度上是应用的责任；A、I、D 才是数据库真正提供的机制。

后文的重点就是这三个由数据库机制保证的字母：I 靠并发控制（§5、§6）、A 和 D 靠日志与恢复（§7）。

五、隔离级别与异常

理想的隔离是可串行化（serializable）——并发执行的结果等价于某个串行执行。但可串行化代价高，于是 SQL 标准定义了一系列弱隔离级别，用「允许哪些异常」来区分。

5.1 三类经典读异常

异常 定义 例子
脏读（Dirty Read） 读到另一个未提交事务的修改 T2 读到 T1 还没提交（可能回滚）的值
不可重复读（Non-repeatable Read） 同一事务内两次读同一行，值不同（因为期间被别的事务改并提交） T1 读余额=100，T2 改成 50 并提交，T1 再读=50
幻读（Phantom Read） 同一事务内两次范围查询，返回的行集不同（有新行插入） T1 查「年龄>30 的用户」，T2 插入一个，T1 再查多一行

5.2 SQL 标准隔离级别

隔离级别 脏读 不可重复读 幻读
读未提交（Read Uncommitted） 可能 可能 可能
读已提交（Read Committed） 禁止 可能 可能
可重复读（Repeatable Read） 禁止 禁止 可能*
可串行化（Serializable） 禁止 禁止 禁止

* 注：MySQL InnoDB 的 RR 级别通过间隙锁（gap lock）额外防住了幻读，是对标准的增强。

5.3 更隐蔽的异常

弱隔离下还有两个 SQL 标准没直接命名、却很危险的异常：

  • 丢失更新（Lost Update）：两个事务读同一值、各自加减后写回，一个覆盖了另一个。解法：原子操作、显式锁（SELECT ... FOR UPDATE）、或 CAS/版本号。
  • 写偏斜（Write Skew）：两个事务读取有交集的数据、基于读到的快照各自做出决策并写不同的行，结果违反了某个跨行约束。经典例子：两名医生同时值班，各自看到「还有另一人值班」就都请假，最终无人值班。写偏斜是快照隔离（SI） 无法防住、必须靠可串行化才能杜绝的异常。

5.4 快照隔离（Snapshot Isolation, SI）

SI 是 MVCC 的产物，也是最常用的隔离级别之一（PostgreSQL RR、Oracle “Serializable” 实际是 SI）：事务开始时看到一个一致性快照，整个事务期间读这个快照，不受其他事务影响。SI 天然防住脏读、不可重复读、幻读，但防不住写偏斜——这就引出了下一节的并发控制机制。

六、并发控制：2PL、MVCC、OCC

并发控制是实现隔离性（I）的机制。三大流派。

6.1 两阶段锁（2PL，悲观）

规则：事务分两个阶段——增长阶段只能加锁不能放锁，收缩阶段只能放锁不能加锁。锁分共享锁（S，读）和排他锁（X，写）。

Strict 2PL（实际使用的版本）：所有锁持有到事务提交/回滚时才一次性释放，避免级联回滚。

  • 保证：可串行化
  • 代价：锁竞争降低并发；读写互相阻塞；可能死锁

死锁处理：

  • 检测：维护等待图（wait-for graph），发现环就选一个牺牲者回滚
  • 预防：超时；或 wait-die / wound-wait 等基于时间戳的策略

6.2 多版本并发控制（MVCC）

现代数据库（PostgreSQL、MySQL InnoDB、Oracle、SQL Server）的主流。核心思想：写不覆盖旧值，而是创建新版本；读读取某个时间点的合适版本。

  • 每行保存多个版本，每个版本带 创建事务 ID（xmin） 和 删除事务 ID（xmax）
  • 每个事务有一个读时间戳/快照，只能看到「在自己开始前已提交」的版本
  • 读不阻塞写，写不阻塞读——这是 MVCC 相比 2PL 最大的优势

  • 垃圾回收：不再被任何活跃事务需要的旧版本要清理。PostgreSQL 靠 VACUUM，InnoDB 靠 purge 线程 清理 undo log。
  • MVCC 天然实现快照隔离；要达到可串行化需额外机制（见 6.4）。

6.3 乐观并发控制（OCC）

假设冲突罕见，事务分三阶段：读阶段（在私有空间读写，不加锁）→ 验证阶段（提交前检查是否与其他已提交事务冲突）→ 写阶段（无冲突则写入，有冲突则回滚重试）。

适合冲突少的场景（读多写少、短事务）；冲突多时大量回滚反而更差。分布式数据库（如 FoundationDB、TiDB 的部分路径）常用 OCC。

6.4 可串行化的实现

方法 机制 代表
Serializable 2PL（S2PL） 严格两阶段锁 + 谓词锁/间隙锁防幻读 传统关系库
SSI（Serializable Snapshot Isolation） 在 SI 基础上检测「危险结构」（读写依赖环），发现则回滚 PostgreSQL Serializable
确定性执行 预先定序，避免运行时冲突 Calvin、FaunaDB

SSI 是重要突破：它保留了 MVCC「读写不互相阻塞」的高并发优势，只在检测到可能导致写偏斜的读写依赖环时才回滚少数事务，从而以较小代价拿到真正的可串行化。

七、崩溃恢复：WAL 与 ARIES

数据库随时可能崩溃（断电、进程被杀）。恢复机制保证 A（原子性） 和 D（持久性）。

7.1 预写日志（WAL）

WAL 黄金法则：在把数据页的修改刷到磁盘之前，必须先把描述该修改的日志刷到磁盘（Write-Ahead）。

为什么这样就够了？因为只要日志在，崩溃后就能重放（redo） 已提交但还没落盘的修改，也能回滚（undo） 未提交却已落盘的修改。日志是顺序写（快），数据页可以延迟、批量、乱序刷（省 IO），两全其美。

7.2 redo 与 undo

  • redo 日志：记录「如何重做」，保证已提交事务的修改不丢（持久性 D）
  • undo 日志：记录「如何撤销」，保证未提交事务能回滚（原子性 A），也为 MVCC 提供旧版本

7.3 ARIES 恢复算法

IBM 的 ARIES 是崩溃恢复的经典范式，几乎所有主流数据库都受它影响。核心概念：

  • LSN（Log Sequence Number）：每条日志的单调递增序号；每个数据页记录 pageLSN（该页最后一次修改对应的日志）
  • WAL 不变式：刷页前保证 log_on_disk_LSN ≥ page.pageLSN

崩溃后 三阶段恢复：

  1. Analysis（分析）：从最近检查点扫描日志，重建崩溃时的活跃事务表和脏页表
  2. Redo（重做）：从最早脏页的 LSN 开始，重放所有修改（包括未提交事务的），把数据库恢复到崩溃瞬间的状态——「重复历史（repeating history）」
  3. Undo（撤销）：回滚崩溃时未提交的事务，用 CLR（Compensation Log Record） 记录回滚动作，保证 undo 本身也可在再次崩溃时幂等恢复

7.4 检查点（Checkpoint）

如果每次恢复都从头扫日志，代价太大。检查点周期性地把脏页刷盘并记录一个一致点，恢复时只需从最近检查点开始，大幅缩短恢复时间。模糊检查点（fuzzy checkpoint） 允许检查点期间不停写，避免卡顿。

八、缓冲池与存储管理

8.1 缓冲池（Buffer Pool）

磁盘慢、内存快，数据库在内存里维护一个 缓冲池 缓存热点数据页：

  • 读页时先查缓冲池，命中直接返回，未命中从磁盘加载并放入
  • 写页时先改缓冲池里的页（标记为 脏页 dirty），延迟刷盘
  • 缓冲池满时按替换策略淘汰页

8.2 页替换策略

朴素 LRU 有个问题：一次大范围扫描会把整个缓冲池冲刷掉（sequential flooding）。改进方案：

  • LRU-K：看最近 K 次访问，区分「真热」和「偶然扫到」
  • 2Q：两个队列，新页先进 FIFO，被再次访问才进 LRU
  • CLOCK / Second-Chance：用环形缓冲 + 访问位近似 LRU，开销更低（PostgreSQL 用 clock-sweep）

8.3 刷盘策略：Steal / Force

两个正交的策略维度，决定了恢复要 redo 还是 undo：

维度 选项 含义 恢复影响
Steal Steal / No-Steal 是否允许把未提交事务的脏页刷盘 Steal ⇒ 需要 undo
Force Force / No-Force 提交时是否强制把所有脏页刷盘 No-Force ⇒ 需要 redo

主流数据库都选 Steal + No-Force（性能最好，代价是恢复时 redo+undo 都要），这正是 ARIES 设计的前提。

9.2 逻辑优化（基于规则）

不看数据分布，纯靠等价变换规则改写：

  • 谓词下推（predicate pushdown）：把过滤条件尽早执行，减少中间数据量
  • 投影下推：只读需要的列（尤其列存收益大）
  • 连接重排序、子查询展开、常量折叠、外连接消除

9.3 物理优化（基于代价，CBO）

同一个逻辑操作有多种物理实现，优化器用统计信息 + 代价模型选最优：

连接算法：

算法 机制 适用
嵌套循环连接（Nested Loop） 外表每行探测内表 小表、有索引
哈希连接（Hash Join） 小表建哈希表，大表探测 大表等值连接、无序
排序归并连接（Sort-Merge） 双方排序后归并 已有序、范围连接

代价估算依赖统计信息（直方图、基数、NDV 唯一值数）：

基数估计（cardinality estimation） 是优化器最难也最易错的一环——估错中间结果行数会导致选错连接顺序和算法，是慢查询的常见根源。

9.4 执行模型

  • 火山模型（Volcano / Iterator）：每个算子实现 next()，逐行拉取。简单通用，但函数调用开销大。
  • 向量化执行（Vectorized）：每次处理一批（如 1024 行）而非一行，摊薄开销、利于 SIMD（ClickHouse、DuckDB）。
  • 编译执行（Codegen）：把查询计划编译成机器码，消除解释开销（如 Spark Tungsten、HyPer）。

十、分布式数据库与 NewSQL

当单机放不下、扛不住时，数据库走向分布式。这里的一切机制都建立在《分布式系统原理》那篇的地基上。

10.1 分片与复制

  • 分片（sharding）：把表按某个 key 水平切分到多个节点（范围/哈希/一致性哈希，详见原理篇 §8）
  • 复制（replication）：每个分片做多副本容错，常用 Raft/Paxos 共识组 保证副本强一致
  • 典型布局：每个分片 = 一个 Raft 组（TiKV、CockroachDB、YugabyteDB）

10.2 三代分布式数据库

代际 特征 代表 取舍
传统分库分表 应用层/中间件手动分片 MyCAT、ShardingSphere 简单但丢失跨分片事务与一致性
NoSQL 放弃关系模型与强一致换扩展性 Cassandra、DynamoDB、MongoDB AP、最终一致、无跨行事务
NewSQL 关系模型 + ACID + 水平扩展 Spanner、CockroachDB、TiDB、YugabyteDB 用共识+MVCC+分布式事务把三者兼得

10.3 NewSQL 的核心配方

以 Spanner / TiDB 为代表，把前面所有技术拼成一个整体：

  1. 分片 + Raft 复制：每个 region/tablet 是一个共识组，容错且强一致
  2. 分布式事务 = 2PC on Raft：2PC 的协调者与参与者状态都被 Raft 复制，消除了传统 2PC 的协调者阻塞问题（详见原理篇 §10.4）
  3. MVCC + 全局时间戳：用 TrueTime（Spanner）或 HLC 混合逻辑时钟（CockroachDB）/ TSO 全局授时（TiDB）给每个事务分配全局有序的时间戳，实现跨分片的快照读与可串行化
  4. 计算存储分离（部分系统）：如 TiDB 的 TiKV（存储）+ TiDB（SQL 计算）+ TiFlash（列存），或 Aurora 的「日志即数据库」把 redo 下推到存储层

10.4 HTAP：混合负载

传统上 OLTP（在线事务，行存、点写）和 OLAP（分析，列存、大扫描）分属两套系统，靠 ETL 同步。HTAP（如 TiDB TiFlash、SingleStore）在同一系统里用行存处理事务 + 列存处理分析 + 副本间实时同步，让分析看到新鲜数据、又不干扰事务负载。
