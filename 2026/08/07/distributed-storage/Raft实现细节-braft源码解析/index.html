Raft 实现细节：百度 braft 源码解析

Raft 实现细节：百度 braft 源码解析

一、braft 的定位与整体结构

braft 是一个只做共识、不管业务的库。它把「让一组节点对一串操作日志达成一致」这件事封装好，业务通过实现一个状态机（StateMachine） 接口接入。

它建立在百度的高性能 RPC 框架 brpc 之上，复用了 brpc 的网络、线程、bthread 协程能力。一个用 braft 的服务，本质是：

1.1 复制状态机模型的落地

braft 严格遵循复制状态机模型（对照原理篇 §7.1）：客户端提交的操作先经 Raft 达成日志一致，日志被 commit 后按序 apply 到你的状态机。你只需保证状态机是确定性的，braft 保证所有副本 apply 相同的日志序列。

二、核心类全景

braft 的实现可以拆成一组各司其职的类，先建立全局地图：

类 职责
Node / NodeImpl 一个 Raft 节点的门面，聚合所有子模块，对外暴露 apply、snapshot、配置变更等接口
LogEntry 一条日志，含 term、index、type、数据或配置
LogManager 日志的内存管理层：追加、缓存、与磁盘存储协调、通知等待者
LogStorage / SegmentLogStorage 日志的持久化层（分段文件存储）
BallotBox 投票箱：追踪每条日志被多少副本确认，推进 commit index
FSMCaller 把已 commit 的日志按序回调到用户状态机（独立线程/bthread）
Replicator Leader 上对单个 Follower 的复制器，发 AppendEntries/心跳/快照
ReplicatorGroup 管理 Leader 到所有 Follower 的一组 Replicator
SnapshotExecutor 快照的生成、加载、安装
ConfigurationManager 集群成员配置的管理与变更
RaftMetaStorage 持久化 term 和 voted_for（崩溃恢复必需）
VoteBallot 选举时的计票

这套划分的思路：把 Raft 论文里的每个子问题（日志、选举、复制、提交、apply、快照、成员）都对应到一个专职类，模块边界清晰，便于测试和优化。

三、日志：LogEntry、LogManager 与 LogStorage

日志是 Raft 的心脏。braft 把它分成三层。

3.1 LogEntry

一条日志条目，核心字段：

  • id：LogId { int64_t index; int64_t term; }——index 和 term 唯一标识一条日志
  • type：ENTRY_TYPE_DATA（业务数据）/ ENTRY_TYPE_CONFIGURATION（成员变更）/ ENTRY_TYPE_NO_OP（Leader 上任时的空日志）
  • data：butil::IOBuf，序列化后的业务操作（零拷贝的 IOBuf 是 brpc 生态的高效缓冲）
  • peers/old_peers：配置类日志才有，记录成员列表

3.2 LogManager：内存 + 持久化的协调者

LogManager 是日志的中枢，关键设计：

  • 内存缓冲（logs_in_memory）：新追加的日志先进内存队列，供快速读取和复制，避免每次都读磁盘。
  • 异步落盘：日志通过 append_entries 提交给一个独立的 disk 线程批量写入 LogStorage，写入完成后回调。这把磁盘 IO 从关键路径上解耦，是吞吐的关键。
  • 等待通知机制（wait/notify）：Follower 的 Replicator、FSMCaller 等都可能在等待「新日志到达」或「某 index 落盘」，LogManager 提供 wait() 注册回调，日志就绪时唤醒。
  • 配置管理：日志里的配置变更条目由 LogManager 联动 ConfigurationManager 维护「每个 index 对应的集群配置」。

3.3 LogStorage / SegmentLogStorage

持久化层，默认实现 SegmentLogStorage：

  • 日志按分段文件（segment） 存储，写满一个 segment（如 8MB 或按数量）就滚动到新文件。
  • 内存维护 index → (segment 文件, 文件内偏移) 的映射，读取时定位到具体 segment。
  • 支持 truncate_prefix（快照后删除旧日志）和 truncate_suffix（Follower 日志冲突时截断）。
  • 分段设计让日志的追加是顺序写（快）、删除旧日志是删整个文件（快）——对照 LSM-Tree 的顺序写哲学。

3.4 元信息持久化

RaftMetaStorage 单独持久化 current_term 和 voted_for。Raft 安全性要求这两个值必须在投票/更新 term 时先落盘再响应，否则崩溃重启后可能重复投票、破坏「一个 term 最多一个 Leader」。这是极易被忽视但绝不能省的持久化点。

四、选举的实现

4.1 触发：election timer

每个 NodeImpl 维护一个 election_timer（随机化超时，对照原理篇 §7.3）。Follower 在超时内没收到 Leader 的 AppendEntries（心跳），就发起选举：

  1. 转为 CANDIDATE，current_term++，voted_for = self，持久化元信息
  2. 重置 election timer（加随机抖动，避免选票瓜分）
  3. 向所有其他 peer 并行发送 RequestVote RPC
  4. 用 VoteBallot 计票

4.2 PreVote：避免任期膨胀

braft 实现了 Raft 的 PreVote 优化：正式自增 term 前，先发一轮 预投票探测「如果我发起选举能否赢」。只有预投票获得多数派，才真正 term++ 发起正式选举。

为什么需要：一个被网络分区隔离的节点会不断选举超时、不断 term++，等它重新入群时，其超高的 term 会迫使正常 Leader 下台，引发无谓的重新选举。PreVote 让这个孤立节点因拿不到预投票而不会污染 term，保护了集群稳定性。

4.3 投票约束

收到 RequestVote 的节点，同意投票需满足（对照 Raft 选举限制）：

  • 请求的 term ≥ 自己的 term
  • 本 term 还没投给别人（voted_for 为空或就是请求者）
  • 候选人的日志至少和自己一样新（比较 last_log 的 term、index）——这条保证已提交日志不会丢

4.4 成为 Leader

获得多数派选票后转 LEADER：

  • 启动到所有 Follower 的 Replicator（ReplicatorGroup）
  • 立即追加一条 NO_OP 日志并复制——通过提交这条本 term 的空日志，间接推进并确认之前 term 的日志提交状态（Raft 论文中「Leader 只能通过提交本任期日志来间接提交旧任期日志」的工程落地）
  • 开始发心跳（空 AppendEntries）维持权威

五、日志复制：Replicator 与 ReplicatorGroup

5.1 一个 Follower 一个 Replicator

Leader 上任后，为每个 Follower 创建一个 Replicator，由 ReplicatorGroup 统一管理。每个 Replicator 独立维护对该 Follower 的复制进度（next_index、flying_append_entries），互不阻塞——慢的 Follower 不拖累快的。

5.2 复制流程

一个 Replicator 的工作循环：

  1. 从 next_index 开始，从 LogManager 取待复制的日志条目
  2. 组装 AppendEntries 请求（含 prev_log_index/term 用于一致性检查、entries、leader_commit）
  3. 通过 brpc 异步发给 Follower
  4. Follower 校验 prev_log 匹配后追加日志、落盘、回 ACK
  5. Replicator 收到成功 ACK，推进该 Follower 的 match_index，并通知 BallotBox

5.3 一致性检查与回退

若 Follower 的 prev_log 不匹配（日志分叉），返回失败并携带冲突信息。Replicator 据此回退 next_index 重试，直到找到双方一致的点，再从那里覆盖 Follower 的后续日志。braft 用 Follower 返回的 last_log_index 等信息加速回退，避免逐条 -1 的慢回退。

5.4 pipeline 与批量

braft 的 Replicator 支持流水线复制（pipelining）：不必等上一个 AppendEntries 的 ACK 就发下一批（flying 请求），大幅提升吞吐；同时对小日志做批量打包。这是它「高吞吐、低延迟」定位的关键实现。

5.5 心跳

Replicator 在没有新日志时定期发空 AppendEntries 作为心跳（heartbeat_timer），维持 Leader 权威、重置 Follower 的 election timer。

六、提交与投票：BallotBox

BallotBox（投票箱） 负责回答：一条日志被复制到多数派了吗？可以 commit 了吗？

6.1 机制

  • Leader 追加日志时，BallotBox 为该 index 登记一个「选票」，初始需要的票数 = 多数派。
  • 每当一个 Follower 的 match_index 推进（Replicator 通知），BallotBox 给 [old_match+1, new_match] 区间的所有日志「投一票」。
  • 当某 index 的票数达到多数派，它及之前的所有日志都可 commit，BallotBox 推进 committed_index。

6.2 关键正确性点

  • 只提交本 term 的日志：BallotBox 结合 term 判断，避免提交旧 term 日志导致的经典 Raft 安全性问题（配合 §4.4 的 NO_OP 日志）。
  • commit 后，BallotBox 通知 FSMCaller 去 apply，同时 Leader 通过下一次 AppendEntries 的 leader_commit 字段把 committed_index 告诉 Follower，Follower 也随之 apply。

七、状态机应用：FSMCaller

日志 commit 只是「达成一致」，真正让操作生效要 apply 到状态机。FSMCaller 专门干这件事。

7.1 异步、有序 apply

  • FSMCaller 在独立的 bthread 里运行，把 [last_applied+1, committed_index] 的日志按 index 顺序回调 StateMachine::on_apply(iterator)。
  • 用批量迭代器（iterator） 一次回调多条，减少调度开销、让业务能批量处理。
  • 与复制解耦：复制/提交在网络线程推进，apply 在 FSMCaller 线程，互不阻塞。

7.2 各种回调

FSMCaller 还负责回调状态机的其他事件：on_leader_start/stop、on_snapshot_save/load、on_error、on_configuration_committed 等。业务通过实现这些回调感知 Raft 状态变化。

7.3 apply 与线性一致

只有 apply 后，写入才对状态机可见。这也是为什么线性一致读要保证「读到的状态至少包含此刻已 commit 的所有写」——见 §10。

八、快照：SnapshotExecutor

日志不能无限增长，否则磁盘爆炸、重启回放太慢。快照（Snapshot） 把状态机在某个 index 的完整状态存下来，之后就能安全删除该 index 之前的日志。

8.1 生成快照

  1. NodeImpl 触发 snapshot()（定时或手动）
  2. SnapshotExecutor 通过 FSMCaller 回调 StateMachine::on_snapshot_save(writer, done)，业务自己把状态写入 SnapshotWriter（业务最懂自己的状态怎么序列化）
  3. 快照包含 元信息：last_included_index、last_included_term、及当时的成员配置
  4. 快照完成后，调用 LogManager 的 truncate_prefix 删除 last_included_index 之前的日志

8.2 安装快照（InstallSnapshot）

当一个 Follower 落后太多，Leader 已经把它需要的日志截断了（日志里没有那么旧的条目），就不能用 AppendEntries 追，改用 InstallSnapshot：

  1. Leader 的 Replicator 发现要发的 next_index 已被快照截断
  2. 改发 InstallSnapshot RPC，把快照传给 Follower
  3. braft 的优化：不通过 RPC 传输大快照本体，而是让 Follower 从 Leader 下载快照文件（复用 brpc 的文件传输），RPC 只传元信息和地址
  4. Follower 调 on_snapshot_load 加载快照、重置状态机和日志

8.3 快照与业务的配合

braft 的快照设计把「怎么存状态」完全交给业务（on_snapshot_save/load），braft 只管「何时做、做完删日志、落后节点怎么装」。这也是为什么像 BaikalDB 这类系统会自己控制快照节奏（每个 Region 单独调度、限制并发快照数），而不完全依赖 braft 的定时快照——避免大量 Region 同时做快照打爆 IO。

九、成员变更

动态增删节点是生产系统必需，也是 Raft 最易出错的地方（配置分裂可能导致双 Leader）。

9.1 单节点变更（single-server change）

braft 采用 Raft 作者推荐的单成员变更方式：一次只增或减一个节点。因为「旧多数派」和「新多数派」在只差一个节点时必然相交，从而不可能同时选出两个 Leader，避免了脑裂。

9.2 实现

  1. 配置变更本身作为一条 CONFIGURATION 类型的日志 追加、复制
  2. 关键：节点在日志被追加（而非 commit）时就立即采用新配置（Raft 的 caught-up 规则），保证变更过程中的安全性
  3. 新增节点先作为学习者（learner） 追日志，追上进度后再正式加入投票，避免拖慢集群
  4. ConfigurationManager 维护「每个 index 对应哪个配置」，配合快照里也存配置，保证任何时点配置可追溯

9.3 Leader 转移（transfer leadership）

braft 支持主动转移 Leader（如运维下线某机）：Leader 停止接收新请求，等目标 Follower 日志追平后，发 TimeoutNow 让它立即超时发起选举，从而快速、干净地交接，无需等自然选举超时。

十、线性一致读：ReadIndex 与 Lease Read

写走 Raft 日志天然线性一致，但读如果也走一遍日志复制，代价太高。braft 实现了两种高效的线性一致读。

10.1 为什么读不能简单读 Leader

一个「自以为是 Leader」的旧 Leader（已被网络分区、集群已选新 Leader）若直接返回本地状态，会读到过时数据，违反线性一致。所以必须确认「我此刻仍是合法 Leader」。

10.2 ReadIndex 读

  1. Leader 记录当前 committed_index 为 read_index
  2. Leader 向多数派发一轮心跳，确认自己仍是 Leader（收到多数派响应 = 此刻无更新的 Leader）
  3. 等状态机的 applied_index ≥ read_index（确保此前所有已提交写都已 apply）
  4. 此时读本地状态，保证线性一致

ReadIndex 避免了走日志复制，但仍需一轮心跳 RPC。

10.3 Lease Read（租约读）

进一步优化：Leader 靠心跳租约——只要在 election_timeout 内收到过多数派心跳响应，就可断定「租约期内不会有新 Leader 产生」，于是无需再发确认心跳，直接读本地。这消除了读的网络往返，延迟最低。

代价与前提：Lease Read 依赖时钟不发生大的漂移（各节点时钟走速差在界限内），是一个用「时钟假设」换性能的权衡（对照原理篇 §5 关于物理时钟的讨论）。braft 两种都支持，可按对时钟的信任程度选择。
