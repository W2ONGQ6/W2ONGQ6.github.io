Ceph 架构与实现深度解析

Ceph 架构与实现深度解析

本文是「分布式存储系统」专题的一篇。Ceph 是唯一一个用同一套底层同时提供对象、块、文件三种存储接口的开源系统，其核心 RADOS + CRUSH 的设计影响深远。本文从 RADOS 讲到 CRUSH、PG、OSD/MON，再到 BlueStore、三种上层接口与故障恢复。

一、Ceph 的统一存储愿景

Ceph 起源于 Sage Weil 的博士论文（UCSC, 2006），目标是构建一个无单点、可线性扩展、自管理的分布式存储系统。它最独特之处是统一存储（Unified Storage）：

三种接口都构建在同一个底层 RADOS（Reliable Autonomic Distributed Object Store） 之上。理解 Ceph 的关键，就是理解 RADOS 和它的定位算法 CRUSH——上层接口只是 RADOS 之上的不同「翻译层」。

Ceph 的两个设计信条：

  • 无中心元数据/无查表定位：数据位置用算法算出来，而非查一张中心映射表（对照《分布式文件存储与 POSIX 语义》§5.5）。
  • 自管理：故障检测、数据恢复、再平衡都由集群自主完成，无需人工搬数据。

二、RADOS：一切的基石

RADOS 是一个可靠的、自治的分布式对象存储。注意这里的「对象」是 RADOS 内部概念（一个有名字、有数据、有属性的存储单元），不同于 S3 的对象。

RADOS 由两类守护进程构成：

组件 全称 职责
OSD Object Storage Daemon 存储实际数据，通常一个 OSD 管一块磁盘；负责读写、复制、恢复、心跳
MON Monitor 维护集群权威状态（Cluster Map），用 Paxos 保证 Map 强一致；不存数据
MGR Manager 监控指标、模块化管理（Dashboard、均衡器等）

核心思想：客户端要读写一个对象，不去问任何中心节点「它在哪」，而是拿着 Cluster Map + CRUSH 算法自己算出它在哪些 OSD 上，然后直连 OSD。MON 只负责维护和分发那份权威的 Cluster Map。

三、CRUSH：无中心的数据定位

CRUSH（Controlled Replication Under Scalable Hashing） 是 Ceph 的灵魂算法。它回答一个问题：给定一个对象，它应该存到哪些 OSD 上？——用纯计算，不查表。

3.1 为什么不用查表

朴素方案是维护一张「对象 → OSD」的映射表。但对象数量是天文数字（PB 级系统有数十亿对象），这张表本身就放不下、也成了中心瓶颈和单点。CRUSH 用确定性伪随机算法替代查表：

只要输入相同，任何客户端、任何 OSD 都能独立算出同样的结果——无需通信、无需中心表。

3.2 CRUSH Map 与故障域

CRUSH Map 描述集群的层级拓扑：root → row → rack → host → osd。放置规则（rule）可指定「副本要分散在不同的 rack」，从而实现故障域隔离——一个机架断电不会同时丢掉所有副本。

3.3 CRUSH 的关键性质

  • 稳定性：增删 OSD 时，只有一小部分数据需要迁移（近似 的比例），而非全量重映射——这是相对朴素哈希取模的巨大优势。
  • 权重感知：每个 OSD 有权重（按容量），CRUSH 按权重分配数据，支持异构磁盘。
  • 确定性：无随机性，可复现，便于排查。

四、Placement Group（PG）：不可或缺的中间层

PG 是 Ceph 里最容易被忽视、却最关键的概念。

4.1 为什么需要 PG

如果让 CRUSH 直接映射「每个对象 → OSD」，会有两个问题：

  1. 计算与追踪成本：数十亿对象，每个都单独算、单独追踪副本状态、单独恢复，开销爆炸。
  2. 恢复粒度太细：一个 OSD 挂了，要逐个对象去别处找副本重建，管理复杂。

PG 把海量对象聚合成有限的桶（一个 pool 通常几百到几千个 PG）：

于是 CRUSH 只需映射「PG → OSD 集合」，数量从数十亿降到数千。PG 是数据放置、复制、恢复、迁移的基本单位。

4.2 PG 与 OSD 的关系

  • 一个 PG 映射到一组 OSD（副本数 = size，如 3），其中一个是 Primary，其余是 Replica。
  • 一个 OSD 上承载许多个 PG（有的是 primary、有的是 replica）。
  • 所有读写某对象的请求都路由到该对象所属 PG 的 Primary OSD，由它串行化并复制到副本——这是 Ceph 保证强一致的关键（对照《分布式文件存储与 POSIX 语义》§3.1 的主副本串行化）。

4.3 pg_num 的选择

PG 数量是重要调参：太少则数据分布不均、恢复并行度低；太多则内存/CPU 开销大。经验公式约为 PG 数 ≈ (OSD 数 × 100) / 副本数，再向上取 2 的幂。

4.4 Peering 与 PG 状态

当 OSD 成员变化，同一 PG 的各副本 OSD 要重新协商（Peering） 出一个权威的、最新的数据版本，达成一致后 PG 才 active+clean。PG 有丰富的状态机（peering / active / degraded / recovering / backfilling / remapped 等），运维 Ceph 很大程度就是看懂 PG 状态。

五、OSD 与 MON：集群的骨架

5.1 Monitor（MON）与 Cluster Map

MON 维护 5 张核心 Map，合称 Cluster Map：

Map 内容
Monitor Map MON 成员信息
OSD Map 所有 OSD 的状态（up/down、in/out）、权重
PG Map PG 的分布与状态
CRUSH Map 拓扑与放置规则
MDS Map （若用 CephFS）MDS 状态
  • MON 之间用 Paxos 对 Cluster Map 的每次更新达成强一致（对照《分布式系统原理》§7），保证全集群看到一致的权威视图。
  • MON 通常部署奇数个（3 或 5） 以形成多数派。
  • MON 不在数据路径上——它只管 Map，数据读写不经过它，这是可扩展性的关键。

5.2 OSD 的自治

OSD 是真正干活的：

  • 存储对象数据（通过 BlueStore，见 §7）
  • 处理客户端读写、执行复制/EC
  • 与其他 OSD 互相心跳，发现故障后上报 MON
  • 执行数据恢复（recovery）和再平衡（backfill）

去中心的故障检测：不是 MON 去 ping 每个 OSD，而是 OSD 之间互相监测（同 PG 的 peer 互相心跳），发现某 OSD 失联就上报 MON，MON 更新 OSD Map 标记其为 down。这把故障检测的压力分散到了整个集群。

六、写路径与一致性

Ceph 提供强一致（线性一致） 的读写。一次写对象的旅程：

  1. 客户端用 CRUSH 算出对象所属 PG 的 OSD 集合，确定 Primary OSD。
  2. 客户端把写请求发给 Primary。
  3. Primary 串行化该 PG 的所有写，把写并行转发给 Replica OSD。
  4. 所有 Replica 把数据写入本地（BlueStore，先落 WAL/journal）后，向 Primary 回 ACK。
  5. Primary 收齐所有副本 ACK 后，才向客户端返回成功。

关键点：

  • 主副本串行化保证了同一对象的并发写有确定顺序（原子性、顺序性）。
  • 等所有副本 ACK（而非多数派）保证了强一致——任何后续读（默认读 Primary）都能看到最新写。
  • 这是典型的 CP 取舍：网络分区导致副本不足时，PG 变 degraded 甚至拒绝写，宁可不可用也不返回不一致数据。

6.1 min_size 与可用性

pool 有 size（副本数，如 3）和 min_size（最少可用副本数，如 2）。当存活副本数 ≥ min_size 时 PG 仍可服务；低于则 PG 停止 IO 以保护一致性——这是可用性与安全性的可调旋钮。

七、BlueStore：现代 OSD 后端

OSD 怎么把对象真正写到磁盘？早期用 FileStore（把对象存成本地文件系统 XFS 上的文件），但存在双写问题：为保证一致性要先写 journal 再写文件系统，而文件系统自己又有日志，形成写放大。

BlueStore（Ceph 现代默认后端）直接管理裸块设备，绕过本地文件系统：

  • 数据：直接写裸设备，避免文件系统开销和双重日志
  • 元数据：存在内嵌的 RocksDB（LSM-Tree，对照《数据库原理》），记录对象到磁盘位置的映射、属性等
  • RocksDB 的 WAL/DB 可放在更快的设备（NVMe/SSD）上，数据放大容量盘（HDD），实现分层
  • 好处：写放大更低、支持数据校验和（检测 bit rot）、内联压缩、精确控制 IO

这是「不信任本地文件系统、自己直管裸设备」的典型思路，和很多高性能存储（包括 AI 场景的 3FS）殊途同归。

八、复制与纠删码

Ceph 的 pool 可选两种冗余策略（对照《分布式文件存储与 POSIX 语义》§6）：

8.1 副本（Replicated Pool）

每个 PG 存 size 份完整副本（默认 3）。写要等所有副本落盘。优点是读快（任一副本可读）、恢复简单（拷贝即可）；缺点是 3 倍存储成本。

8.2 纠删码（Erasure Coded Pool）

用 RS(,) 编码，一个对象切成 数据块 + 校验块，分散到 个 OSD。

  • 例：EC(4,2) 开销 1.5 倍，容忍 2 个故障——比三副本更省、容错相当。
  • 代价：写要编码（CPU）、修复要读 个块（恢复放大），且 EC pool 在 Ceph 里对部分操作（如 RBD/CephFS 的随机小写）支持有限，常需配合副本型缓存或用于对象/冷数据。
  • 典型用法：RGW 对象存储、冷数据用 EC；RBD/CephFS 热数据用副本。

九、三种上层接口：RBD / RGW / CephFS

三者都是 RADOS 之上的「翻译层」，把不同的存储语义映射成 RADOS 对象操作。

9.1 RBD（RADOS Block Device，块存储）

把一个块设备（虚拟磁盘）切成固定大小对象（默认 4MiB）存进 RADOS。

  • 给 KVM/OpenStack/K8s 提供云盘
  • 支持快照、克隆（基于 RADOS 对象的 COW）、thin provisioning
  • 块设备语义简单（定长块随机读写），最容易映射到对象

9.2 RGW（RADOS Gateway，对象存储）

提供 S3 / Swift 兼容 的 RESTful 对象存储接口。

  • 管理 bucket、对象、多租户、ACL、版本、生命周期
  • 大对象分段上传（multipart）后分块存进 RADOS
  • 是 Ceph 对标 S3 的入口（详见本专题《对象存储原理》）

9.3 CephFS（文件存储）

提供完整 POSIX 文件系统，可挂载。

  • MDS（Metadata Server） 管理命名空间（目录树、inode），用动态子树分区扩展、capability 机制协调客户端缓存一致性（详见文件系统篇 §5.3）
  • 元数据也存在 RADOS 里，MDS 只是内存缓存 + journal，MDS 崩溃可从 RADOS 恢复
  • 数据直接走 RADOS，元数据经 MDS——是 Ceph 里最复杂的接口

十、故障检测、恢复与再平衡

Ceph 的「自管理」核心就在这一节。

10.1 故障检测

  • OSD 之间互相心跳，失联达阈值则上报 MON。
  • MON 更新 OSD Map，把该 OSD 标记为 down；若持续下线超过 mon_osd_down_out_interval（默认 10 分钟），标记为 out（不再承载数据），触发数据重分布。
  • Map 变更通过 Paxos 达成一致后分发给全集群，所有客户端和 OSD 用新 Map 重新计算 CRUSH。

10.2 Recovery vs Backfill

OSD 故障后，受影响 PG 的副本数不足（degraded），系统自动补齐冗余：

方式 场景 机制
Recovery OSD 短暂下线后恢复 按 PG log 增量同步缺失的对象（只补差异）
Backfill 新 OSD 加入或长期故障 全量扫描 PG 内对象，整体拷贝到目标 OSD

两者都由 OSD 自主执行，MON 只提供 Map。恢复过程 PG 状态为 recovering/backfilling。

10.3 再平衡（Rebalancing）

增删 OSD 会改变 CRUSH 的输入，一部分 PG 被 remap 到新 OSD，数据随之迁移，直到分布重新均衡。CRUSH 的稳定性保证只迁移必要的一小部分数据。再平衡会占用带宽，可通过 osd_max_backfills 等参数限速，避免影响正常 IO。

10.4 数据一致性守护

  • Scrubbing：PG 定期做轻量 scrub（比对副本元数据）和 deep scrub（比对副本数据内容 + 校验和），主动发现静默损坏并修复。
  • BlueStore 校验和：每次读校验，检测 bit rot。

这套「检测→恢复→再平衡→洗刷」的闭环让 Ceph 能在磁盘/节点不断故障的大规模集群里自愈，无需人工搬数据——这正是它设计目标里「自治（Autonomic）」的体现。
