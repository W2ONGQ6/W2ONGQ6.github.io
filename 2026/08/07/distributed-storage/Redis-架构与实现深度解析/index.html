Redis 架构与实现深度解析

Redis 架构与实现深度解析

本文是「分布式存储系统」专题的一篇。Redis 是最流行的内存数据结构存储，既是缓存也是数据库、消息中间件。本文从它的数据结构与底层编码，讲到单线程事件循环、持久化（RDB/AOF）、过期与淘汰、主从/哨兵/Cluster 的高可用与分布式，力求讲清「为什么 Redis 又快又灵活」。

一、Redis 是什么：内存数据结构服务器

Redis（REmote DIctionary Server）常被叫「缓存」，但它的准确定位是内存数据结构服务器（in-memory data structure store）：

  • 数据主要驻留内存 → 读写都是内存操作，微秒级延迟、单机十万级 QPS。
  • 提供丰富数据结构 → 不只是 KV，而是 String、List、Hash、Set、Sorted Set、Stream、Bitmap、HyperLogLog、Geo 等，把「数据结构」作为一等服务对外提供。
  • 可选持久化 → 靠 RDB/AOF 把内存数据落盘，兼具数据库属性。

一句话：Redis 把内存里的数据结构，通过网络暴露成一个共享的、原子操作的服务。 它的一切设计（单线程、编码优化、持久化、集群）都围绕「在内存速度和数据可靠/可扩展之间取平衡」。

二、数据结构与底层编码

Redis 的精髓在于同一种对外数据类型，底层根据数据规模自动选择不同编码，在内存和速度间权衡。

2.1 对外类型 vs 底层编码

对外类型 底层编码（随规模切换）
String int（整数）、embstr（短字符串，≤44B）、raw（长字符串，SDS）
List quicklist（listpack 节点组成的双向链表；早期 ziplist+linkedlist）
Hash listpack（小）→ hashtable（大）
Set intset（纯整数且少）→ listpack（小）→ hashtable（大）
Sorted Set listpack（小）→ skiplist + hashtable（大）

2.2 关键底层结构

  • SDS（Simple Dynamic String）：Redis 自己的字符串，记录长度（O(1) 取长度）、预分配、二进制安全，避免 C 字符串的缺陷。
  • listpack / ziplist：紧凑的连续内存结构，小数据时省内存（无指针开销），但增删是 O(n)。数据变大就升级为哈希表/跳表。
  • skiplist（跳表）：Sorted Set 的核心， 的有序插入/查找/范围查询。为什么用跳表而非红黑树？实现简单、范围查询友好、并发/持久化时更好处理。
  • dict（哈希表）：Redis 的核心字典（keyspace 本身就是个大 dict），用渐进式 rehash——扩容时不一次性搬，而是每次操作顺带搬一点，避免大字典 rehash 卡顿。

2.3 设计哲学

「小对象用紧凑编码省内存，大对象用高效结构保性能」——这个「按规模自适应编码」的思想，是 Redis 能同时做到省内存和高性能的关键，也是理解它内存占用的基础。

三、单线程事件循环模型

Redis 一个经典的「反直觉」设计：核心命令处理是单线程的，却快得惊人。

3.1 为什么单线程还快

  • 纯内存操作：瓶颈不在 CPU 而在内存/网络，单线程足以打满。
  • 避免锁与上下文切换：多线程要加锁保护共享数据结构，锁竞争和上下文切换本身就是开销。单线程天然无锁，命令执行是原子的。
  • IO 多路复用：用 epoll/kqueue 在单线程里同时处理成千上万个连接的 IO 事件，不为每个连接开线程。

3.2 事件循环（Event Loop）

Redis 基于自研的 ae（Async Event） 事件库，主循环处理两类事件：

  • 文件事件（file event）：socket 可读/可写。用 IO 多路复用（epoll/kqueue/select）监听，把「接收命令→解析→执行→回复」串起来。
  • 时间事件（time event）：定时任务，如 serverCron（每 100ms 级），负责过期键清理、统计、rehash 推进、主从心跳等后台工作。

3.3 单线程的隐患

因为单线程串行执行，一个慢命令会阻塞所有请求。所以要避免：

  • KEYS *、大范围 SMEMBERS/HGETALL、O(n) 的大集合操作
  • 大 key 的删除（用 UNLINK 异步删代替 DEL）
  • 复杂 Lua 脚本

这也是 Redis 6 引入多线程 IO、以及提供异步删除的动因（见 §10）。

四、持久化：RDB 与 AOF

内存数据断电即失，Redis 提供两种持久化把数据落盘（对照《数据库原理》的持久性）。

4.1 RDB（快照）

RDB 是某个时间点内存数据的二进制快照。

  • 触发：save/bgsave 命令，或配置的自动规则（如 900 秒内 1 次写就存）。
  • 实现（COW）：bgsave 时 fork() 出子进程，子进程把内存快照写盘，父进程继续服务。靠操作系统的写时复制（Copy-on-Write）——父进程改数据时才复制页，子进程看到的是 fork 瞬间的一致快照。
  • 优点：文件紧凑、恢复快（直接加载）、对性能影响小（后台 fork）。
  • 缺点：两次快照之间的数据会丢（不是实时持久）。

4.2 AOF（Append Only File）

AOF 记录每一条写命令（追加到文件），恢复时重放这些命令重建数据——本质是 WAL/命令日志。

  • 写回策略（appendfsync）：always（每命令 fsync，最安全最慢）、everysec（每秒 fsync，默认，最多丢 1 秒）、no（交给 OS）。
  • AOF 重写（rewrite）：命令日志会越来越大，bgrewriteaof 后台 fork 子进程，把当前内存状态压缩成最小命令集（如 100 次 incr 变成 1 条 set），控制文件大小。
  • 优点：可配到几乎不丢（everysec/always）。
  • 缺点：文件大、恢复比 RDB 慢。

4.3 混合持久化

Redis 4.0+ 支持 混合持久化：AOF 重写时，用 RDB 格式存基线 + 增量命令用 AOF 格式追加。恢复时先快速加载 RDB 基线，再重放少量增量命令——兼顾 RDB 的快恢复和 AOF 的低丢失。是生产推荐配置。

五、过期与内存淘汰

5.1 过期删除策略

给 key 设了 TTL 后，Redis 怎么删过期 key？组合两种策略：

  • 惰性删除（lazy）：访问 key 时检查是否过期，过期才删。省 CPU，但过期 key 若不被访问会一直占内存。
  • 定期删除（active）：serverCron 周期性随机抽样一批带 TTL 的 key，删掉其中过期的；若过期比例高就多删几轮。平衡 CPU 与内存。

两者互补：惰性保证访问到的一定不过期，定期兜底清理没被访问的。

5.2 内存淘汰（maxmemory-policy）

内存达到 maxmemory 上限时，按策略淘汰 key 腾空间：

策略 含义
noeviction 不淘汰，写请求直接报错（默认）
allkeys-lru / volatile-lru 淘汰最久未用的（全部 / 仅带 TTL 的）
allkeys-lfu / volatile-lfu 淘汰最少使用的（LFU，Redis 4+）
allkeys-random / volatile-random 随机淘汰
volatile-ttl 淘汰最快过期的

近似 LRU/LFU：Redis 不维护严格 LRU 链表（太耗内存），而是采样近似——随机取若干 key，淘汰其中最久未用/最少用的。LFU 用一个带衰减的计数器近似访问频率。这是「用近似换低开销」的典型工程取舍。

六、事务与 Lua 脚本

6.1 事务（MULTI/EXEC）

Redis 事务用 MULTI 开启、命令入队、EXEC 一次性顺序执行：

  • 原子性：EXEC 里的命令不被其他客户端命令打断（单线程串行执行整批）。
  • 无回滚：Redis 事务不支持回滚！若某命令运行时出错（如对 String 做 List 操作），其他命令照常执行。它只保证「语法错误的整批不执行」和「执行时不被打断」，不保证 ACID 的原子回滚——这与传统数据库事务差异很大。
  • WATCH（乐观锁）：WATCH key 后若该 key 在 EXEC 前被改，事务放弃执行，实现 CAS 式乐观并发控制（对照《数据库原理》的 OCC）。

6.2 Lua 脚本

EVAL 执行 Lua 脚本，脚本内多条命令原子执行（单线程 + 脚本执行期间不插入其他命令）。相比事务更灵活：可带逻辑判断、循环。是实现「读-改-写」原子操作、复杂原子逻辑（如分布式锁、限流）的利器。注意脚本也会阻塞单线程，要避免慢脚本。

6.3 Redis 函数（Functions）

Redis 7 引入 Functions，把脚本作为服务端持久化的、可复用的库管理，比每次传 Lua 脚本更工程化。

七、主从复制

单机有单点风险，Redis 用主从复制（replication） 做数据冗余和读扩展（对照《分布式系统原理》§6）。

7.1 复制流程

  1. 从节点 REPLICAOF <master> 后，向主发起同步。
  2. 全量同步：主 bgsave 生成 RDB 发给从，从加载；同时主把期间的新写命令缓存在 replication buffer，RDB 加载完再发给从。
  3. 增量传播：之后主把每条写命令异步转发给从（命令流复制）。

7.2 部分重同步（PSYNC）

主从断连重连时，不必每次全量。主维护一个 replication backlog（环形缓冲） 和复制偏移量：

  • 从重连时带上自己的 offset 和主的 replid
  • 若 offset 还在 backlog 范围内，主只补发缺失的那段命令（部分重同步）
  • 否则退回全量同步

这大幅降低了网络抖动导致的全量同步开销。

7.3 复制的一致性

  • 异步复制：主写完本地即返回，不等从确认 → 低延迟但主故障可能丢未复制的写（对照 PACELC 的 EL 取舍）。
  • WAIT 命令可要求写复制到 N 个从后才返回，提供更强保证但增延迟。
  • 从默认只读，避免数据不一致。

八、哨兵：自动故障转移

主从复制解决了数据冗余，但主挂了要人工切换。Sentinel（哨兵） 提供自动故障转移。

8.1 哨兵做什么

一组哨兵进程（独立于数据节点）持续监控主从：

  1. 监控：定期 ping 主从节点，判断存活。
  2. 主观下线（SDOWN）：单个哨兵认为主失联。
  3. 客观下线（ODOWN）：多数哨兵都认为主下线（达到 quorum），才判定主真的挂了——避免单个哨兵误判（对照原理篇的故障检测）。
  4. 选举 Leader 哨兵：哨兵间用类 Raft 的方式选出一个 Leader 来执行故障转移。
  5. 故障转移：Leader 哨兵从从节点中选一个最合适的（复制偏移最新、优先级高）提升为新主，让其他从改跟新主，并通知客户端。

8.2 关键点

  • 哨兵自身也要多个（≥3，奇数） 以形成多数派，避免哨兵单点。
  • 客户端通过哨兵获取当前主地址，主切换后自动感知。
  • 故障转移期间有短暂不可写窗口，且异步复制下可能丢少量最新写——这是可用性优先的取舍。

九、Redis Cluster：分片与去中心

主从+哨兵解决了高可用，但单主的内存和写吞吐仍是天花板。Redis Cluster 提供水平分片（对照《分布式系统原理》§8 分区）。

9.1 哈希槽（Hash Slot）

Redis Cluster 把整个 key 空间划分为固定的 16384 个哈希槽：

  • 每个主节点负责一部分槽（如 3 主各管 ~5461 个）。
  • key 落到哪个槽 → 由哪个节点处理。
  • 为什么用固定槽而非一致性哈希：槽是显式、可迁移的迁移单位，扩缩容时按槽搬数据、更新槽归属即可，管理直观、迁移可控。

9.2 去中心的路由

  • 无中心代理：每个节点都知道「哪个槽归谁」（通过 Gossip 协议交换集群拓扑，对照原理篇 §9）。
  • MOVED/ASK 重定向：客户端请求发错了节点，节点回 MOVED（槽已永久归属另一节点）或 ASK（槽正在迁移中）重定向。智能客户端会缓存槽映射，直连正确节点。

9.3 分片下的多 key 操作限制

因为不同 key 可能在不同节点，跨槽的多 key 操作（MSET、事务、Lua）受限。解决办法是 hash tag：{user1}:name 和 {user1}:age 用 {} 里的部分算槽，强制同一 key 前缀落到同一槽，从而能一起操作。这是分片系统「保序/原子性只能在同一分片内」的普遍约束。

9.4 高可用

Cluster 里每个主也有从副本，主挂了从自动提升（内置类似哨兵的故障转移，无需单独部署哨兵）。集群需多数主节点存活才能继续服务（判断故障、投票提升从），这是它的可用性下限。

十、Redis 6/7 的多线程与新特性

Redis 一直强调单线程，但也在演进：

版本 特性
Redis 4 惰性删除（UNLINK）、LFU 淘汰、混合持久化、模块系统
Redis 5 Stream 数据类型（类 Kafka 的日志/消费者组）
Redis 6 多线程 IO（网络读写解析用多线程，命令执行仍单线程）、RESP3 协议、ACL、客户端缓存
Redis 7 Functions、AOF 多文件、listpack 广泛应用、性能优化

多线程 IO 的边界

Redis 6 的「多线程」只把网络 IO 的读取/写入/协议解析并行化，命令的实际执行仍是单线程——所以依然无锁、命令仍原子。这精准地缓解了「高并发连接下网络 IO 成瓶颈」的问题，又不破坏单线程执行模型的简洁性。这是一个克制而精准的优化。
