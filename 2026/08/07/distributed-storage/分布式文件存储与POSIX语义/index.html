分布式文件存储与 POSIX 语义

分布式文件存储与 POSIX 语义

本文是「分布式存储系统」专题的第三篇，也是最硬核的一篇。文件系统对外承诺的是一套 POSIX 语义——它在单机上由内核轻松保证，但每一条搬到分布式环境都会引爆一系列一致性、性能与扩展性难题。本文先讲清本地文件系统的抽象，再逐个 POSIX 语义剖析其定义、在分布式下的问题、瓶颈与实现方案，最后纵览主流分布式文件系统的架构取舍。

一、本地文件系统的抽象

在谈分布式之前，先厘清文件系统到底提供了什么抽象——因为分布式文件系统要么忠实复刻它，要么明确地打破它。

1.1 VFS：统一的文件抽象

Linux 用 VFS（Virtual File System） 层为所有文件系统提供统一接口。核心对象：

对象 含义
inode 文件的元数据（大小、权限、时间戳、数据块指针），不含文件名
dentry 目录项，把「文件名」映射到 inode，构成目录树
file 打开的文件实例，含偏移量 offset、打开模式
superblock 整个文件系统的元信息

一个关键洞察：文件名和文件本体（inode）是分离的。这解释了硬链接（多个名字指向同一 inode）、rename 的原子性、以及「删除正在被打开的文件」等看似奇怪的行为——这些语义在分布式下都要专门处理。

1.2 文件名 → 数据的两级映射

  • 第一级（路径解析，path lookup）是元数据操作：逐级查目录，把 /a/b/c 解析到最终 inode
  • 第二级（读写数据）是数据操作：按 inode 的块映射读写数据块

分布式文件系统的第一个根本设计决策，就是是否把这两级分开——元数据与数据分离 几乎是所有现代分布式文件系统的共识（GFS/HDFS 的 Master+ChunkServer、Ceph 的 MDS+OSD）。

1.3 POSIX：可移植的操作系统接口

POSIX（Portable Operating System Interface） 标准规定了文件系统必须提供的系统调用语义：open/read/write/close/lseek/stat/rename/link/unlink/fsync/flock 等，以及它们的一致性与原子性保证。应用程序依赖这些保证正确运行——分布式文件系统若想「透明替换」本地文件系统，就必须实现它们。而这，正是全部困难的来源。

二、POSIX 文件系统语义总览

POSIX 对文件系统的承诺，可以归纳为下面几组语义。它们在单机内核里靠锁、页缓存、原子指令轻松实现；本文第三节将逐一分析它们在分布式下如何被打破与重建。

# POSIX 语义 单机保证 分布式难点
1 原子性写入 / read-after-write 一次 write 对其他进程原子可见 数据分散多节点，可见性需协调
2 写入立即可见（强一致读） 页缓存统一，读总是看到最新写 多客户端各有缓存，一致性需失效协议
3 顺序保证（O_APPEND 原子追加） 内核串行化追加 并发追加需全局串行点
4 字节范围锁 / flock 内核锁表 分布式锁 + 客户端故障释放
5 rename 原子性 单次 inode 操作 跨目录/跨节点的原子改名
6 unlink 时打开引用（open-unlink） inode 引用计数 跨节点引用计数与延迟删除
7 目录操作原子性 & 遍历一致性 目录锁 目录可能跨节点分片
8 元数据一致性（stat/size/mtime） inode 单副本 size 由多个数据节点决定
9 fsync 持久性 刷到本地磁盘 刷到多少个副本才算持久
10 权限与 ACL 检查 内核统一检查 分布式鉴权与缓存
11 硬链接 / 符号链接 inode 引用 跨分片的引用
12 稀疏文件 / 空洞 块按需分配 分布式块分配

POSIX 的核心一致性承诺常被概括为 “write-read 一致性”：一个 write() 成功返回后，任何后续的 read()（无论来自哪个进程/客户端）都必须能看到这次写的结果。这条在单机上理所当然，在分布式下却等价于要求线性一致性——而线性一致性正是 CAP 定理里最贵的那个 C（见本专题《分布式系统原理》）。几乎所有分布式文件系统的性能优化，本质都是在小心翼翼地放松这条承诺。

三、逐个 POSIX 语义深剖

本节是全文核心。每个语义都按 定义 → 分布式下的问题 → 瓶颈 → 实现方案 四段展开。

3.1 原子写入与 read-after-write 一致性

定义：POSIX 要求单个 write() 系统调用的效果是原子的——其他读者要么看到写之前的完整状态，要么看到写之后的完整状态，不会看到「写了一半」。且写返回后立即对所有读者可见（read-after-write）。

分布式下的问题：一次大的 write 可能横跨多个数据节点上的多个块。若无协调，读者可能读到「块 A 是新数据、块 B 还是旧数据」的撕裂写（torn write）。而且写完成的确认从数据节点传回、再传到另一个读客户端，中间存在时间窗口。

瓶颈：要保证原子可见，写路径必须在所有涉及的副本/块上「同时」生效或引入版本，这需要跨节点协调（2PC 或主副本串行化），直接拉高写延迟。

实现方案：

  • 主副本串行化：每个块/对象有一个 primary（GFS 的 primary replica、Ceph PG 的 primary OSD），所有写经 primary 定序后同步到副本，保证单块内写的原子与顺序。
  • 版本 / 时间戳：读携带版本，避免读到中间态；写完成后原子切换版本指针。
  • 写后失效 / 租约：见 3.2。
  • 务实的放松：GFS 明确不保证 write 的字节级原子性（并发写区域可能”未定义 undefined”），只保证追加记录（record append）”至少一次原子追加”——这是用弱化 POSIX 换吞吐的经典案例。

3.2 写入立即可见（缓存一致性）

定义：任一客户端写入后，其他客户端的后续读必须看到新值。单机靠统一的页缓存（page cache）天然满足。

分布式下的问题：每个客户端为性能都会本地缓存数据和元数据。客户端 A 写了、更新了自己的缓存，客户端 B 的缓存还是旧的——B 读到过时数据，违反 POSIX。

瓶颈：若每次读都回源校验（no client cache），一致性满分但性能崩溃（每个 read/stat 都变成一次 RPC）；若放开缓存，就要一套缓存失效/回收协议，其复杂度和消息开销是主要瓶颈。

实现方案：

  • 租约（Lease）：服务端授予客户端一段时间的缓存有效期，到期或被回收前可放心用本地缓存。NFSv4、GFS 用租约。
  • 回调 / 失效通知（Callback / Invalidation）：AFS 的 callback promise——服务端记住谁缓存了某文件，该文件被改时主动通知这些客户端作废缓存。
  • Ceph 的 Capabilities（caps）：MDS 给客户端授予细粒度能力位（可读缓存 Fc、可写缓冲 Fb 等）。当出现共享冲突（多客户端读写同一文件），MDS 撤销相关 cap，把客户端从「可缓存」降级为「必须同步」，从而在无冲突时高性能、有冲突时退回强一致。这是把 POSIX 强一致做对、又不牺牲常见场景性能的典范设计。
  • Close-to-open 一致性：NFS 的常见弱化——只保证「A close 后 B open 能看到 A 的写」，不保证同时打开时的实时可见。用会话边界换取缓存效率。

3.3 顺序保证与原子追加（O_APPEND）

定义：以 O_APPEND 打开的文件，每次 write 都原子地定位到当前文件末尾再写。多个进程并发追加同一文件（如多进程写同一日志），POSIX 保证各自的写不会互相覆盖。

分布式下的问题：「当前文件末尾」是一个全局状态。两个客户端同时追加，都以为末尾是 offset=1000，各写 100 字节，就会互相覆盖 offset 1000–1100。确定末尾并占位，需要一个全局串行点。

瓶颈：所有并发追加都要经过同一个串行化点（primary 或元数据节点），该点成为热点，限制了单文件的并发追加吞吐。

实现方案：

  • primary 分配偏移：由块的 primary 副本串行化所有追加请求，为每个追加原子分配一段互不重叠的偏移区间。
  • GFS Record Append：GFS 提供专门的 record append，由 primary 选定偏移、保证”至少一次”原子追加，允许出现填充（padding）和重复记录，让应用（如 MapReduce）自己去重——再次是用弱语义换高并发吞吐。
  • 单写者约束：HDFS 干脆规定一个文件同时只能有一个 writer（write-once, append-only 模型），从根本上回避并发追加，极大简化了实现——代价是不支持随机写和多写者。

3.4 字节范围锁与 flock

定义：POSIX 提供 fcntl 字节范围锁（byte-range lock）和 flock 文件锁，让多个进程协调对文件的并发访问（读共享锁 / 写排他锁）。

分布式下的问题：锁状态是全局共享资源。更棘手的是持锁客户端崩溃或网络分区——锁若不释放，其他客户端永久阻塞（死锁）。

瓶颈：锁服务是强一致的全局状态，天然是中心化瓶颈；锁的粒度越细（字节范围）状态越多，管理开销越大。

实现方案：

  • 锁服务 + 租约：锁附带租约（lease），持锁者要定期续租；崩溃后租约到期自动释放，避免死锁。这依赖分布式共识服务（Chubby、ZooKeeper、etcd）维护强一致的锁状态。
  • Ceph：MDS 管理文件锁状态，字节范围锁作为文件元数据的一部分由 MDS 协调。
  • 务实的现实：很多分布式文件系统对 flock/fcntl 锁的支持有限或需显式开启（如 NFS 早期需要 lockd/NLM，JuiceFS/CephFS 支持但有性能提示）。应用层往往被建议改用外部协调（如 etcd 锁）而非依赖 FS 锁。

3.5 rename 的原子性

定义：POSIX 要求 rename(old, new) 是原子的——任何时刻观察者要么看到 old，要么看到 new，绝不会两者都不存在或都存在。且若 new 已存在会被原子替换。这是很多软件实现「原子更新文件」的基石（写临时文件再 rename 覆盖）。

分布式下的问题：rename 涉及两个目录项的修改（从旧父目录删、往新父目录加）。若跨目录、且目录元数据分片在不同元数据节点上，这就成了一个跨节点原子操作。

瓶颈：跨节点原子改名需要分布式事务（2PC）或把相关元数据放到同一节点串行化，前者慢、后者限制了目录分片的灵活性。同目录内 rename 相对简单（单节点），跨目录/跨分片 rename 是难点。

实现方案：

  • 元数据事务：把元数据存在支持事务的存储上（如 CephFS 的 MDS journal、JuiceFS 依托事务型 KV/DB 用一个事务完成两个目录项修改），rename 变成一次原子元数据事务。
  • 子树迁移协调：CephFS 多 MDS 下若 rename 跨越不同 MDS 管辖的子树，需 MDS 间协调（迁移 + 加锁），是已知的复杂路径。
  • HDFS：单一 NameNode 持有全部命名空间，rename 就是一次内存中的原子操作 + journal 记录，天然原子——这是集中式元数据的优势（代价见 §5）。

3.6 open-unlink 语义（删除仍打开的文件）

定义：POSIX 规定，若一个文件仍被某进程打开着，即使它被 unlink（从目录删除），文件的数据仍然有效，持有 fd 的进程能继续读写，直到最后一个 fd 关闭才真正释放空间。靠 inode 的硬链接计数 + 打开引用计数实现：只有两者都归零才回收。

分布式下的问题：打开该文件的客户端和存储数据的节点分散各处。要正确实现，必须在全局维护「这个 inode 还被哪些客户端打开着」的引用计数，而客户端可能崩溃（引用永不减一）。

瓶颈：全局打开引用计数是跨节点共享状态，维护它需要额外的元数据交互；客户端故障时需靠租约超时来「兜底减一」。

实现方案：

  • 服务端追踪打开状态 + 延迟删除：unlink 时若发现仍有客户端打开，不真正删数据，而是把 inode 移入一个「待删除/孤儿」区域（如 CephFS 的 stray directory），等最后一个打开引用释放后再回收。
  • 租约兜底：客户端持有的 open 状态附带租约，客户端崩溃后租约到期，服务端视为已关闭，触发延迟删除。
  • NFS 的 silly rename：NFS 客户端删除仍打开的文件时，偷偷把它 rename 成 .nfsXXXX 隐藏文件（因为服务端本身是无状态的、不追踪 open），关闭时再删——一个经典的客户端侧 hack。

3.7 目录操作原子性与遍历一致性

定义：mkdir/rmdir/create/unlink 对目录的修改应原子生效；readdir 遍历应返回一个一致的目录视图。POSIX 对并发修改下的遍历一致性其实较宽松（允许遍历期间的增删表现未定义），但至少每个条目操作本身要原子。

分布式下的问题：热点大目录（一个目录下上百万文件）的元数据可能需要分片到多个节点，此时「列目录」要聚合多节点结果，「在目录里创建文件」要更新分片。并发创建同名文件必须保证只有一个成功。

瓶颈：超大目录是分布式文件系统的经典痛点——单节点放不下、锁竞争激烈、readdir 要扫全部分片。同时 create 需要保证目录内文件名唯一，这是一个跨分片的唯一性约束。

实现方案：

  • 目录分片（directory sharding / fragmentation）：CephFS 把大目录按 hash 拆成多个 dirfrag，分散到不同 MDS，动态分裂/合并。
  • 动态子树分区（dynamic subtree partitioning）：CephFS MDS 集群按目录子树划分负载，热点子树可迁移或分裂。
  • 文件名 hash 定位：按 hash(filename) 决定条目落在哪个分片，create 直接路由到对应分片保证唯一性。
  • 弱化 readdir 一致性：多数系统只保证 readdir 返回某一时刻的近似快照，不保证与并发增删的强一致——符合 POSIX 的宽松规定。

3.8 元数据一致性（stat / size / mtime）

定义：stat() 返回文件的大小、修改时间等元数据，应准确反映最新状态。尤其文件大小（size） 要与实际写入的数据一致。

分布式下的问题：在元数据/数据分离的架构里，文件大小是由数据节点上实际写了多少决定的，而 size 元数据由元数据节点持有——两者天然异步。客户端写数据到 OSD/ChunkServer 后，元数据节点未必立刻知道新的 size。多个客户端并发写时，谁来更新权威 size？

瓶颈：若每次 write 都同步更新元数据节点的 size，元数据节点成为写热点；若不同步，stat 就可能返回过时大小。mtime 同理。

实现方案：

  • Ceph 的能力位协调：写客户端持有 Fw（写）能力时可在本地暂存 size/mtime 更新，stat 若来自别的客户端，MDS 会向持写能力的客户端回收/查询最新 size，保证 stat 的准确性——又是 cap 机制的应用。
  • 主副本上报：primary 数据节点周期性或在 flush 时把 size 上报元数据节点。
  • 松弛的时间戳：很多系统对 atime（访问时间）默认 noatime 或惰性更新，因为严格维护 atime 意味着「读也要写元数据」，开销巨大——这是被业界普遍放松的 POSIX 语义。

3.9 fsync 与持久性

定义：fsync(fd) 返回后，该文件此前的所有写入必须已持久化（掉电不丢）。这是数据库、消息队列等依赖的核心保证。

分布式下的问题：单机 fsync 是「刷到本地磁盘」。分布式下「持久」意味着什么？刷到一个节点的磁盘不够（该节点可能整个坏掉），要刷到足够多的副本才算数——但等多少个副本、要不要等它们都 fsync 到各自磁盘，直接决定延迟。

瓶颈：持久性与延迟的直接矛盾。等更多副本落盘 = 更安全但更慢。跨节点的 fsync 是写路径上最贵的同步点之一。

实现方案：

  • 多副本确认（W 个 ack）：fsync 需等到数据在 个副本上持久化（对应原理篇的 quorum）。 越大越安全越慢。
  • WAL / journal：数据节点先把写追加到本地 journal（顺序写、快）再 ack，兼顾持久与延迟；后台再落到最终位置。
  • 可调持久级别：如 HDFS 的 hflush（可见但未必落盘）vs hsync（强制落盘），把选择权交给应用。
  • 分离式存储的写放大控制：如 3FS、Ceph BlueStore 直接管理裸设备 + 自己的 journal，避免本地文件系统双重日志。

3.10 权限、属主与 ACL

定义：POSIX 规定每次访问都要按 uid/gid + rwx 权限位（及可选 ACL）检查，chmod/chown 修改权限应立即对后续访问生效。

分布式下的问题：权限检查发生在哪？若在客户端做，客户端不可信（可伪造 uid）；若每次都到元数据节点检查，又是热点。且 uid/gid 在不同客户端机器上语义可能不一致。

瓶颈：安全性要求服务端强制检查，性能要求客户端缓存权限——两者矛盾。

实现方案：

  • 服务端强制 + 客户端缓存：元数据节点是权限的权威，客户端缓存权限位（配合租约/失效），大多数检查本地完成，chmod 时失效相关缓存。
  • 统一身份：依赖集群统一的用户目录（LDAP/Kerberos），解决跨机 uid 一致性。CephFS/HDFS 支持 Kerberos 认证。
  • 能力令牌：客户端从元数据节点取得带签名的能力令牌，向数据节点出示，数据节点验证令牌而非自己查权限（GFS/Ceph 思路）。

3.11 硬链接与符号链接

定义：硬链接让多个文件名指向同一 inode（共享数据，链接计数 > 1）；符号链接是一个存着目标路径的特殊文件。POSIX 要求硬链接的所有名字完全等价，删除其一不影响数据（直到计数归零）。

分布式下的问题：硬链接的两个名字可能在不同目录、不同元数据分片上，但必须指向同一 inode 并共享一个全局链接计数。跨分片维护这个计数和引用一致性很麻烦。

瓶颈：硬链接打破了「目录树是严格树形」的假设（变成 DAG），使得基于子树的元数据分区、配额统计、快照都变复杂。

实现方案：

  • inode 集中存储：把 inode 元数据与目录项分开存储，目录项只存「名字 → inode number」，硬链接就是多个目录项指向同一 inode number（JuiceFS 在 KV 元数据引擎里这样实现）。
  • 主链接 + 远程链接：CephFS 区分文件的「primary link」（inode 实际所在）和其他「remote link」，remote link 只存 inode number，访问时再解析。
  • 限制：部分系统（尤其对象存储网关类）不支持或有限支持硬链接，因为其命名空间本就是扁平的 key-value，硬链接语义难以贴合。

3.12 稀疏文件与空洞

定义：POSIX 允许文件有「空洞」——lseek 到很大的偏移再写，中间未写的区域不占实际存储，读时返回 0。stat 的逻辑大小可以远大于实际占用块数。

分布式下的问题：需要区分「逻辑大小」和「实际分配的块」，块按需在数据节点上分配。读空洞区域要返回 0 而不能报错（那里根本没分配块）。

瓶颈：相对其他语义较轻，主要是块分配的元数据管理和「读未分配区域返回零」的正确处理。

实现方案：

  • 按需块分配 + extent 映射：元数据只记录已写入区间（extent），未记录的区间即空洞，读时由客户端/数据层填零返回。
  • 大多数分布式文件系统（CephFS、Lustre、HDFS 的块模型）天然支持稀疏文件，因为它们本就是「按写入分配块」的模型。

四、分布式文件系统的架构骨架

理解了 POSIX 语义的挑战，再看架构就清晰了。几乎所有分布式文件系统都共享同一套骨架。

4.1 元数据与数据分离

$$
\text{客户端} ;\longrightarrow; \underbrace{\text{元数据服务}}{\text{路径解析、inode、权限}} ;+; \underbrace{\text{数据服务}}{\text{读写数据块}}
$$

  • 元数据服务：管理命名空间（目录树）、inode、权限、文件到数据块的映射。小而关键、访问频繁、难以扩展。
  • 数据服务：存储实际的文件数据块，大而简单、可水平扩展。
  • 客户端先问元数据服务「文件在哪、我有权限吗」，拿到数据块位置后直接与数据节点通信读写——数据流不经过元数据节点，这是可扩展性的关键。

4.2 三种典型架构风格

风格 元数据 代表 特点
集中式元数据 单一 Master/NameNode GFS、HDFS 简单、强一致，但元数据节点是瓶颈与单点
集群化元数据 多元数据节点分区 CephFS（多 MDS）、Lustre 元数据可扩展，但分区/迁移复杂
无独立元数据 / 算法定位 用算法（哈希）算出数据位置 Ceph RADOS（CRUSH）、GlusterFS（弹性哈希） 免元数据查询，但重平衡是挑战

4.3 客户端访问方式

  • 内核态 FS 客户端：实现 VFS 接口，挂载后与本地 FS 无异（CephFS kernel client、Lustre client），POSIX 兼容最好、性能最高。
  • FUSE（用户态）：在用户态实现文件系统逻辑（JuiceFS、GlusterFS、CephFS ceph-fuse、s3fs）。开发/部署灵活，但有用户态-内核态切换开销。
  • 专有库 / SDK：如 HDFS 的 Java API、libcephfs——不走 VFS，性能好但要改应用。

五、元数据服务：最难扩展的部分

元数据是分布式文件系统的阿喀琉斯之踵。数据可以近乎无限水平扩展，元数据却难。

5.1 为什么元数据难扩展

  • 操作频繁且小：一次 open /a/b/c/d.txt 要逐级解析 4 层目录，每层一次元数据查询。元数据 QPS 往往远高于数据 QPS。
  • 强一致要求高：命名空间的正确性（唯一性、原子 rename、权限）几乎不能放松，而强一致又难扩展。
  • 树形结构难分区：目录树有天然的层级依赖和热点（根目录、热门目录被所有请求路过）。

5.2 集中式元数据：GFS/HDFS 的选择

GFS Master、HDFS NameNode 把全部命名空间放在单节点内存里。

  • 优点：所有元数据操作在单节点内原子完成，rename、目录操作、一致性都极简单；元数据全在内存，查询极快。
  • 瓶颈：
    • 内存墙：文件数受限于单节点内存（HDFS 经验值约每 1GB 堆存百万级文件对象），海量小文件是灾难。
    • 单点故障：靠 Active-Standby + 共享 journal（HDFS QJM 用 Paxos-like 的 JournalNodes）+ ZooKeeper 做故障切换。
    • 吞吐上限：所有元数据请求打到一个节点。
  • HDFS 后来用 Federation（多个独立 NameNode 各管一部分命名空间）缓解，但那更像「多个独立文件系统拼接」而非真正的分布式元数据。

5.3 集群化元数据：CephFS 的动态子树分区

CephFS 用多个 MDS（Metadata Server） 组成集群，核心创新是动态子树分区（Dynamic Subtree Partitioning）：

  • 把目录树按子树划分给不同 MDS 管理
  • 根据实时负载动态迁移子树、分裂热点目录（dirfrag），把热点从一个 MDS 摊到多个
  • 元数据本身持久化在 RADOS（Ceph 的对象存储层），MDS 只是内存缓存 + journal，MDS 崩溃后可从 journal 恢复

难点在于：跨 MDS 的操作（如跨子树 rename、跨 MDS 的路径解析）需要 MDS 间加锁协调，是复杂度和性能的主要来源。

5.4 KV/DB 引擎化元数据：JuiceFS 的思路

JuiceFS 把元数据完全外包给一个成熟的事务型数据库/KV：Redis、TiKV、MySQL、etcd 等。

  • 目录项、inode、块映射都编码成 KV 记录
  • 利用底层引擎的事务能力实现 rename 原子性、硬链接计数等（把《数据库原理》篇的事务能力直接拿来用）
  • 元数据扩展性、一致性、持久性都「继承」自选定的引擎——如选 TiKV 就获得 Raft 复制的分布式强一致元数据

这是一种「站在巨人肩上」的务实设计：不重新发明元数据存储，而是复用数据库领域几十年的成果。

5.5 无元数据服务：算法定位

GlusterFS 和 Ceph RADOS 走另一条路——不查元数据，用算法直接算出数据在哪。

  • Ceph CRUSH 算法：给定对象名和集群拓扑（CRUSH map），用确定性哈希算出它应存在哪些 OSD 上。客户端和 OSD 都能独立计算，无需查询中心元数据，且集群拓扑变化时只有受影响的对象需迁移。
  • GlusterFS 弹性哈希：对文件名哈希决定落在哪个 brick，无中心元数据节点。

优点是彻底消除元数据查询瓶颈与单点；代价是扩容/换机时的数据重平衡要小心控制，且这种「算法定位」更适合对象/块存储，套在完整 POSIX 文件语义（目录树）上时，文件系统层（CephFS）仍需在其上叠一层 MDS 来管命名空间。

六、数据放置、复制与纠删码

数据层的核心问题：数据放哪、怎么容错、怎么在容错成本和可靠性间权衡。

6.1 分块（Chunking / Striping）

大文件被切成固定大小的块分散存储：

  • GFS chunk = 64MB、HDFS block = 128MB（默认）——大块减少元数据条目数、利于顺序大吞吐（大数据场景）
  • 条带化（striping）：一个文件的连续块分散到不同节点，读写可并行，聚合带宽 = 多节点带宽之和（Lustre、并行文件系统尤其强调）

块大小是一对权衡：大块省元数据、利于大文件顺序读写，但小文件浪费、并发度低；小块反之。

6.2 副本复制（Replication）

最简单的容错：每个块存 份（典型 ）在不同节点/机架。

  • 放置策略：GFS/HDFS 的经典三副本 = 本机架 1 份 + 另一机架 2 份，兼顾容错（跨机架抗机架级故障）与写带宽（同机架副本写快）。
  • 写一致性：经 primary 副本串行化（见 §3.1、§3.3），链式（HDFS pipeline）或主从同步到其余副本。
  • 代价： 副本 = 倍存储成本。3 副本即 200% 的存储开销。

6.3 纠删码（Erasure Coding, EC）

用编码换存储效率。Reed-Solomon RS(, )：把数据切成 个数据块，算出 个校验块，共 块分散存储，任意 块即可恢复原数据，可容忍 个块丢失。

例如 RS(6,3)：存储开销 倍（对比三副本的 3 倍），却能容忍任意 3 块丢失——用一半的存储成本拿到比三副本更强的容错。

代价与瓶颈：

  • 写/编码开销：写要计算校验块（CPU）。
  • 恢复放大（repair amplification）：修复一个丢失块要读取 个其他块，网络与 IO 开销远大于副本模式（副本只需拷 1 份）。这是 EC 的最大痛点。
  • 不适合小文件和频繁更新：更新一小段要重算整组校验。
  • 典型用法：热数据用副本（低延迟、修复快），冷数据用 EC（省成本）——分层存储。Ceph、HDFS（EC 策略）、3FS 都支持 EC。

6.4 数据完整性

  • 端到端校验和（checksum）：每个块存校验和，读时校验，检测静默数据损坏（bit rot）。HDFS、Ceph、ZFS 都做。
  • Scrubbing（洗刷）：后台周期性读取并校验所有数据，主动发现并修复损坏副本。
  • 心跳 + 副本补偿：数据节点故障后，系统检测到副本数不足，自动在其他节点重建副本/EC 块，恢复冗余度。

七、一致性模型的现实取舍

回到全文主线：分布式文件系统在多大程度上兑现 POSIX 的强一致承诺，是它最根本的性格。

7.1 一致性光谱

系统 一致性模型 说明
CephFS 接近完整 POSIX 强一致 靠 cap 机制在无冲突时高性能、冲突时退强一致
Lustre 强一致（分布式锁 LDLM） HPC 场景，靠分布式锁管理器
HDFS write-once + close 后可见 放弃随机写和多写者换简单强一致
GFS 宽松（relaxed），record append 至少一次 明确牺牲字节级原子换吞吐
NFS close-to-open 会话边界一致性
对象存储（S3） 曾最终一致，现读写强一致 但无目录/rename/部分写等 POSIX 语义

7.2 三条务实的放松路线

回顾第三节，几乎所有优化都落在三类放松上：

  1. 放松可见时机：close-to-open（NFS）、租约缓存——不保证实时可见，只保证会话/租约边界一致。
  2. 放松操作语义：write-once（HDFS）、record append 至少一次（GFS）——限制或弱化操作，回避并发协调。
  3. 放松元数据实时性：惰性 atime、异步 size 更新——不实时维护昂贵的元数据。

7.3 CAP 在文件系统中的体现

  • CP 型（CephFS、Lustre、HDFS）：网络分区时宁可拒绝服务也不返回不一致数据，适合要求正确性的场景。
  • AP 型 / 最终一致（早期对象存储、部分跨地域复制方案）：分区时继续服务，容忍短暂不一致，适合互联网海量非结构化数据。

选型的本质：你的应用能容忍 POSIX 语义被放松到什么程度？能接受 write-once 就用 HDFS（大数据）；需要完整 POSIX 挂载就上 CephFS/Lustre；只存不改的海量文件用对象存储 + 网关。

八、主流系统架构巡览

把前面所有概念落到具体系统上。

8.1 GFS（Google File System, 2003）

分布式文件系统的开山之作。单 Master（元数据全内存）+ 多 ChunkServer（64MB chunk，三副本）。为 Google 的大文件、追加为主、高吞吐场景设计，主动放松 POSIX（宽松一致性、record append 至少一次）。奠定了「集中元数据 + 大块 + 客户端直连数据节点」的范式。

8.2 HDFS（Hadoop, GFS 的开源实现）

NameNode（命名空间 + 块映射，内存）+ DataNode（128MB block，三副本或 EC）。write-once、append-only、单 writer，彻底回避并发写难题。为 MapReduce/Spark 等批处理设计。痛点是 NameNode 内存墙（怕小文件）与单点（靠 QJM + ZKFC 做 HA）。

8.3 Ceph / CephFS（统一存储的典范）

底层是 RADOS 对象存储（OSD + CRUSH 算法定位，无中心元数据），其上提供三种接口：块（RBD）、对象（RGW，兼容 S3）、文件（CephFS）。CephFS 用多 MDS + 动态子树分区管命名空间，用 capability 机制精细协调缓存一致性——是完整 POSIX 语义在分布式下做得最全面的开源系统之一。复杂度也最高。

8.4 Lustre（HPC 之王）

高性能计算（超算）主力。MDS/MDT（元数据）+ OSS/OST（对象存储目标），强调条带化并行 IO 榨干聚合带宽，用 LDLM 分布式锁管理器保证强一致。为「少量超大文件、极高聚合吞吐」优化，POSIX 兼容好，但运维重、对小文件和元数据密集负载不友好。

8.5 GlusterFS（无元数据服务器）

用弹性哈希（Elastic Hashing） 按文件名算位置，无中心元数据节点，节点即 brick，可堆叠成各种卷（分布/复制/条带/分散 EC）。部署简单、无单点，但 rename/目录列举等跨 brick 操作和大量小文件场景性能受限。

8.6 JuiceFS（云原生，元数据外包）

元数据引擎（Redis/TiKV/MySQL…）+ 对象存储（S3/OSS…） 的组合式设计。数据切块存对象存储、元数据存事务型 KV，客户端（FUSE/CSI）组装出完整 POSIX 文件系统。用数据库的事务实现 rename/硬链接等强语义，用对象存储拿到近乎无限的数据容量与低成本——云时代的务实路线。👉 本专题有一篇《JuiceFS 架构与实现深度解析》专门深剖它的三级存储格式、读写路径与一致性实现。

8.7 3FS（DeepSeek Fire-Flyer File System）

面向 AI 训练/推理的高性能分布式文件系统，充分利用 NVMe SSD + RDMA 网络，强调高聚合带宽与低延迟随机读（适合海量小样本读取、KV Cache 卸载等 AI 负载）。元数据依托事务型 KV（FoundationDB，无状态 meta 服务），数据自管裸盘并用 CRAQ 链式复制做强一致——是「新硬件 + AI 负载」驱动下的新一代设计（也是本站 KV Cache 专题里 SGLang HiCache 的存储后端之一）。👉 本专题有一篇《3FS 架构与实现深度解析》专门深剖它的无状态元数据、CRAQ 链式复制、Chunk Engine 与 USRBIO 零拷贝 IO。

8.8 一图流对比

系统 元数据 数据定位 一致性 最佳场景
GFS 单 Master Master 查询 宽松 大文件追加、批处理
HDFS 单 NameNode NameNode 查询 write-once 强一致 大数据批处理
