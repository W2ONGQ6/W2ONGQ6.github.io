对象存储原理与实现

对象存储原理与实现

本文是「分布式存储系统」专题的一篇。对象存储（S3、OSS、MinIO、Ceph RGW）是云时代海量非结构化数据的事实底座，也是 JuiceFS、数据湖、备份归档的地基。本文讲清它与文件/块存储的本质区别、扁平命名空间、S3 语义、数据放置、元数据、一致性与纠删码等核心实现。

一、三种存储形态的本质区别

存储有三种基本形态，理解对象存储要先看清它和另两者的分野。

维度 块存储（Block） 文件存储（File） 对象存储（Object）
抽象 定长块的数组（裸盘/云盘） 目录树 + 文件 扁平的 key → object
访问 读写扇区/块（SCSI/NVMe/RBD） POSIX（open/read/write/seek） HTTP REST（PUT/GET/DELETE）
命名 块地址（LBA） 层级路径 /a/b/c 扁平 key（bucket/key）
修改 原地随机读写 支持随机写、追加 整对象读写，一般不支持原地改
元数据 无（裸块） 丰富（权限/时间/inode） 每对象带用户自定义元数据
典型 云硬盘、数据库底层 NAS、共享目录 S3、备份、数据湖、图片视频

对象存储的三个决定性特征：

  1. 扁平命名空间：没有真正的目录树，bucket 下就是一堆 key。所谓「文件夹」只是 key 里带 / 的前缀假象。
  2. 不可变对象 / 整体写：对象一次 PUT 写入，要改就整体覆盖上传（部分实现支持追加，但非原地改）。这是它能极致扩展的关键简化。
  3. HTTP RESTful + 海量扩展：无状态 REST 接口、天然适合互联网规模，单桶可存万亿对象、EB 级容量。

正是「扁平 + 不可变 + REST」这三条简化，让对象存储甩掉了文件系统 POSIX 语义的沉重包袱（对照《分布式文件存储与 POSIX 语义》里那些难题），换来了近乎无限的扩展性和极低的成本。

二、对象存储的数据模型

2.1 三个层级

  • Bucket（桶）：对象的容器，命名空间单位，全局或区域内唯一，承载权限/策略/区域等配置。
  • Object（对象）：由 key（名字）+ data（数据）+ metadata（元数据） 组成。metadata 又分系统元数据（大小、etag、时间）和用户自定义元数据（x-amz-meta-*）。
  • key：对象在桶内的唯一标识，是一个字符串，可含 / 但那只是字符，不构成真实目录。

2.2 「目录」的幻觉

GET bucket?prefix=photos/2026/&delimiter=/ 这类请求能模拟出「列目录」的效果：prefix 过滤前缀、delimiter 把更深层折叠成「公共前缀（CommonPrefixes）」。但底层没有目录 inode，列举本质是对有序 key 空间的范围扫描。这也是为什么对象存储里「重命名一个大目录」很贵——要逐个 copy+delete，没有文件系统那种 O(1) 的 rename。

三、S3 API 与核心语义

Amazon S3 的 API 已成为对象存储的事实标准，几乎所有对象存储都提供 S3 兼容接口。核心操作：

操作 语义
PUT Object 上传/覆盖一个对象（整体写）
GET Object 下载对象，支持 Range 读部分字节
DELETE Object 删除对象
HEAD Object 只取元数据（大小、etag 等）
List Objects (v2) 按 prefix/delimiter 分页列举 key
Multipart Upload 大对象分段上传（见 §9）
Copy Object 服务端复制（rename 靠 copy+delete 模拟）

关键语义点：

  • ETag：对象内容的标识（常是 MD5），用于校验完整性和条件请求。
  • 条件请求：If-Match/If-None-Match/If-Modified-Since，可做乐观并发控制。
  • Range GET：只取对象的一段字节，是 JuiceFS 等按 Block 读取的基础。
  • 无 rename、无追加改写、无字节级随机写：这些正是对象存储用来换取扩展性而主动放弃的能力。

四、整体架构

一个典型的分布式对象存储系统大致分为几层：

  • 接入层：无状态的 S3 协议处理节点，可水平扩展，前面挂负载均衡。负责签名验证（AWS SigV4）、权限、分片路由。
  • 元数据服务：维护「bucket 有哪些对象」「对象的数据在哪些存储节点上」的索引。是扩展性的关键难点。
  • 数据服务：把对象数据分块、加冗余（副本/EC）后存到磁盘。

这套「接入-元数据-数据」分层和文件系统的「元数据/数据分离」一脉相承，只是对象存储的元数据更简单（无目录树层级依赖），因此更容易做到极致扩展。

五、数据放置：如何决定对象存哪

给定一个对象，怎么决定它存到哪些存储节点？两大流派（对照《分布式系统原理》§8 分区）：

5.1 一致性哈希（去中心）

把对象 key 和存储节点都映射到哈希环，对象归属顺时针最近的节点。增删节点只影响相邻数据。配合虚拟节点解决分布不均。Swift、早期 Dynamo 系用此思路。

5.2 算法定位（CRUSH 式）

如 Ceph RGW：对象名 → 哈希 → PG → CRUSH → OSD 集合，纯计算定位，无需查中心表（详见《Ceph 架构与实现》）。

5.3 查表 + 分片（中心元数据）

另一些系统用元数据服务显式记录对象位置，元数据本身分片 + 复制以扩展。灵活但元数据是关键路径。

无论哪种，都要满足：数据在节点/机架/AZ 间均匀分布、副本/EC 块跨故障域放置、扩缩容时迁移量最小。

六、元数据管理

对象存储的元数据比文件系统简单（扁平、无目录树），但量极大（万亿对象），仍是核心挑战。

6.1 元数据内容

  • bucket 级：桶配置、权限策略、区域、版本开关、生命周期规则
  • object 级：key、大小、etag、时间戳、存储类别、用户元数据、数据块位置

6.2 索引结构

  • 需要支持按 key 前缀有序列举（List with prefix），因此元数据常按 key 排序存储（LSM-Tree / B-Tree / 有序 KV）——对照《数据库原理》。
  • 海量对象下元数据要分片（按 bucket、按 key range/hash）到多个节点，每片再复制容错。
  • 元数据存储常直接用成熟数据库/KV（如 Ceph RGW 把桶索引存在 RADOS 的 OMAP 里；很多自研系统用 RocksDB/分布式 KV）。

6.3 桶索引热点

一个超大桶（数十亿对象）的索引若集中一处会成热点，需分片桶索引（bucket index sharding），把一个桶的 key 空间拆到多个索引分片并行处理 List/PUT——这与文件系统的「大目录分片」（文件系统篇 §3.7）是同一个问题的不同马甲。

七、冗余与持久性：副本与纠删码

对象存储以「高持久性」著称（AWS S3 宣称 11 个 9，即 99.999999999% 年持久性）。靠的就是冗余（对照文件系统篇 §6）。

7.1 多副本

对象数据存多份（如 3 份）在不同节点/AZ。简单、读快、恢复快，但 3 倍成本。小对象、热数据常用副本。

7.2 纠删码（EC）

大规模对象存储的主力。RS(,)：对象切 数据块 + 校验块，存 处，任意 块可恢复。

例：RS(10,4) 开销 1.4 倍，却容忍任意 4 块丢失——比三副本省一半还多、可靠性更高。大对象、冷数据几乎都用 EC。代价是编码 CPU 开销和修复时的读放大（修一块要读 块）。

7.3 跨区域复制与 AZ

  • 跨 AZ：副本/EC 块分散到同区域多个可用区，抗单 AZ 故障。
  • 跨 Region 复制（CRR）：异步把对象复制到另一地域，抗区域级灾难，但跨域是最终一致。

7.4 完整性与自愈

  • 每个块存校验和，读时校验，后台 scrub 主动巡检。
  • 检测到副本/EC 块损坏或节点故障，自动重建冗余（对照 Ceph 的 recovery/backfill）。

八、一致性模型的演进

这是对象存储一个有趣的历史演进，值得单独讲。

8.1 曾经的最终一致

早期 S3（及很多对象存储）是最终一致（eventual consistency） 的：

  • 新建对象后立即读：可能读不到（PUT 后 GET 404）
  • 覆盖/删除后读：可能读到旧值
  • 原因：元数据在多副本间异步传播，为了高可用和低延迟（PACELC 里的 EL / PA，对照原理篇 §3.2）

应用不得不加重试、加延迟来应对，很反直觉。

8.2 现在的强一致

2020 年底，AWS S3 升级为强读写一致性（strong read-after-write consistency），且不牺牲性能、不加价：

  • PUT 新对象后，任何 GET/LIST 立即看到
  • 覆盖或删除后，后续读立即反映最新状态

主流对象存储（OSS、MinIO、Ceph RGW 等）现也普遍提供读写强一致。实现上依赖元数据服务的强一致（元数据一变，全局立刻可见——权威在元数据服务，和 JuiceFS 的思路一致）。

8.3 仍然最终一致的部分

  • 跨区域复制：天生异步，仍是最终一致。
  • List 的实时性：极端并发下 List 可能有短暂延迟（取决于实现）。

要点：单区域内的「读己之写」现在通常是强一致的，但跨域、跨副本的地理复制仍需按最终一致来设计应用。

九、大对象与分段上传

对象可能很大（GB~TB），一次 PUT 上传不现实（网络中断就得重来）。Multipart Upload（分段上传） 解决这个问题：

  1. Initiate：向服务端申请一个 uploadId
  2. Upload Part：把大对象切成多段（如每段 8MB~5GB），各段独立并行上传，每段返回一个 ETag
  3. Complete：提交所有段的 (partNumber, ETag) 列表，服务端把它们拼装成一个完整对象
  4. Abort：放弃则清理已传分段（否则占空间，需生命周期规则清理残留）

好处：

  • 并行上传提升大对象吞吐
  • 断点续传：某段失败只重传该段
  • 服务端拼装时各段作为对象的组成部分（内部仍是分块存储）

这与 JuiceFS/Ceph 内部的分块存储天然契合——大对象在底层本就是一堆块。

十、多租户、生命周期与其他能力

对象存储作为云基础服务，还有一系列生产能力：

能力 说明
多租户与鉴权 账号隔离、IAM 策略、Bucket Policy、ACL、预签名 URL（临时授权）
版本控制（Versioning） 保留对象的历史版本，覆盖/删除不丢旧版，防误删
生命周期（Lifecycle） 规则化地迁移存储类别（热→温→冷→归档）或到期删除
存储类别（Storage Class） Standard / IA（低频）/ Glacier（归档）等，成本与取回延迟权衡
服务端加密（SSE） 静态加密（SSE-S3/KMS/C），传输 TLS
事件通知 对象创建/删除触发事件（推给队列/函数），驱动数据处理流水线
CORS / 静态网站 / CDN 回源 Web 场景直接服务静态资源

生命周期与冷热分层

生命周期是对象存储降本的核心：数据刚写入是热的（Standard，多副本或低冗余、低延迟），随时间变冷自动转到归档类别（深度 EC、可能延迟取回、极低价）。这把「冷热分层」自动化，是海量长尾数据经济性的关键。
