一、为什么 vLLM 要重新发明 KV Cache 管理

1.1 问题的起点：连续内存的原罪

在 vLLM 之前，主流的推理系统（如 FasterTransformer、早期 HuggingFace generate）都用一种朴素但致命的方式管理 KV Cache：为每个请求预留一段连续的显存，大小按 max_seq_len 来算。

这带来三种浪费：

浪费类型 成因 类比操作系统
内部碎片（internal fragmentation） 请求实际长度远小于 max_seq_len，预留的空间大部分闲置 分配了一大页却只写了几个字节
外部碎片（external fragmentation） 不同请求预留块大小不一，回收后留下无法利用的空洞 内存空洞放不下新请求
无法共享 每个请求独占一段连续内存，即使 prompt 完全相同也各存一份 没有共享内存机制

vLLM 论文（SOSP 2023）实测：传统系统 KV Cache 的有效利用率只有 20%–40%，也就是说超过一半的显存被白白浪费。而 KV Cache 恰恰是长序列、大批量场景下最稀缺的资源——显存放得下多少 KV Cache，直接决定了能并发多少请求（batch size），进而决定吞吐量。

1.2 核心洞察：这本质是一个内存管理问题

vLLM 团队（UC Berkeley）的关键洞察是：KV Cache 管理不是一个深度学习问题，而是一个经典的操作系统内存管理问题。

操作系统早在半个世纪前就解决了「进程需要大块连续内存、但物理内存碎片化」的矛盾——答案是虚拟内存 + 分页（paging）：

  • 逻辑地址连续，物理地址可以不连续
  • 用页表（page table）做逻辑到物理的映射
  • 按需分配物理页，用多少给多少

把这套思想搬到 KV Cache 上，就是 PagedAttention。

二、PagedAttention：把操作系统分页搬进注意力

2.1 基本数据结构：KV Block

PagedAttention 把每个请求的 KV Cache 切成固定大小的 KV Block（块），类比 OS 的「页」。

  • 每个 Block 存放固定数量 token 的 K 和 V（例如 block_size = 16）
  • Block 在物理显存中可以非连续存放
  • 一个请求的逻辑 KV 序列 = 一个 Block 列表，而不是一整块连续张量

2.2 Block Table：KV Cache 的页表

每个请求维护一张 Block Table，记录「逻辑块号 → 物理块号」的映射。生成到第 个 token 时：

  1. 算出它属于第 个逻辑块，块内偏移
  2. 查 Block Table 找到物理块号
  3. 把新 token 的 K、V 写入该物理块的对应偏移

当当前逻辑块写满，调度器才按需分配一个新的物理块——用多少给多少，内部碎片被压缩到最多一个 block（<4%）。

2.3 PagedAttention 内核

标准注意力内核假设 K、V 是连续张量。PagedAttention 需要一个能读取非连续块的自定义 CUDA 内核：注意力计算时，内核根据 Block Table 逐块 gather K、V，再做 。

vLLM 的 PagedAttention 内核把 K、V cache 分别存在独立的块中，一个 CUDA thread block 负责处理一个 KV block 与 query 的乘加，最后跨块归约。这样既保留了 FlashAttention 式的分块思想，又兼容非连续物理布局。

2.4 效果

指标 传统系统 vLLM
KV Cache 内存利用率 20%–40% 96%+
内部碎片 严重 <4%
外部碎片 有 0
吞吐量（相对 HF） 1× 最高 24×
吞吐量（相对 Orca/FasterTransformer） 1× 2–4×

三、内存共享与写时复制（Copy-on-Write）

分页带来的一个额外红利是：多个请求可以共享同一个物理块。这在两个经典场景里价值巨大。

3.1 并行采样（Parallel Sampling）

一个 prompt 要生成多个候选输出（n>1）。这些候选共享完全相同的 prompt，只在生成阶段分叉。传统做法会把 prompt 的 KV 复制 n 份，而 vLLM 让它们的 prompt 块指向同一批物理块，只在各自开始生成后才分配私有块。

3.2 Beam Search

Beam search 的多个 beam 之间共享的前缀更长、更动态。vLLM 用 写时复制（Copy-on-Write, COW） 处理块级共享：

  • 多个序列的 Block Table 可以指向同一个物理块，该块维护一个引用计数（refcount）
  • 只要 refcount > 1 且需要写入该块（追加新 token），就触发 COW：先复制出一份私有块，再写入
  • 读取（注意力计算）永远不需要复制

论文实测：beam search 场景 COW 带来 37%–66% 的内存节省，并行采样节省 6%–30%。

3.3 为什么 COW 是「免费」的正确性保证

COW 的精妙之处在于：共享是乐观的。只要没人写，大家就一直共享；一旦有人要改，才付出复制的代价，且只影响那个写入者。这与 OS fork() 后的页面共享如出一辙，天然保证了不同序列之间的隔离性——一个序列的写入绝不会污染另一个序列看到的 KV。

四、自动前缀缓存：从哈希链到扁平映射

COW 解决的是同一次请求内部的共享。而跨请求的共享——即两个不同请求恰好有相同 prompt 前缀（系统提示词、少样本示例、多轮对话历史）——由 自动前缀缓存（Automatic Prefix Caching, APC） 处理。

4.1 核心思想：内容寻址的块

vLLM 不用前缀树（这是它与 SGLang RadixAttention 的关键区别），而是给每个满块计算一个内容哈希，把 KV Block 变成**内容寻址（content-addressed）**的对象。

4.2 查找：一个扁平的哈希表，而非树

有了内容哈希，前缀缓存退化成一个扁平映射：

  • 新请求进来，按块计算哈希链
  • 逐块查 prefix_cache：命中就复用该物理块（refcount++），未命中就从 BlockPool 取空闲块
  • 命中的块跳过 prefill 计算——这是 TTFT（首 token 延迟）下降的直接来源

对比 SGLang 的树遍历，vLLM 的哈希表查找是 的单块查询，实现简单、无需维护树结构，代价是前缀匹配的粒度固定为 block（而非任意 token 边界）。

4.3 驱逐：空闲侧的 LRU

被释放的块不会立刻从 prefix_cache 里删除，而是进入空闲侧并保留其哈希——只要还没被重新分配，就仍然可被命中。当需要新块而空闲池耗尽时，按 LRU 回收最久未用的块：

  • free 递减引用计数，refcount 归零则归还到 BlockPool
  • 归还的块仍留在哈希映射中，处于「可复用但可被回收」的中间态
  • 真正被拿去装新数据时，才从映射中移除

这个设计让「缓存」和「空闲池」共用一份物理块，最大化了复用窗口。

4.4 一个直观的收益场景

多轮对话：第 2 轮请求 = 第 1 轮的 [系统提示 + Q1 + A1] + Q2。前面那一大段的 KV Block 在第 1 轮已经算过并缓存，第 2 轮直接命中，prefill 只需计算 Q2。轮次越多、共享前缀越长，收益越大——这也是 Agent、长系统提示词场景下 APC 几乎是「免费加速」的原因。

五、vLLM V1 架构：KV Cache 管理器的重写

2024 年底到 2025 年，vLLM 完成了一次影响深远的架构重写，即 V1。V1 把 KV Cache 管理从 V0 的分散逻辑重构为一套清晰的分层组件，并默认开启前缀缓存。

5.1 核心组件

组件 职责
KVCacheManager 核心分配器（vllm/v1/core/kv_cache_manager.py），对外提供「为请求分配/释放/复用块」的接口
BlockPool 物理块的空闲列表 + 前缀缓存哈希映射，统一管理 block 的生命周期
KVCacheCoordinator 在多个 KV Cache Group 之间路由请求，负责逻辑块到物理池的映射
KVCacheConfig 在 Executor.initialize_from_config 阶段，依据 determine_available_memory() 的探测结果确定块大小、dtype、块数量

5.2 「先探测显存，再决定块数」的初始化

V1 启动时会做一次显存探测：加载权重后跑一次 dummy forward，测出激活等占用，把剩下的显存（受 gpu_memory_utilization 上限约束，默认 0.9）全部换算成 KV Block 数量。这就是日志里那句 # GPU blocks: xxxxx 的由来——它直接决定了并发上限。

5.3 请求的 KV = 块列表，而非连续张量

V1 中每个请求的 KV 依然是一个块列表而非连续张量，这是 vLLM 一切高级能力的地基：

  • 消除碎片 —— 分页
  • 前缀共享 —— 块内容寻址
  • 抢占（preemption）与恢复 —— 显存不足时把低优先级请求的块换出，恢复时重新映射
  • 零拷贝迁移 —— 块可在池间移动而无需搬运张量数据

六、混合 KV Cache 管理器：异构注意力的统一

现代模型不再是清一色的标准 MHA。一个模型内部可能混用多种注意力：

  • 滑动窗口注意力（Sliding Window Attention）：只关注最近 个 token
  • MLA（Multi-head Latent Attention）：DeepSeek 的压缩潜注意力
  • Mamba / 线性注意力层：与注意力层交替（混合架构）
  • Chunked Local Attention：Llama 4 等采用的分块局部注意力

这些注意力的 KV 形态、生命周期、可淘汰范围完全不同。V1 的 混合 KV Cache 管理器（Hybrid KV Cache Manager） 用 KV Cache Group 的抽象把它们统一起来。

6.1 KV Cache Group

  • 只有一种注意力的模型 → 一个 group，包含所有层
  • 多种注意力的模型 → 多个 group，每个 group 一种注意力类型、一个独立的块池
  • KVCacheCoordinator 负责把请求的逻辑块映射到对应 group 的物理池

6.2 滑动窗口的特殊处理

滑动窗口层有一个漂亮的性质：一次前缀命中只需要最后 sliding_window_size 个 token 的 KV 仍在缓存里——更早的 token 反正窗口外看不到，可以安全淘汰。混合管理器据此为滑动窗口层做更激进的块回收，省下大量显存。

6.3 为什么这很重要

如果对所有层一视同仁地按「全注意力」预留 KV，滑动窗口层和 Mamba 层就会浪费大量本不需要的显存。混合管理器让每种层各按其真实需求分配，这是 vLLM 能高效服务 DeepSeek（MLA）、Gemma（滑窗）、Llama 4（chunked local）、混合 Mamba 模型的关键。

七、Chunked Prefill 与连续批处理

KV Cache 的管理离不开调度。vLLM 的两个调度机制直接影响 KV Cache 的分配节奏。

7.1 连续批处理（Continuous Batching）

不像静态批处理要等一整批全部生成完才能换新请求，vLLM 在每一步迭代都动态调整批次：完成的请求立即移出、释放其 KV 块；等待队列里的新请求立即补进、分配新块。KV Cache 池因此始终维持高占用，这是吞吐量的核心来源之一。

7.2 Chunked Prefill（分块预填充）

长 prompt 的 prefill 是计算密集的，会「霸占」GPU 导致正在 decode 的请求卡顿（decode 是内存密集的，两者争抢资源）。Chunked Prefill 把长 prefill 切成若干 chunk，与 decode 请求混在同一个 batch 里执行：

  • 由 long_prefill_token_threshold / max_num_batched_tokens 控制 chunk 粒度
  • 好处：decode 的 TPOT（每 token 延迟）更平滑，prefill 与 decode 的显存/算力占用被拉平
  • 与 KV Cache 的关系：prefill chunk 按块申请 KV，chunk 之间天然对齐 block 边界，配合前缀缓存可跳过已命中的 chunk

八、FP8 KV Cache 量化

再省一半显存最直接的办法：把 KV Cache 从 FP16/BF16 降到 FP8。

8.1 基本用法

vLLM 支持在线 FP8 KV Cache 量化，一个开关即可：

  • fp8（等价 fp8_e4m3）：动态范围小、精度高，是默认与推荐格式
  • fp8_e5m2：动态范围大、精度低

8.2 收益与代价

维度 影响
显存 KV Cache 直接减半（16bit → 8bit），可容纳约 2× 的上下文/并发
带宽 decode 是 memory-bound，读 KV 的字节减半 → 解码更快
精度 e4m3 在多数任务上损失极小；可配合 calibration scale 进一步降低误差
硬件 Hopper（H100）等原生支持 FP8，收益最大

8.3 与其他技术的正交性

FP8 KV Cache 与 PagedAttention、前缀缓存、混合管理器完全正交——它只改变每个 block 里 KV 元素的存储精度，不改变分页、哈希、共享逻辑。因此可以叠加使用：分页 + 前缀共享 + FP8 三管齐下。

九、P/D 分离与 KV Connector

2024–2025 最重要的系统趋势之一是 Prefill/Decode 分离（Disaggregation）：把计算密集的 prefill 和内存密集的 decode 放到不同的实例甚至不同的硬件上，各自独立扩缩容。

9.1 为什么要分离

阶段 特性 理想硬件
Prefill 计算密集（compute-bound），一次算完整 prompt 高算力 GPU
Decode 内存密集（memory-bound），逐 token 生成、狂读 KV 大显存、高带宽 GPU

放在一起时两种负载互相干扰。分离后各自优化，但代价是 KV Cache 要跨实例传输——prefill 算完的 KV 必须搬到 decode 实例。

9.2 KV Connector：可插拔的传输抽象

vLLM 在 vllm/distributed/kv_transfer/ 下提供了 KVConnectorBase_V1 抽象，把「KV 怎么传」做成可插拔后端：

  • 角色：区分 SCHEDULER 与 WORKER，各司其职
  • 调度钩子：get_num_new_matched_tokens（问 connector 有多少 token 的 KV 已在远端就绪）、start_load_kv / wait_for_save（异步发起加载 / 等待落盘）
  • 已有实现：NIXL（跨主机高速传输）、LMCache、Mooncake、Redis 等

9.3 与前缀缓存的协同

KV Connector 不只服务 P/D 分离，也可作为跨实例的共享 KV 池：一个实例算过的前缀 KV，可通过 connector（如 LMCache/Mooncake）被另一个实例复用。这把单机的自动前缀缓存扩展成了集群级前缀缓存。

十、KV 卸载：把冷缓存放到 CPU/NVMe

当 GPU 显存放不下所有想缓存的 KV，vLLM V1 提供 KV 卸载（vllm/v1/kv_offload/）：

  • 用 cumem 分配器做 block 粒度的 CUDA 虚拟内存控制，把冷块换出到 主机 RAM / NVMe
  • 需要时再换回 GPU
  • 与前缀缓存配合：命中一个已卸载到 CPU 的前缀块时，先搬回 GPU 再复用——虽然比 GPU 命中慢，但远快于重算

这一思路与 SGLang HiCache 的三级缓存殊途同归（详见姊妹篇 SGLang 文章的对比章节），本质都是「用更大更慢的存储层换取更高的缓存命中率」。

十一、工程调优速查表

围绕 KV Cache，vLLM 上线时最值得关注的旋钮：

参数 作用 建议
gpu_memory_utilization 显存用于 KV Cache 的上限比例 默认 0.9；单卡独占可调到 0.92–0.95，留余量给激活
block_size 每个 KV Block 的 token 数 默认 16；长序列可试 32 提升内核效率
enable_prefix_caching 自动前缀缓存 V1 默认开启；共享前缀多的场景务必保持开启
kv_cache_dtype KV 存储精度 Hopper 上 fp8 可近乎免费翻倍容量
max_num_batched_tokens 单步批内最大 token（含 prefill chunk） 调大提升吞吐、调小降低 TTFT 抖动
long_prefill_token_threshold 触发 chunked prefill 的阈值 长 prompt + 在线服务场景下调低，保护 decode 延迟
--kv-transfer-config 配置 KV Connector（P/D 分离 / 集群缓存） 大规模部署时启用 NIXL / LMCache / Mooncake
swap_space / KV offload 冷 KV 卸载到 CPU/NVMe 显存吃紧、前缀复用价值高时启用

排查建议：先看启动日志的 # GPU blocks 与运行时的 KV cache usage；命中率看 prefix cache hit rate。利用率长期偏低说明 batch 打不满，命中率偏低说明前缀复用没生效或缓存被频繁驱逐。
