SGLang KV Cache 技术方案深度解析

SGLang KV Cache 技术方案深度解析

本文是 KV Cache 全方位技术指南 专题的姊妹篇之一。
上一篇我们拆解了 vLLM 的分页哲学，这一篇聚焦 LMSYS 出品的 SGLang——它把 KV Cache 复用做到了极致：用基数树（Radix Tree）自动共享任意长度的前缀，用缓存感知调度放大命中率，再用 HiCache 把缓存扩展到 GPU / CPU / 外部存储三级。

一、SGLang 的出发点：不止是推理引擎

SGLang（arXiv 2312.07104，UC Berkeley / LMSYS）诞生时瞄准的问题比「单请求推理快」更大——它想高效执行结构化的 LLM 程序（Structured Language Model Programs）：

  • 多轮对话
  • 少样本提示（few-shot）
  • 思维树 / 思维链等分支结构
  • 带控制流的 Agent 程序

这类程序有一个共同特征：大量请求之间存在重叠的前缀。系统提示词、少样本示例、对话历史、公共的推理前缀……在传统引擎里这些前缀会被反复重算、反复存储。

SGLang 的核心主张：既然前缀复用如此普遍，就应该把它做成运行时自动、跨请求、任意粒度的一等公民。这就是 RadixAttention。

二、RadixAttention：用基数树管理 KV Cache

2.1 为什么是基数树（Radix Tree）

回忆 vLLM 的自动前缀缓存：它用块级内容哈希 + 扁平哈希表，前缀匹配的粒度是一个 block（如 16 token）。SGLang 换了一种数据结构——基数树（Radix Tree，压缩前缀树）：

  • 树的每条边代表一段 token 序列（不是单个字符，而是一串 token）
  • 从根到某节点的路径 = 一个前缀
  • 相同前缀的请求自然共享同一条路径上的节点，不同处自动分叉

2.2 与哈希表方案的关键差异

维度 vLLM（哈希表） SGLang（基数树）
匹配粒度 block 对齐（如 16 token） 任意 token 边界（更细）
数据结构 扁平 BlockHash → Block 压缩前缀树，边=token 序列
分叉表示 隐式（哈希不同即不同） 显式树节点分裂
淘汰单位 block（LRU on free） 树上的叶子节点（LRU）
直观性 需理解哈希链 前缀关系一目了然

基数树的优势在于天然表达前缀的层级与分叉关系：多轮对话的每一轮是树上的一条延伸路径，思维树的每个分支是一次节点分裂，共享部分永远只存一份。

2.3 LRU 缓存 + 引用计数

RadixAttention 在基数树上维护一个 LRU 缓存：

  • 每个节点记录被哪些活跃请求引用（引用计数）
  • 正在被使用的节点不可淘汰
  • 显存不足时，从叶子开始按 LRU 淘汰最久未用的节点（叶子先于内部节点，保证不破坏仍被共享的前缀）

2.4 命中的收益

新请求到来时，从根开始沿树匹配最长公共前缀：命中的那段前缀直接复用已有 KV，跳过 prefill 计算，只对未命中的尾部做计算并作为新分支挂到树上。前缀越长、复用越多，TTFT 下降越显著。

三、TokenAttention：token 级的内存池

RadixAttention 解决「哪些前缀可共享」，而底层物理内存怎么分配则由 TokenAttention 负责。

3.1 从 block 粒度到 token 粒度

vLLM 的 PagedAttention 以 block（如 16 token） 为分配单位，好处是页表小、内核规整，代价是最后一个未满的 block 有内部碎片，且前缀匹配被迫对齐到 block 边界。

SGLang 的 TokenAttention 把分配粒度进一步细化到 单个 token：

  • KV Cache 内存被组织成一个 token 级的内存池，每个 token 的 KV 是一个可独立寻址的槽位
  • 分配 / 回收都以 token 为单位 → 内部碎片趋近于 0
  • 与 RadixAttention 的任意 token 边界匹配天然契合——树上共享到第 个 token，就精确复用 个 token 的槽位

3.2 为什么 token 级粒度重要

前缀共享的价值取决于能匹配多长。如果匹配被迫对齐到 16 token 的 block，一段长 133 token 的公共前缀只能复用到 128（8 个满 block），剩下 5 token 白算。token 级粒度把这 5 token 也复用了。在系统提示词、少样本这类长度不规整的前缀上，累积收益可观。

3.3 代价与权衡

更细的粒度意味着索引开销更大（要管理更多更小的槽位），对注意力内核的 gather 效率也提出更高要求。SGLang 通过高度优化的 Triton / CUDA 内核与 page-size 可配置（后期版本支持 page > 1）来平衡「碎片最小」与「内核效率」。

四、缓存感知调度：让命中率最大化

有了基数树，请求以什么顺序被调度会极大影响命中率——这是 SGLang 的一个独到之处：Cache-Aware Scheduling（缓存感知调度）。

4.1 问题：调度顺序影响命中

假设队列里有一批请求，它们共享不同的前缀。如果随意调度，一个刚被算出并缓存的前缀可能因为后续请求不相关而被 LRU 淘汰，等到真正需要它的请求上来时又得重算。

4.2 SGLang 的做法：按前缀匹配长度排序

SGLang 的调度器在选择下一批请求时，优先调度与当前缓存前缀匹配最长的请求：

  • 匹配长的请求先跑 → 立即吃到缓存红利、跳过大段 prefill
  • 共享同一前缀的请求被聚拢在相近的时间窗口执行 → 该前缀在被这些请求全部用完前不会被淘汰
  • 论文中这种排序配合 RadixAttention 的 LRU，显著提升了缓存命中率

4.3 与连续批处理的结合

缓存感知调度不是取代连续批处理，而是在「选谁进入下一批」这一步注入前缀感知。它和 continuous batching、chunked prefill 一起，构成 SGLang 高吞吐的调度层。SGLang 论文报告在结构化工作负载上相较此前系统有最高数倍吞吐提升，核心来源正是 RadixAttention + 缓存感知调度带来的高命中率。

五、HiRadixTree 与 HiCache：三级层级缓存

RadixAttention 的天花板是 GPU 显存容量：上下文变长、对话轮次变多，早期 KV 就会被 LRU 挤出去，命中率随之下跌。2025 年 9 月 LMSYS 推出的 HiCache（博客）正是为突破这个容量墙。

5.1 三级存储层级

HiCache 把 KV Cache 铺在速度递减、容量递增的三层存储上：

层级 介质 特性
L1 GPU HBM 最快、最小
L2 主机 CPU DRAM 中速、中等容量
L3 外部存储（磁盘 / 远端内存） 最慢、容量最大

一个**缓存控制器（cache controller）**自动在三层间加载与备份 KV，对上层透明。

5.2 HiRadixTree：跨层的页表

HiCache 在 RadixAttention 的基数树之上扩展出 HiRadixTree——它「充当一张页表，索引同时驻留在 GPU 和 CPU 内存中的 KV Cache」。也就是说，树节点不再假设 KV 一定在 GPU，而是记录每段前缀的 KV 当前在哪一层，查找时据此决定是直接命中、从 CPU 搬回、还是从外部存储预取。

5.3 命中路径

新请求匹配 HiRadixTree 后可能出现三种命中：

  1. GPU 命中：直接复用，零搬运（最快）
  2. CPU 命中：把 KV 从 DRAM 搬回 GPU 再用
  3. 外部存储命中：先从 L3 预取到 CPU，再按需搬回 GPU

5.4 实测收益

  • Novita AI（Qwen3-Coder-480B 编码 Agent，对话超 25K token、约 8 轮，用 3FS KVStore）：平均 TTFT 下降 56%，吞吐翻倍，缓存命中率从 40% 升到 80%
  • 蚂蚁集团（DeepSeek-R1-671B，PD 分离，通用问答，用 Mooncake）：命中相较全量重算带来 TTFT 下降 84%
  • LMSYS 内测：最高 6× 吞吐提升、80% TTFT 下降

六、数据平面与控制平面优化

三级缓存的挑战在于搬运的代价可能吃掉命中的收益。HiCache 从数据平面和控制平面两方面把搬运成本压到最低。

6.1 数据平面：让搬运更快

① GPU 辅助的 I/O 内核
不满足于标准 cudaMemcpyAsync，HiCache 用自定义内核实现 CPU–GPU 传输，吞吐最高提升 3×。

② 解耦的内存布局

  • GPU 池保持 layer-first（层优先） 布局，兼容注意力计算内核
  • 其他层用 page-first（页优先） 布局，让每次事务搬运更大、更连续的数据块
  • 配合 zero-copy，典型部署下 吞吐再提升最高 2×

6.2 控制平面：让搬运更聪明

不同层的传输策略不同，因为外部存储的延迟比主机–GPU 更高、更不可预测。

层间重叠（layer-wise overlapping，GPU miss / CPU hit）
CPU–GPU 带宽高，于是在计算第 层的同时，预加载第 层的 KV，把搬运延迟藏到计算背后。

预取（prefetch，外部存储命中）
一旦检测到 L3 命中，控制器就机会性地把数据从存储预取到主机内存。策略可配：

  • best-effort：若请求即将被调度就取消在途预取，优先压低 TTFT
  • staging：更激进地暂缓请求以提高复用，优先拉高吞吐

写策略（把数据往慢层写）

  • write-through（直写）：带宽充足时，缓存收益最强
  • write-through-selective（选择性直写）：用命中计数只备份热点，削减 I/O 负载
  • write-back（回写）：当慢层自身也吃紧时，缓解容量压力

七、可插拔存储后端

HiCache 的 L3 被设计成可插拔的：接入一个新后端只需实现三个函数——

调度与同步全部交给中心化的缓存控制器。已支持的后端包括：

后端 特点
Mooncake 以 KV Cache 为中心的分离式存储，RDMA 高速传输
DeepSeek 3FS DeepSeek 开源的高性能分布式文件系统
NIXL 传输库，桥接 GPU-direct、云对象存储等后端
HiCacheFile 参考实现，落地到本地文件

这种「三函数接口」的设计意味着：企业可以把自家的分布式 KV 存储（Redis 集群、对象存储、自研 KVStore）快速接入，让集群级、持久化的 KV 复用成为可能。

八、结构化生成与 KV Cache 的协同

SGLang 的名字来自它的结构化生成语言。这套前端能力和 KV Cache 后端是深度协同的。

8.1 压缩有限状态机（Compressed FSM）约束解码

当输出需要遵循 JSON Schema、正则等约束时，SGLang 用压缩 FSM 驱动约束解码：把确定的多个 token 一次性跳过（jump-forward），减少无谓的逐 token 采样。这不仅加速解码，也让约束部分的 KV 结构更规整，便于缓存复用。

8.2 程序级前缀复用

SGLang 的前端原语（fork、gen、多轮 chat）会显式地把程序结构暴露给运行时。例如思维树的 fork：多个分支共享 fork 之前的全部前缀，这在基数树上就是一次节点分裂——分裂点之前的 KV 只存一份、被所有分支共享。前端的结构直接翻译成了后端基数树的形状，前缀复用「免费」发生。

九、对 MLA 等新架构的支持

KV Cache 方案必须跟上模型架构的演进。SGLang 对新一代注意力有专门优化。

9.1 MLA（DeepSeek 多头潜注意力）

MLA 缓存的是压缩潜向量而非完整 K/V，KV Cache 直降 90%+。SGLang 为 DeepSeek 系列提供了约 7× 更快的 Triton 注意力后端来处理 MLA 的特殊计算模式，并让 RadixAttention 在潜向量维度上正确做前缀共享——即缓存的是潜向量段，而非展开后的 K/V。

9.2 与量化、page-size 的组合

  • KV Cache 可配合低精度存储进一步压缩
  • --page-size（如 64）在 HiCache 场景下平衡搬运效率与匹配粒度
  • 这些旋钮与 RadixAttention / HiCache 正交，可叠加

9.3 面向 PD 分离与 Dynamo 生态

HiCache 正在与 PD 分离（Prefill/Decode Disaggregation） 做协同设计，并接入 NVIDIA Dynamo 生态。在分离式部署下，prefill 实例算出的 KV 通过 Mooncake / NIXL 等后端沉淀到共享层级，decode 实例与后续请求可跨实例命中——把单机的 RadixAttention 放大成集群级前缀复用。

十、vLLM vs SGLang：KV Cache 方案对比

两者都源自 UC Berkeley，都把 KV Cache 复用做成一等公民，但技术路线各有侧重。

维度 vLLM SGLang
内存管理核心 PagedAttention（block 分页） TokenAttention（token 级内存池）
前缀复用数据结构 块级内容哈希 + 扁平哈希表 基数树（RadixAttention）
匹配粒度 block 对齐（如 16 token） 任意 token 边界
查找复杂度 哈希 单块 树遍历最长前缀
调度 连续批处理 + chunked prefill 连续批处理 + 缓存感知调度
层级缓存 KV 卸载（CPU/NVMe） HiCache 三级（GPU/CPU/外部）
跨实例共享 KV Connector（NIXL/LMCache/Mooncake） 可插拔存储后端（Mooncake/3FS/NIXL）
异构注意力 Hybrid KV Cache Manager（group） MLA 专用后端等
设计气质 通用、事实标准、生态最广 结构化程序、极致前缀复用

一句话总结差异

  • vLLM 把 KV Cache 当操作系统内存：分页 + 内容寻址，通用稳健，生态最大。
  • SGLang 把 KV Cache 当前缀树 + 分级存储：任意粒度复用 + 缓存感知调度 + 三级 HiCache，在多轮对话、Agent、共享前缀密集的负载上把命中率推到极致。

两者的很多能力正在相互收敛：vLLM 补齐了卸载与 KV Connector，SGLang 用 HiCache 补齐了层级存储；它们也共享 Mooncake / NIXL 这类底层传输后端。选型时更多看工作负载特征：前缀高度重叠 / 多轮 Agent 场景 SGLang 的树 + 调度优势明显；通用高吞吐 / 生态兼容 场景 vLLM 是稳妥默认。

十一、工程调优速查表

参数 / 开关 作用 建议
--enable-hierarchical-cache 开启 HiCache 三级缓存 长上下文 / 多轮场景开启
--hicache-ratio CPU 层相对 GPU 的容量倍数 常用 2，DRAM 富余可增大
--hicache-io-backend kernel 用 GPU 辅助内核搬运 追求 CPU↔GPU 高吞吐时启用
--hicache-mem-layout page_first 非 GPU 层用页优先布局 提升搬运吞吐
--hicache-storage-backend 选择 L3 后端（hf3fs / mooncake / …） 按基础设施选型
--hicache-storage-prefetch-policy 预取策略（best-effort / staging / timeout / wait_complete） 压 TTFT 用 best-effort，拉吞吐用 staging
--page-size KV 分页粒度（如 64） HiCache 下平衡搬运效率与匹配粒度
--chunked-prefill-size chunked prefill 粒度 保护 decode 延迟
--mem-fraction-static 静态显存占用比例 类似 vLLM 的显存利用率旋钮

排查建议：关注缓存命中率（RadixAttention / HiRadixTree hit rate）与 TTFT。命中率低时检查请求前缀是否真有重叠、缓存感知调度是否生效、GPU 缓存是否被过快淘汰（可考虑上 HiCache 扩容）。
