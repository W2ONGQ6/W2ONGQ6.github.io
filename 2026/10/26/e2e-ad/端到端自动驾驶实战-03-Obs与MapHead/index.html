引言：同一 BEV，不同输出语义

动态目标需要实例中心、尺寸、朝向和速度；地图需要连续拓扑结构。共享 encoder 能让二者交换上下文，但不应强迫它们共用同一种标签或 decoder。

一、obs head：中心热图加回归量

一个简洁的 CenterPoint 风格目标头输出：类别热图、中心 offset、尺寸、yaw 的 sin/cos 和速度。

训练时只在有效目标中心附近回归。推理时做 local-max NMS、解码到米制坐标，再以合法的尺寸与速度范围过滤。

最小例子：BEV heatmap 在 有峰值，结合上一章的栅格定义，它对应前方 10 m、左侧 2 m。若回归头给出 offset 、速度 m/s，则解码器把中心细化到该格内，并输出一辆约以 3 m/s 向前行驶的目标；没有峰值的背景格不会产生 box。

二、map head：栅格先行，矢量后置

第一版把车道中心线、边界、人行横道和停止线作为多标签 BEV mask；它容易与现有栅格数据对齐。

后续若要接车道拓扑，可从 mask 骨架化得到 polyline，或使用 query decoder 直接预测折线与连接关系。不要在无矢量标注时先把问题做成复杂的 set prediction。

最小例子：map head 的“车道中心线”通道在前方连续十几个格为 1，骨架化后可得到一条中心折线；“道路边界”通道在其左右各有一条线。规划器由此知道候选轨迹可以沿中心线前进，但不应越过两侧边界。

三、规划怎样使用它们

规划 head 可以直接读取共享 BEV，也可以读取 obs/map 的中间 feature；训练时保留这些辅助头的显式损失，避免规划梯度把可解释结构完全冲掉。UniAD 的“规划导向”不等于删除感知监督，而是让所有任务在一个最终目标下共同优化。

四、Obs 与 Map 的经典做法

Obs：从 box 到时序 object query

路线 代表工作 做法 优缺点
图像检测 Faster R-CNN / YOLO 每相机检测后做多视角关联 成熟但 3D 几何和遮挡关联容易割裂
BEV 中心点 CenterPoint（2021） BEV heatmap 找中心，再回归 box/速度 高效、代码直观，适合本专题首版
3D query PETR（2022） 在图像 feature 中加入 3D 位置编码，用 query 回归目标 省去显式稠密 BEV，但几何调试较难
时序 query StreamPETR（2023） 传播 object query 以保留运动与遮挡状态 更适合 tracking 与 prediction，状态管理更复杂

Map：从像素掩码到向量与拓扑

路线 代表工作 做法 适用性
栅格分割 HDMapNet（2021） 输出车道、边界等 BEV mask 标签和可视化最直观，适合首版
自回归 polyline VectorMapNet（2022） 从 keypoint/序列生成地图折线 直接得到矢量地图，但训练和解码更难
集合 query MapTR（2023） DETR 式 query 匹配实例级 polyline 更利于拓扑与紧凑存储，需要 Hungarian matching

当规划只需局部边界约束时，mask head 是合理的工程第一步；当任务需要车道连接、红绿灯关系和远距离 route 时，再升级 vector/map query。

小结

obs 和 map 提供稀疏结构；下一篇的 occ 与 freespace 提供密集几何与可行驶约束。
