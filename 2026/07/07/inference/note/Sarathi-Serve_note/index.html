Sarathi-Serve: Taming Throughput-Latency Tradeoff in LLM Inference

1. TL;DR / 一句话总结

Sarathi-Serve 通过**停滞感知调度（Stall-Aware Scheduling）**解决了 LLM 推理中吞吐量与延迟的根本性权衡：当解码请求因内存带宽不足而 “停滞” 时，调度器精准地插入预填充（prefill）请求来利用闲置的 GPU 计算单元，从而在几乎不影响延迟的情况下，将吞吐量提升 40-60%。

2. 研究背景与动机 (Background & Motivation)

2.1 核心问题：吞吐量 vs 延迟

LLM 推理服务面临一个经典的经典工程权衡：

传统的解决思路：

  • 增大批处理：提高吞吐量，但延迟随之线性增长
  • 减小批处理：降低延迟，但 GPU 利用率不足
  • 连续批处理 (vLLM)：部分缓解，但未根本上解决

2.2 Prefill 和 Decode 的不对称性

Sarathi-Serve 的核心发现：Prefill 和 Decode 在资源需求上有本质差异。

维度 Prefill（预填充） Decode（解码）
计算特征 计算密集型 (Compute-bound) 内存密集型 (Memory-bound)
操作类型 大量 GEMM（并行处理所有 token） 逐 token GEMM + KV Cache 读取
GPU SM 利用率 高 (80-95%) 低 (20-40%)
内存带宽利用 中 极高（瓶颈）
算术强度 高 (FLOPS/Byte 大) 低 (FLOPS/Byte 小)

关键洞察：当 Decode 请求因内存带宽不足而 “停滞” 时，GPU 的计算单元（SMs）实际上处于闲置状态。这意味着有 “免费的午餐” 可用 —— 在不影响 Decode 延迟的情况下，可以同时执行 Prefill 计算。

Insight 1: Decode 的 “停滞” 是 GPU 架构特征，不是 Bug

Sarathi-Serve 的核心洞察在于重新定义了 “停滞”（Stall）的含义。在传统的性能工程中，停滞被视为需要消除的低效现象。但 Sarathi-Serve 认识到：Decode 阶段的停滞是 高算术强度操作在低算术强度阶段后等待内存的自然结果，这是 GPU 架构的固有特征，无法通过软件彻底消除。因此，正确的策略不是 “消除停滞”，而是 “利用停滞”。

Insight 2: Prefill 和 Decode 资源需求的互补性

两个阶段恰好是 “互补”的：

  • Decode 急需内存带宽，但 SM 使用少
  • Prefill 急需 SM 计算，但内存带宽使用可控

这种资源需求的互补性意味着它们可以在同一 GPU 上以接近零干扰的方式共处，这是混合批次调度能够成功的基础。

Insight 3: 微架构级别的调度粒度

Sarathi-Serve 的调度不是 batch 级别的（如传统的 “一轮 Decode 后插入一轮 Prefill”），而是 SM 指令周期级别的。通过 CUDA Stream 的硬件交错执行，Prefill 和 Decode 的 warps 在 SM 上以 warp 调度周期粒度交错运行。这种细粒度调度使资源利用率达到了接近理论上限的水平。

Insight 4: 与传统 OS 调度问题的类比

Sarathi-Serve 解决的问题本质上类似于经典的操作系统 I/O 调度问题：当进程因 I/O 阻塞时，CPU 调度器切换到另一个就绪进程。在 GPU 的上下文中，”内存带宽瓶颈” 扮演了 “I/O 阻塞” 的角色，”Prefill 请求” 扮演了 “就绪进程” 的角色。这提供了一个优雅的概念框架来理解问题。

8. 优势与局限 (Strengths & Limitations)

8.1 优势

  1. 接近零代价的吞吐提升：在几乎不影响 Decode 延迟的情况下提升 40-60% 吞吐。
  2. 无侵入式设计：不需要修改模型权重或架构，纯调度层面优化。
  3. 降低了 Prefill 尾延迟：Prefill 请求不必等待整个 Decode 批次完成，显著降低等待时间。
  4. 理论基础清晰：基于 GPU 微架构的资源竞争分析，可推广到其他 GPU 架构。
  5. 与现有系统兼容：可基于 vLLM 或 TensorRT-LLM 实现，作为调度器的增强。

8.2 局限

  1. GPU 架构依赖：SM 利用率的精确估算依赖于具体的 GPU 微架构（A100 vs H100 vs L40S 差异很大），需要针对每个 GPU 型号校准。
  2. 批次配置敏感：Prefill 插入的时机和数量对配置参数（max_prefill_tokens, batch_size 等）敏感，不当配置可能导致延迟抖动。
  3. 长序列 Prefill 问题：非常长的 Prefill（>8000 tokens）可能仍会干扰 Decode，因为占用大量 SM 周期。
  4. 模型架构差异：不同架构（Dense vs MoE）的 Decode 计算特征不同，SM 预算模型需要相应调整。
  5. 调度开销：每步的 SM 预算估算和 Prefill 选择增加了调度器的 CPU 开销（但通常 <50us，可忽略）。

9. 下游影响与后续工作 (Impact & Follow-ups)

9.1 学术影响

  • 在 OSDI 2024 获得 Best Paper Award
  • “停滞感知” 的概念被后续多个推理系统采纳（vLLM v0.5+, TensorRT-LLM v0.9+）
  • 引发了关于 LLM 推理微架构调度的一波研究热潮

9.2 工业应用

  • Sarathi-Serve 的调度器设计被集成到多个商业 LLM 服务平台
  • 云服务商采用类似策略优化 GPU 实例的推理吞吐
  • 混合批次调度成为 LLM 推理引擎的事实标准

9.3 后续工作

  • Sarathi-Serve v2：支持 chunked prefill，将大 Prefill 请求自动分割
  • Multi-GPU 扩展：将停滞感知调度扩展到多 GPU TP 设置
  • 自适应 SM 预算：在线学习代替离线校准，适应动态工作负载
  • Disaggregated Extension：与 Prefill/Decode 分离架构（如 Splitwise）的集成
