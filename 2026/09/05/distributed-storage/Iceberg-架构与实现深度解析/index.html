Apache Iceberg 架构与实现深度解析

如果说对象存储解决的是“数据放哪”，那 Iceberg 解决的就是“这批文件在某个版本里，怎样才算一张表”。它不是一个计算引擎，而是一套开放表格式：把快照、元数据树、分区演进、schema 演进和 row-level delete 这些能力从数据库里拆出来，放到数据湖里。

一、Iceberg 是什么

Apache Iceberg 是一个开放的表格式规范，目标是让湖仓中的表像数据库表一样可管理，但底层仍然跑在对象存储或文件系统上。

它解决的不是“怎么算”，而是这些问题：

  • 表怎么提交才原子
  • 文件怎么找到并裁剪
  • 分区布局怎么演进
  • schema 怎么加字段、改字段、重命名
  • 历史版本怎么保留和查询

换句话说，Iceberg 是把数据库表语义搬到文件系统之上。

二、为什么数据湖需要表格式

纯文件数据湖有个老问题：文件能放，但表不好管。

没有表格式时，常见痛点是：

  1. 文件越来越多，元数据越来越散
  2. 分区目录暴露物理布局，修改成本高
  3. 并发写容易互相覆盖
  4. 历史版本、回滚、审计都很难做

Iceberg 的思路很直接：不要让引擎直接理解“目录树就是表”，而是让表拥有独立的元数据树。

三、元数据树：metadata / snapshot / manifest list / manifest file

Iceberg 的核心是一个多层元数据树。

这套结构的价值在于分层：

  • metadata file：表的总入口，记录 schema、partition spec、当前 snapshot 等
  • snapshot：某一时刻表的完整视图
  • manifest list：某个 snapshot 包含哪些 manifest
  • manifest file：具体列出哪些 data file / delete file 参与了这个 snapshot

官方 spec 里强调，manifest list 和 manifest file 里都带有统计信息，查询引擎可以靠这些元数据跳过不相关文件。

四、快照、时间旅行与隔离

Iceberg 的 snapshot 是时间旅行的基础。

每次提交都会形成新 snapshot，旧 snapshot 仍可保留一段时间，因此你可以：

  • 查“昨天那版表”
  • 回滚到旧版本
  • 做审计和复现

这本质上是一种表级 MVCC：读者看到的是某个稳定快照，而不是正在变化的底层文件集合。

五、隐藏分区与分区演进

Iceberg 最漂亮的设计之一是 hidden partitioning。

传统 Hive 风格分区把物理目录暴露给用户，查询时常要显式写分区列；Iceberg 则把分区变换藏在表格式里。用户按逻辑列查询，系统自动推断哪些分区可以裁剪。

这带来两个结果：

  • 用户不再被物理目录绑架
  • 分区策略可以随时间演进，而不破坏历史数据

比如历史数据按月分，新数据按天分，Iceberg 仍能把它们放在同一张表里。

六、Schema 演进

Iceberg 支持加列、删列、改列、重命名等 schema 演进操作，且尽量保持无副作用。

这对长期运行的数据平台特别重要，因为真实业务的字段结构总会变：

  • 埋点字段会加
  • 业务口径会改
  • 旧列会废弃

如果 schema 不能演进，湖仓就会被迫频繁重建表。Iceberg 的价值就在于把这个麻烦变成常规操作。

七、Row-level Delete 与更新语义

Iceberg 不是只能“追加写”。它支持 row-level delete / equality delete / position delete 等机制，让更新和删除可以在表格式层面表达出来。

这意味着：

  • 不必重写整张表
  • 不必把更新变成粗暴的全量覆盖
  • 查询引擎可以结合 delete files 解释“哪些行已经不算数”

不过这也带来维护成本，所以 Iceberg 很强调后续的 compaction、rewriting 和 maintenance。

八、提交模型与乐观并发控制

Iceberg 的提交是乐观并发控制风格的。

写入方先基于当前元数据构造新 snapshot，提交时再检查是否有人抢先改了表。如果冲突，就 refresh 后重试。

这个模型很适合湖仓，因为：

  • 读多写少很常见
  • 大多数写冲突其实并不高频
  • 可以把复杂的锁管理压缩成版本检查

九、Branch / Tag / 维护任务

Iceberg 近几年一个很重要的增强，是把 branch 和 tag 纳入表生命周期。

它们允许你：

  • 为实验分支保留独立快照线
  • 为审计标记重要历史版本
  • 给不同生命周期设置不同保留策略

配套的维护动作也很关键：

  • expire_snapshots 清理旧快照
  • rewrite manifests / data files 优化布局
  • remove orphan files 清理孤儿文件

没有这些维护，元数据树会越长越重。

十、性能：为什么元数据能帮查询变快

Iceberg 的加速点不是“魔法存储格式”，而是更聪明的元数据裁剪。

它有两层过滤：

  1. 先用 manifest list 过滤掉不可能命中的 manifest
  2. 再用 manifest file 的文件级统计跳过不相关 data files

这就是为什么文档会把 metadata tree 描述成一棵表级索引树。它让查询规划阶段就能少看很多文件。

十一、与 ByteHouse / 引擎生态的关系

Iceberg 本身不提供计算。它的定位是让 Spark、Flink、Trino、DuckDB、ByteHouse 这类引擎围绕同一张表协作。

ByteHouse 的外部表能力就很典型：它可以直接读 Iceberg，不必把数据先搬进自家格式里。这正是湖仓互操作的核心意义：

  • 表语义统一
  • 文件存储统一
  • 引擎可以多样化

所以 Iceberg 的价值，不只是“表格式”，而是把湖仓从单引擎私有格式，推进到多引擎开放协议。
