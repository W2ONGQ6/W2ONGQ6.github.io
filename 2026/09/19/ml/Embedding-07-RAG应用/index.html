一、RAG 架构概述

1.1 什么是 RAG？

RAG (Retrieval-Augmented Generation) 是一种结合检索和生成的技术架构：

  1. 检索（Retrieval）：从知识库中找到相关文档
  2. 增强（Augmented）：将检索到的文档拼接到提示词
  3. 生成（Generation）：LLM 基于上下文生成答案

1.2 为什么需要 RAG？

LLM 的局限：

  • 知识截止日期：GPT-4 训练数据截至 2023 年 4 月
  • 幻觉问题：编造不存在的信息
  • 无法访问私有数据：企业内部文档、实时数据

RAG 的优势：

  • 实时更新：知识库可随时更新
  • 可追溯性：答案有来源文档支撑
  • 领域适配：无需微调 LLM，只需更新知识库

二、Embedding 在 RAG 中的作用

2.1 离线索引构建

步骤：

  1. 文档分块：长文档切分为 chunk（如 512 tokens）
  2. Embedding 编码：将每个 chunk 转换为向量
  3. 向量存储：存入向量数据库（Milvus/Weaviate/Qdrant）

2.2 在线检索

步骤：

  1. 查询编码：用户问题转换为向量
  2. 向量检索：在数据库中找最相似的 Top-K
  3. 重排序（可选）：用 Cross-Encoder 精排

三、向量数据库选择

3.1 主流向量数据库对比

数据库 开源 部署方式 性能 特色功能 适用场景
Milvus ✅ 本地/云 很高 GPU加速、分布式 大规模生产
Weaviate ✅ 本地/云 高 多模态、GraphQL 多模态检索
Qdrant ✅ 本地/云 高 Rust实现、过滤强 高性能需求
Chroma ✅ 本地 中 轻量、易用 原型开发
Pinecone ❌ 云 很高 托管服务 快速上线
FAISS ✅ 本地 很高 纯向量索引库 简单场景

四、混合检索（Hybrid Search）

4.1 为什么需要混合检索？

纯向量检索的局限：

  • 忽略关键词匹配（如专有名词、代码）
  • 对罕见词表现差（Embedding 未见过）

BM25 的优势：

  • 精确匹配关键词
  • 不依赖预训练模型
  • 对专有名词、代码友好

混合检索 = 向量检索 + BM25

5.4 Chunk Size 选择

Chunk Size 优点 缺点 适用场景
小（256-512） 精准定位、噪声少 上下文不完整 FAQ、简短问答
中（512-1024） 平衡 - 通用知识库
大（1024-2048） 上下文完整 噪声多、检索慢 长文档理解

六、重排序（Reranking）

6.1 为什么需要重排序？

问题：双编码器（Bi-Encoder）无交互，精度有限

解决：两阶段检索

  1. 召回（Bi-Encoder）：快速检索 Top-100
  2. 精排（Cross-Encoder）：精确排序 Top-10

七、RAG 评估

7.1 评估指标

检索质量：

  • Recall@K：Top-K 中包含相关文档的比例
  • NDCG@K：考虑排序位置的归一化增益
  • MRR：第一个相关文档的倒数排名

生成质量：

  • 答案准确性：人工评估 or LLM-as-a-judge
  • 事实一致性：答案是否与检索文档一致
  • 引用质量：答案是否正确引用来源

八、高级技巧

8.1 查询改写（Query Rewriting）

问题：用户查询口语化、模糊

解决：用 LLM 改写为更适合检索的形式

8.2 假设性文档嵌入（HyDE）

思路：先让 LLM 生成假设答案，再检索与假设答案相似的文档

优势：假设答案与真实文档更相似（都是”答案”格式，而非”问题”格式）

8.3 自查询（Self-Querying）

问题：元数据过滤（如”2023年的报告”）

解决：用 LLM 提取过滤条件

九、总结

9.1 RAG 最佳实践

  1. Embedding 模型选择：BGE-M3（中文）、E5-Mistral（英文）
  2. Chunk Size：512-1024，overlap 50-100
  3. 检索策略：混合检索（向量 + BM25）
  4. 重排序：Top-100 召回 + Cross-Encoder 精排
  5. 向量数据库：Milvus（大规模）、Qdrant（高性能）

9.2 性能优化

  • 离线优化：预计算 Embedding、索引优化（HNSW）
  • 在线优化：批量检索、缓存热查询
  • 成本优化：小模型召回 + 大模型精排

9.3 常见坑

❌ Chunk 过大：噪声多，检索不精准
❌ 无重排序：Top-1 可能不是最相关的
❌ 忽略元数据：时间、类别等过滤很重要
❌ 未评估检索质量：盲目优化生成，忽视检索问题
