选 Embedding 模型时，最容易犯的错误是直接挑排行榜第一名。排行榜回答的是“某个版本在一组公开数据上的平均表现”，而工程上真正的问题是：它能否在你的语言、文档、相关性标准、延迟和合规约束下稳定工作？

本篇给出一套可复现的选型方法。模型、价格和榜单会变化，但这套方法不会很快过期。

一、先定义任务，再讨论模型

1.1 相同的向量，不同的相关性

“相关”至少有四种常见含义：

任务 query 认为相关的结果 主要风险
FAQ 检索 “怎么退款？” 对应退款流程 同义改写、口语化
知识库 RAG “合同最长可续多久？” 含具体期限和条件的段落 数字、否定和时效性
商品召回 “通勤轻薄双肩包” 风格、价位和属性匹配的商品 多意图与冷启动
去重 / 聚类 一段新闻 同一事件的其他报道 主题相同不等于事实相同

请先写下“什么算相关”“什么绝不能命中”。若 query 问的是“不支持哪些地区”，仅用语义相似的双编码器往往无法精确处理否定和约束；这类任务通常需要元数据过滤或重排序器。

1.2 建立最小评测集

没有业务评测集，就没有可靠的模型选型。一个有用的起点是 100–300 条 query，每条至少标注一个正例；高价值 query 可标 relevant / partially_relevant / irrelevant 三档。评测集应覆盖：

  • 高频与长尾 query；
  • 短问题、长问题、错别字和口语表达；
  • 专有名词、代码、产品型号、数字和日期；
  • 多语言 query 与跨语言文档；
  • 已知失败案例，尤其是线上投诉或人工兜底样本。

按 document_id 或业务实体切分训练 / 验证 / 测试集，而不是随机切分 chunk。否则同一文档的近重复段落可能同时出现在训练和测试中，离线分数会虚高。

二、如何读懂 MTEB 与公开榜单

2.1 MTEB 测什么？

MTEB（Massive Text Embedding Benchmark）覆盖检索、语义文本相似度、分类、聚类、重排序、配对分类与 bitext mining 等任务。它是筛选候选模型的好起点，但不是业务验收。

指标 回答的问题 适合何时看
Recall@K 正例有没有进入候选池？ 召回层、RAG 首阶段
MRR@K 第一个正确结果排得够不够前？ FAQ、单答案搜索
NDCG@K 多个结果及其位置是否合理？ 有多级相关性或搜索结果页
MAP 整个排序列表的精度如何？ 多相关文档任务
Spearman 相似度排序是否与人工评分一致？ STS、去重辅助诊断

2.2 平均分为何会误导？

一个平均分掩盖了至少五件事：语言覆盖、文档长度、领域词汇、任务指令格式和计算预算。比如，一个模型可在英文短句 STS 上出色，但对中文法规中的条款编号、长文档切分或多语言检索并不一定合适。

阅读榜单时请同时确认：模型版本、评测版本、是否用了查询指令、向量维度、最大输入长度、是否做了 L2 归一化，以及许可证。任何没有这些前提的“模型 A 比模型 B 高 1 分”都不应直接用于采购或上线决策。

三、候选模型应按“能力族”而非单日排名比较

下表列出常见选择方向。版本、维度和许可证会迭代，请以上游 model card 为准。

能力族 代表模型 / 系列 适合场景 使用时要核对
通用轻量双编码器 MiniLM、all-* Sentence-Transformers 系列 原型、低延迟、英文或通用短文本基线 语言覆盖、领域迁移能力
指令化检索模型 E5、multilingual-e5 等 query 与 passage 角色明确的检索 query: / passage: 前缀或指令格式
中文 / 多语言通用模型 BGE、GTE、Qwen Embedding 等系列 中文知识库、跨语言语义检索 中文长尾、最大长度、商用许可证
混合检索 / 多向量模型 BGE-M3、ColBERT 类方案 需要语义、关键词或 token 级匹配兼顾 索引体积、稀疏字段和融合策略
Cross-encoder 重排序器 BGE reranker、MS MARCO 类 reranker 对 Top-K 候选精排 吞吐、最大 pair 长度、批量推理
多模态模型 CLIP / OpenCLIP、ImageBind 类模型 图文检索、以图搜商品、视频帧检索 模态覆盖、领域偏差、图片预处理

3.1 密集、稀疏和多向量：不是同一类索引

密集向量（dense） 擅长语义改写：“忘记登录密码” 可以找到 “账户凭据重置流程”。稀疏向量 / BM25 擅长原词、编号、报错码和人名。多向量 / 晚期交互 保留更多 token 级证据，通常更准，但索引更大、更复杂。

对于企业知识库，最稳妥的起点通常不是三选一，而是 dense 与 BM25 并行召回，使用 RRF 融合，再在有限候选上精排。第 07 篇会给出完整链路。

四、可复现的模型评测协议

4.1 分两轮做，先宽后深

第一轮只挑 3–5 个候选模型，以相同数据、相同分块和相同索引参数比较。目标是淘汰明显不适合的候选，而不是调到极限。

第二轮对前两名模型调优：查询模板、chunk 大小、是否归一化、ANN 参数、稀疏融合权重、重排序深度。这样可以避免“模型 A 的默认参数”与“模型 B 的精调参数”这种不公平比较。

五、按约束做选型

5.1 场景决策矩阵

约束 推荐起点 下一步验证
中文 RAG、百万级 chunk 中文 / 多语言双编码器 + BM25 合同编号、产品名、时间条件的命中率
多语言知识库 多语言模型 + 平行 query 测试集 中→英、英→中与低资源语言的差异
低延迟或边缘部署 小模型、较低维度、量化 P95 编码延迟、内存、召回损失
高精度问答 双路召回 + cross-encoder Top-100 覆盖率和精排后的 NDCG
高度专业领域 通用模型做基线，再用领域数据微调 漏标正例、灾难性遗忘和新旧数据泛化
隐私或合规敏感 本地部署、可审查许可证 模型权重、日志、数据留存与访问边界

5.2 不要忽略文档与查询的不对称性

很多检索任务中，query 短而含糊，文档长且信息密度高。对于支持任务指令的模型，应以其规定格式分别编码 query 与 document；不要因为 API 看起来相同，就用同一无前缀文本处理两端。

同理，文档的 chunk 策略比“选哪个 1024 维模型”更常决定最终质量。若答案被切断、表格被拆散或标题与正文分离，再强的模型也难以稳定召回正确证据。

六、上线、回滚与漂移监控

6.1 模型切换是一项索引迁移

安全的迁移顺序是：

  1. 固定一份 query / qrels 测试集，离线比较新旧模型；
  2. 用新模型全量重建一个新 collection，保留文档、chunk 和模型版本；
  3. 对一小部分流量进行 shadow 或 A/B 对比，记录零结果率、点击、人工纠错和延迟；
  4. 达到门槛后切换别名；保留旧索引直到回滚窗口结束。

6.2 需要监控什么？

  • query 长度、语言、领域和空结果率的分布是否改变；
  • Top-K 分数是否整体漂移，是否出现热门 hub 文档；
  • ANN 召回、索引延迟和过滤条件命中率；
  • 用户点击、改写 query、人工追问和“答案无依据”的反馈；
  • 新增文档是否及时完成切分、编码与索引，删除文档是否真正不可检索。

这些指标会把“模型似乎不行”拆解为可修复的具体问题：数据变了、索引参数变了、标注定义变了，还是编码器真的不适配。

七、选型检查清单

  • 已定义业务相关性和不可命中条件。
  • 已按文档 / 业务实体隔离测试集，而非随机切 chunk。
  • 以相同 chunk、模板、归一化和索引参数比较候选模型。
  • 同时看 Recall、排序质量、P95 延迟、显存 / 成本与许可证。
  • 检查了模型的最大长度、语言、查询前缀和向量维度。
  • 评估了 dense、关键词召回和 reranker 的组合，而非只比单一向量模型。
  • 已为模型、chunk 规则和索引参数建立可回滚的版本记录。

结论：把公开榜单用于“提出候选”，把自己的标注集用于“做决策”。一个在业务失败集上可解释、可复现、能满足延迟预算的第二名模型，通常比一个难以部署的榜首模型更有价值。
