Qwen专题-04：代码模型与智能体 —— 从函数补全到仓库级执行

核心问题：会写代码，为什么还不一定会完成开发任务

补全一个函数通常有明确输入输出；修改真实仓库则需要寻找入口、理解依赖、遵守既有约定、调整多个文件，并通过测试确认行为。Qwen 的代码路线从 CodeQwen1.5、Qwen2.5-Coder 逐步走向 Qwen3-Coder 与 Coder-Next，训练目标也从代码序列扩展到可执行的任务过程。

阅读重点：代码模型负责生成与决策，智能体框架负责工具、上下文和执行循环，测试环境提供反馈。 三者一起决定端到端任务表现。

一、能力阶梯：从局部正确到任务完成

层次 输入 期望输出 常见失败
代码补全 光标前后代码 合适的中间片段 语法正确但与上下文不符
函数生成 描述与函数签名 通过测试的函数 漏边界条件
仓库修改 需求、源码与约束 多文件一致的改动 只修调用方、遗漏实现或配置
代码智能体 需求与可操作环境 经执行验证的最终结果 忽略报错、重复尝试、过早结束

前三层主要关心产物，最后一层还关心行动过程。一个能通过函数题的模型，并不自动学会如何分析构建失败或判断任务已经完成。

二、CodeQwen1.5：学习代码的上下文结构

  • 官方模型卡：CodeQwen1.5-7B，2024 年代码模型节点。
  • 作者 / 机构：Qwen Team，阿里巴巴。

简介

CodeQwen1.5 为 Qwen 的专用代码路线建立了基础。代码语料不仅包含自然语言说明，还包含变量定义、类型、模块关系和大量重复语法结构，需要专门的数据处理与训练安排。

核心技术：Fill-in-the-Middle

普通续写只根据左侧上下文预测后续；实际编辑器常需要根据前缀和后缀补全中间部分。FIM 将训练样本重排成能够利用两侧上下文的形式。

后缀中的断言为中间片段提供了约束。FIM token 和输入格式必须使用对应 tokenizer 的定义，不能假定所有代码模型共享同一套特殊标记。

代表意义

代码模型开始从“会继续写程序文本”转向“能利用编辑位置周围的信息”。这仍然属于代码生成能力；读取文件、应用补丁和运行测试需要额外的执行框架。

三、Qwen2.5-Coder：数据质量、合成与能力平衡

  • 论文：Qwen2.5-Coder Technical Report，2024-09-18 首发，后续版本补充完整尺寸矩阵。
  • 作者 / 机构：Binyuan Hui 等，Qwen 团队、阿里巴巴。
  • 模型矩阵：0.5B、1.5B、3B、7B、14B、32B。

简介

报告介绍基于 Qwen2.5 架构、在超过 5.5T token 代码相关语料上进行持续预训练的模型系列。重点不仅是代码生成，还包括补全、推理、修复，并尽量保留通用和数学能力。

核心创新一：清洗与混合比代码数量更重要

仓库中存在重复项目、自动生成文件、压缩资源以及质量不一的代码。简单收集更多仓库会放大重复与噪声。清洗、去重和合理混合有助于模型学习有价值的结构，而不只是常见样板。

保留自然语言和数学数据也有实际原因：开发需求以自然语言描述，算法复杂度和边界分析依赖数学，模型不能只擅长输出语法片段而无法理解需求。

核心创新二：可扩展的合成数据

合成数据可以构造编程问题、解答与修复示例，为稀缺任务补充训练分布。真正有价值的部分在于质量控制：代码是否可执行、测试是否与需求一致、示例是否覆盖多样语言与难度。

代码执行提供比文本相似度更强的信号，但运行成功还不够。一个函数可能没有抛异常，却产生错误结果；测试样例过少也可能使错误实现通过筛选。

核心创新三：面向多种代码任务训练与评估

生成、补全和修复需要不同上下文。修复任务必须利用错误反馈，仓库场景需要理解符号之间的关系，因此不能只用单一函数生成基准评价整个系列。

代表意义

Qwen2.5-Coder 让专用代码模型具备较完整的尺寸与任务覆盖，也是 Qwen3 数据工程中代码合成的重要来源。它为智能体提供更好的代码底座，但本身并不包含一个自动执行任意命令的运行环境。

四、Qwen3-Coder：训练目标向可执行任务迁移

  • 官方资料：Qwen3-Coder 仓库。
  • 代表开放模型：480B-A35B-Instruct、30B-A3B-Instruct。
  • 发布阶段：2025 年 7 月起；作者为 Qwen Team。

简介

Qwen3-Coder 将 agentic coding 作为重点，关注工具使用、仓库理解和多步开发任务。代码质量与行动策略开始在同一工作流中评价。

核心创新与工程含义

执行反馈进入能力训练。 模型可以依据测试、命令和环境返回值调整后续行动。对一次失败进行定位和修正，比重复生成另一段看似合理的代码更接近真实开发。

长上下文帮助仓库理解。 官方资料介绍原生 256K 上下文及相应外推支持。长窗口可以容纳更多接口与调用关系，但不意味着应把所有文件无差别塞进去。无关日志和构建产物仍会占用预算、干扰判断。

函数调用格式与框架适配。 模型需要输出框架能够解析的工具调用，而框架需要把结果以正确格式送回。模型性能相同，若模板或工具解析器不匹配，也可能表现为“只描述要做什么，却没有真正调用工具”。

代表意义

Qwen3-Coder 将编程任务的成功标准从单段代码拓展到行动后的结果。SWE-bench 一类仓库评测同时依赖模型、工具框架、上下文与预算，不能全部归因于权重本身。

五、Qwen3-Coder-Next：以混合架构支撑长任务

  • 官方模型卡：Qwen3-Coder-Next。
  • 技术资料：官方仓库及报告入口。
  • 基础结构：基于 Qwen3-Next-80B-A3B-Base，80B 总参数、约 3B 激活参数。

简介

Coder-Next 将 Next 的混合注意力与 MoE 结构用于代码智能体，官方描述的训练重点包括可执行任务合成、环境交互与强化学习。

核心创新

更低的每 token 计算与长上下文结构。 代码智能体可能反复读取较长历史和文件，降低每轮成本具有实际价值。但权重仍然是 80B 量级，“面向本地开发”不等于任何个人设备都能直接运行。

从失败中恢复。 修复工作流经常经历“改动 → 测试失败 → 分析 → 再修改”。训练若只包含一次成功样例，模型就缺少处理中间失败状态的经验；环境交互为这些状态提供数据。

适配不同执行框架。 同样的工具在不同 CLI / IDE 中可能有不同名字与参数格式，框架适配因此是可用性的一部分，而不是安装完成后的可选装饰。

版本边界

模型卡明确注明 Coder-Next 仅支持非思考模式。这不否定它能进行复杂任务决策，而是说明它不以该 checkpoint 的显式 Thinking 输出模式提供服务。不要因为名称里有 Qwen3，就强行套用首发 Qwen3 的模式开关。

六、Qwen-Agent 与 Qwen Code：模型之外的执行系统

Qwen-Agent提供围绕工具调用、检索等能力的应用框架；Qwen Code则面向终端开发工作流。它们是软件框架，不是又一代模型权重。

执行系统至少需要保留工具调用 ID、参数、退出状态和相关输出。对长日志提取必要上下文，对独立任务隔离状态，对修改结果做可追溯记录。模型提出的操作还需要由运行环境按配置的范围执行。

七、用一个真实开发任务评测

例如“给列表接口加入分页，并保持已有调用兼容”。一个完整结果应包含参数校验、查询层调整、返回格式、调用方兼容以及必要验证。可以观察：

  • 是否找到已有接口与测试，还是另起一套重复实现。
  • 是否正确处理默认页码、边界值和空结果。
  • 是否根据真实执行结果修复错误。
  • 是否报告最终改动与尚未验证的部分。

记录任务成功率、工具次数、总耗时和回归问题，比只统计生成了多少行代码更能反映生产价值。随着 Qwen3.6 / 3.8 继续强调长任务执行，这套评测方法仍然适用。
