Codex: Evaluating Large Language Models Trained on Code

“Codex: Evaluating Large Language Models Trained on Code”

核心信息

  • 标题: Evaluating Large Language Models Trained on Code
  • 标题翻译: 评估在代码上训练的大语言模型
  • 作者: Mark Chen, Jerry Tworek, Heewoo Jun, Qiming Yuan 等58位作者
  • 机构: OpenAI
  • 发表时间: 2021年7月
  • 发表渠道: arXiv预印本
  • arXiv: 2107.03374
  • 论文链接: https://arxiv.org/abs/2107.03374
  • 代码 / 项目: HumanEval benchmark公开
  • 论文类型: 基准论文 + 方法论文

原文摘要翻译

我们介绍Codex，一个在GitHub公开代码上微调的GPT语言模型，并研究其Python代码编写能力。Codex的一个独立版本驱动了GitHub Copilot。在HumanEval——我们发布的一个新的包含164道手写编程题的评估集——上，Codex解决了28.8%的问题（pass@1）。当对每个问题采样100次时，正确率提升至70.2%。我们进一步发现，重复采样是一个有效策略——对每个问题生成多个候选解并从中选择通过最多测试用例的那个。最后，我们探讨了代码生成模型的局限性和更广泛的影响。

创新点

  1. HumanEval评测基准的创建：这是Codex论文最持久的遗产。HumanEval包含164道手写编程问题，每道题包括函数签名、docstring描述和unittest测试用例。其核心创新是”功能正确性”（functional correctness）作为评测标准——不检查生成的代码是否与参考答案”看起来相似”，而是测试它是否通过所有单元测试。这彻底改变了代码生成评测的范式。

  2. pass@k指标的引入：pass@k的定义是：对每个问题生成k个候选解，如果其中至少有一个通过所有测试，该问题即视为解决。这个指标优雅地捕捉了代码生成的一个关键特性——用户可以从多个生成候选中选择最佳的一个。

  3. 系统性的代码微调探索：论文从GPT-3出发，系统探索了代码微调数据规模（从159MB到54GB GitHub代码）对编程能力的影响。关键发现是：GPT-3本身不会编程（HumanEval 0%），但微调后Codex最高可达72.3%（pass@100）。

  4. 重复采样策略的理论与实践：论文证明pass@k随k呈对数增长——生成更多候选项并从中选择，比提升pass@1更高效。

一句话总结

Codex通过在GitHub代码上微调GPT模型，提出HumanEval评测基准和pass@k指标，在简单编程问题上达到72%正确率（pass@100），开创了AI代码生成时代并直接催生了GitHub Copilot。

研究问题

核心问题分解

GPT家族模型通过在代码上微调后，能获得怎样的编程能力？这种能力如何随着模型规模和数据规模变化？如何设计一个合理的评测基准来衡量代码生成模型的能力？

子问题 1：GPT-3 到 Codex 的迁移效率

GPT-3在自然语言任务上展示了令人印象深刻的少样本能力，但在HumanEval上得分为0%——它根本不会编程。核心问题是：通过在54GB GitHub代码上进行领域适配微调，模型能从0%提升到多少？这种迁移学习的效率如何？

Before this paper：没有人系统地量化过”自然语言预训练 + 代码微调”的潜力。大部分代码生成研究使用从零训练的专用模型（如CodeBERT, GraphCodeBERT），其性能远低于人类开发者。

子问题 2：代码微调数据的规模效应

关键对照实验：用159MB → 1.5GB → 15GB → 54GB的递增代码数据进行微调，观察pass@1的变化。是否存在scaling law？边际收益递减的拐点在哪里？

子问题 3：代码评测的科学方法

在Codex之前，代码生成评测混乱不堪——Bleu score、token-level accuracy、ROUGE被不加区分地用于代码评测。但这些文本相似度指标与”代码是否正确运行”之间的相关性很弱。如何设计一个既能量化评测又贴近实际使用场景的新评测范式？

子问题 4：pass@k的对数增长性质

pass@k随k增长的模式是什么？是线性的（pass@k = k * pass@1），还是对数的（每翻倍k带来固定的收益增量）？这对产品设计（建议几个候选给用户）有直接启示。

Before-This-Paper Pain Points

  1. “看起来像”不等于”确实对”：使用Bleu评测代码生成的论文系统性高估了模型能力——一个”看起来很正确”的代码可能在第一个测试用例就崩溃。
  2. 评测基准的贫乏：没有标准的、手写的、包含测试用例的编程问题集。研究者各自使用自制的数据集，无法横向比较。
  3. GPT-3的”编程盲点”：虽然GPT-3展示了从自然语言描述生成简单HTML/CSS的能力，但在需要精确逻辑的Python函数编写上完全失败（0% HumanEval）。
  4. 代码生成的产品化难题：即使模型有时能生成正确的代码，用户如何从多个候选中高效选择？缺乏”多候选审查”的量化框架。

数据与任务定义

训练数据

  • 54GB GitHub公开Python文件（从约159GB原始文件中去重和过滤后）
  • 从2020年5月前的GitHub仓库中收集
  • 包含函数定义、类、文档字符串、测试文件、Jupyter notebooks等
  • 关键过滤步骤：
    • 文件长度过滤：排除<100字符或>1M字符的文件
    • 重复过滤：排除与HumanEval评测集高度相似的文件（防止评测泄露）
    • 质量过滤：排除生成代码率高的文件（自动生成的代码）

HumanEval基准

  • 164道手写编程问题，覆盖Python基础编程
  • 每道题包含：
    • 函数签名：def function_name(param1: type, param2: type) -> return_type:
    • Docstring：用自然语言描述的功能需求（1-5句）
    • 参考实现：一个正确的Python实现（用于验证测试用例）
    • 测试用例：多个 assert function(input) == expected 语句
  • 问题类型分布：
    • 字符串处理（~30%）：如反转字符串、提取子串、格式化
    • 列表/序列操作（~25%）：如查找最大元素、合并列表、过滤
    • 数学计算（~20%）：如斐波那契数列、素数检测、数值近似
    • 递归/算法（~15%）：如深度优先搜索、动态规划
    • 数据结构（~10%）：如树遍历、图算法
  • 难度分布：主要为CS101-201级别（大学前两门编程课），少量CS301级别

评测指标

  • pass@k：对每个问题生成k个代码片段（使用nucleus sampling + 不同随机种子），如果至少1个通过所有测试则该问题正确。无偏估计公式：

方法主线

机制流程：从GPT-3到Codex的完整6步链路

Step 1：基座模型选择与配置

  • 输入：GPT-3系列预训练权重（12B参数变体）
  • 操作：
    1. 选择GPT-3 12B作为基座——权衡了参数量（更大的175B训练成本过高）和初始能力（12B已经有基本的语言理解和逻辑能力）
    2. 保留GPT-3的完整架构：decoder-only Transformer，96层，96个注意力头，d_model=12288
    3. 使用GPT-3的tokenizer（不引入代码特定的token），让模型学习代码的token pattern
  • 输出：待微调的GPT-3 12B模型
  • 目标：从自然语言能力强的基座出发，通过代码微调定向注入编程能力

Step 2：代码数据处理与格式化

  • 输入：159GB原始GitHub Python文件
  • 操作： 使用标准语言建模格式——将代码视为普通的文本token序列，使用next-token-prediction目标。不需要任何代码特定的结构化处理（如AST解析）。
  • 输出：54GB清洁代码语料
  • 目标：最大化高质量、多样化的Python代码覆盖

Step 3：代码微调训练

  • 输入：54GB代码语料 + GPT-3 12B权重
  • 操作：
    1. 使用标准自回归语言建模损失：
    2. batch_size: 128个序列，每个序列1024 tokens
    3. 学习率：从GPT-3的微调学习率开始（约1e-5），线性衰减
    4. Adam optimizer，gradient clipping=1.0
    5. 训练约100B token（约2个epoch过54GB数据）
    6. 分布式训练：使用数百块GPU并行
  • 输出：Codex-12B模型权重
  • 目标：将GPT-3的通用语言理解能力与GitHub代码中的编程模式结合

Step 4：推理时的代码生成

  • 输入：HumanEval问题（函数签名 + docstring）和Codex模型
  • 操作：
    1. 构造prompt：def {function_name}({params}):\n """{docstring}"""\n
    2. 使用nucleus sampling (top-p=0.95) 从模型的输出分布中采样
    3. 温度 T：对于pass@1使用T=0（贪婪解码），对于pass@k使用T=0.8（增加多样性）
    4. 停止词检测——遇到以下模式时停止生成：
      • \nclass：新类定义开始
      • \n#：注释行（可能表示新代码段）
      • \nif __name__：脚本入口点
      • \n\n\n：连续空行（函数体结束）
    5. 生成直到停止或达到最大token限制（通常512 tokens）
  • 输出：生成的代码字符串
  • 目标：根据自然语言描述生成功能正确的Python函数

Step 5：功能正确性验证

  • 输入：生成的代码字符串和HumanEval的测试用例
  • 操作：
    1. 语法检查：在隔离沙箱中尝试 compile(code_string, '<test>', 'exec')
    2. 如果编译失败（SyntaxError）→ 标记为”未通过”
    3. 如果编译成功，在沙箱中执行代码并运行所有测试用例
    4. 设置执行超时（5秒）和内存限制，防止死循环或资源耗尽
    5. 所有 assert 语句通过且无异常 → 标记为”通过”
  • 输出：每个生成代码的通过/失败状态
  • 目标：客观地判断生成代码的功能正确性

Step 6：pass@k的统计估计

  • 输入：所有问题的通过/失败结果（每个问题 n=200 个样本，其中c个通过）

pass@k 对数增长的理论解释

pass@k 的增长模式近似为对数函数而非线性函数：

这一模式可以从”极端值理论”理解：k次独立采样中至少一次成功的概率取决于尾部概率。如果pass@1的概率为p，则pass@k的概率为1-(1-p)^k。当p较小时，1-(1-p)^k ≈ 1 - e^{-pk} ≈ pk（线性）。当p接近1时，增长变得次线性（对数化）。

对数增长的实际含义：

  • pass@1=28.8% → pass@10=46.8%（+18pp，每次翻倍k约增益9pp）
  • pass@10=46.8% → pass@100=72.3%（+25.5pp，但翻倍了更多次）

从k=1到k=2的增益远大于从k=50到k=51——边际收益递减。

深度分析

为什么GPT-3在HumanEval上是0%——“知道”与”会做”的鸿沟

GPT-3虽然在某些场合展示了从自然语言描述生成代码的能力（如HTML/CSS生成），但在需要精确逻辑和Python语法的HumanEval上得分为0%。深层原因：

  1. 训练数据中代码比例极低：GPT-3的预训练数据中代码占比估计<5%（主要来自CommonCrawl中偶然包含的代码片段）。这意味着模型在预训练中平均每20个token才见到1个代码token——远不足以建立对Python语法和编程模式的可靠统计知识。
  2. 代码的精确性要求远高于自然语言：自然语言容忍大量的模糊性、语法错误和语义漂移。代码不容忍——少一个冒号、多一个空格、用错一个变量名，整个程序就无法运行。GPT-3的自然语言生成能力无法简单地迁移到代码的精确性要求。
  3. Codex的微调本质上是”领域适配”：54GB代码数据的微调让模型接触到了Python语法、标准库API、算法模式、惯用表达等代码特有的”语言游戏规则”。这不是”注入新知识”，而是”格式化的领域技能激活”。

pass@k 对数增长的产品启示

pass@k的对数增长模式意味着：

  1. 从pass@1到pass@10的增益（+18pp）> pass@10到pass@100（+25.5pp，但翻了10倍而非2倍）——这对产品设计有直接启发。Copilot在产品中提供约10个建议（用户可用Tab切换），这是有理论依据的：在10个候选中至少有一个正确的概率（46.8%）远高于单个建议（28.8%），而翻倍到20个建议的边际收益已经很小。

  2. pass@1仍然是实际可用性的核心指标：在IDE中，用户通常只看1-2个建议——如果第一个建议经常出错，即使pass@10很高，用户体验也很差。Copilot的UX设计（Tab接受第一个建议或Alt+]浏览备选）反映了这一现实。pass@1衡量”用户第一次看到的就是正确的”的频率，这是用户体验最敏感的维度。

  3. 多候选策略在测试驱动的开发中尤为有效：如果开发者先写测试、后写实现，可以自动化地运行所有候选代码并选择通过测试最多的一个——这不需要人工审查。但在实践中，大多数Copilot场景是”写代码然后手动测试”而非”先写测试”。

HumanEval的持久遗产——一个评测基准超越模型本身的案例

HumanEval可能是Codex论文最重要的贡献，甚至超过了Codex模型本身。它建立的评测标准包括：

  1. 功能正确性 > 表面相似性：用实际运行测试用例取代文本相似度指标，将评测锚定在”代码是否能用”而非”代码看起来像不像参考答案”。
  2. 手写问题 > 自动构造的问题：164道由OpenAI研究人员手写的编程题确保了问题质量、清晰度和评测价值——自动爬取的问题可能包含歧义或低质量描述。
  3. 多尺度的pass@k：同时报告pass@1（单次尝试）、pass@10（小规模重试）、pass@100（接近上限），提供了模型在不同使用场景下的完整能力画像。
  4. 防止评测泄露的关注：Codex团队在构建HumanEval时将其与GitHub训练数据进行了相似度过滤——这是评测基准能够”公平评测”的前提条件。

HumanEval的持续影响力证明了构建优质评测基准的价值——即使模型一代代更新（GPT-4 pass@1 ≈ 87%，远超Codex的28.8%），HumanEval仍然是衡量代码生成模型能力的事实标准之一。

Codex vs Copilot——从研究到产品的关键差距

Codex论文中的模型与GitHub Copilot中使用的模型之间存在关键差异：

  1. 模型版本：Copilot发布时使用的模型不是论文中的Codex-12B，而是基于GPT-3.5（约175B）的改进版本。论文故意淡化这一点——将”最先进的”模型细节保持模糊以保护商业机密。
  2. 延迟优化：Copilot需要<100ms的单行补全延迟——论文中的Codex从未针对这一延迟目标进行优化。产品化需要大量的模型蒸馏、量化、KV缓存优化等工作。
  3. IDE集成：Copilot的核心竞争力不仅在于模型质量，还在于与VS Code/IDE的深度集成——上下文感知（当前文件、打开的其他文件）、光标位置、用户编码风格等。纯模型评测（HumanEval）无法捕捉这些产品集成带来的提升。
  4. 安全过滤：Copilot包含额外的安全层——过滤生成代码中可能的恶意模式、避免复制训练数据中的版权代码、以及敏感信息泄露防护。这些都不在学术论文的评测范围内。

这些差异说明了一个更广泛的模式：学术论文模型与产品化模型之间的差距通常比论文自身的消融实验差异大得多，但外部观察者难以量化——因为产品模型的许多优化和增强细节是商业机密。

局限

  1. HumanEval过于简单：164道题主要是CS101级别（字符串处理、列表操作、基础算法）。一个合格的CS本科毕业生应能轻松达到pass@1 > 90%。GPT-4后来达到pass@1 ≈ 87%，使HumanEval开始接近”天花板”（更难的评测基准如SWE-bench、CodeContests随之出现）。

    具体影响：HumanEval无法区分”好的”代码模型和”非常好的”代码模型——一旦某个模型达到85%+ pass@1，HumanEval就失去了区分度。评测基准需要足够的”难度天花板”来挑战最好的模型。

  2. 仅Python评测的单语言局限性：虽然Codex展示了多语言的能力，但HumanEval仅覆盖Python。Python的语法简洁和动态类型使得代码生成相对容易——C++或Rust的复杂语法和内存管理要求可能对模型构成完全不同的挑战。

  3. 样本泄露的固有风险：GitHub训练数据中可能包含HumanEval问题的解答（虽然Codex团队进行了记忆检测和去重，但完全杜绝泄露在实践中是不可能的）。这一问题随着模型在GitHub数据上训练量的增加而加剧——后来的Code Llama、DeepSeek-Coder等都面临类似的泄露风险。

    缓解路径：（a）定期发布新的评测集（如LiveCodeBench），（b）在过滤训练数据时使用语义相似度（而非仅精确字符串匹配），（c）使用数据截止日期后的问题（如2024年的LeetCode问题）。

  4. pass@k依赖随机采样但k=100在用户体验中不现实：pass@100=72.3%意味着用户需要检查100个候选建议才能有72.3%的概率找到正确答案——在真实IDE交互中（用户点击Tab接受建议），这是完全不可能的。pass@1（28.8%）更贴近实际用户行为，但论文通过强调pass@100来夸大模型的”上限”能力。

  5. 未考虑代码质量维度：功能正确性评测完全是”工具性”的——代码是否正确运行。但它不评估：

    • 时间/空间复杂度：一个O(2^n)的暴力解法可能通过测试用例但实际不可用
    • 代码风格：是否符合PEP 8、是否有意义的变量名、是否有适当注释
    • 安全性：是否存在SQL注入、路径遍历等安全漏洞
    • 可维护性：代码是否模块化、是否容易理解和修改

    这些问题在SWE-bench和后来的代码质量研究（如CodeBLEU、SecurityEval）中被部分解决。

  6. docstring到代码的单向生成：HumanEval测量的是”给定自然语言描述，生成代码”。但实际编程中大量场景是反向的——“给定代码，生成注释/docstring”，或双向的——“给定代码和注释，修改变量名”。

  7. 无对话式编程场景：HumanEval假设”一次生成，完整函数”。但Copilot的实际使用中，代码补全是增量的、对话式的、上下文相关的——用户在编写代码的过程中不断地接受/拒绝/修改模型的建议。HumanEval无法捕捉这种交互式使用模式。

  8. 计算成本没有被量化：论文未报告训练Codex的计算成本（GPU小时数、碳排放），这使得社区难以评估复现的可行性。54GB数据在12B模型上的微调估计需要数百个GPU日——远超出大多数学术实验室的预算。

可复用洞见

  1. 功能正确性 > 表面匹配：

    • 洞见：用unit test而非文本相似度评测代码生成，是使评测贴近真实价值的范式转移。这个原则可推广到任何”正确性 > 表面相似性”的生成任务——SQL查询、数学证明、逻辑推理等。
    • 为什么泛化：代码、SQL、数学等领域的核心价值是”它是否完成了要求的功能”，而非”它是否看起来像标准答案”。文本相似度指标系统性高估了模型能力（模型可以生成”看起来正确但逻辑错误的代码”）。
    • 如何具体应用：为任何逻辑生成任务构建自动化、可执行的评测——SQL查询（执行并比较结果）、数学证明（用Lean/Coq检查）、配置文件（检查语法和一致性）。

  2. pass@k揭示模型潜力但pass@1决定用户体验：

    • 洞见：pass@k反映了模型在”理想条件”下的能力（用户可以无限审查候选方案），而pass@1反映实际用户体验（第一个建议是正确的概率）。产品设计应在两者之间平衡。
    • 为什么泛化：任何AI辅助系统在”单次建议”和”多建议审查”场景下性能差异巨大——从推荐系统（top-1 vs top-10）到翻译（第一个翻译 vs 多翻译候选）。
    • 如何具体应用：（a）在报告结果时同时报告pass@1和pass@k，（b）优化模型使其在pass@1上有竞争力（通过更好的采样策略、输出排序等），（c）设计UX使得用户方便地浏览多个候选方案（如Copilot的Alt+]切换）。

  3. 域内微调的巨大杠杆——大基座+领域数据：

    • 洞见：GPT-3(0%) → Codex(72.3% pass@100)的跳跃证明：大模型+少量域内数据微调可以产生显著的领域能力，不需要从零训练领域专用的模型。这一模式（”通用预训练+领域后训练”）随后成为行业标准。
    • 为什么泛化：大型通用模型已经在广泛的概念、逻辑和语言模式上积累了丰富的内部表示。领域微调仅需要在这些已有表示上建立”如何应用于该领域”的映射。这是”迁移学习”的极端成功案例。
    • 如何具体应用：（a）优先使用大型通用模型作为起点（即使它们最初在目标领域表现差），（b）收集或合成高质量的领域数据，（c）使用轻量微调（LoRA、prefix-tuning）而非全量训练来降低成本。

  4. 评测基准的长期影响力可以超越模型本身：

    • 洞见：HumanEval的持续使用（在2021年提出，到2025年仍是标准基准）证明：建设一个好的评测基准对社区的贡献可能超过模型本身——模型过时了，基准仍在定义研究问题。
    • 为什么泛化：一个好的评测基准定义了一个研究问题的”标准语言”——它使不同方法之间可以量化比较，驱动社区的集中改进。这类似于ImageNet之于计算机视觉、GLUE/SuperGLUE之于NLP。
    • 如何具体应用：（a）在设计评测基准时，投入足够的精力在问题质量、评测客观性和长期可维护性上，（b）确保基准有成长的”难度天花板”——为未来更好的模型留出区分度，（c）重视防泄露设计。

  5. 代码生成评测的”沙箱执行”模式是AI评测的未来：

    • 洞见：在隔离的沙箱中执行生成的代码并用测试用例验证——这种”生成+执行+验证”的模式不仅是代码评测的最佳实践，也为其他”可执行”生成任务（如命令序列、配置部署、工作流定义）提供了标杆。
    • 为什么泛化：可执行评测消除了主观判断的需求——结果是对/错，不需要人工评分。这使评测完全自动化、可重复、可扩展——是AI评测的”圣杯”。
    • 如何具体应用：对任何”可执行”的AI输出设计沙箱验证流程——Shell命令（在Docker容器中执行）、API调用序列（在test server上重放）、UI操作序列（在headless browser中验证）。

我的笔记

Codex论文的发表标志着AI代码生成从”有趣的研究方向”转变为”可行的产品技术”。GitHub Copilot在论文发表前已开始内测，论文的发表是为了学术公开和技术声明——OpenAI希望建立学术基准并确立技术领先地位。

从论文写作来看，Codex是OpenAI的”产品驱动型研究”的代表作——论文的核心价值不在于模型架构的创新（一个12B GPT变体+代码微调），而在于系统性地建立了一个新的研究领域的评测标准和方法论。这种”定义问题 > 发明方法”的研究风格在NLP和计算机视觉领域一再被证明是最有影响力的（想想ImageNet是如何定义图像识别研究10年+）。

Copilot的商业成功（截至2024年已超过180万付费用户）极大增强了Codex论文的历史地位。但有趣的是，Copilot后来的版本早已不用原始的Codex模型——它被GPT-3.5、GPT-4等更强的模型取代。但HumanEval基准和pass@k指标的地位更加稳固了——它们已成为代码生成领域的”黄金标准”。

从学术诚信角度看，Codex论文的样本泄露问题值得关注。论文承认这一问题并采取了缓解措施（在发布HumanEval前从训练数据中移除匹配内容），但不能完全排除间接泄露——例如，一个模型可能在StackOverflow的解答中见过类似的问题。这个问题是所有基于Web数据的代码模型的固有问题——随着模型和训练数据规模的增长，评测”公平性”变得越来越难以保证。

历史定位与影响

Codex是连接两个时代的桥梁：

  • GPT-3时代（2020-2021）：语言模型的主要应用场景是文本生成和NLU任务
  • LLM代码时代（2021-至今）：代码成为LLM的核心能力维度，催生了从Copilot到Devin的整个AI编程工具生态

它在时间线上的特殊位置——发表于2021年7月，恰好在ChatGPT引爆公众对LLM的兴趣（2022年11月）之前约16个月——使其成为”预ChatGPT时代”最重要的应用引领性工作之一。当公众还在为GPT-3写诗而惊叹时，Copilot已经在默默地改变程序员的工作方式。

前瞻性判断

  1. HumanEval 2.0 或其后继者将产生——保持”功能正确性评测”的核心优势，但扩展至多语言（Python + JS + Java + Rust）、多文件、以及涵盖API调用和框架使用的复杂度。
  2. pass@k可能被pass@budget取代——衡量在固定计算预算（如100次API调用）下能解决多少问题，而非固定采样次数k。这更好地对齐实际约束。
  3. 代码质量的自动评估将补全功能正确性评测——结合静态分析工具（如SonarQube）和LLM judge来评估生成的代码不仅正确，而且安全、高效、可维护。
  4. “代码生成”和”代码理解”的评测将统一——未来的评测可能要求模型不仅能写新函数（HumanEval的范式），还能理解和修改现有代码库（SWE-bench的范式），在同一基准内覆盖全谱系能力。

后续问题

  1. 能否设计一个HumanEval 2.0——保持功能正确性评测的核心优势，但扩展至多语言、多文件、涵盖框架（如React, Django）和API使用？

  2. pass@k能否被”智能选择”取代——生成少量优质候选（如3-5个）覆盖多样化的解决方案空间（通过semantic diversity采样），而非生成k个候选（其中许多是功能相同的冗余变体）？

  3. 随着模型进步，HumanEval已接近天花板（GPT-4 pass@1约87%，o1-preview pass@1约92%）。下一个”足够难”的代码基准应该是什么——SWE-bench？LiveCodeBench？CodeContests？

  4. 功能正确性评测能否扩展到代码质量维度——自动检测生成的代码是否存在性能问题（时间复杂度）、安全漏洞（OWASP Top 10）、或可维护性问题（代码异味）？

  5. HumanEval的沙箱执行模式能否推广到其他需要”功能正确性”的AI评测领域——如数学证明（自动证明验证）、数据库查询（查询结果匹配）、脚本执行（运行时检查）？
