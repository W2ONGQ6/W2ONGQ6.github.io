Voyager: An Open-Ended Embodied Agent with Large Language Models

Voyager: 基于大语言模型的开放式具身智能体

核心信息

原文摘要翻译

在开放世界中构建具备持续学习能力的具身智能体是 AI 领域的核心挑战。本文提出了 Voyager，首个基于大语言模型的开放式具身终身学习智能体，在 Minecraft 中自主探索、发现技能并持续进步，无需任何人类干预或模型微调。Voyager 包含三个核心组件：(1) 由 GPT-4 驱动的自动课程（Automatic Curriculum），根据智能体当前技能水平自主提出更难的目标；(2) 持续增长的技能库（Skill Library），将成功完成的程序存储为可复用代码；(3) 迭代式提示机制（Iterative Prompting Mechanism），通过环境反馈和执行错误进行代码自我修正。在 Minecraft 中，Voyager 收集的独特物品数量比以前的最先进方法多 3.3 倍，探索距离延长 2.3 倍，解锁科技树里程碑的速度快 15.3 倍。Voyager 根本上挑战了”强化学习是智能体在开放世界中学习的唯一途径”这一传统认知。

研究问题

核心问题：在一个开放式的（open-ended）3D 世界中，智能体能否不通过强化学习（RL）的梯度更新、不依赖人类标注数据，仅凭 LLM 的推理和代码生成能力，实现持续的技能获取和自主探索？

传统 RL 方法在 Minecraft 中面临根本性困难：稀疏奖励（某些目标需要数千步才能获得首个奖励）、组合性（技能需要组合使用）、以及探索空间的无限性（新的目标和配方不断解锁）。Voyager 试图以纯 LLM 驱动的方法绕开这些问题——它不学习”哪种动作大致正确”，而是直接生成可执行的 JavaScript 代码来完成任务。

创新点

  1. 自动课程（Automatic Curriculum）：GPT-4 根据智能体当前技能水平和探索进度自动提出越来越难的下一目标——实现了一种基于 LLM 的”新颖性搜索”（novelty search），驱动持续向未探索领域推进。

  2. 技能库（Skill Library）：将每次成功完成的任务代码存储为可复用技能，以嵌入向量索引检索。遇到新任务时检索最相关已有技能作为参考——实现复杂行为的增量组合，缓解灾难性遗忘。

  3. 迭代式提示机制（Iterative Prompting Mechanism）：代码生成后经过环境反馈、执行错误和自验证的多轮迭代完善——确保最终输出的代码能够正确执行。

  4. 证明了 LLM 替代 RL 在开放世界中的可行性：在 Minecraft 这个无限开放的世界中，纯 LLM + 巧妙的记忆管理就能实现持续的技能获取和自主探索。

一句话总结

Voyager 证明了 LLM 通过自动课程、技能库和迭代式提示机制，可以在 Minecraft 这个无限开放的世界中实现持续的技能获取和自主探索，无需任何梯度更新或人类干预——从根本上挑战了”RL 是开放世界学习唯一途径”的传统认知。

组件一：自动课程（Automatic Curriculum）

动机

传统课程学习（curriculum learning）的局限：固定难度阶梯无法适应每个智能体的实际进度，稀疏奖励导致 RL 智能体在开放世界中极易陷入”停滞”（找不到下一个有意义的目标）。Voyager 用 GPT-4 替代了课程设计者——它根据智能体的当前状态动态选择”最有价值的下一个目标”。

组件二：技能库（Skill Library）

设计动机

Minecraft 中的任务不是孤立的——“制作钻石剑”需要先会制作木棍（来自技能”制作木板”）、需要先会设置熔炉（来自技能”制作熔炉”）、需要先会挖钻石（来自技能”深入开采”）。技能库将这些底层技能保存为可复用的代码片段，使得复杂任务的代码生成可以从已有技能组合而来，而非从零开始。

组件三：迭代式提示机制（Iterative Prompting Mechanism）

设计动机

LLM 生成的代码往往在第一次尝试时存在错误——因为 LLM 可能不清楚 Minecraft 的具体 API、物品 ID、坐标系统等细节。迭代式提示通过执行反馈闭环来修正这些错误。

迭代修正流程

展示了从初始代码生成 → Minecraft 执行 → 错误收集 → 错误分析 → 代码修正 → 再执行的完整循环。最多迭代 5 轮。如果 5 轮后仍失败，标记任务为”暂不可达成”，反馈给自动课程以调整下一个目标。

三种反馈类型

反馈类型 来源 示例 修正策略
语法错误 Minecraft API TypeError: bot.findBlock is not a function 检查 API 文档，使用正确函数名
逻辑错误 执行结果 “找不到熔炉，因为离得太远” 扩大搜索范围或先移动到目标附近
语义错误 自验证 “代码执行完了但物品栏没有铁锭” 检查冶炼逻辑是否正确、配方是否正确

这个自验证步骤过滤了”代码执行无报错但结果不对”的静默失败。

详细机制流程（Numbered）

流程 A：主循环

Step 1：环境感知与状态更新

  • 输入：Minecraft 游戏 API（物品栏、生命值、位置、已解锁配方、附近方块）
  • 操作：调用 Mineflayer API 批量查询智能体状态
  • 输出：结构化的 agent_state 字典

Step 2：自动课程 — 目标选择

  • 输入：agent_state + 探索历史 + 失败历史
  • 操作：GPT-4 综合科技树进度、新颖性得分、生存需求，选择最有价值目标
  • 输出：自然语言目标描述（如 “采集 3 个铁矿石并用熔炉冶炼成铁锭”）

Step 3：技能库检索

  • 输入：目标描述的嵌入向量 × 技能库中所有技能的嵌入向量
  • 操作：计算余弦相似度，返回 Top-K（K=5）
  • 输出：K 个最相关技能的完整代码 + 描述

Step 4：迭代式代码生成与修正

  • 输入：目标描述 + agent_state + Top-K 技能代码 + Minecraft API 文档片段
  • 操作：
    a. GPT-4 生成初始代码 code_v0
    b. 在 Minecraft 中执行 code_v0
    c. 收集执行反馈（错误 / 成功 / 自验证结果）
    d. 如果失败，将反馈加入 Prompt，GPT-4 生成 code_v{n+1}
    e. 重复直到成功或达到最大迭代次数（5）
  • 输出：可成功执行的代码 或 失败标记

Step 5：技能库更新

  • 输入：成功执行的代码 + 任务描述 + 自验证结果
  • 操作：生成嵌入向量，与代码一起存入技能库
  • 输出：更新后的技能库（大小 +1）

Step 6：状态持久化与下一轮

  • 输入：当前执行结果
  • 操作：更新 agent_state，记录探索历史
  • 输出：新一轮循环从 Step 1 开始

流程 B：技能细化的子循环

Step 1：技能候选评估

  • 输入：已有技能库大小 N
  • 操作：评估最近 M 个技能的成功率（是否仍有效）
  • 输出：技能质量报告（哪些需要重新验证）

Step 2：技能过时检测

  • 输入：技能库中所有技能 × 最近执行的成功/失败记录
  • 操作：如果某技能的依赖项发生变化（Minecraft 版本更新导致 API 不同），标记为”可能过时”
  • 输出：过时技能列表

Step 3：技能重建

  • 输入：过时技能列表 + 当前 Minecraft API
  • 操作：对每个过时技能，使用迭代式提示重新生成（利用其他依然有效的技能作为参考）
  • 输出：更新后的技能代码

关键发现：

  • 三个组件都至关重要，但迭代式提示是”最不可缺”的——移除后性能崩盘最严重（独特物品从 63 降到 11）
  • GPT-4 替换为 GPT-3.5 导致 40% 的性能下降，说明代码生成能力仍有显著差距
  • 技能库的贡献主要体现在后期——前期技能库小，影响可忽略；后期技能库成为组合性复杂任务的关键

RL vs LLM：两种学习范式的根本差异

Voyager 的关键洞察是：LLM 的预训练语料中已经包含了关于 Minecraft 的大量世界知识（Wiki、论坛帖子、YouTube 字幕）。训练一个 RL agent 从头学习”先做木板才能做工作台”这样的常识，相当于在海量已知信息上浪费算力。LLM 的”常识”为 Agent 提供了极高的起点——这就是为什么 Voyager 不需要梯度更新。

技能库与灾难性遗忘

RL 智能体在学习新技能时，往往会”遗忘”旧技能（灾难性遗忘）。Voyager 的技能库以代码形式存储——代码不会被遗忘。更重要的是，新技能调用旧技能作为子程序——这强化而非削弱了旧技能的可用性。

这类似于软件工程中的”库”概念——添加新的依赖不破坏旧的 API。技能库实现了”增量式学习”的最理想版本：新能力建立在旧能力之上，旧能力保持可用。

迭代式提示 vs Fine-tuning

相比 Fine-tuning（将执行反馈通过梯度更新融入模型权重），迭代式提示的优势：

维度 Fine-tuning 迭代式提示
样本效率 低（需要多个样本） 高（每次执行即反馈）
特定性 模型权重全局改变 反馈仅影响当前任务
灾难性遗忘 高风险 零风险
部署成本 每次更新需重新训练+部署 零成本（代码级）
可解释性 低（权重变化难理解） 高（代码可读、修改历史可追溯）

为什么选 Minecraft？

Minecraft 是测试开放式学习的理想平台：

  1. 无限自由度：3D 世界 + 建造 + 战斗 + 农业 + 红石电路——几乎任何目标都可以定义
  2. 明确的科技树：有清晰的”进度路径”作为评估指标
  3. 组合复杂性：后期的复杂物品需要数十个底层步骤——测试真正的组合规划能力
  4. 丰富的 API：Mineflayer 提供了完整的 JavaScript 接口
  5. 社区知识：大量在线教程和 Wiki 确保 LLM 的预训练语料中有足够的相关知识

局限

  1. 依赖 LLM 预训练中的 Minecraft 知识：Voyager 的表现高度依赖 GPT-4 预训练语料中关于 Minecraft 的知识。如果换成一个冷门的、LLM 不熟悉的游戏或领域，Voyager 的表现会大幅下降。对于真实世界中的新领域（如操控一个新型机器人），LLM 缺乏先验知识的情况下，这一方法的有效性存疑。

  2. 代码生成引入的脆弱性：生成的 JavaScript 代码需要精确匹配 Mineflayer API——微小的 API 版本差异、参数名称变化、异步/同步的不一致都可能导致代码失败。Voyager 通过迭代修正缓解了这一点，但无法根除——5 轮修正后仍有约 20% 的任务无法完成。

  3. 缺乏对物理世界的泛化：Minecraft 是一个离散的、网格化的世界——每个方块是明确的、动作是原子性的。将其扩展到连续物理环境（如机器人操作）时，”生成代码→执行”的范式将面临连续控制、传感器噪声、物理不确定性等全新挑战。

  4. 计算成本：GPT-4 每一次目标选择、代码生成、代码修正都需要调用：

    • 每轮主循环：2-10 次 GPT-4 调用（课程选择 + 代码生成 + 多次修正）
    • 每个游戏日内约 30-50 次调用
    • 在 GPT-4 的 API 定价下，单次完整的 Voyager 运行成本巨大
    • 这在真实机器人应用中不可承受（需要高频决策+低成本）

  5. 技能库的语义退化：随着技能库增长，相似技能可能变得难以区分——“打开木门”和”打开铁门”在嵌入空间中极为接近，检索可能返回错误相关技能。更需要的是结构化的技能表示（如带类型签名的函数）而非仅依赖嵌入相似度。

  6. 目标选择的局部最优：自动课程基于当前状态做决策，没有长期规划能力——可能困在”局部最优”：反复采集附近的资源而不移动，因为 GPT-4 每次评估认为当前区域仍有未收集的资源。需要添加显式的”滞留检测”和”强制探索”机制。

  7. 自验证的不可靠性：让 GPT-4 自评代码是否成功存在固有偏差——模型倾向于认可自己的输出。自验证在某些边缘案例中给出了 False Positive（代码实际未达成目标但判定为成功），导致错误的技能被存入技能库，后续任务基于错误技能进一步放大错误。

可复用洞见

洞见 1：用代码而非权重来表示”学习到的技能”

核心思想：与其通过梯度更新让模型”记住”新能力（微调），不如将技能保存为可执行的代码。代码天然可审计、可组合、可修正——而且不会被遗忘。

如何在你的工作中应用：

  • 对于 Agent 系统，维护一个”可复用操作库”——不是嵌入向量，而是真实的可执行函数
  • 对于自动化流水线，将成功执行的任务步骤保存为模板，下次直接组合
  • 关键模式：skill = (code, description, embedding, dependencies) 四元组
  • 代码级别的增量学习：每次成功的执行都是技能库的净增长

洞见 2：LLM 预训练知识 = 零样本先验

核心思想：只要 LLM 在预训练中见过某领域的信息，它就已经有了一个巨大的”常识库”。不要从头训练——把这个常识库当作起点。

如何在你的工作中应用：

  • 在选择要解决的任务时，优先考虑 LLM 已有大量知识的领域（节省训练成本）
  • 在 Agent 的 Prompt 中显式引用 LLM 已知的概念（如 “你是一个 Minecraft 专家”）
  • 对于新领域，先投喂相关文档给 LLM（小样本学习），再让其生成代码
  • 避免在 LLM 已经隐式掌握的概念上做显式训练

洞见 3：反馈闭环是 Agent 鲁棒性的秘密

核心思想：执行 → 失败 → 错误反馈 → 修正 → 再执行——这个闭环是弥补”LLM 不理解具体执行环境”的关键。不是让 LLM 一次生成完美代码，而是给它修正的机会。

如何在你的工作中应用：

  • 对于任何 Agent 系统，加入”执行 → 自检 → 修正”循环（而非期望一次成功）
  • 将错误信息本身作为 Prompt 的一部分返回——LLM 擅长从错误信息中推理修复方案
  • 设置最大修正轮次（防止无限循环），记录失败任务供后续分析
  • 对于生产系统，加入自验证步骤（让 LLM 判断代码是否真正达成了目标）

洞见 4：技能组合性 > 技能数量

核心思想：Voyager 不一定比基线有更多”独特技能”——它的优势在于每个新技能可以调用所有已有技能作为子程序。这种组合性使能力增长是非线性的。

如何在你的工作中应用：

  • 设计 Agent 的能力时，优先考虑可组合性——每个新能力应调用已有的基础能力
  • 使用函数式编程范式：让 Agent 生成的代码是纯函数，输入输出明确
  • 建立清晰的依赖图——知道哪些技能是其他技能的前置条件
  • 对于对话 Agent，将”对话模式”设计为可组合的（如”道歉模式”可以嵌入”拒绝模式”中使用）

洞见 5：自动课程 = 用 LLM 理解进度 + 用好奇心驱动探索

核心思想：传统的课程学习需要人工设计阶梯——Voyager 证明了 LLM 可以理解智能体的当前进度（通过物品栏、解锁配方等结构化数据），并自主推断”下一步该学什么”。这本质上是将”教学决策”自动化。

如何在你的工作中应用：

  • 对于自适应学习系统，让 LLM 分析用户当前的知识点并推荐下一步
  • 对于 Agent 系统，维护一个”能力清单”（类似于 Minecraft 的物品栏），供 LLM 推断进度
  • 加入”新颖性驱动”——不仅推进度，还要奖励探索未访问区域

我的笔记

读后反思

Voyager 最颠覆性的论断是：在开放世界中，代码生成 + 记忆管理可能是比 RL 梯度更新更高效的学习方式。 这一论断建立在 LLM 预训练语料中已经包含了大量世界知识这一事实上——为什么要在 Minecraft 中从头学习”铁矿石需要镐来开采”这个事实，当 LLM 已经知道它？

这让我重新思考”学习”的本质：RL 的学习本质上是”从无到有的经验积累”，而 Voyager 的学习是”从已有的丰富知识中调用和组织”。前者的战场是全新领域（没有任何先验知识的物理环境），后者的战场是人类知识已经充分覆盖的领域（大部分工程任务）。

关键认识

代码是最优雅的记忆格式。 与嵌入向量（模糊、无逻辑、不可解释）不同，代码天然保存了逻辑结构。技能库不仅仅是一个记忆系统——它是一个不断增长的、可执行的程序库。这让我想到了”软件 2.0”的概念：也许未来的”模型学习”就是将成功的行为模式编译为代码。

与 Toolformer 的联系

Voyager 的迭代式提示与 Toolformer 的自监督工具学习在哲学上一脉相承：两者都试图让 LLM 学习”何时以及如何调用外部能力”——只是 Voyager 的”外部能力”是 Minecraft API + 自身技能库，而 Toolformer 的是计算器/搜索等通用工具。

未探索的方向

  1. 跨智能体技能共享：如果多个 Voyager 实例共享同一个技能库，是否能指数级加速探索？
  2. 技能库的自动优化：当技能库中的重复技能太多时，能否自动合并和泛化？
  3. 从代码到动作：在真实机器人上，能否将”生成 Python 控制代码”替代”手动编程的控制器”？
  4. 课程的安全约束：如果自动课程提出一个”危险”目标（如摧毁自己的基地），如何引入安全护栏？
  5. 跨世界泛化：在 Minecraft 中学习的”采集-制作-建造”模式，能否泛化到其他生存建造游戏？
