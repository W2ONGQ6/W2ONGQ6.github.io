AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation

AutoGen: 通过多智能体对话实现下一代 LLM 应用

  • 标题: AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation
  • 标题翻译: AutoGen：通过多智能体对话实现下一代 LLM 应用
  • 作者: Qingyun Wu, Gagan Bansal, Jieyu Zhang 等
  • 机构: Microsoft Research / Penn State University / University of Washington
  • 发表时间: 2023 年 8 月
  • 发表渠道: 持续更新的开源社区项目

原文摘要翻译

多智能体对话是一种使多个语言模型能够通过对话协作解决复杂任务的强大范式。本文提出了 AutoGen，一个通过”可对话智能体”（conversable agent）抽象实现多智能体对话的通用框架。在 AutoGen 中，每个 Agent 可以是一个 LLM、一个工具、一个人类用户、或它们的任意组合，Agent 之间通过标准化的消息传递协议进行对话。框架提供了多种开箱即用的对话模式：双智能体辩论、多智能体顺序协作、分层群聊和嵌套对话。AutoGen 还支持灵活的人类介入循环（Human-in-the-loop），使人类用户可以在关键决策点自然介入。我们在数学问题求解、代码生成、数据分析和问答系统等多样化场景上进行了充分验证，证明了多智能体对话模式在提高答案质量和可解释性方面优于单次 LLM 调用。

研究问题

核心问题：当单个 LLM 的回答质量不足时，能否通过”让多个 LLM 或 Agent 互相讨论”来产生更高质量的最终输出？

单个 LLM 的局限是已知的：容易产生幻觉、答案缺少多方检验、一次生成难以自我纠错。AutoGen 提出”对话即编程”（Conversation Programming）的范式：通过编排多个 Agent（各自有不同角色、能力和 LLM）之间的对话来求解复杂任务——就像组织一支团队开会解决问题一样。

创新点

  1. Conversable Agent 核心抽象：每个 Agent 可以是 LLM、工具、人类用户的任意组合——Agent 之间通过标准化的消息传递协议对话，构建多智能体系统如同让多个角色”开会讨论”一样直观。

  2. 灵活的人类介入循环（Human-in-the-Loop）：人类用户被自然地作为对话参与者之一——在关键决策点介入提供反馈或修正，不需要人类参与时自动推进。

  3. 丰富的预设对话模式：辩论式、顺序协作、分层群聊、嵌套对话——开箱即用，无需复杂的调度逻辑。

  4. 代码执行与工具使用原生集成：Agent 可以生成并执行代码，并在代码执行出错时将错误反馈纳入对话——形成”生成-执行-反馈-修正”闭环。

  5. 多智能体框架的事实标准化：AutoGen 以其优雅的抽象和 Microsoft 的背书，迅速成为多智能体框架的事实标准。

一句话总结

AutoGen 通过”可对话智能体”的核心抽象和丰富的预设对话模式，将多智能体系统从学术概念变成可工程化的基础设施，大大降低了多 LLM 协作应用的开发门槛，使”多个 Agent 开会讨论”成为解决复杂任务的标准范式。

Conversable Agent 抽象

展示了 Agent 的三大核心能力（receive / generate_reply / send）以及 Agent 的四种类型：LLM Agent、Tool Agent、Human Agent、Composite Agent。所有 Agent 通过统一的 send-receive 接口通信——这就是”Conversation Programming”的核心。

Agent 的统一接口

这个简单而优雅的设计使任何能”接收消息并产生回复”的实体都可以作为一个 Agent 参与对话——不需要关心它是 LLM、工具调用、人类用户还是它们的组合。

Agent 类型

Agent 类型 实现方式 用途 示例
LLM Agent generate_reply → LLM API 调用 推理、生成、分析 GPT-4 驱动的代码生成 Agent
Tool Agent generate_reply → 工具函数执行 执行实际操作 Python 代码执行器、数据库查询器
Human Agent generate_reply → 等待人类输入 关键决策把关 “请审查此代码变更是否合理”
Composite Agent generate_reply → 触发子对话 复杂多步推理 嵌套对话（子对话完成后汇总）
Teachable Agent generate_reply → LLM + 用户反馈记忆 从人类反馈中学习 逐步学习用户偏好的个人助手

模式 4：嵌套对话（Nested Chat）

嵌套对话的关键特性：

  • 父 Agent 发起子对话，子对话有独立的上下文和历史
  • 子对话完成后，汇总结果返回给父对话
  • 子对话期间，父对话挂起等待
  • 子对话可以有自己的子对话（树形递归结构）

适用场景：需要分阶段处理的大任务（如撰写研究论文：先调研、再写作、再审核）

对话编程（Conversation Programming）详解

概念

“对话编程”（Conversation Programming）是 AutoGen 提出的核心范式：用编程的方式定义 Agent 之间的对话流程——将”对话流”作为一种新的编程原语。

与传统工作流编程的对比：

维度 传统工作流（Airflow/Temporal） Conversation Programming
执行单元 函数/任务 Agent（具有推理能力的对话实体）
控制流 if-else, for, try-catch 对话转向（谁回复谁）
数据流 显式参数传递 对话历史中的消息
灵活性 静态（预定义 DAG） 动态（Agent 根据对话内容决策）
人类参与 需要特殊处理 原生支持（Human Agent）
错误处理 异常捕获 → 重试/失败 Agent 讨论错误 → 自行修正

对话终止与转向

代码执行集成

AutoGen 最强大的特性之一是”对话中的代码执行”——Agent 可以在对话中生成代码、执行代码、并在出错时将错误反馈作为对话的一部分。

  1. Executor Agent (Docker sandbox):
    执行代码 → 捕获 stdout/stderr/exit_code

  2. 如果成功:
    Executor → Coder: “执行成功，输出为: [result]”

  3. 如果失败:
    Executor → Coder: “执行失败，错误信息: TypeError on line 42…”
    Coder → Executor: “我修复了问题，这里是新代码: …”
    回到步骤 2

好的角色 Prompt 包含:

  1. 角色定位
    “你是一位有15年经验的Python开发者，专精于数据处理”

  2. 行为约束
    “每次回复必须包含：分析、代码、和预期输出”
    “如果不确定，明确说’我不确定’而不是猜测”

  3. 协作约定
    “当接收来自 Critic 的反馈时，
    首先确认你是否同意这个反馈，
    然后说明你将如何修改代码”

  4. 终止条件
    “当你认为代码已完整且无错误时，回复 ‘FINAL CODE:’”

  5. 输出格式
    “始终用以下格式回复：
    ANALYSIS: <分析内容>
    CODE: <代码内容>
    EXPLANATION: <代码说明>”

TERMINATE 模式下的交互:

  1. Agent A 自动推理并发送消息给 Agent B
  2. Agent B 自动回复
  3. Agent A 基于 B 的回复自动修正
  4. …（多轮自动对话）…
  5. Agent B 回复: “TERMINATE: 最终代码已生成并通过测试”
  6. UserProxyAgent 暂停 → 显示结果给人类
  7. 人类可以选择: 接受、修改、或重新开始对话

Question: “In how many ways can 5 people sit around a round table?”

Solver: “For a round table, the formula is (n-1)!.
So the answer is 4! = 24.”

Critic: “Wait——for a round table, we need to consider whether
rotations are considered the same arrangement.
If yes, then (n-1)! is correct.
But if the question implies distinct seats,
the answer would be 5! = 120.
Since the question says ‘around a round table’
without specifying numbered seats, (5-1)! = 24 is correct.”

Solver: “Good catch. I agree that the standard convention for
a round table is that rotations are equivalent, so 24 is correct.”
