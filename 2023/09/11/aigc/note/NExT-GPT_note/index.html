NExT-GPT: Any-to-Any Multimodal LLM

“NExT-GPT: Any-to-Any Multimodal LLM”

  • 机构: 新加坡国立大学 (NUS) NExT++ 研究中心

原文摘要翻译

多模态大语言模型（MM-LLM）正在迅速发展，但大多数现有系统仅支持多模态输入而输出纯文本。本文提出NExT-GPT，首个端到端的任意到任意多模态大语言模型，支持文本、图像、视频和音频四种模态的任意组合输入和输出。我们将LLM作为核心推理引擎，通过轻量级适配器连接模态专用编码器和解码器。整个系统仅需微调约1%的参数（输入和输出投影层），编码器、LLM和扩散解码器均保持冻结。我们构建了模态切换指令微调（MosIT）数据集和策略，赋予模型复杂的跨模态推理和内容生成能力。ICML 2024 Oral。

创新点

  1. LLM作为中央代理的模态路由架构 —— LLM作为”大脑”进行跨模态语义推理，输出包含文本token和”模态信号token”——后者指示解码层生成哪种模态的内容。这是”LLM + 工具”范式在多模态生成中的首次系统实现——LLM不仅仅”理解”多模态输入，还能”指挥”多模态输出。

  2. 极端轻量训练（约1%参数） —— 仅训练输入投影层和输出投影层，编码器（ImageBind）、LLM（Vicuna-7B）和扩散解码器（Stable Diffusion等）全部冻结。扩展到新模态只需训练新的投影层——这是”冻结-适配”范式在any-to-any场景的极致应用，训练成本约为全量微调的1/100。

  3. MosIT数据集与模态切换指令微调 —— 手工构建约5000条高质量跨模态指令数据，覆盖”文本+图像 -> 视频”、”音频+文本 -> 图像”等复杂组合。每条指令包含：(1) 多模态输入指令，(2) LLM的推理输出，(3) 模态信号token，(4) 最终的多模态输出。MosIT赋予模型跨模态语义理解与内容生成能力。

  4. 四模态编解码器的统一编排 —— 首次将文本（LLM tokenizer）、图像（Stable Diffusion）、视频（Zeroscope）、音频（AudioLDM）四种解码器统一在LLM的调度下工作——LLM决定”何时生成什么模态”。

一句话总结

NExT-GPT以LLM为中央推理引擎连接模态专用编解码器，仅微调1%参数即实现四模态任意到任意生成，是ICML 2024 Oral论文。

研究问题

核心问题：能否构建一个统一的框架，使用户可以用任意模态（文本/图像/视频/音频）作为输入，LLM理解后生成任意模态的输出——而无需为每种输入-输出组合训练独立模型？

子问题拆解

  1. 模态路由问题：面对任意模态组合的输入，LLM如何决策”应该输出什么模态”？
  2. 参数效率问题：四种模态四种编码器四种解码器——如果全量训练，参数爆炸。能否以1%的参数实现？
  3. 跨模态推理问题：LLM如何在没有直接训练信号的情况下，将文本推理能力迁移到跨模态推理（如”根据这张图片的声音，推测可能发生了什么”）？
  4. 数据构建问题：any-to-any的指令数据如何构建——所有模态组合的穷举 = 16种输入-输出组合，每种的训练数据从何而来？

数据与任务定义

MosIT数据集构建


Figure 1: 来源—原论文。

MosIT（Modality-switching Instruction Tuning）数据集是NExT-GPT的关键贡献——解决”any-to-any的指令数据从何而来”的问题。

构建策略：

  1. 收集已有的单模态-单模态配对数据（如文本-图像配对来自 LAION，文本-音频配对来自 AudioCaps）
  2. 通过LLM辅助将这些配对扩展为”跨模态指令”——合并多个配对，构造复杂的跨模态输入-输出对
  3. 人工审核和改写，确保指令自然、多样、合理

方法主线

架构设计


Figure 2: 来源—原论文。

NExT-GPT的架构遵循”编码-推理-解码”的三段式设计：

第一段：多模态输入编码

模态 编码器 冻结 输入投影 可训练
文本 LLM tokenizer (Vicuna) 否（嵌入层包含在LLM中） 无 否
图像 ImageBind ViT 是 Linear + Transformer（~2M） 是
视频 ImageBind Video encoder 是 Linear + Transformer（~2M） 是
音频 ImageBind Audio encoder 是 Linear + Transformer（~2M） 是
  • 为什么选择 ImageBind：ImageBind已经将图像、视频、音频对齐到统一嵌入空间——这为多模态输入提供了天然的语义一致性。所有非文本模态的嵌入已经在同一空间中，只需要一个统一的输入投影来映射到LLM空间
  • 输入投影层设计：每种模态的输入投影是独立的（不同模态的特征维度不同），但架构相同——一个轻量Transformer（4层，4头，~2M参数）将模态特征映射到LLM的嵌入维度

第二段：LLM中央推理

  • 模型：Vicuna-7B (LLaMA-based)

  • 角色：接收投影后的多模态输入token，进行跨模态语义推理

  • 输出类型：

    1. “Hidden Text” token：LLM的中间推理输出——模型”思考过程”的痕迹
    2. “Visible Text” token：用户可见的文本回复
    3. “Modality Signal” token：特殊token，指示后续应该生成哪种模态

    例如输出序列：[Hidden Text] … [Text] “Based on the image…” [IMG_SIGNAL]

  • 为什么LLM能做到跨模态推理：LLM在纯文本训练中已经学会了抽象推理——当多模态输入被投影到LLM的嵌入空间时，LLM将其视为”某种外语”并尝试推理。ImageBind的统一嵌入空间确保了不同模态的语义在LLM看来是连贯的

第三段：多模态输出解码

模态 解码器 冻结 输出投影 可训练
文本 LLM自身（自回归生成） 是（LLM的投影层可训） 无 包含在LLM微调中
图像 Stable Diffusion 2.1 是 Transformer（~2M） 是
视频 Zeroscope (基于ModelScope) 是 Transformer（~2M） 是
音频 AudioLDM 是 Transformer（~2M） 是
  • 扩散解码器的条件注入：LLM输出的”Hidden Text” token通过输出投影层转换为条件向量，注入扩散解码器的去噪过程——作为控制生成内容的条件信号
  • 为什么选择这些解码器：它们是各自模态的SOTA开源模型，且支持条件生成（文本条件 -> 图像/视频/音频）

机制流程

机制 1：多模态输入处理

  1. 模态检测：用户输入被自动分类为文本、图像、视频、音频或其组合
  2. 编码：每种模态通过对应的编码器编码为嵌入向量
  3. 投影：各模态嵌入通过各自的输入投影层映射为统一的LLM token序列
  4. 拼接：所有模态的token按顺序拼接，加上模态分隔符

机制 2：LLM跨模态推理

  • LLM接收拼接后的多模态token序列
  • 通过自注意力机制在模态间传递信息——文本token可以”关注”图像token，音频token可以”关注”视频token
  • LLM输出的序列中包含三种token：
    1. Hidden Text（内部推理，用于后续解码器的条件信号）
    2. Visible Text（用户可见文本）
    3. Modality Signal（触发特定解码器）

机制 3：模态信号路由

模态信号token是一个简单的分类决策——LLM输出特殊token [IMG]、[VID]、[AUD] 来指示下一段内容应由哪个解码器生成。

路由逻辑：

  • 如果用户要求”生成一张图” -> LLM在推理后输出 [IMG] token -> 触发 Stable Diffusion
  • 如果用户要求”描述这张图并生成一段相关视频” -> LLM输出文本描述 + [VID] token -> 触发 Zeroscope
  • 如果用户没有明确要求输出类型 -> LLM根据上下文推断最自然的输出模态

机制 4：多模态内容生成

  • 文本生成：LLM直接自回归生成——标准流程
  • 图像/视频/音频生成：
    1. LLM输出的”Hidden Text” token通过输出投影层编码为条件向量
    2. 条件向量注入对应扩散解码器的去噪过程
    3. 扩散解码器从头生成对应的模态内容

深度分析

LLM作为中央代理的优势与代价

优势：

  1. 统一的推理接口：所有模态的推理都通过LLM完成——不需要为每种模态组合设计独立的推理模块
  2. 跨模态常识：LLM在文本中学会的世界知识可以被跨模态推理利用——“雨声 + 森林图片 = 雨林漫步”这种联想是LLM的强项
  3. 可解释性：LLM的Hidden Text token提供了可读的”思考过程”——用户可以理解模型为什么生成了某个图像

代价：

  1. 模态信息的压缩损失：图像/视频/音频的丰富信号被压缩为LLM能理解的”文本化”语义——低层次的模态特定信息（如音色、笔触细节）可能丢失
  2. 序列化瓶颈：LLM必须按顺序处理所有输入——如果输入包含长视频 + 长音频，LLM的上下文窗口和注意力计算能力成为瓶颈
  3. 生成质量受限于解码器：LLM只能输出条件信号给冻结的解码器——如果解码器本身对某个特定场景的生成能力不足，LLM无法补偿

模态信号token的巧妙与粗糙

模态信号token是一个极简的设计——就一个特殊token标记”接下来用哪个解码器”。这个设计极其简洁但也极其粗糙：

巧妙之处：

  • 零学习成本——LLM本身就擅长输出特殊token（[EOS]、[SEP]等）
  • 可扩展——新增模态只需要加一个新的信号token
  • 可组合——LLM可以输出”文本 -> [IMG] -> 文本 -> [VID]”的序列

粗糙之处：

  • 只有”选择解码器”的功能，无法”精细控制解码参数”——不能告诉Stable Diffusion “用暖色调、高对比度、广角构图”
  • 单token的模态信号缺少输出质量反馈——如果生成的图像质量差，LLM不会知道也不会重试
  • 缺乏”模态混合”信号——如”生成一个包含图像和音频的短视频”，这需要更复杂的信号结构

MosIT数据集的5K魔数

5K条数据听起来很少（相比LLaVA的158K），但NExT-GPT证明”质量 > 数量”在这个场景下依然成立。为什么会这样？

  1. 编码器/解码器的冻结大大降低了对训练数据量的需求：NExT-GPT只在训练”输入输出投影层”——这些层的学习目标很简单（”将模态A的嵌入映射到LLM空间”），5K个多样化的示例已经足够
  2. LLM本身有强大的先验：Vicuna-7B在纯文本任务上已经有很强的指令遵循能力——MosIT只需教会它在多模态上下文中使用这些能力
  3. ImageBind的事先对齐减少了训练负担：因为输入编码已经在同一空间，投影层只需要做”坐标转换”而非”空间对齐”

NExT-GPT vs CoDi vs Unified-IO 2

维度 NExT-GPT CoDi (Microsoft) Unified-IO 2 (Allen AI)
架构哲学 LLM中央 + 模态工具 组合扩散模型 统一 token + 单 Transformer
模态数量 4 6 7+
推理引擎 Vicuna-7B (LLM) 无统一推理（扩散串联） 单一 Transformer
可训练参数 ~1% ~100% ~100%
跨模态推理 强（LLM推理） 弱（扩散的条件传递） 中（统一架构）
生成多样性 受限于解码器 中 中
架构灵活性 高（更换解码器即可） 低（重训全模型） 低（重训全模型）
开源性 完全开源 部分开源 开源

本质区别：NExT-GPT选择”联邦制”——LLM是”总统”，各模态组件是”州”，各自相对独立。CoDi和Unified-IO 2选择”单一制”——一个统一模型处理所有模态。联邦制更灵活（可替换组件）但协调成本更高（模态间有信息损失），单一制更紧凑但更僵化（一个地方出问题整个系统受影响）。

NExT-GPT在BLIP-2/LLaVA的基础上向前迈出了一大步——从”多模态输入 -> 文本输出”升级到”多模态输入 -> 多模态输出”。这是从”理解”到”理解+生成”的关键跃迁。

局限

  1. 生成质量受限于冻结解码器的能力上限：如果Stable Diffusion无法很好地生成某个特定概念（如”一只拿着巧克力棒的熊猫”），NExT-GPT也无法——即使LLM完美理解了用户的需求。LLM只能提供条件信号，不能提升解码器本身的能力。这是”联邦制”架构的根本限制。

  2. 模态信号token机制粗糙：只能选择用哪个解码器，不能精细控制解码参数——无法指定”暖色调”、”高对比度”、”广角”等。这导致多步骤生成控制困难——如”先生成一张草图，再在此基础上细化”，LLM无法传递”基于上一张图”这种迭代信息。

  3. 仅约5000条MosIT数据可能不足：跨模态指令的多样性有限——某些模态组合（如”视频+音频 -> 图像”）可能只有几十条数据，训练不充分。ICML审稿人也指出了这一点——5K数据能证明可行性，但不足以覆盖多模态推理的全部复杂度。

  4. LLM的上下文窗口瓶颈：视频和音频输入可能极其冗长（一段3分钟的视频可能包含数百帧），而LLM的上下文窗口（Vicuna-7B为2K token）无法容纳完整的模态编码。NExT-GPT使用平均池化压缩时需模态输入——不可避免地丢失细节。

  5. 缺乏多轮多模态对话能力：NExT-GPT主要处理单轮”输入 -> 输出”——不支持用户在看到生成的图像后说”我不喜欢这个颜色，调暗一点”这种多轮迭代。多轮多模态对话需要模型记住之前生成的图像/视频/音频——这是当前架构未解决的问题。

  6. 扩散解码器的推理速度：Stable Diffusion的图像生成需要20-50步去噪（约2-5秒），视频生成更慢（约20-60秒）。对于实时对话场景，扩散解码器的延迟是体验瓶颈——用户期望LLM的文本回复是秒级的，但模态生成让对话突然变慢。

  7. 评估方法的局限性：any-to-any系统的评估极其困难——有16种输入-输出组合，每种需要不同的质量指标。NExT-GPT使用各模态独立的指标（FID、FVD、FAD），但这些指标无法衡量”跨模态语义一致性”这一核心要求。人工评估虽有帮助但主观且不可规模化。

可复用洞见

  1. “LLM作为中央代理 + 模态工具”的架构是构建多模态Agent系统的标准范式：NExT-GPT的架构不是专门为”生成”设计的——它可以推广到任何”LLM需要调度多个专业工具”的场景。例如，一个多功能AI助手可以：LLM理解用户意图 -> 调用搜索工具 -> 调用图像工具 -> 调用翻译工具。NExT-GPT证明了LLM有能力在多个”工具”之间做路由和调度。

  2. 仅训练投影层实现跨模态迁移（1%参数）：当数据有限时首先考虑这种高效策略——NExT-GPT证明了即使在any-to-any这样复杂的场景中，1%的参数也足够。这已经不仅是”训练效率”的问题，而是”可行性”——如果全量训练需要数万美元的计算资源，而1%只需要数百美元，后者是学术研究可行的，前者不是。

  3. 模态信号token是LLM与外部生成器之间的简洁接口设计：这个设计的妙处在于它利用LLM本身的语言生成能力来做”工具选择”——LLM不需要学习新的接口，只需要输出特殊token。这比单独的”模态分类头”更自然，也更容易扩展到新模态。

  4. 质量vs统一的权衡是有意识的设计选择：NExT-GPT用2-6%的生成质量损失换来了统一的跨模态推理界面——这不是bug而是feature。这种权衡在未来可能会缩小（更好的投影层设计），但不会消失——“统一”和”专项优化”之间有一个根本性的张度。

我的笔记

对后续研究的启发

  1. 从”多模态输入”到”多模态输出”的必然趋势：BLIP-2/LLaVA解决了”让LLM看懂图文”，NExT-GPT解决了”让LLM输出图文音视”。这是MM-LLM演化的自然进程——先理解，再生成。预计未来所有主要的MM-LLM都将支持多模态输出。

  2. “联邦制”vs”单一制”的架构之争：NExT-GPT的联邦制架构（中央LLM + 外围工具）和Unified-IO 2的单一制架构（统一Transformer）代表了两种哲学。联邦制更适合快速迭代和社区协作（每个模态组件可以独立升级），单一制更适合追求极致性能（没有模态间信息损失）。

  3. ICML Oral的意义：NExT-GPT获得ICML 2024 Oral（7/7/7/8的评分）说明学术界对”any-to-any”方向的认可——这不是一个渐进式的改进，而是开辟了一个新的研究方向。

实际应用场景

  1. 全能型AI创作助手：用户上传一段视频 -> NExT-GPT描述视频内容 -> 生成合适的配乐 -> 生成一个缩略图。全程一个模型完成，不需要切换工具。

  2. 跨模态搜索：用户哼唱一段旋律 -> NExT-GPT识别旋律 -> 搜索相关电影 -> 生成电影海报。这是纯文本模型或纯视觉模型都不可能完成的任务。

  3. 无障碍技术：为听障人士生成视频的实时字幕和描述，为视障人士将图像和视频转换为详细的文字或音频描述。

我如果复现会关注什么

  1. MosIT数据集中不同模态组合的”质量梯度”——哪种组合训练得最好，哪种最差？这决定了NExT-GPT的实际能力轮廓
  2. LLM在多模态推理时的内部表示——Hidden Text token是否真的包含了”跨模态语义”，还是只是文本化的浅层映射？
  3. 能否用更小的LLM（如1B）实现类似的跨模态路由能力——如果1B的LLM也能做到，那边缘部署就可行了

后续问题

1. 细粒度解码器控制

问题：如何让LLM不仅选择解码器，还能传递精细的控制参数（如”暖色调、50%透明度、广角”）？

研究方向：

  • 增加多token的模态控制信号——如[IMG: warm_tone: high_contrast: wide_angle]格式
  • 训练LLM在Hidden Text中编码解码器参数——下游投影层学会解析这些参数

潜在影响：将NExT-GPT从”粗粒度模态选择”升级为”细粒度模态控制”，实用性大幅提升。

2. 多模态多轮对话

问题：如何支持用户在看到生成的图像后提出修改意见——实现真正的多模态多轮对话？

研究方向：

  • 将生成的多模态输出编码为输入token反馈给LLM——形成”生成-反馈-修改”的闭环
  • 在MosIT数据中加入多轮多模态对话数据

潜在影响：从”一次性生成工具”进化为”交互式多模态创作伙伴”。
